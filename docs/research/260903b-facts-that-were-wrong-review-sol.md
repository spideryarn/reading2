1. **Demonstrated hole — deleted or renamed files disappear from the guard.** `resolveCodePath` returns only existing paths, and callers silently discard `null` ([doc-links.test.ts](/home/greg/code/spideryarn2/.claude/worktrees/cite-not-restate/tests/doc-links.test.ts:453)). Both `` `src/deleted.ts:12` `` and `` `src/deleted.ts` § `gone` `` produce no citation, so deleting the cited file makes the test greener. The positive control actually enshrines this for `src/x.ts` ([line 504](/home/greg/code/spideryarn2/.claude/worktrees/cite-not-restate/tests/doc-links.test.ts:504)). This is the most important silent-success hole. Treat unresolved paths beginning with known repository roots (`src/`, `tests/`, `scripts/`, etc.) as stale; ignore only clearly external references.

2. **Demonstrated hole — Markdown-linked symbol citations are not parsed.**  
   `` [`src/blocks.ts`](../../src/blocks.ts) § `definitelyGone` `` returns no citation. There are currently 34 citations of that shape in the evergreen corpus, versus only 10 that the symbol parser sees. Parse the linked form and resolve its target, not merely its label; this also removes ambiguity when identical basenames exist. A line-number link whose text differs from its target—`[implementation](../../src/blocks.ts#L12)`—*is* caught by the present line regex, but the positive control does not prove that case.

3. **Demonstrated holes — two plausible line-number spellings and repository-local absolute paths escape.** `` `blocks.ts line 12` ``, `` `blocks.ts L12` ``, and an absolute path to this worktree all passed. The first two are plausible enough to cover cheaply; `:L12`, lowercase `#l12`, and similar inventions are theoretical. Conversely, bare `blocks.ts:12`, ordinary `:12-20`/`#L12-L20` ranges, and Markdown link targets are already caught. The absolute-path exemption ([line 454](/home/greg/code/spideryarn2/.claude/worktrees/cite-not-restate/tests/doc-links.test.ts:454)) is a real risk because Codex emits precisely that form; reject absolute paths inside the current repository while continuing to ignore external ones. The prefix search is mildly ambiguous for duplicate basenames, but mostly theoretical once citations use full repo-relative paths.

4. **Demonstrated hole — substring symbol matching is too weak.** ``§ `Bloc` `` passes against `src/blocks.ts` solely because it contains `Block`; therefore `save`→`saved` can preserve a rotten citation ([line 530](/home/greg/code/spideryarn2/.claude/worktrees/cite-not-restate/tests/doc-links.test.ts:530)). For identifier-like symbols, the cheap tightening is escaped matching with identifier boundaries such as `(?<![$\\w])…(?![$\\w])`. Keep literal substring matching for prose anchors and CSS selectors if necessary. Even then, this only establishes that an anchor remains somewhere—including a comment—not that the surrounding documentary claim is true; that limitation is acceptable if stated honestly.

5. **Reasoned assessment — `stripFences` is right.** It strips fenced blocks, not inline code. Inline code must remain visible because it is the prescribed citation syntax. Ignoring fenced output is justified by real build/error excerpts such as those in `deployment.md`; otherwise stack traces would become false positives. Tilde fences are an over-detection risk, not a rotten-citation escape.

6. **Demonstrated weakness in the positive control.** It proves the two canonical line spellings, one range, prefix resolution, and the unlinked symbol syntax. It does not prove the dominant linked-symbol form, a link whose label differs from its target, missing repo files, repository-local absolute paths, prose-style line references, or rejection of a prefix-only symbol. The `nonsuch` fixture only proves parsing; it never exercises the stale filter. I would add those cases, particularly the first four. The existing suite itself passes: 13/13.
