# A 409 and a 404 arrived as 500, in production only

From 2026-08-28 until 2026-09-01, two ordinary refusals in the comments API reached the
reader as `500 This app asked its database for something it would not do`:

| what the reader did | what the route means to answer | what production answered |
|---|---|---|
| saved a passage under an id another comment already has (a second tab, a stale client) | 409 | 500 |
| retried the answer on a comment that had been deleted | 404 | 500 |
| retried the answer on a bookmark, or on one already being answered | 409 | 500 |

It was live rather than latent, and only live: production runs `SPIDERYARN_STORE=postgres`
and the fault does not exist on the filesystem path. It was found by accident, while
measuring something else, by pointing `tests/comment-referee-mark.test.ts` at Postgres.

## The root cause

Not a wrong line. **A rule expressed as a list of class names, in a file that the classes
themselves never have to know about.**

`guardDbStore` ([src/store/db-errors.ts](../../src/store/db-errors.ts)) wraps every
Postgres store, and replaces every error it is not told to keep with a generic
`StoreFailure`. It has to: a failed Drizzle query's `Error.message` carries the failed
statement *and its bound parameters*, which for the `comments` table is the reader's own
selected quote and the model's whole answer. One rendered on the homepage on 2026-08-27.
So the direction is inverted deliberately — an allowlist of what may pass, not a
blocklist of what may not.

The allowlist had two doors:

```ts
if (err instanceof ChatConflict) return true;
if (err instanceof CheckpointRequestError) return true;
if (err instanceof StaleAttemptError) return true;
if (err instanceof IllegalTransition) return true;
if (err instanceof ProductRefused) return true;
return typeof (err as { status?: unknown }).status === "number";   // ← the other door
```

`CommentIdTaken` and `NotAnExplanation` went through neither. `pgCommentStore` threw them,
the guard replaced them with `StoreFailure`, and the `instanceof CommentIdTaken` in
[src/routes.ts](../../src/routes.ts) could not match an object that no longer existed. The
route fell through to its final `: 500`.

**The class-name door is the whole of the root cause.** It is a list, kept in a file that
knows about neither routes nor comments, and every new refusal type has to remember to
join it. Two did not — and the second door exists *precisely because somebody had already
noticed that*: it was added so an error could declare its own answer without this file
learning its name. The convention was there; nothing pointed the new classes at it.

## The commit that introduced it

`5fc1743` (2026-08-28) — *"A comment is now the free thing, and the model is a tick-box"*.
One commit added all three halves: `CommentIdTaken` and `NotAnExplanation` in
`src/comments.ts`, the throws in `src/store/pg-comments.ts`, and the two `instanceof`
branches in `src/routes.ts`. It landed into a tree where the guard had wrapped the comment
store since `a61a921` (2026-08-26), so the mapping was dead on arrival — it never worked
in production for a single request.

That commit is not careless: it has two GPT Sol reviews, and the 409 is described in its
message ("`create` (free, 409 on a real collision)"). The 409 it describes is real in
`src/comments.ts`, real in `src/store/pg-comments.ts`, and real in `src/routes.ts`. It is
untrue only of the composition of the three, which no single file shows.

## Why nothing caught it

**Every test that covered it ran on the unwrapped side.** Two files assert
`rejects.toBeInstanceOf(CommentIdTaken)` and both are green and both are honest:
`tests/comments.test.ts` drives the filesystem store, which nothing wraps; and
`tests/store-comments.test.ts` imports `pgCommentStore` **straight from
`src/store/pg-comments.js`**, which is the raw store — the guard is put on in
`src/store/index.ts` (`guarded("comments", pgCommentStore, fsCommentStore)`), so importing
the module the throw lives in gets you the version production does not run.

**And that is why the sibling class was caught and this one was not.** `IllegalTransition`
had exactly this bug on the upload store, and `tests/store-uploads-parity.test.ts` found it
the moment the store went behind the guard. The difference is one line of module structure:
`pg-uploads.ts` and `pg-jobs.ts` apply the guard **at their own export** —

```ts
export const pgUploadStore: UploadStore = guardDbStore("uploads", rawPgUploadStore);
```

— so a test that imports `pgUploadStore` gets the guard whether it meant to or not.
`pg-comments.ts` exports the raw object and lets `store/index.ts` wrap it, so a test that
imports `pgCommentStore` gets the guard only by accident of not doing so. **Where the
wrapper is attached decides what the tests can see**, and nothing marks the two placements
as different choices.

So the coverage existed, was green, and was about a code path production does not take.

This is the shape of
[260831h](260831h-db-migrate-applies-nothing-when-a-journal-timestamp-jumps-the-queue.md)
and of [silent-success.md](../reusable/silent-success.md): the check and the code shared an
assumption, so the check agreed. The specific version here is worth naming on its own,
because it is not the usual "the check did nothing" —

> **A test that exercises one of two adapters is evidence about that adapter and about
> nothing else.** A wrapper on the other one is invisible to it, and a wrapper is exactly
> the kind of thing that gets attached later, by a different commit, for a different
> reason.

And a route status is unusually easy to be wrong about, because **there is no wrong-looking
state**: a 500 has a message, a status line and a stack. Nothing anywhere prints
"expected 409".

## The fix, and the two we did not take

`CommentIdTaken` gets `readonly status = 409`; `NotAnExplanation` gets a `status` computed
from its `why` (404 for `missing`, 409 for the other two). Both in
[src/comments.ts](../../src/comments.ts), next to the message the number is about.

- **Rejected: two more `instanceof` lines in `mayPassThrough`.** Smallest, and it leaves
  the trap exactly where it was — the list stays a list, and the third refusal type will
  forget it too. This bug is the second instance, which is the argument against.
- **Rejected: a shared base class or a marker property for "a refusal the reader should
  see".** It is the general answer, and it is a third way to say a thing this codebase can
  already say twice. Nine store-side classes already declare `readonly status` —
  `PublishRefused`, `NotTheLiveAttempt`, `StepRunNotHeld`, `WrongArticle`, `StampDisagrees`,
  `NoStoredDocument`, `RawSourceDisagrees`, `MissingRawObject`, `CorruptRawObject` — plus
  `JobConflict`, plus `retryJob`'s `Object.assign(new Error(…), { status: 409 })`. Adding a
  marker would mean two marks for one idea and a sweep to keep them agreeing.
- **Chosen: the numeric `status`.** It is the established idiom, it is the door the guard
  already holds open, it makes the number a property of the refusal rather than of a
  handler, and it makes the two store adapters answer identically — which is the actual
  defect.

**Nothing was weakened.** A `status` is not a licence to leak, and both messages were
checked against the guard's own test for a class it lets through: *the type is closed and
its message is built from values we chose.* `CommentIdTaken`'s is a fixed sentence and an
id; `NotAnExplanation`'s is one of three fixed sentences and an id. The id is `spya`-shaped
before either store sees it — both call sites (`createFree` and `answer` in `src/routes.ts`)
gate it with `isSpideryarnId` — so no quote, body, title or model answer can reach these
messages. `tests/db-error-scrub.test.ts` pins that, and pins from the other side that a
Drizzle failure with bound parameters is still scrubbed out of its message, its stack and
its enumerable properties.

## The siblings — the whole list

`src/store/db-errors.ts` is the one place that decides, so this is enumerable rather than a
judgement call. Every error class thrown from inside a guarded store, and every class a
route maps to a status:

| class | thrown inside a guarded store? | passes the guard | verdict |
|---|---|---|---|
| `CommentIdTaken` | yes (`pg-comments.ts`) | now, via `status` | **was the bug — fixed** |
| `NotAnExplanation` | yes (`pg-comments.ts`) | now, via `status` | **was the bug — fixed** |
| `ChatConflict` | not yet (thrown in `chat.ts`, above the store) | named in the list | fine |
| `StaleAttemptError`, `IllegalTransition`, `ProductRefused`, `CheckpointRequestError` | yes | named in the list | fine |
| `PublishRefused`, `NotTheLiveAttempt`, `StepRunNotHeld` (`pg-revisions.ts`) | yes | `status` 409 | fine |
| `WrongArticle`, `StampDisagrees`, `NoStoredDocument`, `RawSourceDisagrees` (`artifacts-pg.ts`) | yes | `status` 500/409/422/409 | fine |
| `MissingRawObject`, `CorruptRawObject` (`raw-document.ts`) | yes | `status` 500 | fine |
| `JobConflict` | no (`jobs.ts`) — and `routes.ts` matches it for the response body, not the status | `status` 409 | fine |
| `CorruptObject` (`blobs.ts`) | no — `blobStore()` follows the credentials and is not wrapped | no `status`, not listed | **latent**: it becomes a scrubbed 500 the day a blob read moves inside a guarded store. Its message is a key and fixed prose, so a `status` would be safe if it ever needs one. |
| `EmbeddingFailure` | no (`embeddings.ts`) — `embeddingHttpError` converts it in `routes.ts` before the generic handler | `status` is `number \| null`, so `null` would **not** pass | **latent**, same conditions. The `null` is deliberate (no status when nothing answered), so the fix there would be the class list or a converted status, not a lie. |
| errors carrying `code: "ENOENT"` (filesystem store → 404) | filesystem stores are not wrapped | n/a | fine, and `scrubDbError` refuses to copy a non-SQLSTATE `code` for exactly this reason |

So: **two live, both fixed; two latent and both currently unreachable.** Nothing else in
`src/routes.ts` maps a class to a status.

## What would have caught the whole class

In rough order of what it costs against what it catches:

1. **Attach the guard at the store's own export, the way `pg-uploads.ts` and `pg-jobs.ts`
   already do.** One line moved, and every existing test of `pgCommentStore` starts
   exercising what production runs — including the three that already assert
   `toBeInstanceOf(CommentIdTaken)`, which would then have been red on 2026-08-28 with
   nobody writing anything new. This is the single highest-value change on the list, and it
   generalises: a wrapper that a test can import its way around is a wrapper the tests do
   not cover. Not done here — `src/store/pg-comments.ts` and `src/store/index.ts` were
   outside this landing's file set, and moving it needs a check that nothing depends on the
   raw object.

   **Done on 2026-09-03**, by the sweep in
   [260903e](../plans/260903e-sweep-recorded-rather-than-fixed-defects.md) § Stage 1 item 2.
   Two things this entry did not anticipate, both found by making the move:

   - **The wrapper had to become idempotent.** `guarded()` in `src/store/index.ts` would
     then have wrapped an already-wrapped store, and a second pass is *not* a no-op:
     `scrubDbError` copies a SQLSTATE onto the error it hands back but has nothing to copy an
     **errno** onto, so an `ECONNRESET` stops answering `isTransient` and `STORAGE_BUSY`
     ("wait a few seconds and try again") comes back out as `STORAGE_FAILED` ("a bug, and
     trying again will not help"). `src/jobs.ts` persists that as the `retry`/`bug` kind, so
     it is the Retry button on the reader's card. The first fix put an `isGuardedStore` check
     in `guarded()`; GPT Sol's review pointed out that this protects one composition path and
     leaves every other caller able to double-wrap, so `guardDbStore` itself now returns an
     already-branded store unchanged and `guarded()` is back to its one-line form.
     `tests/store-guarded.test.ts` § 4 asserts the identity and that a blip is still
     transient after two wraps.
   - **The `toBeInstanceOf(CommentIdTaken)` assertions all stayed green** — the `status`
     fix above is doing its job — but two assertions in `tests/comment-sweep.test.ts` went
     red, and that is the finding. `patch()`'s two argument refusals are plain `Error`s
     with no `status` and no place on the class list, so the guard replaces *"needs the
     attempt that beginAnswer() returned"* with the generic database sentence. **That was
     already true of every request production served**; only the test could not see it,
     which is this postmortem's own thesis arriving one file over. The test now asserts the
     consequence — neither write reached the row — rather than the wording. Whether those
     two refusals should carry a `status` of their own is a reader-facing copy decision and
     was left for Greg.
2. **A parity test for refusals, not just results.** `tests/store-parity.test.ts` compares
   what the two adapters *return*. Nothing compares what they *throw* —
   `tests/store-uploads-parity.test.ts` does, for one class, which is how
   `IllegalTransition` was caught. One case per named refusal, on every parity file, is the
   general version.
3. **A test on the guard, for each class the routes name.** Now written
   (`tests/db-error-scrub.test.ts` § *a refusal the comment store makes*): it wraps a
   throwing store in `guardDbStore` and asserts the object arrives unchanged. No database,
   no article, no route — milliseconds, and it is where the next person to add a refusal
   type will see the rule stated.
4. **A static check that the two lists agree.** Every class `src/routes.ts` matches with
   `instanceof` in its error handler must either be named in `mayPassThrough` or declare a
   numeric `status`. That is `npm run check`-shaped (`docs/project/static-analysis.md`) and
   it is the only one of the three that cannot be forgotten. Not built; it would need a
   thrown-from-a-store list as well, and the table above is currently that list.

**Does stage 4 — deleting the filesystem store — fix the class?** It fixes *this instance*
and a good deal of its camouflage: with one adapter, a test of the comment store is a test
of the comment store production runs, and the "the coverage existed and proved nothing"
half goes away. It does not fix the class. The guard would still be an allowlist of class
names; a new refusal type would still be scrubbed unless it declared a `status`; and the
symptom would still be a 500 that looks entirely healthy from every angle except the number.
Point 4 above is the only one that closes it; points 1–3 are what make the failure loud in
the meantime, and point 1 is the one to do next.

## Follow-ups

- The two `instanceof` branches in `src/routes.ts` are now unreachable — the `status` line
  above them answers first. They are kept as the second door and as the explanation of
  *why* those numbers, with the numbers themselves living on the classes so the two cannot
  disagree. Delete them when somebody is next in that function for another reason.
- `src/store/db-errors.ts`'s header says "Four things pass" above a list of five. Left
  alone here to keep this landing to its file set.
