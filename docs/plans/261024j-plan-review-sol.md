1. **High — A colleague’s real address can still auto-fill the draft.** The plan deliberately adds colleague searches ([plan D1](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:41)), but the current rule accepts any whole email token from any named search result ([author-lookup.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/author-lookup.ts:383)), and `finishLookup` automatically fills the empty draft ([pg-author-gifts.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/store/pg-author-gifts.ts:637)). If the model returns the colleague’s address as `email`, it passes every present check. **Change:** do not mix colleague results into the auto-fill evidence pool. Either run pattern discovery separately, remove colleague searches, or make all addresses found after broadening the search candidates requiring *Use this address*. Add a test where the result contains a colleague’s valid address and the model claims it belongs to the author.

2. **Medium — “Their page” is not established by rule 1.** `homepageUrl` need only be any exact search-result URL ([plan D2](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:47)); the validator proves only that the URL occurred in results, not that the page belongs to the author ([author-lookup.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/author-lookup.ts:365)). Even the author name is not checked against the source text ([author-lookup.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/author-lookup.ts:375)). A hostile or mistaken result can therefore be presented as “written on their page” and “likely.” **Change:** use neutral copy such as “found on this page, which the lookup identified,” unless authorship is independently verified. Store/show `fetchDocument`’s final redirected URL as the actual source.

3. **Medium — “Pattern seen” checks a domain, not an address pattern.** D3 promotes a guess whenever any address at the same domain occurs ([plan D3](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:85)). Seeing `jane.smith@example.edu` supports `first.last@example.edu`; it does not support `awarth@example.edu`. It is nearly meaningless for `gmail.com`, and the model may still assign “high.” **Change:** compute confidence entirely in code. High should require an exact, reproducible local-part transformation from a named colleague to the author; same-domain-only evidence should remain low, and public-mail domains should never count as institutional patterns. The simpler safe design is to omit likelihood chips and show provenance—“found on page,” “same domain,” or “unsupported guess.”

4. **Medium — The decoder will create ordinary prose false positives and has underspecified negatives.** Flattening a document and accepting spaced ` at ` turns “Learn more at example.com” into `more@example.com`; flattening across blocks can join unrelated text, while `textContent` may also include scripts and styles. Conversely, the rule “name or alt is `at`, `@` or `arroba`” does not clearly include the stated `at-sign.png` example ([plan D2](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:55)). **Change:** remove `script`, `style`, `template`, `head`, and `noscript`; scan bounded DOM-local chunks such as anchors, table rows and individual blocks; define case, extension, query-string, entity and percent-decoding rules precisely; and treat unbracketed natural-language `at` as low-confidence unless the local part matches a strong author-name form.

5. **Medium — Fetch and candidate work are not actually bounded as claimed.** `fetchDocument` defaults to 50 MB, three attempts and a 30-second timeout per attempt ([fetch.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/fetch.ts:782)); passing only `timeoutMs: 10_000` can therefore take roughly 30 seconds per page, contradicting the plan’s 20-second total ([plan D5](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:112)). D2 also says every match becomes a row, with no candidate cap. A large hostile HTML page can impose substantial jsdom memory, regex and database work. **Change:** set an explicit small HTML cap, `attempts: 1`, and an overall deadline; deduplicate the two requested URLs and normalized addresses; and cap candidates per page and lookup before building an unbounded array.

6. **Medium — “Only when no address was seen” is still a prompt instruction, not a server rule.** D3 says the prompt lists guesses only when no address was seen, but its code checks do not say to discard guesses when `findings.email` is non-null ([plan D3](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:80)). The model is already treated as untrusted. **Change:** enforce `guesses = []` in code whenever a seen address survives; test a response containing both a verified address and several high-confidence guesses.

7. **Low — The legacy suggested address is not necessarily usable as an address.** Current code preserves malformed model output in `suggestedEmail` when it fails `looksLikeEmail` ([author-lookup.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/author-lookup.ts:383)). D4 folds that value into *Possible addresses* and gives every row *Use this address* ([plan D4](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:95)); the resulting PATCH will simply fail validation. **Change:** fold it in only if it normalizes and passes `looksLikeEmail`; otherwise leave it in the historical notes without a button.

8. **Low — The proposed row shape cannot support all the UI claims and lacks stated invariants.** The UI distinguishes plain, disguised and guessed addresses, but the table stores only `kind = on-page | guess` ([plan D4](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:95)). It also omits a uniqueness rule for `(lookup_id, position)` and consistency checks for kind, confidence, normalized address, source and `pattern_seen`, despite the project’s database-constraint convention ([sql.md](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/project/sql.md:15)). **Change:** add a structured discovery kind (`plain`, `mailto`, `disguised`, `guess`) and database checks/uniqueness, with bounded application fields.

9. **Low — Using a candidate through the existing PATCH loses its provenance.** A changed address clears `email_lookup_id` ([pg-author-gifts.ts](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/store/pg-author-gifts.ts:960)), after which the card labels it “typed by you” ([AdminAuthorGifts.tsx](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/src/web/AdminAuthorGifts.tsx:156)). **Change:** either relabel null provenance as “chosen or typed by you,” or add a candidate-selection operation that accepts a candidate ID, verifies it belongs to this gift, and records its lookup. Candidate selection must also close any open Send confirmation and refresh the preview; the existing `expected` snapshot prevents a stale confirmation from sending, but that race should be tested.

10. **Medium — The listed tests miss the main adversarial cases.** Stage 1 lists positive decoder examples and broad confidence checks ([plan Stages](/var/tmp/spideryarn-worktrees/fbw5yavh-author-email-search/docs/plans/261024j-author-lookup-tries-harder-reads-the-author-s-page-and-proposes-likely-addresses.md:119)), but not: colleague-address auto-fill; an unrelated page called a homepage; seen email plus guesses; natural-prose and cross-block false positives; script/style text; malformed `mailto:`; duplicate/candidate overflow; retry versus total timeout; redirect provenance; stale/lost `finishLookup` inserting no candidates; malformed legacy suggestions; or MCP’s exact allowlisted candidate shape. **Change:** add these as boundary tests, including a positive control proving each rejection test would fail if its guard were removed.

Verdict: **Revise before building—the final Send still requires Greg’s browser press, but the colleague search can auto-fill the wrong real address, and the proposed provenance and confidence labels overstate what the server has proved.**
