# Code review findings: Feedback buttons coloured positive and negative

1. **Medium — the new stylesheet is absent from the independent cascade manifest, so the repository's stylesheet guard fails.** `src/web/styles.css:76-77` deliberately imports `button-tone.css` last, but `tests/styles-entry-is-imports-only.test.ts:237-241` still ends its hand-written `MANIFEST` at `reading-comfort.css`. `npx vitest run tests/styles-entry-is-imports-only.test.ts` therefore fails both the exact-order check and the every-sheet-present check. This is also the particular silent mistake `docs/project/design-css-overview.md:23` says every new sheet requires a second edit to prevent.

   **Fixed:** `button-tone.css` is now the final entry in that independent manifest. Its two previously failing order/presence assertions pass.

2. **Medium — the design-system copy says Cancel preserves a draft, but one of the live Cancel buttons it lists deletes the draft.** The new Family says “Red here is not destructive: Cancel keeps the draft” and lists addendum Cancel among its users (`src/web/DesignPage.tsx:1651-1657`); the stylesheet header makes the same broad claim (`src/web/styles/button-tone.css:9-11`). In the real addendum flow, however, Cancel calls `addenda.cancel` (`src/web/FeedbackAddendum.tsx:255-261`), whose contract says “the box shuts and its words go” and whose implementation calls `forget(report)` (`src/web/FeedbackAddendum.tsx:51-52,137-142`). A reader of `/design` could therefore infer that pressing this red Cancel is reversible and lose a half-written addendum. The tone can still mean “back out” rather than “delete”; the copy must not promise draft retention or call every use non-destructive.

   **Fixed:** `/design` and the stylesheet now describe red as a back-out cue, explicitly distinguish Write's retained draft from the addendum's discarded local draft, and continue to reserve the filled destructive variant for a dedicated destructive action.

3. **Low — the focused tests do not pin Defer's two new disabled-state distinctions.** `FeedbackEarlier.tsx:1407-1409` correctly gives Defer `data-working` only while its own deferral is in flight, while `disabled={sending || deferring}` also disables it during a reply send. But the new assertions only check the tone class at rest (`tests/feedback-dialog.test.tsx:3613-3620`) and the generic CSS rules (`tests/feedback-dialog-styles.test.ts:123-127`). Removing `data-working` from Defer would make an in-flight deferral fade to 45%; adding it whenever disabled would keep Defer visually live while a reply is sending; either regression would leave the focused suites green. The component test needs to observe both in-flight states.

   **Fixed:** the held-request tests now assert disabled + `data-working` while Defer itself works, and disabled without `data-working` while Send reply works.

4. **Low — the cascade test cannot detect a Tailwind paint utility on a toned button, even though that layer always wins.** The hand-written styles are imported into `@layer app`, below `utilities` (`src/web/tailwind.css:38,72-73,118`), so a later `tw:text-*`, `tw:border-*`, `tw:bg-*` or `tw:opacity-*` class on a toned button overrides `button-tone.css` regardless of its last import or specificity. The stylesheet test inventories only selectors in the hand-written reader sheets (`tests/feedback-dialog-styles.test.ts:24-26,67-85`), while the JSX checks only whether a `tone-*` class is present (for example `tests/feedback-dialog.test.tsx:3098-3107`). Current callers have no competing utility, so they render correctly today; adding `tw:text-foreground` beside `tone-positive` would make Send neutral while both focused suites remained green. The caller tests should reject Tailwind paint utilities on every toned Feedback button.

   **Fixed:** every toned Feedback caller is now checked through one helper that requires exactly one tone and no `tw:` utility, making the layer boundary explicit.

5. **Low, wider than this stage — two written sources now misstate the stylesheet order or the Cancel semantics.** `docs/project/design-css-overview.md:24` says `reading-comfort.css` is the final sheet after `site.css`, although `button-tone.css` is now later. The already-filed question for Greg says without qualification that “Cancel keeps your draft” and proposes that any act losing something uses the destructive fill (`docs/user-feedback/questions/q-yvmweg.md:27-35`), which conflicts with the existing addendum Cancel above. These files are outside the requested implementation stage; leaving them unchanged makes the proposed rule and the cascade map disagree with the live code.

   **Reported, not changed:** both are outside the implementation stage, and `controls.md` remains untouched as requested.
