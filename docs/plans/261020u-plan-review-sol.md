1. **High — The screen-reader claim shown to Greg is false.** The linked [question](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/docs/user-feedback/questions/q-f8yb5s.md:19) says “Screen readers do not use it to navigate.” JAWS explicitly assigns Backspace to “Back a Page,” so JAWS may intercept it before Spideryarn can substitute the chip action. NVDA does not document plain Backspace as a browse-mode command, and VoiceOver does not appear to either, but those two remain unmeasured. More decisively, option B conflicts with all three: B means “next button” in [JAWS](https://support.freedomscientific.com/content/html/jawshq/JAWS-Keystrokes.html), [NVDA browse mode](https://download.nvaccess.org/releases/2025.3/documentation/userGuide.html), and [VoiceOver single-key Quick Nav](https://support.apple.com/guide/voiceover/quick-nav-vo27943/mac), including VoiceOver on iPad. B should be removed or described as an accessibility-conflicting option, not a safe fallback. G already has the analogous “graphic” conflict; that is not a reason to add another.

2. **High — The proposed gating does not cover modeless dialogs, the drawer, or focused controls.** The [build sketch](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/docs/plans/261020u-backspace-takes-the-way-back.md:77) mentions typing, `defaultPrevented`, and native modals. A window listener with those guards would still act while focus is on a button in Chat, Comment, Annotate, or the Dock’s modeless `role="dialog"` drawer. It would also turn Backspace into Return while focus is on the chip’s own × button. G is stricter than the plan implies: it refuses ineligible focused controls and refuses body-inferred navigation behind a modeless dialog. The plan should define Backspace as yielding to the top surface—following the Escape tiers’ ownership principle without making Backspace another Escape—and specify behavior for both chip buttons.

3. **Medium — The browser account needs correction and qualification.**

   - Chrome desktop: Backspace no longer navigates Back since Chrome 52; high confidence, though not live-measured in this review ([Chromium issue 608016](https://bugs.chromium.org/p/chromium/issues/detail?id=608016)).
   - Firefox desktop: the default changed in Firefox **87**, not 86, and users can restore navigation with `browser.backspace_action=0`; high confidence ([Firefox 87 release notes](https://www.mozilla.org/en-GB/firefox/87.0/releasenotes/)).
   - Safari on macOS: uncertain without physical measurement. Current WebKit source defaults `BackspaceKeyNavigationEnabled` to true outside the iOS family, while Apple’s current Safari shortcut guide documents Command-[ rather than Backspace. Safari may override the embedder default. Keep the measurement gate and do not tell Greg yet that no browser feature is being taken away ([WebKit preference](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml), [Apple Safari shortcuts](https://support.apple.com/guide/safari/keyboard-shortcuts-and-gestures-cpsh003/mac)).
   - iPadOS: current WebKit source sets the iOS-family default to false, so Safari should not navigate on Backspace; moderate-to-high engine-level confidence, but Safari, Chrome, and Firefox should still be checked on the actual iPadOS/hardware-keyboard combination. VoiceOver is a separate interception layer.

   “No default browser action in ordinary Chrome/Firefox configurations” is defensible; “free key” is too broad.

4. **Medium — The risk is not limited to thirty seconds, and “no chip means nothing” is not universally true.** [ReturnChip](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/src/web/ReturnChip.tsx:126) pauses its timeout indefinitely while hovered or focused, then starts a fresh thirty seconds. This matters especially when keyboard focus is on either chip button. Also, once the component unmounts, Safari or customized Firefox—and JAWS—can resume their own Backspace-as-Back behavior. Thus Backspace can mean position-only while the chip exists and full history Back after it disappears.

5. **Medium — The phone pill is an unresolved scope decision.** [Reader](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/src/web/reader/Reader.tsx:5036) renders either the section `ReturnChip` or `BandBackChip`. On a covering phone band, pressing the section chip steps the band aside and replaces it with *back to ⟨mode⟩*. A listener inside `ReturnChip` then unmounts, so a second Backspace will not press the visible mode pill. The question should tell Greg whether Backspace means “section return only” or “press whichever way-back pill is visible.”

6. **Medium — The component placement is good, but `key-chord.ts` cannot currently supply what the plan promises.** Mounting the listener in `VisibleReturnChip` is the right lifecycle shape. However, [key-chord.ts](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/src/web/key-chord.ts:51) has helpers for modified chords, typing, and IME; it has no shared plain-key predicate covering no modifiers, repeat, composition, `defaultPrevented`, and typing. The plan must either extract such a helper and use it consistently in G, `/`, and Return, or acknowledge a local predicate. The test list should add `type=search`, nested `contenteditable`, modifiers, composition, `defaultPrevented`, native and modeless dialogs/drawer, both focused chip buttons, the phone-pill transition, and the fade/held-timeout state.

7. **Low — Two smaller factual wordings should change.** “No key presses it” should be “no dedicated shortcut”: after Tab, Enter or Space activates the button. Also, after an accidental Return, browser Back can undo it, but “the chip’s own journey stamp” generally cannot redo that just-undone journey; after a single journey the return removes the chip, while an `earlier` stamp represents an older journey.

8. **Info — The central repo facts and escalation decision are correct.** The search found no global Backspace handler; the only app use is local to `TagEditor`. Browser Back traverses the earlier history entry, including its `?mode=`, whereas `returnFromJump` keeps the current mode and changes position only. Going to Greg is required: this is a non-admin suggestion with credible browser, focus, and accessibility trade-offs, exactly the “research and bring it to Greg” case in [feedback-reports.md](/var/tmp/spideryarn-worktrees/fbyjnpjg-backspace-way-back/docs/project/feedback-reports.md:294). A can remain the conditional recommendation after these caveats; B is not sound.
