1. **High — Converting to HTML is sound as a pipeline derivative, but not as the only retained source.**

   **Evidence:** The plan deliberately discards the original and drops Word images ([plan:50](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/plans/261011j-upload-text-markdown-and-word-files.md:50), [plan:113](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/plans/261011j-upload-text-markdown-and-word-files.md:113)), contrary to “Never lose what the reader gave us” ([vision.md:121](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/project/vision.md:121)). This also makes existing features misleading:

   - Feedback promises “the file it was made from” and “the original” but would attach converted `source.html` ([feedback-article.ts:2](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/feedback-article.ts:2), [feedback-article.ts:77](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/feedback-article.ts:77)).

   - The injection scan claims to inspect the raw source specifically because extraction loses hidden text ([security.md:998](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/project/security.md:998)), but `source-scan` will receive Mammoth’s semantic HTML after Word colours, positioning and other hiding evidence have gone ([source-scan.ts:204](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/source-scan.ts:204), [source-scan.ts:216](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/source-scan.ts:216)).
   - Rebuild will mechanically work, but it deliberately reuses the stored derivative and therefore never benefits from a corrected converter ([jobs.ts:3739](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/jobs.ts:3739)).

   The ordinary HTML path itself is compatible: stage 2 already accepts uploaded HTML without a URL, stage 3 sanitises it, `cameOffADisk` uses the retained filename, and the slug comes from that filename ([pipeline.ts:2839](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/pipeline.ts:2839), [pipeline.ts:3068](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/pipeline.ts:3068), [SourceLink.tsx:117](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/web/SourceLink.tsx:117), [routes.ts:7269](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/routes.ts:7269)).

   **Fix:** Retain the original under a separate content-addressed reference, record a durable `convertedFrom`/source-format fact, and keep the generated HTML as the stage-2 derivative with `kind: "html"`. Export and feedback should include the original; the source scan must either inspect it properly or clearly report DOCX as unexamined rather than call the derivative “raw”. If that storage/provenance work is too large, take the simpler option the plan passed over: ship text/Markdown first and defer Word.

2. **High — The proposed `fflate.unzipSync` ZIP-bomb guard is not sound.**

   **Evidence:** The filter sees central-directory `size` and `originalSize`, then deflate entries are expanded into `new Uint8Array(su)` ([fflate index.mjs:2693](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:2693)). But the inflate loop continues processing the complete stream after that typed array is full; out-of-bounds writes are discarded and the truncated buffer is returned ([fflate index.mjs:395](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:395), [fflate index.mjs:411](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:411)). Consequently, the proposed test—“returns ≤1 KB or refuses”—can pass while the process still inflates the entire 100 MB payload.

   Stored entries are a separate hole: method 0 copies `compressedSize`, not the checked `originalSize` ([fflate index.mjs:2701](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:2701)). Repeated central entries can also point at the same input data and multiply retained memory.

   `unzipSync` trusts names, method and sizes from the central directory and consults the local header principally to locate the payload ([fflate index.mjs:1851](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:1851)). It does not reconcile central/local disagreement. Data descriptors do not help because the synchronous reader uses central sizes; ZIP64 merely supplies the same trusted size fields. Thus the claim at [plan:125](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/plans/261011j-upload-text-markdown-and-word-files.md:125) is false.

   **Fix:** Stream entries lazily and abort on actual emitted decompressed bytes, with per-entry and cumulative limits. Skip media without opening it; reject duplicate names, unsupported/encrypted methods, more than 2,000 entries, and stored entries whose compressed and uncompressed sizes differ. A Node-oriented reader such as `yauzl` already provides lazy entries, stored-size validation and destroyable streams; still count emitted bytes yourself and destroy immediately over 32 MiB ([official yauzl documentation](https://github.com/thejoshwolfe/yauzl/blob/master/README.md)). Re-zip validated parts at level 0. Tests must prove early refusal—not merely truncated output—for lying deflate sizes, stored entries, central/local disagreement, data descriptors, ZIP64 and duplicate/shared-offset entries.

3. **Medium — XML entity expansion is not reachable, but Mammoth still needs a process boundary and a stronger version contract.**

   **Evidence:** Installed xmldom chooses only its predefined XML entity map ([dom-parser.js:75](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/dom-parser.js:75), [entities.js:12](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/entities.js:12)); its DTD parser records identifiers without installing or recursively resolving the internal subset ([sax.js:590](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/sax.js:590)). Billion-laughs and XXE are therefore not reachable through this parser.

   However, Mammoth itself warns that hostile documents can exhibit pathological CPU or memory behaviour and recommends a separate thread with a timeout ([README.md:526](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/README.md:526), [Mammoth security guidance](https://github.com/mwilliamson/mammoth.js/blob/master/README.md#security)). Version 1.12.3 fixed a concrete ReDoS and still repeats that recommendation ([NEWS:1](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/NEWS:1)). A 32 MiB XML-byte limit does not bound DOM-node amplification, nesting or future algorithmic bugs.

   The external-file CVE is fixed from 1.11.0 and access defaults to false ([options-reader.js:65](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/lib/options-reader.js:65), [GitHub advisory](https://github.com/advisories/GHSA-rmjr-87wv-gf87)), but 1.12.2 separately fixed prototype pollution capable of turning `externalFileAccess` back on ([NEWS:13](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/NEWS:13)). The locked 1.12.3 is safe; the plan’s “≥1.11.0” floor is incomplete.

   **Fix:** Run the entire DOCX preflight and Mammoth call in a terminable worker/process with a timeout and memory limit. Require at least 1.12.3, pass `externalFileAccess: false` and `includeEmbeddedStyleMap: false` explicitly, and specify an image converter that returns no HTML nodes and never calls an image read method. Test an embedded-image document and a forced timeout.

4. **Low — The staging MIME choices are acceptable, but the CLI and deploy contracts need to be explicit.**

   **Evidence:** `text/markdown`, `text/org` and reStructuredText have registered MIME types ([IANA registry](https://www.iana.org/assignments/media-types)), but using `text/plain` for private staging is harmless because the filename and verified bytes—not the staging header—decide the format. The browser must therefore make a supported converted extension win over any OS MIME guess; otherwise valid `.md`/`.org` files can be narrowed away.

   The CLI currently classifies to `DocumentKind` and indexes canonical `CONTENT_TYPE[kind]` ([stage.ts:475](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/stage.ts:475), [stage.ts:497](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/stage.ts:497)). It must instead classify to the wider upload format and label the staging PUT through `uploadContentType`/`formatContentType`; `CONTENT_TYPE` correctly remains canonical HTML/PDF only ([blobs.ts:121](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/store/blobs.ts:121)).

   The deploy does not apply bucket changes: it only refuses drift ([deploy.ts:1412](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/deploy.ts:1412)). The explicit repair command performs and verifies the update ([check-buckets.ts:146](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/check-buckets.ts:146), [check-buckets.ts:200](/var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/check-buckets.ts:200)).

   **Fix:** State and test extension-first browser acceptance across realistic MIME guesses; update the CLI staging mapping; add `text/plain` and the DOCX MIME to the bucket; and say that `check-buckets --prod --apply` must run before the deploy gate, rather than that the bucket change happens “through the deploy”.
