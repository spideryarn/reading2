1. **Should-fix — Q1: the local `search_web` tool is the better design, but add the exact regression test.** The spike establishes that both designs work; the local tool avoids a guide-specific recovery branch in the shared loop and makes the evidence an ordinary message ([investigation](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/investigations/261012b-web-search-subagent-spikes.md:47), [plan](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/plans/261012g-web-search-through-a-subagent-for-chat-and-the-guide.md:34)). The loop will not lose `search_web` when it and `offer_next_steps` arrive together with no prose: it records the complete assistant call list, appends a result for every call, and only treats next steps as terminal when that same round wrote prose ([converse.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/converse.ts:3542), [converse.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/converse.ts:3645), [converse.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/converse.ts:3677)). Both results therefore reach the next round. The Stage 1 test list should nevertheless include precisely: zero prose, `search_web` plus `offer_next_steps`, both addressed tool results present in round two, then a prose answer. That is the protocol failure this work exists to prevent, and the current list does not pin it ([plan](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/plans/261012g-web-search-through-a-subagent-for-chat-and-the-guide.md:119)).

2. **Blocker — Q2: no, `read_web_page` for the guide is not plainly authorised.** Greg plainly authorised getting guide search working and proposed a search-subagent handoff. “For the caller-agent to retrieve if it chooses to” can mean receiving the returned links/summary; it does not unambiguously choose option A over the explicitly offered “search only, no page-reading” option ([question](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/user-feedback/questions/q-w26r6u.md:9)). Page-reading changes an enforced tool boundary: `runTool` treats `toolsFor(kind)` as a gate, and the guide deliberately excludes `read_web_page` ([security-map.md](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/project/security-map.md:117), [chat-tools.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/chat-tools.ts:608), [chat-tools.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/chat-tools.ts:769)). Take the plan’s “Chat can open these pages” branch and ask Greg separately.

3. **Should-fix — Q3: result fencing is appropriate, but query exfiltration is missing from the plan’s security treatment.** Validating the URL against `collectSearchEvidence`, replacing the title with the search annotation’s title, and fencing the complete result is the right treatment for the cheap model’s paraphrase ([plan](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/plans/261012g-web-search-through-a-subagent-for-chat-and-the-guide.md:70), [openrouter-stream.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/openrouter-stream.ts:508)). It validates provenance of the link, not the truth of the sentence; the plan should avoid calling the sentence itself “validated.”

   The fence operates after the query has already left. `PROFILE_RULES` tells every profiled conversation never to put the profile into a search query or tool argument, but that remains prompt mitigation ([profile.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/profile.ts:163)). The plan needs a hard query-length cap, a hard per-turn `search_web` call budget, and tests for both. `MAX_TOOL_ROUNDS` limits rounds, not calls in one batch; every requested call is run sequentially ([converse.ts](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/src/converse.ts:3552)). Otherwise an injected private article can emit several search queries carrying article/profile fragments and several paid calls.

   Chat’s existing provider search already has the same broad query-exfiltration exposure, so this is not a novel vulnerability class. What changes is that the previously article-local guide acquires that outbound channel, and the new local tool gives the application an opportunity to enforce a real bound. Without page-reading, there is no additional guide-specific unsupervised action: next steps are reader-pressed, and automatic saving accepts only the reader’s own typed words.

4. **Should-fix — Q4: Stage 2’s direction is right, but its switch criterion omits a metric it explicitly measures.** The plan measures time to first word, yet the gate requires only search success, links, side-by-side quality, and lower cost ([plan](/var/tmp/spideryarn-worktrees/fbvc6uzm-web-search-subagent/docs/plans/261012g-web-search-through-a-subagent-for-chat-and-the-guide.md:128)). Because the proposed path adds roughly nine seconds and another conversation round, latency must be part of the decision. The gate should require:

   - target/control behaviour no worse;
   - answer quality no worse;
   - citation chips preserved, not merely links in prose;
   - total turn cost lower;
   - time to first useful prose not materially worse.
