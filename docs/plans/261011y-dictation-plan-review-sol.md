1. **P1 — Part 1 remains broken in the fleet dashboard.** [tools/fleet/transcribe.ts:92](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/tools/fleet/transcribe.ts:92) still treats anything below 37,000 base64 characters as silence. A one-second recording is roughly 19 KB base64 at the documented Chrome AAC rate, and nearer 5 KB at 32 kbps WebM, so the shared client accepts it and the fleet server discards it at [tools/fleet/transcribe.ts:237](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/tools/fleet/transcribe.ts:237). Fix: lower or centralise this floor, update the rate-limiter decision at `routes-transcribe.ts:395`, and add a realistic one-second fleet test. The product path otherwise looks sound: its floor is only 2,000 characters, `MediaRecorder.stop()` supplies the terminal sub-timeslice chunk, and there is no hook-level duration check.

2. **P1 — `phase === "opening"` does not identify a new session, so the proposed cleanup can cancel Stop.** The plan says opening clears the hold at [plan:110](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/docs/plans/261011y-dictation-short-recordings-and-a-double-press-that-lands.md:110), but Chromium’s recogniser returns to `opening` when it restarts after an ordinary pause within the same session at [useDictation.ts:1589](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/src/web/useDictation.ts:1589). During the hold, `stopRequested` is still false, so this race is possible; clearing the timer means the microphone simply continues after the reader pressed Stop. Fix: bind the pending stop to an explicit session generation, not a phase. A recogniser restart keeps the generation; device change/new capture changes it. The timer must read the latest generation and `armed`, not a render-time closure. Test recogniser restart, device change, cap, capture failure, and StrictMode.

3. **P1 — keyboard double-press will move focus away from Stop after the first activation.** Every field toggle schedules focus back onto the text box at [useDictationField.ts:483](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/src/web/useDictationField.ts:483). Thus Enter or Space activates Stop once, then the next key activates or edits the box rather than the still-visible button. In the command bar, the second Enter instead reaches `enter()` and is refused as busy. Fix: when the first Stop press opens the hold, keep focus on the button; restore the box focus only when a single-stop timer expires, if appropriate. Add DOM tests using actual Enter and Space activation rather than direct callback calls.

4. **P1 — pending “must stop” and “may send” state must be separate.** The plan requires a `doneKey` change to withdraw sending while still honouring Stop at [plan:111](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/docs/plans/261011y-dictation-short-recordings-and-a-double-press-that-lands.md:111). Reusing the current key-change cleanup at [useDictationField.ts:277](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/src/web/useDictationField.ts:277) to clear the hold would instead cancel the pending Stop and leave the microphone running. Fix: capture `{sessionGeneration, doneKey}` on the first press; the timer always stops that still-current session, while a second press sends only when the captured key and current `onDone` still match. Otherwise the second press performs an ordinary immediate stop.

5. **P2 — the 300 ms window contradicts the plan’s own measured click spacing.** The successful examples were approximately 320 ms and 490 ms apart at [plan:70](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/docs/plans/261011y-dictation-short-recordings-and-a-double-press-that-lands.md:70), yet both would expire under the proposed 300 ms hold at [plan:90](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/docs/plans/261011y-dictation-short-recordings-and-a-double-press-that-lands.md:90). Fix: measure the actual pointer-event interval from the reported gesture, then either use a window that covers it or separate the 300 ms stop delay from a longer stable second-press target.

6. **P2 — “nothing changes on screen while it holds” is not guaranteed on Chromium.** The live recogniser can still publish final and interim results during those 300 ms at [useDictation.ts:1465](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/src/web/useDictation.ts:1465). Those updates resize Chat’s textarea at [ChatPanel.tsx:3191](/var/tmp/spideryarn-worktrees/fbaz6puq-dictation-short-and-double-click/src/web/ChatPanel.tsx:3191) and the fitted Quiz/Feedback boxes, potentially moving the same button the hold is intended to preserve. Fix: add a browser test that delivers a recogniser result between presses and asserts the button’s hit rectangle remains fixed; if it moves, buffer/freeze live decoration and layout until the hold resolves.

Deleting `again`, `pressable`, `stoppedAt`, `endedWith`, and `stopAwaitingEnd` is otherwise safe: they serve only the old after-Stop window. Keep `wantSend`, `delivered`, `sendingAfter`, the `sendTick`/key checks, and their `onEnd` clearing—those enforce real-transcript-only sending and prevent Retry from inheriting the wish. Chat’s wrapper, Feedback closing, unmount, cap, and a third press are sound once the pending timer is cleared synchronously and bound to the session as above.
