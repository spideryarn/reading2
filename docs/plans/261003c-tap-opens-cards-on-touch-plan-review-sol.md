1. **P1 — A cardless Structure row will become a silent two-tap target unless the caller explicitly bypasses `useTapReveal`.** The hook’s `commits` argument controls only the hint; `commit()` still returns `false` and arms itself on the first finger tap regardless of `commits` ([useTapReveal.ts:64](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/useTapReveal.ts:64), [useTapReveal.ts:105](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/useTapReveal.ts:105)). Structure has real visible rows where `row.card === null` ([StructurePanel.tsx:327](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/StructurePanel.tsx:327)). Therefore `useTapReveal(card !== null)` is not sufficient: the “here” row’s first tap would do nothing and display nothing. Fix: bypass `commit()` unless a card exists, and preferably split the card-bearing trigger into a child component that owns the hook. That also avoids allocating hook state/callbacks for the potentially huge measuring copies rendered with `tip={false}` ([StructurePanel.tsx:625](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/StructurePanel.tsx:625)). Outline’s measuring copies are already safe because they render only `RowBody`, not `Row` ([OutlinePanel.tsx:523](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/OutlinePanel.tsx:523)).

2. **P1 — Take option (b), but put the overhang behind every control instead of trying to enumerate “visible marks” with `:has()`.** On a non-active row under `(hover: none)`, the exhaustive set of potentially visible gutter children is:

   - `.blk-cmt`, when an existing bookmark/note is displayed;
   - `.block-chat.has`, when its slot is displayed;
   - `.blk-permalink.failed`, when displayed;
   - any displayed permalink/chat/bookmark/help/more control that is `:focus-visible`;
   - every ordinary control in a `[data-open]` gutter;
   - `span.blk-read` itself when `--read` gives it non-zero width.

   The relevant rules are at [gutter.css:581](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:581), [gutter.css:599](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:599), [gutter.css:674](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:674), [gutter.css:797](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:797), and [gutter.css:857](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:857). A set bookmark is `.blk-cmt`; `.blk-bookmark` is the affordance for creating one ([BlockGutter.tsx:547](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/BlockGutter.tsx:547)). No selector can robustly ask whether a child is visibly painted after the container-query/display/opacity rules. Instead, layer all direct `button`/`a` controls above the reading strip structurally—e.g. positioned with `z-index: 1`—and keep the strip/its pseudo-element below them. Hidden controls already have `pointer-events:none`; visible controls then win their own rectangles, while blank portions of the column remain usable by the widened strip. This is future-safe and supports (b); (a) leaves the reported feature practically untappable.

3. **P1 — The reading-time trigger becomes interactive while remaining completely hidden from keyboard and assistive technology.** It is explicitly `aria-hidden="true"` ([BlockGutter.tsx:877](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/BlockGutter.tsx:877)); `BlockLinkCard` refuses to attach `aria-describedby` to such a trigger ([BlockLinkCard.tsx:343](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/BlockLinkCard.tsx:343)); yet CSS makes it an active help target ([gutter.css:967](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:967)). Adding click handling sharpens that mismatch. Fix: make an explicit accessibility decision in the plan—either expose it as a named, keyboard-operable disclosure with a visible focus treatment, or expose the same reading-time explanation through an existing accessible gutter control. Do not leave an `aria-hidden` click target as the finished design.

4. **P2 — The reading-line click path is otherwise sound, but the new click handler must cancel the pending open timer as well as the close timer.** A direct child can opt back into hit-testing even though `.blk-gutter` is `pointer-events:none`; the strip already does so ([gutter.css:218](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:218), [gutter.css:967](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/styles/gutter.css:967)). Its click bubbles to `document`, and TableView will not select the block because `.blk-gutter` is in `NOT_A_BLOCK_SELECTION` ([TableView.tsx:426](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/TableView.tsx:426), [TableView.tsx:464](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/TableView.tsx:464)). ProseHoverCard’s tap selector does not match it, and BlockLinkCard has no `useDismiss`. The touch `pointerover`/`pointerout` only schedule a close, so clearing that close timer at click is sufficient for touch. However, a mouse can click during the 240ms cold-hover delay: `arm()` has then left `openTimer` pending, and `show()` does not clear it ([BlockLinkCard.tsx:433](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/BlockLinkCard.tsx:433), [BlockLinkCard.tsx:443](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/BlockLinkCard.tsx:443)). That late hover callback can overwrite the new card’s “opened by click” provenance and defeat scroll dismissal. Fix: the click path must clear `openTimer`, clear `closeTimer`, clear `pending`, then call a source-aware `show(el, clientY, "click")`. Test click-before-240ms, advance the timer, then scroll.

5. **P2 — Scroll dismissal is safe, provided it also revokes the recorded press.** Tooltip mounting and `autoUpdate` listen for scroll but do not cause one ([Tooltip.tsx:234](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/Tooltip.tsx:234)). Outline deliberately changes its own `scrollTop` only when the current row changes, and explicitly avoids `scrollIntoView` ([OutlinePanel.tsx:329](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/OutlinePanel.tsx:329)). Thus opening a row card should not immediately dismiss it; the band’s windowing also does not scroll merely because a tooltip opened. On the second tap, the hook closes before `onJump`, so the jump’s scroll is harmless. The remaining edge is a scroll between `pointerdown` and `click`: the hook’s press snapshot can still say `wasOpen:true` after the scroll closed the card ([useTapReveal.ts:36](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/useTapReveal.ts:36), [useTapReveal.ts:90](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/useTapReveal.ts:90)). Fix: the capture-phase scroll handler should set both `press.current = null` and the armed state to `null`. Windowed-row unmounting is otherwise naturally safe because the state belongs to the row component.

6. **P2 — Per-row state does avoid the 260828g trap; add a group-level regression test so it stays true.** Each `useTapReveal` instance owns its own `armed` state ([useTapReveal.ts:69](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/useTapReveal.ts:69)), so a delay-group close or stale hover close can only clear that row, unlike the shared Spine state that allowed one member’s close to clear another member’s open card ([260828g-spine-hover-cards.md:29](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/docs/postmortems/260828g-spine-hover-cards.md:29)). Controlled mode also supplies `mouseOnly`, preventing touch hover from owning the open state ([Tooltip.tsx:261](/home/greg/code/spideryarn2/.claude/worktrees/fba868zs-tap-opens-rich-tooltips/src/web/Tooltip.tsx:261)). On an ordinary iPad sequence, the second press records `wasOpen:true`; the click’s erroneous `"mouse"` label is irrelevant, so it commits. A hover-opened card also commits on the first finger tap because the press saw it open. Fix the test plan to render at least two real rows inside the real `TooltipGroup`: hover A→B, touch-open A→touch B, advance both the 90ms close and 400ms group timeout, then verify B still opens and its second iPad-style tap jumps. A single-row unit test cannot catch this class.

**Verdict:** Sound direction, but revise before building: explicitly bypass cardless rows, replace the mark-enumerating `:has()` with structural stacking, and address the reading line’s accessibility and timer provenance.
