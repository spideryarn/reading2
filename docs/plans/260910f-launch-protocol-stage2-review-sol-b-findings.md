# Stage 2 review findings — Sol B

## F21 — P1 — established

`run-codex --launch-dir` does not preserve the last attempt's answer at the launch-default path when the wrapper rejects the run. At committed `scripts/run-codex.ts:655-657`, it records the temporary `runPlan` output path immediately. The failure ladder at lines 671-693 calls `process.exit(1)`, so the copy to `args.output ?? launch.defaults.answer` at lines 696-704 is reached only on success. A non-zero run that wrote a partial answer, and even the existing empty-answer fixture, therefore produces an `exit.json` whose `answer.path` is `/tmp/run-codex-…/output-N.txt`, not `<artefactDir>/answer.md`; the attempt directory does not contain the promised durable answer. This breaks the agreed scheduled-dispatch seam: “paths in `exit.json` … defaulting to `<artefactDir>/answer.md`”. Reproduced against an isolated export of commit `3858a4a9`: a stand-in Codex wrote two whitespace bytes and exited 0; the wrapper exited 1, the attempt had no `answer.md`, and `exit.json` recorded `"path":"/tmp/run-codex-9qym8F/output-1.txt"` with `cause:"empty-answer"`.

- Test/input: run `run-codex.ts --prompt p --sandbox read-only --launch-dir <valid-dir>` with a stand-in Codex that writes a partial or whitespace answer to `-o` and then exits non-zero (or exits zero with the whitespace answer). `tests/run-codex.test.ts:1159-1163` already supplies the empty-answer case but asserts only `bytes`/`usable`, so it passes while the path is temporary; lines 1171-1181 assert the launch-default path only on success.
- Smallest fix: for launched runs only, compute `args.output ?? launch.defaults.answer`, copy the last attempt's output there (when it exists), and call `notePaths` before the failure ladder. Keep `answerIsUsable(outFile)` and the per-attempt temporary files, so fallback isolation and non-launch behavior remain unchanged. Extend the non-zero/empty-answer launch tests to assert both the path and the file under the attempt directory.

## F22 — P0 — reasoned

The new tests that rely on a stand-in `claude`/`codex` at the front of `PATH` do not make it impossible for the wrapper to resolve the real binary. For example, `tests/overseer-launchers.test.ts:711-714` constructs and preflights an `env` whose `PATH` finds the stand-in, then the session runs `run-claude`. But committed `scripts/run-claude.ts:722` calls `loadRepoEnv()` first, and `scripts/subagent-cli.ts:452-455` delegates to `loadEnvLocal()`, whose explicit contract is that `.env.local` overrides inherited variables. Thus a valid developer-local `.env.local` containing `PATH=…` replaces the tested path after the preflight and before both `claude auth status` and the paid CLI spawn. The same hole exists in the added launch-dir subprocess helpers (`tests/run-claude.test.ts:760-768`, `tests/run-codex.test.ts:1097-1107`) and the “no CLI on PATH” checks. The current worktree's `.env.local` does not define `PATH`, so this review did not launch a real CLI; the finding is about the required invariant, and this is the exact process-boundary precedence trap documented in `src/env.ts:46-65`.

- Test/input: add `PATH=/a/path/containing/the/real/cli` to `.env.local`, then run the real-tmux test at `tests/overseer-launchers.test.ts:696-742`. Its line-714 preflight still sees the stand-in because it runs before the wrapper loads `.env.local`; inside `run-claude`, the file wins and the real binary can run. (Do not perform this reproduction: it can spend money.)
- Smallest fix: in every spawned test-wrapper environment, include `PATH` in inherited `SPIDERYARN_ENV_PINNED` (and preferably pin the account-routing variables the fixture deliberately removes), then make the preflight run through `loadRepoEnv` or have the stand-in leave an early marker and refuse if it was not the executable used. This keeps production precedence unchanged while making a real CLI structurally unreachable in tests.

## F23 — P1 — established

The committed `gjd-remote` job does not write `exit.json` on every end after it has written `start.json`. The only exit writer is at `scripts/gjd-remote.ts:2800-2803`, after Claude returns. But the launched shell writes `start.json` at lines 2731-2737 and then has several earlier terminating paths: `cdGuard` at line 2743, the missing-`claude` `failTo` at 2748-2749, account identity/config guards inserted by `accountJobParts` at line 2760, and the account-start bookkeeping refusal at 2769-2770. `failTo` is an `exit 1` (`scripts/gjd-remote.ts:1869-1872`), so each path ends the supervisor without reaching line 2801. Reconciliation sees a valid start, a gone same-boot supervisor, and no exit, and correctly holds `outcome-unknown`; Greg must dispose a run whose shell actually knows it ended before Claude. This contradicts property 2's one final `exit.json` on every way the run can end, and the Stage 2 gap list does not disclose it.

- Test/input: generate the committed job with a valid launch, then make the target directory disappear after the box-side check but before the job reaches `cdGuard` (the existing comment at `scripts/gjd-remote.ts:2738-2742` names exactly this reproducible race). The job writes a parseable `start.json`, `cdGuard` calls `failTo` and exits 1, and `exit.json` is absent. Removing `claude` from the job `PATH` is a simpler deterministic input with the same result. `tests/gjd-remote-launch-id.test.ts:177-208` assembles only a successful directory guard and a Claude that returns normally; lines 229-237 merely compare source ordering, so no existing test fails.
- Smallest fix: immediately after the successful start writer, install an `EXIT` trap that writes the shell exit status through the shared durable exit writer. On the normal Claude-return path, write the existing exit record and disable the trap before the later bookkeeping/`exec bash -l`, so exactly one final record is produced. Add actual-job-shaped tests for at least the directory and missing-CLI guards, asserting `start.json` and `exit.json` both round-trip and Claude never ran.

## F24 — P2 — established

The SIGHUP/orphan contract is not exercised for `run-codex`. Production wiring is present at committed `scripts/run-codex.ts:517-524` (`onHangup: launch?.hangup`), and the shared `runChild` behavior is exercised end to end only by the `run-claude` tmux test at `tests/run-claude.test.ts:961-1017`. `tests/run-codex.test.ts` contains no SIGHUP or `onHangup` assertion. Deleting the one `onHangup` line from `run-codex` would therefore leave all of its tests green while a launched Codex child once again survived its wrapper and no `exit.json` was written. This is exactly the requested class of test that passes when the relevant code does nothing.

- Test/input: remove `onHangup: launch?.hangup` at `scripts/run-codex.ts:523` and run `tests/run-codex.test.ts`; no committed test observes the regression.
- Smallest fix: add a launched `run-codex` subprocess test with a stand-in child that records its pid and blocks, send SIGHUP to the wrapper, then assert the child is gone and the correlation-bound `exit.json` has `cause: "hangup"`. It can signal the wrapper directly and need not depend on real tmux; apply F22's pinned-`PATH` safeguard.
