1. **P1 — The cancellation copy implies a fresh Free allowance, which is false.**  
   The plan says an ending subscription “goes back to the free allowance” without saying that paid-period additions already consumed it ([plan:91](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/plans/261002b-voucher-note-to-recipient-gift-on-profile-whole-dollar-spend.md:91>)). Free usage is lifetime and counts every successful ingest, including paid months ([pg-billing.ts:552](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-billing.ts:552>)); the policy explicitly says cancellation may leave no Free capacity ([billing.md:331](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/project/billing.md:331>)).  
   **Fix:** Ending copy should say: “This does not reset your Free allowance. Articles added while subscribed already count toward that lifetime allowance.” If the tooltip must give a number, add a server-computed future Free limit and remaining capacity rather than implying the allowance is newly available. Test an ending subscriber whose lifetime usage exceeds Free.

2. **P2 — `trialing` plans cannot truthfully use the proposed renewal wording.**  
   `trialing` is an entitled paid status ([tiers.ts:87](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/billing/tiers.ts:87>)), but `ReaderPlan`’s paid arm loses that distinction ([billing-plan.ts:199](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/billing-plan.ts:199>)). The server retains it only in the purchase arm because trial transitions differ ([summary.ts:132](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/billing/summary.ts:132>)). Therefore “starts again on 3 Nov, back to 20” is not established for a trial: the trial may convert, end, or fail payment.  
   **Fix:** Carry a paid-plan phase such as `"trial" | "paid"` or a narrower `renewsAllowance` fact. Give trials separate copy and add a trial case to the plan-copy tests. This is lower severity because Spideryarn does not currently sell trials, but the state is supported.

3. **P2 — The re-address path needs an explicit “effective post-patch note” rule.**  
   The plan promises that re-addressing renders the note “as it stands after the patch” ([plan:58](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/plans/261002b-voucher-note-to-recipient-gift-on-profile-whole-dollar-spend.md:58>)). Currently the locked voucher projection reads email and articles, then queues from those values ([pg-vouchers.ts:640](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-vouchers.ts:640>), [pg-vouchers.ts:681](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-vouchers.ts:681>)). A naïve implementation that passes only `patch.recipientNote` will omit a previously saved note when PATCH changes only the address.  
   **Fix:** Select the stored recipient note under the voucher lock, compute `effectiveNote = patch.recipientNote === undefined ? current.recipientNote : patch.recipientNote`, and pass that to the new delivery. Test:

   - edit note only → existing delivery remains frozen;
   - re-address later → new delivery contains the saved note;
   - re-address and edit together → new delivery contains the patched note;
   - retry → sends the original frozen body.

   Retry, revoke, and idempotency otherwise remain sound because delivery reads only frozen outbox fields ([pg-voucher-emails.ts:558](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-voucher-emails.ts:558>)).

4. **P2 — HTML escaping is sufficient, but the plan needs provenance and control-character handling.**  
   Escaping `& < > " '` in an HTML text node prevents markup and link injection, and there is no header-injection path because the note never enters `to`, `from`, or `subject`; those are separate JSON fields ([email.ts:52](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/email.ts:52>)). The remaining problem is that the email is visibly from Spideryarn ([email.ts:39](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/email.ts:39>)), while the plan deliberately gives the note no label ([plan:46](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/plans/261002b-voucher-note-to-recipient-gift-on-profile-whole-dollar-spend.md:46>)). Literal URLs may also be auto-linked by mail clients. Control characters, CR-only breaks, and Unicode line separators are not covered by “turn newlines into `<br>`”; the existing mail helper already treats these as capable of creating deceptive lines ([email.ts:250](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/email.ts:250>)).  
   **Fix:** Label it “A note from the person who sent this gift,” in both parts. Normalize CRLF/CR and Unicode separators to `\n`, remove other control characters, and optionally cap line count as well as 500 characters. Test NUL, CR-only, U+2028/U+2029, ampersands, quotes, and a literal URL; assert the HTML creates no note-supplied `href`.

5. **P2 — Falling back from `periodAllowance` to current `limit` defeats the field’s purpose.**  
   The plan correctly observes that `limit` may be prorated, but then proposes using it as the fallback ([plan:105](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/plans/261002b-voucher-note-to-recipient-gift-on-profile-whole-dollar-spend.md:105>)). That could turn “back to 20” into “back to 33.” Entitlement becomes paid only after a tier has been found in the same tiers snapshot ([pg-billing.ts:409](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-billing.ts:409>)), while the prorated override applies only to its matching period ([quota-adjustment.ts:304](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/billing/quota-adjustment.ts:304>)).  
   **Fix:** Take `periodAllowance` from that already-proven tier row. If the invariant cannot be represented cleanly, return `unknown` or fail loudly; do not silently substitute `limit`. Test a prorated switch explicitly: current `limit = 33`, `periodAllowance = 150`, next-period copy says 150.

6. **P3 — The gifted-Free example states the wrong headline number.**  
   “3 articles for the life of the account (3 free + 20 from a gift)” ([plan:91](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/docs/plans/261002b-voucher-note-to-recipient-gift-on-profile-whole-dollar-spend.md:91>)) first calls the allowance 3 and then describes an allowance of 23. The entitlement actually adds gifts to the lifetime limit ([pg-billing.ts:388](</home/greg/code/spideryarn2/.claude/worktrees/fb-voucher-note-and-profile/src/store/pg-billing.ts:388>)).  
   **Fix:** Say “23 articles for the life of the account (3 included + 20 from a gift). It does not reset monthly.”

The whole-dollar design has no substantive edge-case defect: conventional half-up behavior gives `$1` at exactly $0.50, positive amounts below that become `<$1`, zero calls remain an em dash, and sorting remains by nanos. Pin the $0.499999999/$0.50 boundary in tests.

Adding optional `gifts` to the paid `ReaderPlan` arm is otherwise safe: current consumers that inspect gifts first narrow to Free/lapsed, and paid gifts remain excluded from entitlement by `freeEntitlement`.

**Overall conclusion:** The three-stage approach holds, including the frozen outbox, shared plan-help UI, and whole-dollar formatting. It should not be built unchanged: findings 1–5 need to be incorporated, chiefly the cancellation/trial truthfulness, effective-note handling during re-address, and note provenance.
