I would not build the plan unchanged. The reveal timing, flash paint, accessibility, and verification need tightening first.

1. **P1 — Reveal scrolls and flashes before React has opened the section.**

   Evidence: the plan dispatches the event, immediately calls `scrollIntoView`, then immediately flashes ([plan:36](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:36)). The listener’s `setOpen(true)` only schedules the render; `showing` controls both hidden and unmounted bodies ([Metadata.tsx:3543](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:3543), [Metadata.tsx:3593](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:3593)). Near the document foot, a shut section may not leave enough scroll range to place its heading at `scroll-mt-24`; opening it later increases the range but does not reliably retarget the already-started native scroll. The existing jump machinery explicitly waits for scrolling to settle before flashing ([keynav.ts:296](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/keynav.ts:296), [keynav.ts:338](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/keynav.ts:338)).

   Concrete fix: open first, wait for the committed DOM, then scroll with a helper that remeasures and reports settled/cancelled, and only flash on settled. Generalising the existing glide machinery is robust; the simpler v1 is an instant scroll on the next animation frame followed by the flash. If the event remains, test that the body is already shown when the scroll function is invoked.

2. **P1 — The proposed section-level inset shadow will be hidden by the page’s cards.**

   Evidence: the plan applies an inset `box-shadow` to the outer `<section>` ([plan:56](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:56)). Inset shadows paint over that element’s background but underneath its descendants. Most section contents paint opaque `tw:bg-card` surfaces ([card.ts:16](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/card.ts:16), [Metadata.tsx:871](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:871), [Metadata.tsx:1398](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:1398)). The prose-cell version works because the shadow is on the element that owns the painted surface ([prose.css:130](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/styles/prose.css:130)).

   Concrete fix: use a non-interactive `::after` overlay above the section’s descendants, with a genuinely translucent tint and `pointer-events:none`, or apply the wash to the heading and each painted card. Do not put the opaque `--highlight-wash` above text unchanged; introduce an alpha overlay colour. Verify the actual rendered pixels or computed pseudo-element styles over an opaque card.

3. **P1 — Reveal moves the viewport but not keyboard or screen-reader focus.**

   Evidence: the plan mentions only scrolling and a visual flash ([plan:34](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:34)). Focus therefore remains in the fixed search box or contents button while the visible page moves elsewhere. The existing “Share…” navigation already scrolls and then focuses the destination heading ([Metadata.tsx:710](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:710)), but only the sharing heading is currently made programmatically focusable through `landing` ([Metadata.tsx:3503](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:3503), [Metadata.tsx:3565](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:3565)).

   Concrete fix: make every section heading programmatically focusable and focus it with `preventScroll:true` after arrival. This can replace the one-off `landing` prop. The flash remains the visual cue; focus supplies the equivalent navigation to assistive technology.

4. **P2 — Searching body text while deferring the matching line does not satisfy “scroll to the right place.”**

   Evidence: body text is included in the corpus ([plan:68](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:68)), but landing on the actual match is deferred on the claim that sections are at most a screenful or two ([plan:95](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:95)). “AI processing” alone has fourteen rerun rows ([Metadata.tsx:1520](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:1520)) followed by every pipeline stage ([Metadata.tsx:1491](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:1491)). A query matching an output path can land several screens above the match.

   Concrete fix: either exclude body text in v1 and search only the stable destination-level fields—label, aside, keywords and synonyms—or retain the matched descendant/snippet and scroll and flash that match after opening. The present hybrid promises item-level finding but provides section-level navigation. This is the one deferral in the conclusion that is not reasonable as written.

5. **P2 — The body/aside search index has no defined freshness or visibility contract.**

   Evidence: the current scanner observes only `childList` mutations and compares only `id` and `label` ([PageContents.tsx:79](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/PageContents.tsx:79), [PageContents.tsx:94](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/PageContents.tsx:94)). Aside text changes after asynchronous reads, including pipeline status and cost ([Metadata.tsx:719](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:719), [Metadata.tsx:1782](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:1782)); text-node changes need not produce `childList` mutations. Also, `keepMounted` content is mounted but explicitly hidden ([Metadata.tsx:3593](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/Metadata.tsx:3593)): `textContent` includes it, while “visible text” and `innerText` suggest excluding it.

   Concrete fix: define the corpus precisely. If DOM indexing remains, observe `characterData` and the relevant data attributes, compare every indexed field, and deliberately use either hidden-inclusive `textContent` or visible-only extraction. Test a query entered before Export appears and before a dynamic aside changes, then assert that results update without another keystroke. Dropping body indexing as in finding 4 removes most of this machinery.

6. **P2 — The ranking rules are not ordered enough to produce predictable results.**

   Evidence: the plan independently says field priority and direct-over-synonym priority, without defining which wins when they conflict ([plan:79](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:79)). It also does not say whether repeated body occurrences add score, or how ties resolve. A direct body occurrence could therefore beat a synonym match in the correct label, and a long “AI processing” body could win by repetition. Strict AND also makes ordinary queries such as “how much did this cost” fail on the filler words.

   Concrete fix: score each query token once, using its single best evidence; make the ordering explicit, for example exact phrase, then field priority, then direct/prefix/synonym within that field. Preserve page order for exact ties. Ignore a small set of query stopwords when another substantive term exists. Add adversarial tests: synonym-label versus direct-body, short versus repeated body text, ties, punctuation, and “how much did this cost”—not only the uncontested `price → What it cost` case.

7. **P2 — The search box will jump vertically as its results filter.**

   Evidence: the entire current nav is centred with `top-1/2` and `-translate-y-1/2` ([PageContents.tsx:189](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/PageContents.tsx:189)). The plan puts the input inside that box and changes the number of rows on every keystroke ([plan:63](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:63)). Filtering twelve rows to one reduces the box height and moves its top—and the focused input—down by roughly half the removed height.

   Concrete fix: give the searchable margin a stable top and available-height box, with only the results list scrolling, or reserve a stable list height. Keep safe-area, wordmark, and dock clearance explicit.

8. **P1 — The proposed checks can pass while the important failures above remain.**

   Evidence: the component test checks only “opens and carries the flash class,” while the browser pass is unspecified ([plan:108](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:108)). A class can exist while an opaque child hides its effect; the current flash suite deliberately checks the winning computed style, not just class presence ([block-flash.test.ts:151](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/tests/block-flash.test.ts:151)). A scroll spy can report a call without proving the section was open first or that the heading arrived on screen. The 390px pass cannot exercise this feature because the plan deliberately hides it below `xl` ([plan:97](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/docs/plans/261001s-metadata-contents-opens-and-flashes-its-section-and-a-search-box-above-it.md:97)). Finally, current lookup code carefully scopes duplicate section IDs to each page ([PageContents.tsx:127](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/PageContents.tsx:127), [PageContents.tsx:203](/home/greg/code/spideryarn2/.claude/worktrees/fb7y-83-metadata-toc-flash-and-search/src/web/PageContents.tsx:203)); the new tests do not pin that property.

   Concrete fix: add integration coverage for both a hidden `keepMounted` section and an unmounted section; assert the body is visible at the instant scrolling begins; assert the class survives the opening render, restarts, and expires; mount two Metadata roots with duplicate IDs and prove the second nav changes only the second page. In a real 1440px browser, use a collapsed bottom section, measure its heading after settlement, and verify the flash’s rendered overlay over an opaque card. Treat 390px only as an explicit “absent and no overflow” check. Use `useId()` for the input, results list and label so the duplicate-page fixture does not introduce duplicate control IDs.

The narrow-window and keyboard-shortcut deferrals are reasonable. Deferring models/embeddings is also sensible; a small deterministic synonym table is proportionate here. The matching-line deferral is reasonable only if body-text search is removed from v1.
