## Findings

1. **[P2] Pen/stylus input still commits on the first press.**  
   [ShelfEntry.tsx](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:503) recognizes only `pointerType === "touch"`. Floating UI deliberately treats `"pen"` as mouse-like ([installed implementation](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/node_modules/@floating-ui/react/dist/floating-ui.react.utils.esm.js:205)), so a quick Apple Pencil or Surface Pen press can activate Edit/Open/Archive before its delayed hover card opens. This is inconsistent with `touch.md`, which elsewhere treats Apple Pencil as finger-equivalent. Decide explicitly whether pens belong to reveal-then-commit; the current result looks accidental. The running `dispatchTouchEvent` pass will not catch this.

2. **[P2] “A mouse is unchanged” is false.**  
   The commit branch unconditionally calls `setArmed(null)` ([ShelfEntry.tsx:513](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:513)). Consequently, clicking Copy or Re-fetch closes a mouse-opened tooltip and it remains closed even though the pointer is still over the trigger. Keyboard Enter also closes the focus-opened card. Previously, `useDismiss` had `referencePress: false`, so activation did not close it. Either preserve the prior behavior by clearing only a touch-armed card, or narrow the claim and add a deliberate test for the new behavior.

3. **[P2, hybrid devices] The row is still not guaranteed to be visible to a finger.**  
   The gesture correctly uses the press’s pointer type, but visibility still relies on `(hover: none)` ([ShelfEntry.tsx:593](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:593), [tailwind.css:100](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/tailwind.css:100)). A touchscreen laptop whose primary pointer can hover does not match that query. Touch may establish `:hover` or focus after hitting the invisible row, but the controls are undiscoverable beforehand. The ordinary mobile CDP configuration will probably report `hover: none`, so it will not test this. Check a hybrid media configuration with no preceding mouse movement.

4. **[P3] Re-fetch can promise an action that the second tap refuses.**  
   `commits={hasWebUrl}` ([ShelfEntry.tsx:608](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:608)) ignores `rerunning`, while the button is disabled when `rerunning` ([ShelfEntry.tsx:620](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:620)). Tapping the spinner opens a card saying “Tap again to do it”; tapping again merely closes the card because `IconButton` refuses the click. This should be `hasWebUrl && !rerunning`, with a pending-request test.

5. **[P3] `KEYS` does not make JSX typos fail safely, and Copy is untested.**  
   `data-action` accepts any string. An invalid value makes `actionAt` return `null`, which lets the first touch activate the child—the unsafe failure mode. The comment claiming a typo “should fail here” is therefore wrong ([ShelfEntry.tsx:729](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/src/web/ShelfEntry.tsx:729)). None of the touch cases exercises Copy ([touch tests](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/tests/shelf-action-touch.test.tsx:171)), so `data-action="cop"` would leave all 11 green while restoring the original bug for that control. Derive the DOM attribute from `ActionTip`’s typed `id`, or at minimum test first/second tap for every actionable control. `KEYS` should also be `as const` with `ActionKey` derived from it; its present `readonly string[]` annotation allows the list and union to drift.

## Answers to the event-order questions

- Capture-phase `stopPropagation()` is sufficient here. React 19 stops dispatch when moving from the row to the child, and the native stop prevents reaching target listeners. Floating UI currently installs no reference `click` behavior because `useDismiss` defaults `referencePress` to false.
- `preventDefault()` on the cancelable click prevents the anchor’s navigation, including `target="_blank"`. The browser pass should nevertheless assert that no new page/tab appears, rather than only inspect `defaultPrevented`.
- `useDismiss`’s document `pointerdown` does not close when pressing the currently open tooltip’s own reference. Pressing another trigger closes the old tooltip before click, but fresh `null` and stale “other id” both take the reveal branch, so correctness does not depend on closure freshness there.
- The installed `useFocus` does default to `visibleOnly: true` and tests `:focus-visible` ([Floating UI implementation](/home/greg/code/spideryarn2/.claude/worktrees/shelf-tips-touch/node_modules/@floating-ui/react/dist/floating-ui.react.esm.js:3014)). Chrome should therefore ignore ordinary pointer-induced focus. If the browser reports the touched button as `:focus-visible`, the first tap will indeed commit; the jsdom tests cannot detect that because their “touch” helper emits only `click`.
- Treating pointerless clicks as commits is correct for keyboard and assistive-technology activation.

I expect the plain Chrome `dispatchTouchEvent` pass to succeed for finger input. It should specifically record `pointerdown → focus → click`, the click’s actual `pointerType`, `:focus-visible` during focus, absence of a new tab on the first Open tap, and persistence after the compatibility mouse events. I would separately test pen input, hybrid visibility, and the 28px adjacent hit targets; the ordinary mobile emulation covers none of those.
