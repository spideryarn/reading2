R1 — P1 — established. The proposed background refresh would violate the spend-recording contract. The request collector closes when the route returns; later calls become unrecorded “late finishes” ([routes.ts](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/src/routes.ts:6459), [ai-spend.ts](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/src/ai-spend.ts:928)). Vercel provides `waitUntil`, but using it under the existing collector would not fix accounting; it merely keeps the invocation alive. [Vercel documents `waitUntil` for cache updates](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package). Recommendation: send/end the deterministic response, then `await` the claimed refresh before the handler returns. Alternatively, use `waitUntil` with a separate durable collector carrying the captured owner—more machinery.

R2 — P1 — established. The cache key omits model inputs. The plan sends profile, title, gist and candidates, but hashes only revision ids plus extractor version ([plan lines 57–65, 105–112](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/docs/plans/260929c-shelf-topics-chosen-by-a-model.md:57)). Profile edits, reader title renames, regenerated gists, prompt changes and model upgrades would leave an apparently fresh but wrong selection. Hash the normalized, sorted actual input plus prompt/selector version and pinned model. Refresh active-only on archive/restore; do not refresh active+archived merely because status changed. Search, sorting, Unread, comments and reading state should never refresh.

R3 — P1 — reasoned. Stale GETs have no claim, backoff or spend fuse. Multiple tabs, the existing pending polling loop, repeated failures, profile edits, or archive/restore churn could duplicate paid calls indefinitely. Claim `(owner, scope, input_hash)` atomically with a lease; call only after candidate extraction has `pending === 0`; fence writes; record failed attempts with retry-after; and add a per-owner daily/global-fuse rate bucket. Attribute production calls to a new `shelf-topics` `AiJob`, `scope_kind=request`, and that shelf’s owner. Do not consume ingest quota: billing’s contract is that existing reading remains available and only adding an article spends that allowance.

It does not permit silently adding an unnamed default model: the page deliberately enumerates every model ([PrivacyPage.tsx](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/src/web/PrivacyPage.tsx:383)). [OpenRouter privacy policy](https://openrouter.ai/privacy/). Logs must contain no titles, gists, profiles, prompts or malformed output.

R5 — P2 — established. The spike does not prove the key can call Jev. It invokes `openRouterJson("eval")`, whose fixed route is chat completions, and never posts to `/api/alpha/decisions` ([spike](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/evals/shelf-topics/spike-jev.ts:25)). Thus “reached both endpoints’ front doors” is unsupported, and Stage 1 cannot be both “no product code changes” and “through the gateway”: the gateway has no Decisions path or wire. Run one real, metered Decisions request and preserve its response schema, exact answered model, provider and cost. OpenRouter confirms that Jev uses `POST /api/alpha/decisions`. [OpenRouter Jev guide](https://openrouter.ai/blog/insights/what-is-jev/).

R6 — P2 — reasoned. The eval is a useful smoke test, not enough to select a general production arm. Three shelves × two runs gives at most six observations per contrast; one same-arm pair measures almost nothing. The judge is asked what is meaningful “to this reader” without receiving the profile that the arms received, and sees labels without their memberships, so it cannot assess whether a topic forms a coherent filter. The synthetic shelf has no stated expected-good/expected-bad labels, and short mixed texts may yield thin or artificial candidates. Use roughly 10–12 representative cases, three stochastic runs, several duplicated/swapped controls, compact full membership per candidate, the same profile/persona, and pre-labelled synthetic distractors. Keep Greg’s actual shelf and Greg’s inspection as the decisive target check.

R7 — P2 — established/reasoned. Score-per-candidate followed by programmatic coverage greedy is a fair—and probably best—use of Jev: semantic judgment stays in the model; counting and diversity stay in code. But each score question must name the candidate explicitly and define verbal anchors for 0–3; Jev does not see question IDs and evaluates questions independently against shared state. [OpenRouter’s documented question semantics](https://openrouter.ai/blog/tutorials/how-to-use-jev/). Send all questions in one request. A `noul` loses useful gradation; repeated `choice` calls are a poor way to obtain 30 selections. For a fair primary comparison, have every model score candidates against the same rubric and run the same greedy. Treat direct chat ordering as a separately declared secondary arm, not a post-hoc rescue when coverage disappoints.

R8 — P2 — established. The current chooser has no seam for external per-candidate quality: `candidateTopics` only exposes candidates, while the greedy consumes private computed quality ([choose.ts](/home/greg/code/spideryarn2/.claude/worktrees/shelf-topics-llm/src/shelf-terms/choose.ts:639)). The eval would otherwise copy production greedy, contrary to the prompting guide. Add a behavior-preserving pure reranking seam with tests before the eval. Also predeclare every arm; “run through greedy if under-covers” is outcome-dependent analysis and can manufacture a winner.

R9 — P2 — reasoned. An alpha endpoint is acceptable only because this feature is cached, non-critical and has a deterministic fallback. Pin `typesafe/jev-1.13`, not `~latest`; enforce a strict response schema, deadline, failure backoff and circuit breaker; re-evaluate before upgrading. If an existing chat-wire model is within the eval’s noise band, prefer it: one existing wire and direct key validation are materially simpler than a sixth alpha wire.

**Verdict: revise before building—the propose/model-score/greedy idea is sound, but the current eval cannot establish a winner and Stage 2 would produce stale, duplicate, and potentially unmetered calls; the simplest credible v1 is an existing chat-wire model with validated scores, persisted output, and an awaited post-response refresh.**
