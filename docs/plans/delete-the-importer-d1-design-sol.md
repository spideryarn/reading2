NO-SHIP

1. **Critical — verified: the transaction ends too early.** D1’s `commit` includes artefact write, `assertProduced`, and `finishStep`, but not the job transition. Yet the plan already says those belong together ([delete-the-importer.md](/Users/greg/Dropbox/dev/experim/spideryarn2/docs/plans/delete-the-importer.md:1582)). `releaseStep` and `finish` currently open their own statements ([pg-jobs.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/store/pg-jobs.ts:252)). After the artefact transaction commits, `failExpired` can invalidate the attempt before release. The revision says done while the job says interrupted.

   `noteProgress` may remain outside: its running text is cosmetic. The terminal release/finish is not. Job-step status drives `stillForced`, completion, and retry force ([jobs.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/jobs.ts:245), [jobs.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/jobs.ts:853), [jobs.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/jobs.ts:1510)).

   **Smallest correction:** make the Postgres commit own a transaction-bound job release/finish too. On the last step it must also publish the revision; on failure it must fail the revision and job together. That requires transaction-taking variants of the job and revision operations, plus an explicit lock order. The filesystem session keeps its weaker sequential protocol.

2. **Critical — verified: a converted step can omit an output and still succeed using the carried old one.** `ArtifactParts` is partial ([artifacts.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/store/artifacts.ts:766)), and `assertProduced` merely reads whatever is now present ([pipeline.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/pipeline.ts:556)). `beginDraftIn` carries old artefacts forward. Therefore `{ parts: {} }`, or an `extract`/`toc`/`blocks` product missing one required part, can pass against the copied value and be marked done. For `blocks`, that can commit new stamped HTML beside old block rows.

   The proposed “no `parts`” guard is also not expressible cleanly through `commit(..., fn)`: the session never receives the product. An empty object is truthy and calls `write` with nothing.

   **Smallest correction:** pass the product into `commit`, and before any write require that every `step.produces` key is present with a defined value. A Postgres session rejects absent `parts`; a filesystem session permits absence only for an explicitly unconverted step. Test against a carried draft, not an empty one.

3. **High — verified: the `reads` seam has the right intent but the wrong type and lifetime.** `readOnlyPgArtifacts` deliberately returns only four read methods ([artifacts-pg.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/store/artifacts-pg.ts:1306)), while `PipelineStep.run` currently requires the full mutable `ArtifactStore` ([pipeline.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/pipeline.ts:383)). Calling the proposed object an `ArtifactStore` either fails typechecking or forces writable/throwing methods back into the run phase.

   Also, a session cannot be made “once per job.” Every `/advance` mints a new attempt and runs one step; `JobDraftRef` embeds that attempt. Reusing a session from request A makes request B stale.

   **Smallest correction:** define a real `ArtifactReads` type containing the six required read operations. Construct a session once per successful claim, after `openOrBeginJobDraft`, rebinding the same draft to the new attempt. Route the preflight `stepIsDone` through `session.reads` too; otherwise filesystem artefacts can cause a Postgres step to skip. Specify what happens to a newly copied draft when every requested step skips.

4. **High — verified: only the happy-path commit is designed.** `beginStep` must remain outside the long run, but a handled failure needs a short failure transaction: mark the step `error`, fail/clear the draft, and end the job. Otherwise the step stays `running`, the terminal job retains its draft pointer, and retry creates a different draft.

   Upload verification is another durable transition omitted from this coordinator. The existing design elsewhere correctly requires successful verification—or rejection—to be fenced with the job outcome. Cost rows and resumable checkpoints should remain outside: they record work actually spent even when the artefact is rejected.

   **Smallest correction:** add a `StoreSession.fail(...)` path and transaction-aware upload settlement/rejection. Keep `collectSpend`, checkpoints, logs, and the initial interrupted marker outside.

5. **Medium — verified path, conditional on someone running the importer concurrently:** the draft baseline itself is stable, but the article lineage is not. `jobs_only_one_running` excludes another job, and `openOrBeginJobDraft` reopens rather than recopies. Retry uses a new draft; cancel/expiry leaves stale writes fenced. The importer writes the published revision, not this draft, so I found no route among those that silently changes the draft baseline and then accepts reminted IDs.

   However, the importer bypasses the job constraints and can update or replace `current_revision_id` during the model call ([import.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/store/import.ts:586), [import.ts](/Users/greg/Dropbox/dev/experim/spideryarn2/src/store/import.ts:1014)). Publication does not verify that the current revision is still the one the draft was copied from. The later job can therefore overwrite a concurrent import. `--prune` can delete the article and draft; the job fence then refuses, safely but destructively.

   **Smallest correction:** while the importer exists, refuse import and prune for any slug with an active job. The planned “current revision has a source reference” refusal does not cover the first Postgres job while its current revision is still importer-produced.

6. **Medium — verified: the landing size is reasonable, but the proposed test proof is too narrow.** Wrapping nine string returns in `{ detail }` is mechanical and can land separately from the first real conversion. A fake step is useful for testing the coordinator, but it does not prove carried-output handling, attempt rebinding, preflight store selection, job-transition atomicity, or publication.

   **Smallest correction:** keep D1 separate, but require tests for: a missing part over a carried artefact; stale attempt between run and commit; rollback of artefacts and job transition together; two `/advance` claims reopening one draft with different attempts; Postgres preflight with misleading filesystem files present; and an all-skipped job. Mutate each guard and confirm the intended assertion fails. `arc` can remain the next, first real user.

The run/commit split itself is sound. Under the present writer set, baseline reads outside the transaction are safe for the job-owned draft. `collectSpend`, checkpoints, logging, and `beginStep` should remain outside; product validation, artefact writes, successful step completion, terminal job transition, publication/failure, and upload terminal state belong inside the appropriate short commit.
