## New finding

### F8 — P1 — Established: account teardown is omitted from the “all cache writers/deleters” protocol

- **Candidate:** A0 names response commit, touch, invalidation and eviction as the operations participating in the atomic protocol, but not account teardown: [main A0](</Users/greg/dev/spideryarn/reading2/docs/plans/260905e-main-app-architecture-review.md:161>). Its generic “account changes” test does not state the required teardown race outcome.

- **Source evidence:** [`apiFetch` captures the request owner](</Users/greg/dev/spideryarn/reading2/src/web/lib/api.ts:658>) and can save the response later. On sign-out, [`forgetUser`](</Users/greg/dev/spideryarn/reading2/src/web/lib/offline-store.ts:293>) deletes the owner’s current rows, but nothing fences an already-issued response from writing that owner’s body afterward. The auth callback starts that asynchronous deletion at [api.ts](</Users/greg/dev/spideryarn/reading2/src/web/lib/api.ts:1096>).

- **Concrete consequence:** A cacheable request for owner A pauses; A signs out and `forgetUser(A)` completes; the response then arrives and recreates A’s private cached body. This violates the stated account/privacy contract that sign-out drops that reader’s copies. Owner partitioning prevents B from reading it through the normal API, so this is P1 rather than a claimed cross-account P0 disclosure.

- **Minimal replacement wording:**
  “Account teardown participates in the same atomic protocol. `forgetUser(owner)` atomically advances and retains an owner-retirement epoch and deletes that owner’s bodies; no ticket reserved before retirement may commit afterward. Test: pause an A response after reservation, complete sign-out/account switch, release the response, and assert that no A body is recreated while B’s rows remain unchanged.”
