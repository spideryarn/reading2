1. **P1 — Sequential POSTs do not guarantee Trajectory is younger than Quotes and Ideas.** The queue orders by `(created_at, id)` and ignores a newer queued dependency (`src/store/pg-jobs.ts:805-815`). Ordinary jobs preserve an application-host timestamp (`src/jobs.ts:3258-3269`, `src/store/pg-jobs.ts:602`), so successive requests handled by clock-skewed instances can be stored out of order. The repository already names this exact cross-instance-clock problem (`src/store/pg-successor.ts:228-233`). Trajectory could therefore claim first and refuse for missing Quotes. This also weakens the claim that every auto job necessarily waits behind the database-timestamped Labels successor. **Fix:** either batch-enqueue the jobs server-side with database-generated monotonic timestamps, or make the Trajectory job include `["quotes", "ideas", "trajectory"]`, so correctness does not depend on job age. If retaining five single-step client POSTs, change ordinary enqueue timestamps to the database clock.

2. **P2 — Trajectory waits for Quotes and Ideas jobs to become terminal, not to succeed.** `blockedByAnother` considers only `queued` and `running` predecessors (`src/store/pg-jobs.ts:811-815`). If a fresh article’s Quotes job errors, Trajectory becomes runnable and then throws `TRAJECTORY_NO_QUOTES`; it also refuses when Quotes succeeds but produces no usable body quote (`src/pipeline.ts:4085-4115`, `src/messages.ts:1368-1392`). On a re-add with current Quotes, the Quotes job skips through the normal freshness check (`src/jobs.ts:1003-1022`), and Trajectory can succeed or skip; if old usable Quotes remain after a failed regeneration, it may still succeed. **Fix:** document and test this state matrix—Quotes error, empty/abstract-only Quotes, and current re-add—and decide whether an automatic Trajectory failure is acceptable. If not, add success-aware dependency handling or queue its prerequisites in the same job with an explicit retry policy.

3. **P2 — Opening Trajectory can create a second job row; it does not necessarily “join” the auto job.** The automatic request is `[trajectory]`, while an empty Trajectory panel requests `[quotes, ideas, trajectory]` (`src/web/useTrajectory.ts:185-203`). The work key hashes the complete step list (`src/store/jobs.ts:81-114`), so these requests do not deduplicate. Ordinarily this should not double-spend Trajectory: both jobs write `trajectory`, cannot overlap (`src/sharing-steps.ts:164-178`), and the later one should skip once the artefact is current (`src/jobs.ts:1003-1022`). It can still add a redundant job, serialize work differently, and re-run if profile/freshness changes between requests. Tweets and the other four single-step modes do deduplicate when their request shape matches. **Fix:** align the automatic Trajectory request with the panel’s prerequisite shape, or explicitly accept the second row and add an integration test covering both insertion orders and asserting only one model call with a stable profile.

4. **P2 — A failed background POST is silently lost after navigation.** SPA navigation itself is safe: it only writes history (`src/web/router.ts:1226-1247`), the requests carry no component-owned abort signal (`src/web/useJobs.ts:375-390`), and the app-wide job session remains mounted (`src/web/App.tsx:83-102`). However, `run` converts any failed POST to `null` (`src/web/useJobs.ts:349-369`), the proposed loop continues, and a later successful action clears the shared error. Because AddPage has unmounted, nobody reports which mode was missed. A reload or tab close during the sequential chain also prevents the remaining POSTs, a gap not covered by the plan’s “closed before import finishes” caveat. **Fix:** make this a durable server-side batch, or at minimum retry idempotently and persist/report the failed step names. Parallelize the independent first four requests to shorten the vulnerable window, then enqueue Trajectory using the ordering fix in finding 1.

The derived five-step list is otherwise correct (`tweets`, `glossary`, `quotes`, `ideas`, `trajectory`), and bare-slug job requests spend no ingest slot (`src/routes.ts:8967-8979`), have no route rate limit or per-reader active-job cap, and are governed only by the machine-wide default concurrency of three (`src/jobs.ts:437-464`).
