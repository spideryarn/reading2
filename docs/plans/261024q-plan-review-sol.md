1. **F1 — P0 — established.** The receiving flow is not bound to the reader who accepted the capture. The plan asynchronously takes the capture and calls `uploadEngine.send()` ([plan:141](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:141>)), but the existing account-switch guard recognizes only `add` and `add-upload` ([add-visit.ts:72](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/add-visit.ts:72>), [App.tsx:587](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/App.tsx:587>)). More importantly, the upload singleton reads `uploadEngine.reader()` only when each request starts ([uploadEngine.ts:603](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/uploadEngine.ts:603>)); if reader A’s delayed extension reply resumes after the engine has stopped or rebound, `null` or B is passed and `apiFetch` binds the write to whoever the tab then holds ([api.ts:516](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/lib/api.ts:516>)). That can store a private signed-in publisher page in B’s account. The OAuth round trip itself is sound and stays in one tab via tab-scoped storage ([auth-return.ts:9](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/auth-return.ts:9>), [AuthCallback.tsx:132](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/AuthCallback.tsx:132>)); the gap is the async work after it. **Fix:** make `add-from-extension` an add visit, pass its `readerId` into the receiver, invalidate late replies on unmount/account change, and make `send` retain/check that reader rather than rereading the singleton’s current reader. Test delayed reply across A→B and A→signed-out→B, asserting that no grant, PUT, or queue request leaves.

2. **F2 — P1 — established.** The shared capture function cannot be injected with the proposed signature. The plan retains `capturePage(win, maxBytes)` and passes it as `executeScript({func,args})` ([plan:113](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:113>)); the present function likewise requires a `Window` ([save-page-bookmarklet.ts:67](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/save-page-bookmarklet.ts:67>)). Chrome serializes `func`, loses its execution context, and requires every argument to be JSON-serializable, so `window` cannot be supplied. [Chrome’s scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting) documents both constraints. **Fix:** make the injected function obtain `window` from its execution context and take only serializable arguments, while allowing tests to supply a window separately, e.g. `capturePage(maxBytes, win = window)`. Add a real `executeScript` test using the production-built function, not only a source round-trip.

3. **F3 — P1 — reasoned.** Origin plus tab ID prevents other sites and extensions from directly taking the capture, but it does not prove the request comes from the intended top-level receiver document. The checks name only `sender.origin` and `sender.tab.id` ([plan:86](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:86>)). If that still-pending tab is navigated to another site which embeds the receiver as an iframe, the iframe has the allowed Spideryarn origin and the same tab ID and can trigger an unintended upload. It cannot read the cross-origin result, but it can spend a slot. Omitting `externally_connectable.ids` correctly blocks other extensions, as [Chrome documents](https://developer.chrome.com/docs/extensions/reference/manifest/externally-connectable). **Fix:** additionally require `sender.frameId === 0`, the exact receiver URL, and a random single-use nonce opened with the tab and echoed in the take request. The nonce can live in the fragment so it does not reach server logs.

4. **F4 — P1 — reasoned.** The handoff lacks an atomic lifecycle. It cannot store by the new tab’s ID before creating that tab; if `tabs.create` starts navigation to the receiver immediately, the receiver can ask before the IndexedDB transaction commits ([plan:37](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:37>)). “Reply once and delete” also needs one read-write transaction: two concurrent takes can both read before either deletes, while the proposed tests cover only a sequential second take ([plan:131](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:131>)). Concurrent effects are realistic in local development because the app runs under React Strict Mode ([main.tsx:243](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/web/main.tsx:243>)). **Fix:** create an inert/blank tab, persist the record, then navigate it; perform get-and-delete in one IndexedDB read-write transaction; clean up on `tabs.onRemoved`; enforce expiry when reading, not with a worker timer; and test two simultaneous takes plus a request racing initial persistence.

5. **F5 — P1 — established.** Deferring all repeat-click handling knowingly ships duplicate articles and duplicate slot charges ([plan:150](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:150>)), and the proposed later endpoint does not solve the common rapid-double-click case. `slugForUrlKey` matches a saved-from URL only on a published current revision ([find-article.ts:145](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/src/store/find-article.ts:145>)); while the first upload or ingest is pending, there is nothing for that GET to find. **Fix:** v1 should coalesce locally while a handoff is live: retain a small tombstone keyed by source tab and source URL after deleting the HTML, and focus the existing receiver/upload tab on another click. Remove it when that tab closes or after a bounded expiry. The held server lookup can later cover repeats after publication.

6. **F6 — P1 — established.** Production has an unresolved extension-ID bootstrap dependency. The receiving page must name the production extension ID ([plan:91](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:91>)), but the research correctly says the store public key—and therefore the store-compatible development ID—is available only after an item exists ([research:44](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/research/261024c-chrome-extension-mv3-store-and-updates.md:44>)). The first dashboard upload is deferred until Stage 5 ([plan:158](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:158>)). Chrome’s documented process explicitly requires uploading an unpublished draft before obtaining that key ([manifest `key` documentation](https://developer.chrome.com/docs/extensions/reference/manifest/key)). Thus Greg cannot simply perform one final publication step under the current sequence. **Fix:** either schedule an early draft-item upload and a later final submission, or avoid compile-time ID coupling by putting `chrome.runtime.id` plus the nonce in the receiver URL fragment and having the page contact that explicit runtime ID.

7. **F7 — P2 — established.** The update command is underspecified at the authentication boundary. The research says three fetches need only “a service-account token” ([research:86](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/research/261024c-chrome-extension-mv3-store-and-updates.md:86>)), and the plan promises `npm run extension:publish` with credentials Greg creates once ([plan:160](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:160>)), but nothing obtains or protects the short-lived access token. [Chrome’s service-account instructions](https://developer.chrome.com/docs/webstore/service-accounts) require either `gcloud` impersonation with the appropriate IAM authority or a signed JWT/key workflow. **Fix:** choose one exact method, state where its long-lived credential lives outside Git, mint a short-lived scoped token, verify upload completion with `fetchStatus`, and refuse to publish unless upload state and version are confirmed.

8. **F8 — P1 — reasoned.** The store/privacy deliverable is not precise enough for the data actually collected. “A paragraph on what the extension sends and when” ([plan:147](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261024q-chrome-extension-one-click-add-the-page.md:147>)) does not ensure the listing and dashboard disclose that one click captures and transmits the current URL and whole rendered DOM, potentially including personalized page chrome, form content, and account-visible material—the bookmarklet deliberately retains textareas, selects, and content-bearing structures ([261017b plan:83](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:83>)). Chrome classifies website content, form data, and browsing activity as sensitive user data and requires accurate pre-install disclosure and a privacy policy ([User Data FAQ](https://developer.chrome.com/docs/webstore/user_data), [privacy fields](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)). **Fix:** make the exact listing disclosure, dashboard data-category selections, `activeTab`/`scripting` justifications, local 15-minute retention, server retention/deletion, and recipients/subprocessors explicit plan outputs and tests—not merely drafted “listing text.”

9. **F9 — P2 — reasoned.** A single 50 MiB spike does not prove every allowed capture fits through messaging. The upload cap measures UTF-8 blob bytes, while Chrome JSON-serializes messages and caps the serialized message at 64 MiB ([research:33](</var/tmp/spideryarn-worktrees/fbxsfrsg-chrome-extension/docs/research/261024c-chrome-extension-mv3-store-and-updates.md:33>), [Chrome messaging limits](https://developer.chrome.com/docs/extensions/develop/concepts/messaging)). Quotes, backslashes, and control characters expand under JSON, so valid HTML below the 50 MiB upload limit can exceed the messaging limit. **Fix:** spike adversarial escaping as well as ordinary HTML and either establish a lower extension-specific cap with margin or introduce bounded chunking. Measure both the `executeScript` result and external-message response.

Verdict: REWORK
