# 261029f plan review, GPT Sol (read-only, high effort, 2026-10-29)

The diagnosis is not proved by the feedback URL, and option A has several ordering and integration holes.

1. **High — Diagnosis: `?mode=chat&guide=1` is not unique to first-open.** The ordinary Guide command writes exactly that state ([Reader.tsx:1188](../../src/web/reader/Reader.tsx:1188)); it remains until the conversation list answers ([ConversationModes.tsx:1061](../../src/web/modes/conversation/ConversationModes.tsx:1061)). Because `mode` and `guide` count as explicit article state, reload suppresses restoration ([last-view.ts:385](../../src/web/last-view.ts:385), [last-view.ts:492](../../src/web/last-view.ts:492)). **Suggested change:** retract the URL-only inference; require storage or diagnostic evidence that `claimFirstOpen` actually ran, and test reload while Guide is pending.

2. **High — Diagnosis: `none` proves only that the current `(origin, readerId, slug)` key is absent.** The key includes the reader ID ([last-view.ts:311](../../src/web/last-view.ts:311)); signed-out and signed-in visits therefore use different keys ([storage-reader.ts:14](../../src/web/lib/storage-reader.ts:14)). The same person can read a public article signed out, then sign in in the same browser and receive first-open. Account switching produces exactly the guide in the real App test ([last-view-app-reader-change.test.tsx:132](../../tests/last-view-app-reader-change.test.tsx:132)). **Suggested change:** conclude only “that identity/slug key was absent at the decision,” not “different browser/device” or “never stored.”

3. **Medium — Diagnosis: there are additional same-browser missing-key paths.** A hung auth initialization can render a public article while `known=false`, which disables `useLastView` ([useSession.ts:96](../../src/web/useSession.ts:96), [App.tsx:256](../../src/web/App.tsx:256)); legacy storage can be adopted and removed by another account sharing the browser ([last-view.ts:563](../../src/web/last-view.ts:563)); view-as deliberately neither reads nor saves ([last-view.ts:803](../../src/web/last-view.ts:803)). Site-data clearing is observationally identical because `getItem() === null` maps directly to `none` ([last-view.ts:587](../../src/web/last-view.ts:587)). **Suggested change:** qualify the diagnosis and explicitly rule these out where evidence permits.

4. **Low — Diagnosis: a reload race can retain Guide without `at=`.** Position writes are debounced for 300 ms ([params.ts:54](../../src/web/params.ts:54)); scrolling calls `setAt` later from the measurement frame ([useReadingPosition.ts:229](../../src/web/reader/useReadingPosition.ts:229)). Reloading during that window can preserve a pending Guide instruction without the new `at`, after which explicit state blocks the stored place. **Suggested change:** add a reload/pagehide test during the debounce; either flush position synchronously or recognize this stale instruction.

5. **Low — Diagnosis: no ordinary same-identity path was found.** With the same UUID, canonical slug and origin, intact storage, and a settled address, the add-page mark cannot override a stored view; storage errors return `failed`, not `none` ([last-view.ts:582](../../src/web/last-view.ts:582)); boot rewrites do not create Guide ([router.ts:1209](../../src/web/router.ts:1209)); and there is no service worker ([offline-store.ts:1](../../src/web/lib/offline-store.ts:1)). StrictMode and bfcache also expose no such path. **Suggested change:** state this narrower conclusion rather than “not a same-browser bug.”

6. **High — Design: device identity does not establish freshness.** The plan permits a 60-second server lag, then assumes a row from another device is newer ([plan:57](../../docs/plans/261029f-your-place-in-an-article-follows-you-to-another-device.md:57), [plan:64](../../docs/plans/261029f-your-place-in-an-article-follows-you-to-another-device.md:64)). Device B can have newer unsent local movement while the server still names A, so the rule sends B backwards. Reload’s `pagehide` POST is best-effort and untracked ([useReadingTime.ts:394](../../src/web/useReadingTime.ts:394)). Ordinary reading-time writes may also overlap ([useReadingTime.ts:90](../../src/web/useReadingTime.ts:90)), allowing place replacements to complete out of order. **Suggested change:** for v1, use the server only when no local key exists. For full sync, use an opaque server revision plus local dirty/base-revision state and serialize or conditionally accept writes.

7. **High — Design: the “existing opening GET, parallel with article load” does not exist at that point.** `useLastView` decides in `App`, before ownership is known ([App.tsx:264](../../src/web/App.tsx:264)). `useReadingTime` mounts only in `OwnedReader`, after the article fetch has completed ([ArticlePage.tsx:239](../../src/web/article/ArticlePage.tsx:239), [ArticlePage.tsx:704](../../src/web/article/ArticlePage.tsx:704)). Moving the GET to `App` makes signed-in visitors call an owner-only route; leaving it where it is makes the latency sequential and unavailable to first-open. Failure behavior is also unspecified. **Suggested change:** design a shared owner/access fetch or include place in the owned article response; define whether GET failure opens plain, waits, or applies Guide.

8. **Medium — Design: the late-arrival guard needs an actual movement signal.** URL state does not change for every within-section movement, while the finer place is saved separately. The existing save effect also writes immediately on mount ([last-view.ts:898](../../src/web/last-view.ts:898)), potentially creating `""` while the server decision is pending. `firstOpenHref` itself checks only route and address state ([last-view.ts:748](../../src/web/last-view.ts:748)). **Suggested change:** capture an arrival generation and cancel both server restore and Guide/modal on any scroll/input, query navigation, reader/slug change, or local-place mutation; suspend the initial empty save until the opening decision settles.

9. **Medium — Design: piggybacking needs different delivery semantics.** Today a flush with no pending seconds sends nothing ([useReadingTime.ts:370](../../src/web/useReadingTime.ts:370)); the route requires only `seconds` and rejects other fields ([routes.ts:1353](../../src/routes.ts:1353)); failed batches are deliberately dropped ([useReadingTime.ts:399](../../src/web/useReadingTime.ts:399)). Thus place-only flushes are new requests, and a replaceable place should be retried unlike additive seconds. **Suggested change:** track place dirtiness separately, permit validated place-only POSTs, retain the latest place after failure, avoid unchanged POSTs, and specify transaction/partial-success behavior.

10. **High — Design: ownership transfer must delete `reading_place`.** A table keyed only by `article_id` would otherwise move the old owner’s activity to the new owner. Transfers classify every article-linked table and delete reader state before changing ownership ([pg-article-transfer.ts:123](../../src/store/pg-article-transfer.ts:123), [pg-article-transfer.ts:549](../../src/store/pg-article-transfer.ts:549)); reading time is already classified this way ([pg-article-transfer.ts:151](../../src/store/pg-article-transfer.ts:151)). **Suggested change:** add `reading_place` to the transfer inventory/counts as reader state and test deletion on transfer.

11. **Medium — Design/privacy: the proposal stores more than “your place.”** `saved_at` creates a durable article-specific activity time, while the random device ID links rows from the same browser. The full remembered search includes mode, filters and selected terms/items ([last-view.ts:99](../../src/web/last-view.ts:99)); the proposed privacy sentence discloses none of that. **Suggested change:** the simpler v1 is one validated block ID, restored only when the browser has no local key—no device ID, clock, opaque query string, or overwrite conflict. If full-view sync remains intentional, validate values server-side, key the device ID per reader, disclose the identifier and saved time, and include the row in export and transfer coverage.
