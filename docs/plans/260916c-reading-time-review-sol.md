The plan should not be built unchanged. I found seven P1 issues and two P2 risks.

## Findings

1. **P1 — `.band-covers` does not mean a band is covering the prose.**  
Claim: recording stops whenever `.reader.band-covers` is present ([plan:86](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:86)).  
Evidence: `fit.modeW === 0` also adds that class when no band is open—especially Plain mode—and the code explicitly requires every consumer to also name `.mode-band` ([Reader.tsx:1900](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/reader/Reader.tsx:1900)). Conversely, `?text=0` can leave rows on screen while their prose cells are absent ([Reader.tsx:294](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/reader/Reader.tsx:294), [TableView.tsx:1696](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/TableView.tsx:1696)).  
Fix: pass an explicit gate from `Reader`: `proseOn && !(bandOpen && fit.modeW === 0)`. Test narrow Plain counting, narrow open-band suppression, and `?mode=hierarchy&text=0` suppression.

2. **P1 — additive POSTs and the proposed retry/exit delivery cannot be made correct together.**  
Claim: failed batches are merged back and resent; `leavingFetch` is used for both hidden and pagehide “the way `useProfile` already does it” ([plan:181](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:181)).  
Evidence: `useProfile` uses ordinary `apiFetch` on hidden and `leavingFetch` only on pagehide ([useProfile.ts:173](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/useProfile.ts:173)). Its duplicate pagehide send is safe specifically because the PATCH is idempotent ([useProfile.ts:98](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/useProfile.ts:98)). An additive POST is not: a committed request whose response is lost will be added twice when retried. `leavingFetch` returns `void` and swallows transport failure, so it cannot support “merge back on failure” ([api.ts:1073](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/lib/api.ts:1073)). Failed-minute accumulation also disproves the plan’s claims that cadence bounds values to 3,600 and that the exit body is always small; keepalive is capped near 60 KiB ([api.ts:1076](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/lib/api.ts:1076)).  
Fix: the simpler v1 is at-most-once delivery: ordinary fetch on hidden, pagehide only for pending—not in-flight—data, and never retry a transport-uncertain batch. This matches the plan’s willingness to lose up to a minute. If retries are required, add batch idempotency keys and server-side deduplication. Test “server committed, response lost,” hidden→pagehide, long offline accumulation, and keepalive sizing.

3. **P1 — opening an article and simply reading it may record nothing.**  
Claim: the reader must have generated one of the listed input events during the last 120 seconds ([plan:82](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:82)).  
Evidence: arrival, focus, and returning the document to visible are not included, and the proposed tests cover only idle suppression—not first-screen reading ([plan:210](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:210)).  
Fix: initialize activity when an enabled visible reader mounts, and refresh it on `visibilitychange → visible`, `pageshow`, or focus. Add tests for reading the first screen without a gesture and returning after a long hidden period.

4. **P1 — the privacy statement “Not when” is false at the system level.**  
Claim: no timestamps means the service keeps “how long, never when,” and the feature is shown “to nobody else” ([plan:165](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:165), [plan:188](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:188)).  
Evidence: every POST creates a timestamped HTTP log containing method, path and therefore article slug ([routes.ts:6307](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/routes.ts:6307), [log.ts:153](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/log.ts:153)). The current policy already discloses those logs and says the operator can see stored data ([PrivacyPage.tsx:167](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/PrivacyPage.tsx:167), [PrivacyPage.tsx:223](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/PrivacyPage.tsx:223)). Also, every block row is sampled, not only paragraphs ([TableView.tsx:1616](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/TableView.tsx:1616)).  
Fix: say that the reading-time record stores accumulated totals rather than a reading history, while ordinary short-lived request logs still show when updates arrived. Say “blocks/passages,” and “not shown to other readers,” rather than “paragraphs” and “nobody else.”

5. **P1 — the proposed spine paint order contradicts the spine’s existing correctness rule.**  
Claim: draw reading time after parts, current-location fill, and ticks ([plan:118](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:118)).  
Evidence: the spine has no intervening `z-index`; tree order is paint order, and its current comment explicitly says permanent fills must be before the ticks or they obscure the article’s subdivision ([Spine.tsx:790](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/Spine.tsx:790)).  
Fix: use `parts → reading-time → here → ticks → jump/search/viewport/hits`, and add an order test alongside `spine-here.test.ts`.

6. **P1 — the executable reading-time formula is missing the minutes-to-seconds conversion.**  
Claim: `expected = max(3 s, words ÷ 230 wpm)` ([plan:103](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:103)).  
Evidence: `words / 230` produces minutes; implemented literally, a 300-word block would saturate after three seconds.  
Fix: specify the code formula as `Math.max(3, words * 60 / 230)`. Add explicit numeric cases, including zero words and 300 words.

The corrected scheme will generally produce a uniformly thick visited region with a sharp boundary at roughly 40%, because all fully visible blocks accrue the same wall time and level 4 saturates. That serves “where did I get to?” but offers little distinction within normally read material. The browser check should deliberately read to 40%, linger on one screen, and verify both the frontier and the limited linger contrast—not merely “scroll, wait, see something thicken.”

7. **P1 — export handling specifies only one of two mandatory projections.**  
Claim: add one exported destination, `augmentations/reading-time.json` ([plan:200](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:200)).  
Evidence: every `ARTICLE_TABLE_COVERAGE` entry must separately declare `rollback` and `bundle` destinations ([article-rows.ts:71](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/store/article-rows.ts:71)). The named path covers only the reader bundle.  
Fix: decide both projections in the plan. Because this is reader data, preserve it in rollback too—probably as a sidecar with an explicit update to the pinned legacy-output contract. If rollback must omit it, state that loss and why.

8. **P2 — the recorder’s hot path is unspecified and can reintroduce known long-article costs.**  
Claim: every second, find every visible row, update `shown`, and derive levels; only the spine display needs no new measurement ([plan:60](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:60)).  
Evidence: full-table querying and geometry have already dominated a 2,046-block article’s script time ([rows.ts:13](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/rows.ts:13)). `TableView` is memoized, but updating React `shown` state every second would still rerender `Reader` and recompute maps ([TableView.tsx:740](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/TableView.tsx:740)).  
Fix: maintain a visible-row set with `IntersectionObserver`; rect-read only that small set. Keep seconds and pending batches in refs, and update React state only when a block crosses a display level.

9. **P2 — the experimental switch is a sensible rollout gate, but it is not consent.**  
Claim: readers with it on “opted into” this new personal-data collection ([plan:142](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/plans/260916c-show-where-you-have-spent-time-reading-in-the-spine-and-gutter.md:142)).  
Evidence: its current promise is that unfinished controls appear; it describes itself as clutter management, not authorization or privacy consent ([experimental-features.md:37](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/docs/project/experimental-features.md:37), [experimental-copy.ts:23](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/web/experimental-copy.ts:23)). Existing enabled accounts will start recording automatically after deployment.  
Fix: keep both recording and display behind the switch for this v1—it minimizes collection and preserves “off hides, never deletes”—but describe it as feature availability, not consent. If explicit consent is intended, add a separate reading-map toggle.

The generated `<style>` approach is sound today: the app has no CSP blocking it, `TableView` is memoized, and block IDs are selector-safe. The composite FK is also sound: identities are explicitly never deleted and re-extraction only upserts them ([schema.ts:1073](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/db/schema.ts:1073), [artifacts-pg.ts:1210](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/store/artifacts-pg.ts:1210)). Omitting `owner_id` is correct because ownership is inherited through the article ([owner.ts:4](/home/greg/code/spideryarn2/.claude/worktrees/fb41-reading-time-heatmap/src/owner.ts:4)).

**Verdict: Do not build as written; revise the recording gate, delivery semantics, privacy copy, formula, paint order, and export decision first.**
