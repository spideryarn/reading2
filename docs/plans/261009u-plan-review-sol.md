REJECT

The plan has the right product flow and server-side admin gate, but several concurrency, provenance, and email-safety invariants are not yet settled.

- **F1 — P1 — Send can race an edit and email the wrong snapshot.** The plan resolves the audience before its transaction, then issues with a predicate that checks only status and non-null email ([plan:107](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:107), [plan:111](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:111)). Meanwhile, PATCH locks the voucher and can change its email, name, and note ([pg-vouchers.ts:873](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:873), [pg-vouchers.ts:907](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:907)). A send can therefore calculate the audience for address A, wait behind a PATCH to address B, issue B’s row, and queue an email using stale A-derived data. **Fix:** read a snapshot including `updated_at`, resolve externally, then issue with a compare-and-swap on that snapshot; retry if it changed. Queue solely from the matching snapshot/`RETURNING` row. Test with a paused audience lookup racing PATCH and lookup-fill.

- **F2 — P1 — The unfinished-lookup check is a check-then-insert race.** Steps 4 and 5 check for an unfinished run before creating its row ([plan:204](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:204), [plan:206](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:206)). Two simultaneous requests can both see none and buy two searches. **Fix:** in one short transaction, lock the voucher, refuse a recent pending lookup, mark an expired pending lookup failed, and insert the new pending row before releasing the lock. Define `outcome = NULL` while pending and add constraints tying `finished_at`, `outcome`, and `failure` together. Test two concurrent presses and assert one model call.

- **F3 — P1 — A replay after Send creates a second draft.** Uniqueness covers only rows where `issued_at IS NULL` ([plan:80](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:80)); Send removes the row from that index, so a delayed/replayed `POST /author-gifts` can insert a fresh draft for the same article ([plan:203](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:203)). It also means restoring an older discarded draft can collide with a newer live one. **Fix:** give the author-gift campaign a persistent per-article identity that survives sending, or retain a separate author-gift draft/campaign row linked to the eventual voucher. If repeat campaigns are wanted, require an explicit “new gift” action and idempotency key. Define restoration conflicts as a 409. Test a lost author-gift response replayed after Send.

- **F4 — P1 — A draft leaks into the live voucher audience calculation.** `giftAudienceFor` sums all unclaimed, unrevoked vouchers addressed to the recipient ([pg-vouchers.ts:413](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:413), [pg-vouchers.ts:421](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:421)). The plan inventories claim, entitlement, PATCH, and retry, but not this path ([plan:92](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:92)). An addressed draft would inflate the “after this gift” numbers in another gift email, including its own Send. **Fix:** add `issued_at IS NOT NULL` to this sum and include every `billing_vouchers` query in the draft-inertness test inventory.

- **F5 — P1 — “Nothing is ever emailed automatically” lacks a final sending-side guard.** The planned protections stop PATCH and manual retry from queuing/sending a draft ([plan:100](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:100)), but automatic reservation currently accepts any queued delivery ([pg-voucher-emails.ts:614](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-voucher-emails.ts:614)), while retryability checks only revocation and address equality ([pg-voucher-emails.ts:604](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-voucher-emails.ts:604)). A missed producer path would still send. **Fix:** require `v.issued_at IS NOT NULL` in both automatic and retry reservation, and preferably in the queueing function under the voucher lock. Test that even a deliberately seeded queued email belonging to a draft cannot be reserved.

- **F6 — P1 — `generation_id` cannot identify the lookup’s complete cost.** The plan uses it as the lookup-to-ledger key ([plan:167](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:167), [plan:175](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:175)). It is a provider reconciliation handle, whereas `ai_calls.id` is the locally minted call identity and `run_id` groups a piece of work ([schema.ts:3753](/var/tmp/spideryarn-worktrees/author-gift/src/db/schema.ts:3753), [schema.ts:3755](/var/tmp/spideryarn-worktrees/author-gift/src/db/schema.ts:3755)). Transport retries produce multiple ledger rows ([ai-call.ts:2177](/var/tmp/spideryarn-worktrees/author-gift/src/ai-call.ts:2177)), and a failed call throws without returning its generation ID to the lookup ([ai-call.ts:2638](/var/tmp/spideryarn-worktrees/author-gift/src/ai-call.ts:2638)). Thus retries and failed-but-priced calls are missed. **Fix:** correlate by a dedicated `author_lookup_id` on `ai_calls`, or store a lookup-scoped collector `run_id` and sum all its `author-lookup` rows. Test success, transport retry, priced failure, and unpriced failure separately.

- **F7 — P1 — Showing only the latest lookup can show false provenance for the current voucher fields.** Re-lookups preserve existing email/name ([plan:148](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:148)), but the list returns only the latest lookup ([plan:175](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:175)). If run 1 fills `a@example.com` and run 2 finds `b@example.com`, the page can display A beside B’s source. A manual edit has the same problem. **Fix:** record which lookup actually supplied each field, clear that provenance on manual edit, and display that exact source. Show later runs separately as “found but not applied,” or show the full short history.

- **F8 — P1 — The migration order as written does not produce the claimed backfill.** The plan says the new column has `DEFAULT now()` and existing rows are then updated where it is null ([plan:66](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:66), [plan:84](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:84)). If the column is added with the default first, existing rows receive the default value, so `WHERE issued_at IS NULL` updates nothing. **Fix:** in one migration transaction: add nullable `issued_at` without a default; backfill from `created_at`; set the default to `now()`; then add constraints/indexes. The backfill and dropping `email NOT NULL` are backward-compatible/additive in the intended sense. Drizzle sending `{ issuedAt: null }` explicitly bypasses the default; omitting the property invokes it.

- **F9 — P1 — “Appears in the extract” needs an exact email verifier, not substring matching.** The plan currently specifies only a case-insensitive appearance test ([plan:142](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:142)). `ann@example.com` appears inside `joann@example.com`; a substring test would bless a hallucinated address. Model output also bypasses the existing request parser. **Fix:** extract syntactically valid email tokens from the named evidence, normalize them with the existing rule ([pg-vouchers.ts:94](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:94)), validate with `looksLikeEmail`, and require exact normalized equality. Anything malformed or merely embedded becomes a suggestion, never the voucher address.

- **F10 — P1 — The security account understates what the model can do.** The plan says the model acts only by filling draft fields and that no charge follows from its answer ([plan:260](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:260)). But the model also chooses web searches: tool calls are outbound actions and spend money, and search-result pages are untrusted instructions. The project explicitly treats fences as mitigation, not a boundary ([security.md:923](/var/tmp/spideryarn-worktrees/author-gift/docs/project/security.md:923), [security.md:933](/var/tmp/spideryarn-worktrees/author-gift/docs/project/security.md:933)). **Fix:** state this risk honestly; tell the model explicitly that both article data and search results are data, not instructions; record actual search count; flag unexpected excess. If a real hard search bound is required, the current model-directed tool cannot provide it—use deterministic code-built searches or accept and document the admin-triggered residual risk.

- **F11 — P2 — Making drafts separate from live vouchers is now the simpler design.** The rejected alternative claims it would need a separate editor ([plan:244](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:244)), but the plan already builds a separate Drafts UI and lookup history. A durable `author_gift_drafts`/campaign row would avoid nullable live-voucher emails, `issued_at`, claim changes, entitlement assumptions, PATCH branching, and retry defences. On Send, call existing `createVoucher` with a stable voucher UUID; its replay machinery already queues once ([pg-vouchers.ts:485](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:485)). Mark the draft sent after create/replay. This also gives author-gift replay and provenance a natural home.

- **F12 — P2 — Fire-and-forget is safe for ordinary SPA navigation, but the plan’s guarantee is too strong.** Existing High-powered AI uses a controller that catches failures and outlives the page ([add-high-power.ts:166](/var/tmp/spideryarn-worktrees/author-gift/src/web/add-high-power.ts:166)); the proposed author request is merely launched and navigation happens immediately ([plan:221](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261009u-author-gift-draft-voucher-from-the-add-page.md:221)). SPA navigation normally does not abort `fetch`, but token acquisition may not yet have dispatched it, rejection must be caught, and closing/reloading the tab is not safe. **Fix:** make the route durably create the link, draft, and pending lookup row quickly, return `202`, then run the lookup as after-response work with explicit article attribution. Await that short acceptance before navigating and surface failure. This leaves only the optional lookup asynchronous, not creation of the draft itself.

The server-side admin boundary is correctly chosen: the namespace is defined by the exact `/api/admin` segment ([routes.ts:13170](/var/tmp/spideryarn-worktrees/author-gift/src/routes.ts:13170)) and refused before route dispatch ([routes.ts:13200](/var/tmp/spideryarn-worktrees/author-gift/src/routes.ts:13200)).
