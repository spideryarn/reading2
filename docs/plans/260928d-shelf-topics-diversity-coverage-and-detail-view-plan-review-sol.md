R1 — P3, established. The acronym diagnosis overstates the bug. `foldKey` already maps `LLMs → llm`, `GPUs → gpu`, and `NGOs → ngo`; only short plurals such as `AIs → ais` escape because of the `length <= 3` return. Recommendation: describe this as the two-letter-acronym case and test `AIs`/`UIs` plus ordinary short words.

R2 — P1, reasoned. The symmetric overlap coefficient can sacrifice coverage. If a small, high-quality phrase is selected first, a larger related topic containing it has coefficient 1 and is hard-skipped—even if it reaches many new articles. Thus selecting “AI systems” first could prevent later “AI”. The statement that ≥0.9 means “a near-subset that adds almost nothing” is false in that direction. Recommendation: make new-work count primary, then skip a lexically related candidate only when the candidate itself adds zero or at most one new work. Use directional containment `|candidate ∩ chosen| / |candidate|`, not the symmetric coefficient, for that decision.

R3 — P1, reasoned. `(discounted coverage) × sqrt(quality)` is not “coverage first”; sufficiently large quality differences can still select a smaller subset before its superset. The additional `1 − max overlap` penalty double-penalises overlap and can demote a topic that reaches several new works. Recommendation: compare candidates lexicographically: new works first, discounted already-covered works second, quality third, key last. This is simpler and makes the coverage claim true; the redundancy rule then removes late subsets.

R4 — P1, established. “Rank order does not jump when you select” conflicts with the current client structure. `ShelfTerms` explicitly moves `selected` topics to the front, then appends twelve unselected topics. Merely replacing `byCount` with server order will still reorder chips on selection and can show more than twelve. Recommendation: render `terms.filter((term, index) => index < 12 || chosen.has(term.key))` in server order. Test DOM order in `ShelfTerms`/the shelf integration test; a route-order test cannot catch the client sort.

R5 — P2, established/reasoned. The plan does not establish that near-total coverage@5–8 is attainable. Candidates must cover at least two works, so isolated articles cannot ever be covered; the previous measurement reached only 0.76 at K=20 and 0.92 at K=30. Reporting the new algorithm alone cannot distinguish a poor selector from an impossible corpus. Recommendation: report the eligible-article ceiling and an unweighted maximum-coverage baseline at 5/8/12, and make “do not push if coverage@8 materially trails that ceiling” an explicit gate.

R6 — P2, established. Bumping `EXTRACTOR_VERSION` invalidates every cached run. The route then performs up to two seconds of extraction/writes per response and the client repeatedly requests it every 400 ms until settled; readers may see partial, reordering topics over several slow requests. This is rollback-safe because versions coexist, but the plan has no cold-cache timing gate. Recommendation: measure a fully cold v2 load, including request count and total settled time, before the deploy. Update the explicit extractor-version test. No route-order or storage-contract change otherwise makes Stage 1 independently unsafe.

R7 — P2, reasoned. Stage 2 leaves the interaction between “All topics” and “More detail” undefined: whether there are four combined states, whether detail shows twelve or all topics, and whether “All” remains meaningful in detail view. The proportional bar’s denominator and whether counts reflect the current narrowed view are also unspecified. Recommendation: define that state machine, URL history/default behavior, `readHref` links, focus behavior, and ensure colour is decorative rather than the only identifier before mocking.

Verdict: revise Stage 1’s selection rule and client ordering before building; after a cold-cache and coverage-ceiling gate, it is otherwise safe to ship independently.
