# Plan review — 261020a

Verdict: **revise before build**. Part B currently repeats a race the existing preview machinery was explicitly written to prevent, and Part A does not yet define the profile-load/save state machine tightly enough to guarantee that the page neither leaves under the reader nor waits forever.

1. **P1 — A queued `ctx.report` write can overwrite the step's completed transition; the plan's claim that the transition overwrites it is backwards.** The proposed writer is asynchronous and `noteProgress` replaces the whole `steps` array (`docs/plans/261020a-add-page-asks-why-higher-and-about-you-says-when-it-is-ready-and-shows-import-progress.md:141-146`; `src/store/pg-jobs.ts:1985-1997`). The fence is only job id, attempt, running status and live lease (`src/store/job-fence.ts:83-97`). A non-final step's transactional commit deliberately keeps that same claim live (`src/store/pg-jobs.ts:2317-2345`), so a report write already on the wire can land *after* the commit and restore its snapshot of `status: "running"`, `detail` and `progress`. This is precisely the preview race documented in `src/jobs.ts:1235-1252` and reproduced by the delayed, cloned snapshot in `tests/jobs-walk.test.ts:1084-1133`. Use one per-step serialized transient-writer queue (preferably shared by report and preview), and await its drain on both success and failure before deleting transient fields and committing the settlement. The tests proposed at plan lines 180-182 are insufficient: add the same delayed-snapshot regression for report/progress, proving a non-final step cannot be put back to running after its commit. Swallowing a `StaleAttemptError` inside this mid-step display writer remains appropriate; the actual step commit is the authoritative fence.

2. **P1 — “`state` not clean” does not define a safe completion gate: `loading`, a failed initial GET, and a completed save require different decisions.** `SaveState` has six states, and both `clean` and `saved` mean that the draft matches the server (`src/web/useAutosavedText.ts:51-79`). A failed `GET /api/reader` calls `fail`, producing `error` while the plan also hides the box (`src/web/useProfile.ts:108-119`; plan:77-80). Treating every non-`clean` state as a hold therefore either (a) lets completion auto-open while the GET is still pending, before learning that the profile is empty, or (b) turns a failed GET into an invisible permanent hold. Making the completion effect reactive to later profile changes creates the opposite bug: after focus/typing put the page in `ready`, a successful blur save can make the state safe and auto-open even though the plan promises that blur is not a decision to leave (plan:92-95). Specify a monotonic decision: if completion beats the GET, wait for that first GET outcome; a failed or non-empty result releases the *initial* automatic decision; an empty result enables the offer and evaluates focus/dirty/in-flight once; once interaction chooses `ready`, it never returns to automatic opening. Gate save errors only when an empty-profile offer was actually shown. Add tests for completion-before-GET, GET failure after completion, and save-success-after-focus/blur.

3. **P1 — A “plain textarea” does not inherit the profile box's no-word-loss contract, and the plan attributes behavior to the wrong layer.** `useProfile()` supplies loading, ordered writes and the unmount/pagehide fallback, but it does not supply the idle timer, blur handler, save status, character counter or unload warning (`src/web/useProfile.ts:99-121`). Those live in `ProfileBox`: `useIdleCommit` at `src/web/ProfileBox.tsx:58-112`, the warning at `src/web/ProfileBox.tsx:114-131` and its wiring at `src/web/ProfileBox.tsx:225-240`. More importantly, that component deliberately omits `maxLength`, because the browser would silently discard the suffix of a paste; it shows the count and lets the server refuse the save while retaining every word (`src/web/ProfileBox.tsx:15-28`). Plan lines 82-85 must explicitly require those non-dictation pieces and explicitly forbid `maxLength`, rather than saying they come from the hook. Test an over-limit paste remains intact and reports the refusal, an idle draft saves, and a dirty/error/in-flight draft installs the unload guard.

4. **P1 — “Deleted, with `detail`, when the step finishes” covers only `runStep`; progress and running detail can survive pause, requeue, expiry and Stop.** The store has six other settlement doors, and their common `settledSteps` transformation currently removes only `preview` (`src/store/pg-jobs.ts:990-1055`; the six-door parity test is `tests/store-jobs-parity.test.ts:1900-1953`). A requeued attempt also clears only `preview` when it starts (`src/jobs.ts:1479-1488`). Thus a paused PDF can be shown as pending with the old fraction/detail, and the next attempt can begin with the previous attempt's progress. Define `progress` and a running report's `detail` as transient across all those doors, remove them when a running step is settled, and clear them on start. Do not indiscriminately erase `detail`: successful steps intentionally replace the running report with `product.detail` before commit (`src/jobs.ts:1575-1597`), and the parity suite deliberately preserves a done step's detail (`tests/store-jobs-parity.test.ts:1956-1969`). Extend the six-door preview table to progress/running detail and add a next-attempt-start assertion.

5. **P2 — “Open the article” does not actually wait for the About-you save, so a failed ordinary PATCH is hidden by navigation and reduced to a best-effort unmount write.** The plan says the button commits both values but that “the unmount write covers the rest” (`docs/plans/261020a-add-page-asks-why-higher-and-about-you-says-when-it-is-ready-and-shows-import-progress.md:92-95`). `commit()` is fire-and-forget (`src/web/useAutosavedText.ts:82-105,184-267`). The unmount path does preserve ordering behind an in-flight write, but it cannot show a refusal once the component is gone and ultimately calls a best-effort `leave` (`src/web/useAutosavedText.ts:177-182,240-258,281-304`). Make the explicit Open action wait until both purpose and profile are settled, surface a profile refusal in the still-visible page, and let **Open without saving** abandon the profile draft as well as the purpose draft. Keep the unmount write as the safety net for involuntary navigation, not as the success path for the button.

6. **P2 — The proposed universal text “parts read” is not true for the assets fraction.** `collectAssets` sets the denominator to the capped `fetchable` image list (`src/collect-assets.ts:954-961`) and increments `done` in `finally`, including fetch, validation, budget and storage failures (`src/collect-assets.ts:1248-1262`). PDF progress likewise counts completed checks, including an exhausted failed check (`src/pdf-read.ts:3615-3645`). The fraction is honest as work attempted/completed, but not as content successfully read. Carry a unit/label with the structured progress or render by step: for example, “23 of 69 chunks checked” and “8 of 12 images checked.” Keep the bar's accessible label equally literal.

7. **P2 — Persisting every `ctx.report` is a much wider write-volume change than the import progress requested, and the plan has not measured it.** `ctx.report` feeds roughly twenty model-backed modes, not just PDF extraction and assets (`src/pipeline.ts:3709,4006,4277-6040`), while `noteProgress` rewrites the full steps JSON and returns the full job row (`src/store/pg-jobs.ts:1985-1997`). At five seconds, the measured 216-second PDF is about 44 extra row writes and the runner's roughly 740-second maximum window permits about 148; each also makes subsequent polls non-identical. The simpler scoped change is to persist only reports carrying the new structured `progress` value, which delivers the two requested bars. If live detail for every mode is an intentional second feature, state that scope, count its production write/poll cost, and keep it as a separate decision rather than calling the cost only “one extra row write per five seconds” (plan:141-146).

8. **P2 — The absolute claim that report detail “never” reaches the poll is false, although it is true for PDF extraction and assets today.** `ctx.report` mutates the same in-memory `step.detail` object (`src/jobs.ts:1353-1365`), and a later preview call persists the whole `job.steps` array (`src/jobs.ts:1271-1278`). The `simple` step supplies both callbacks (`src/pipeline.ts:5144-5152`), so its preview write can incidentally carry the latest report detail into Postgres. PDF extract and assets do not call preview, so their counts really do stay in the worker and never reach the poll (`src/pipeline.ts:3291-3296,4139-4143`). Narrow plan lines 54-56 and 133-137 to “report does not persist by itself; these two steps have no other write while running.” I found no test assertion that requires detail never to persist, but the rationale/comments in `src/web/AddArticle.tsx:560-570`, `tests/job-card-progress.test.tsx:178-186` and `docs/project/ingest-queue.md:1685-1689` must be updated because they currently make the same absolute claim.

9. **P3 — The measurement's fetch sample count is off by one.** The raw table contains nine completed fetch steps: the eight completed imports plus the upload whose extract later failed (`docs/plans/261020a-import-durations-measurement.md:37-48`). Under the stated “done steps only” method, fetch is therefore `n=9`, not `n=8` (`docs/plans/261020a-import-durations-measurement.md:50-54`; plan:117-125). Its median 1.3 s and max 3.5 s do not change, so this does not alter the decision against a time estimate, but the sample definition/count should be corrected before the measurement is cited.

Two relevant checks did not produce additional findings. Reader changes are already fenced twice: `App` remounts `AddPage` with `key={user.id}` (`src/web/App.tsx:559-585`), while profile writes and the unmount write are bound to the reader for whom the hook was created (`src/web/useProfile.ts:44-48,85-107`). Preserve those mechanisms; an additional key around only the visible box would not reset a hook owned by its parent. Also, the lease fence itself is correct; the race in finding 1 exists specifically because a successful non-final commit intentionally keeps that valid claim.
