The plan needs rework before implementation.

1. **High — Option B cannot authenticate as described.** Spideryarn deliberately uses an `Authorization: Bearer` header instead of cookies, specifically to avoid CSRF ([api.ts](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/src/web/lib/api.ts:64)). A form POST from a publisher page cannot read Spideryarn’s token or set that header. Therefore this is not presently “a cookie-authenticated POST needing CSRF thought”; it is an unauthenticated request. Making it work requires a real handoff design—for example, opening an authenticated Spideryarn capture page and transferring the document with `postMessage`, after which that page uses the existing direct-to-Storage upload path. A long-lived account token embedded in the bookmarklet would be unsafe because it executes amid hostile page scripts. This materially changes B’s work and security assessment.

2. **Medium — Reusing `UploadPicker` unchanged gives multi-file recovery the wrong meaning.** Picking or dropping two files bypasses the single-upload engine and immediately starts minimal batch imports ([UploadPicker.tsx](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/src/web/UploadPicker.tsx:170)); those files get only metadata, cost a hundredth each, and do not navigate to `/add/upload/<id>` ([ingest-queue.md](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/docs/project/ingest-queue.md:520)). That is sensible on the shelf, but surprising in a control presented as the way around this failed article. Give `UploadPicker` a single-file/recovery mode: no `multiple`, refuse multi-file drops plainly, while retaining validation, quota preflight, one-file drop-to-commit, status, and `uploadEngine`.

3. **Medium — The proposed HTML advice is likely to send readers into another refusal.** Safari’s Save As formats are “Web Archive” and “Page Source,” not a plain generic HTML choice; Web Archive is unsupported here ([Apple’s Safari guide](https://support.apple.com/guide/safari/save-part-or-all-of-a-webpage-ibrw1089/26.0/mac/26)). The plan’s own research notes that Chrome/Edge’s “Single File” is MHTML and is also unsupported. “HTML file” therefore assumes knowledge the copy rules say not to assume ([copy.md](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/docs/project/copy.md:30)), and saved source may not preserve a dynamically revealed page. Prefer: “If the page opens in your browser, use its Download PDF button if it has one. Otherwise, save the page as a PDF, then upload that file here.” It is longer-running for Spideryarn, but reliable and actionable. `copy.md` otherwise permits this advice: it explains what happened and what to do next.

4. **Medium — Option A needs a safer middle option and provenance rules.** Today registry fetches are restricted to fixed API hosts, registry-supplied URLs are never followed, and paper-source candidates are addresses Spideryarn constructs from validated identifiers ([security.md](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/docs/project/security.md:1129), [fetching.md](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/docs/project/fetching.md:461)). A general “fetch the address OpenAlex/Unpaywall chose” reverses that boundary. The cheaper, safer middle is a fixed-host repository adapter: validate a PMC identifier, construct the Europe PMC API address locally, fetch it through the complete guarded path, and convert JATS without external-entity or external-resource resolution. The option should also preserve the requested publisher URL, record the actual copy read, and disclose when it imported an accepted manuscript or repository version rather than the publisher version.

5. **Medium — Option C overstates extension permissions.** An action-invoked extension can normally use `activeTab` plus `scripting`, gaining temporary access only to the tab on which the reader clicked; it need not request persistent host permission on every site. Chrome explicitly presents web clipping as an `activeTab` use case ([Chrome extension documentation](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)). Store review, cross-browser packaging, maintenance, and an authenticated handoff still make C the largest option, but the privacy/permission comparison should be corrected before Greg chooses.

6. **Low — Tighten the Part 1 predicate and acknowledge the leftover record.** Stable codes, `codeOfMessage(job.error)`, and an explicit `SUGGESTS_UPLOAD` set are the right shape; parsing prose or using `failureKind` would be wrong. But `job.url` is not itself an import predicate—mode jobs also carry URLs, as `isImportJob` documents ([job-state.ts](/var/tmp/spideryarn-worktrees/fbx5e966-fetch-refused-bot-check/src/job-state.ts:47)). Use the URL route/origin plus `isImportJob(job)` and `job.url !== undefined`. Also state that recovery creates a separate upload-origin article: it has no source URL, is not associated with the failed URL, and the old failed job remains on the shelf unless explicitly forgotten. That is acceptable for a simple v1, but currently invisible in the plan.

7. **Low — The scraping rejection is directionally right but too broad.** Distinguish ordinary headless rendering, which generally will not solve this wall, from a challenge-solving service that deliberately evades anti-automation controls. The latter is rightly not recommended; the stronger reasons are fragility, recurring cost, publisher terms, and the privacy/security burden if cookies or authenticated sessions ever enter the flow. “Explicit access control” is less precise for an openly licensed article behind a bot challenge.

The single-mount `LIMITS_ID` assumption is safe on the current mutually exclusive shelf/add routes, and the existing single-upload quota preflight remains appropriate. An unrelated tab-wide transfer should be labelled as such on this page rather than appearing to be the replacement file.
