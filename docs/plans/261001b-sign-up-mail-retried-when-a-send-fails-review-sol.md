- **P1 — Other instances retain stale cache entries.** Instance A inserts and sends; instance B loses the insert race and executes `remember(ownerId)`; A’s send fails, deletes the row, and clears only A’s cache. Every later request handled by B returns at the cache check without consulting the now-empty ledger. The same race is possible between overlapping calls in one process. The current unconditional cache write before `if (!isNew)` is the problem. - **P1 — Release failure is unhandled, and safely retrying it needs row identity.** If the delete definitively fails, the unsent row remains and retries remain permanently suppressed. Retrying `DELETE WHERE owner_id = ?` after an ambiguous database error is unsafe: the first delete may have committed, another instance may have reinserted, and the retry could delete that new claim. A single, non-retried delete does not normally delete a concurrent reinsert under Postgres MVCC; the dangerous case is an unknown outcome followed by retry. Use a per-attempt token/lease for conditional release, or describe deletion honestly as a one-shot best-effort improvement. - **P2 — Duplicates are possible after an ambiguous send failure.** The 10-second timeout can fire after Resend accepted the request. This is probably acceptable for an admin notification, but the plan should call the behavior at-least-once rather than imply otherwise. Simplest honest choices:

1. Keep deletion as explicitly best-effort, do not cache conflict losers, log a failed release, and accept possible duplicates/lost retries; or
2. If retries must be dependable, keep the row and add pending/sent state plus a retry lease. Requests can claim expired pending rows, so this does not require the scheduler the plan assumes.
