## Findings

- **P1 — `git worktree remove` does not make its lock check a lease, so a peer can lock and enter after Git has checked and still lose the tree.** `scripts/worktree-remove.ts:768-786`. Concrete scenario: the late liveness read returns `idle`; removal starts `git worktree remove`; Git checks the currently-unlocked registration and begins its clean-tree scan; `EnterWorktree` then writes the peer's lock and moves the Claude process into the tree; Git does not re-check that new lock and deletes the live tree. This is distinct from the named “enters without locking” residual: the peer did lock successfully. **Reproduced:** yes, in `/tmp/worktree-lock-race.VpwmpC` with a disposable worktree containing 30,000 tracked files. Starting `git worktree remove`, waiting 20 ms, and then running `git worktree lock --reason peer-arrived` produced `lock_status=0`, `remove_status=0`, and `path_exists=no`. Closing it needs an exclusion shared with `EnterWorktree`; another read in this script can only move the race. The false stronger claim in the code comment was corrected in this review; the behavior cannot be closed inside this script.

- **P2 — the ghost path still skips liveness and can unregister a worktree while a live peer is inside its renamed directory.** `scripts/worktree-remove.ts:657-665`, `scripts/worktree-remove.ts:472-513`. Concrete scenario: a peer's process has its cwd in `wt`; the directory is renamed to `wt-away`; the registration is classified as a ghost because the registered path is absent; `removeGhost` proves the reflog and calls plain `git worktree remove wt`, deleting the live tree's administrative directory and HEAD reflog without ever asking liveness about `wt-away`. **Reproduced:** yes, in `/tmp/worktree-ghost-live.6dfuVD`: a live `sleep` had cwd `/tmp/worktree-ghost-live.6dfuVD/wt-away`, plain scoped removal returned 0, the moved directory remained, and its registration vanished. This is older than `c87ceec8` and already named in the plan, but it is a second live-tree gap, so “bar the one named gap” is not true for all registered worktrees.

- **P3 — two single-threaded parts of the new failure contract were untested: a late `unknown`, and a peer lock acquired after the late read but before Git's own check.** `tests/worktree-remove.test.ts:644-750`, `scripts/worktree-remove.ts:778-790`. Concrete scenarios: the injected second liveness result is `unknown` and must refuse while restoring the original lock; or the injected second read locks the worktree for a peer and returns `idle`, after which Git must refuse and the failed attempt to restore the old lock must leave the peer's lock intact while reporting honestly that restoration failed. The committed tests covered late `in-use`, a changed pre-unlock lock, and idle twice, but neither branch above. **Reproduced and fixed:** yes. Two tests were added. With the sandbox's false `spawnSync` error shimmed only for the run, all five tests in the block pass. Mutating away the late read makes the two new tests and the two existing late-read-dependent tests fail on their assertions.
