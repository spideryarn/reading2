Verdict: **approve with changes**. The trim itself is sound, and moving synchronous duplicate tracking into the hook is React-safe, but the plan misses a serious delete/rename race and overstates the storage bound.

- **P1 — A rename can resurrect a search the reader deleted.** [useSearch.ts:345](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/web/useSearch.ts:345), [useSearch.ts:360](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/web/useSearch.ts:360), [useSearch.ts:383](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/web/useSearch.ts:383), [useSearch.ts:507](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/web/useSearch.ts:507), [plan:58](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/docs/plans/261001i-search-pending-rows-survive-the-trim-and-the-duplicate-guard-follows-a-renamed-run.md:58)  
  Suppose the client sends `A`, the server begins `B`, and the reader deletes optimistic row `A` before the `begin(B)` frame arrives. `remove(A)` tombstones and DELETEs `A`, which does not exist on the server. The begin handler then changes `liveId` to `B`, but the tombstone remains under `A`; `done(B)` therefore re-adds the row. If the stream ends silently, nothing ever DELETEs `B`. A rename must transfer the tombstone and immediately issue `forget(B)`. The URL updater must replace `A` only if `A` is still active, otherwise a prior untick/delete will be undone. The same identity migration also affects `chosen`/pending colour PATCHes: recolouring optimistic `A` before `begin(B)` currently loses the choice both locally and on reload. Treat rename as migration of every per-ID client state, not only the in-flight map and `?runs=`.

- **P2 — The route drops its sweep protection before the result is stored.** [routes.ts:4214](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/routes.ts:4214), [routes.ts:4218](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/routes.ts:4218), [routes.ts:4228](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/routes.ts:4228), [pg-searches.ts:434](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/store/pg-searches.ts:434)  
  `searching.delete(key)` runs before `searchStore.finish`. If the total request has crossed the 90-second grace, a same-process GET in that gap supplies an empty `keep` set, sweeps the row to `error`, and makes `finish` update nothing. The 60-second model timeout plus 30 seconds of slack makes this rare, but article/database operations have no hard bound. Keep the key until after `finish` by moving deletion into an outer `finally`. A sweep does not literally delete the row, but it can still discard the paid answer mid-flight.

- **P2 — “Bounded by searches actually in flight” and “cannot pin rows for ever” are not true.** [plan:28](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/docs/plans/261001i-search-pending-rows-survive-the-trim-and-the-duplicate-guard-follows-a-renamed-run.md:28), [routes.ts:8964](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/routes.ts:8964), [routes.ts:8973](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/routes.ts:8973), [pg-searches.ts:454](/home/greg/code/spideryarn2/.claude/worktrees/fu-search-reliability/src/store/pg-searches.ts:454)

Even after a GET turns them into errors, they remain until another begin trims them. There is also deliberately no in-flight concurrency cap. Either describe this honestly as a soft/event-driven bound, or reclaim expired attempts during `begin` and/or trim immediately after `sweepPending`. The current conclusion overclaims what the change guarantees.

## What is sound

The implemented trim shape—rank all rows, then delete only selected rows whose status is still non-pending—is correct. The repeated SQL status predicate protects against state changes, retry-reset runs under the article lock and bypasses the insert trim, and `sweepPending` updates rather than deletes. The remaining direct deletions are the reader’s explicit DELETE and the article’s cascade, both intentional.

A ref-backed in-flight registry mutated synchronously before starting the async request is also sound under React batching and StrictMode, provided the version bump is a functional state update and request initiation remains outside React state updaters.

A simpler duplicate guard is to track **request lifetime by trimmed question**, not by the server row ID: a ref-count or map keyed by the original request token can add before POST and remove in `finally`. It never needs re-keying. The actual ID rename is then confined to row state, tombstones/colour state, and the conditional `?runs=` replacement. This matches what the UI really asks—“is this question already out?”—and removes one identity-sensitive moving part.
