## Findings

1. **Medium — `db:admin-password` reports invalid credentials during the migration window.** On every pre-rename machine, pulling this code changes `readAdminCredentials` to return the new address based solely on the existing password file ([scripts/seed-accounts.ts:140](/home/greg/code/spideryarn2/scripts/seed-accounts.ts:140)). Until `db:seed-owner` runs, the database still has the old address, yet `db:admin-password` exits successfully and prints the new one ([scripts/db-admin-password.ts:29](/home/greg/code/spideryarn2/scripts/db-admin-password.ts:29)). `browser-sign-in` likewise fails until seeding. This is the repository’s “success over stale state” pattern. The file needs a migration/version marker, or the commands/docs must explicitly refuse or warn until the rename has run.

2. **Medium — the four-part fence establishes location, not provenance.** The statement “No row we did not seed is reachable” is false ([scripts/seed-accounts.ts:260](/home/greg/code/spideryarn2/scripts/seed-accounts.ts:260)): the known laptop row was originally created by Google, not this seed ([260831ab…md:212](/home/greg/code/spideryarn2/docs/plans/260831ab-seed-local-admin-user-for-remote-box.md:212)). `planAccountEmail` sees only the id and normalized email ([scripts/seed-accounts.ts:285](/home/greg/code/spideryarn2/scripts/seed-accounts.ts:285)); it cannot distinguish the expected legacy fixture from an imported or manually created row with the same tuple.

   For an ordinary peer Google sign-in, accidental capture is effectively impossible because Google generates a different UUID. A deliberate peer who can create that exact UUID likely already has the local service key. So the practical risk is narrow—but a restored/imported/shared stack is genuinely an unhandled case. If exclusive ownership is required, verify the legacy address/password returns the fixed `sub` before renaming. Otherwise document the real assumption: this is a trusted, single-purpose local stack whose fixed fixture identity belongs to the repo.

3. **Medium — the old real address remains inside the upgraded account.** The historical laptop row has a Google identity ([260831ab…md:212](/home/greg/code/spideryarn2/docs/plans/260831ab-seed-local-admin-user-for-remote-box.md:212)). The new `PUT` changes the primary email ([scripts/db-seed-owner.ts:277](/home/greg/code/spideryarn2/scripts/db-seed-owner.ts:277)), but GoTrue v2.195 creates/updates an `email` identity; it does not rewrite the existing Google identity or Google-derived user metadata ([tagged GoTrue source](https://github.com/supabase/auth/blob/v2.195.0/internal/api/admin.go)). Consequently:

   - An upgraded laptop has Google plus email identities; a fresh box has email only.
   - Greg’s real address can remain in Google identity/user metadata and detailed Studio views.
   - `app_metadata.provider` can remain `"google"`, so the profile may display `dev-admin@… · via google` ([AccountSection.tsx:35](/home/greg/code/spideryarn2/src/web/AccountSection.tsx:35)) even after password sign-in.

   If the goal is only to rename `auth.users.email`, document that narrower result. Making it a wholly dummy identity would require separately approved identity cleanup.

4. **Low, speculative — arbitrary peer mutation can race both writes.** The code reads the target address and id ([scripts/db-seed-owner.ts:312](/home/greg/code/spideryarn2/scripts/db-seed-owner.ts:312)), then performs an unconditional rename ([scripts/db-seed-owner.ts:336](/home/greg/code/spideryarn2/scripts/db-seed-owner.ts:336)); later it may perform an unconditional password update ([scripts/db-seed-owner.ts:387](/home/greg/code/spideryarn2/scripts/db-seed-owner.ts:387)). A peer changing the fixed-id row between those operations can have their newer row renamed or password-reset. The final sign-in prevents a false final success, but cannot undo the mutation.

   Cooperative concurrent seed runs are fine, and a concurrent creation of the target address should make GoTrue reject the rename. The dangerous case requires an unrelated concurrent writer. A second read immediately before each write narrows the window; eliminating it requires locking or conditional-update support.
