# Independent review of F2 and F6 wording

Candidates: `40ea6ea43` and `36cd57218`. Findings recorded before fixes. Other agents' uncommitted merge work is excluded.

- **K1 — P1, fixed: the wait footprint does not share the visible sentence's wrapping.** `mode-band.css` gave `flex: none` to both ghost children, including the sentence span. The visible span can shrink, so a long line can overflow before 600ms and wrap to a taller box afterwards. Restricted the fixed flex sizing to `svg.band-waiting-ghost`. The regression uses the actual wait rules and computed flex sizing: hidden shrink 0 versus visible shrink 1 before the fix, equal afterwards. It proves the sizing correction, not measured browser heights.
- **K2 — P1, fixed: Skim's newly offered depth bar can miss reveal and every observer.** `RouteHead` installed the hook while its fieldset was absent when only one depth was offered. A ready route refresh can offer several depths while keeping the same chosen depth, so neither effect dependency changed when the fieldset arrived. The trigger now includes fieldset presence. A real `SkimPanel` rerender with Most selected throughout failed at scrollLeft 0 instead of 130 before the fix, then passed. The shared hook and OrderGroup did not change.
- **K3 — initially suspected arrow defect, not established; no fix.** Reaching the window is not proof that article navigation took a step. `keynav.ts` explicitly leaves unclaimed horizontal arrows to the browser and calls `preventDefault` when it handles a horizontal action or article step. Native scrolling of the focused bar in the unclaimed case is consistent with that contract. Cancelling at the chip would suppress article handling because keynav ignores already prevented events; changing `overflow-x` to hidden would remove the intended swipe interaction. A live double movement despite article default cancellation would be a separate established bug, but no such evidence was obtained here.
- **K4 — P2, recommendation only: overflow discovery depends on a partial label.** The plan explicitly chooses horizontal scrolling. The reported Candi… cut and Search's 27px overflow are enough to cue a swipe, but a clip exactly between buttons or the criterion row's 79px overflow can conceal a whole option. Prefer retaining a visible scrollbar when all options cannot fit. Do not reintroduce wrapping, reduce font size or add a permanent fade that can cover a whole chip or its focus ring. Smaller padding may help Referee but cannot solve the longer criterion labels. Browser execution was blocked, so no speculative layout adjustment was made.

Contrast: enabled, unselected chip labels are ordinary small text and need 4.5:1 under [WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); unselected does not mean disabled. A real 3.19:1 text/background pair would fail. However, that supplied Light measurement does not match the candidate tokens. Resolving the candidate's `--ink-faint` against `--panel` gives **5.49:1 Dark / 5.82:1 Light**. The selection fill is **1.19:1 / 1.12:1** and selected ink **14.25:1 / 18.10:1**. Weight plus ink carries selection, so the fill is not its sole indication under [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html). No contrast edit is justified from the supplied value alone; repeat the browser measurement against the exact candidate before treating it as a palette failure.
