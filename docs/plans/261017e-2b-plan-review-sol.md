F1 — P1 — Live’s server endpoint would gain page-reading accidentally.  
Evidence: the plan adds `read_web_page` to `toolsFor("guide")` while leaving it out of `GUIDE_TOOLS` ([plan:149](/var/tmp/spideryarn-worktrees/qi-qsy8nqyt-guide-reads-pages/docs/plans/261017e-bring-a-web-page-into-chat.md:149)). Live advertises only `GUIDE_TOOLS` ([live.ts:451](/var/tmp/spideryarn-worktrees/qi-qsy8nqyt-guide-reads-pages/src/live.ts:451)), but its endpoint first accepts every name in `LIVE_SERVER_TOOLS`, which includes `read_web_page`, then calls `runTool` with `kind: "guide"` ([routes.ts:4991](/var/tmp/spideryarn-worktrees/qi-qsy8nqyt-guide-reads-pages/src/routes.ts:4991), [routes.ts:5006](/var/tmp/spideryarn-worktrees/qi-qsy8nqyt-guide-reads-pages/src/routes.ts:5006)). Once `toolsFor("guide")` contains the tool, that second gate permits it. Worse, this endpoint creates a fresh `ToolContext` for each call, so the WeakMap counter would reset and provide no Live cap.  
Recommended change: add an explicit Live-guide server allowlist based on `GUIDE_TOOLS`, not `toolsFor("guide")`, and test a direct `POST …/live-tool` asking a guide to `read_web_page`, asserting no fetch. Live should remain without this tool.
