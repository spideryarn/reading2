2. **Should-fix — old threads cannot remain “current” through both checks; the plan needs to distinguish stale from outdated explicitly.** The GET/Metadata path can correctly avoid a stale warning by comparing `tweets/1–4` with `articleFingerprint`. The pipeline cannot skip those threads: `stepIsDone` compares the recorded stamp with today’s expected hash, prompt version and model ([src/pipeline.ts:1051](/home/greg/code/spideryarn2/.claude/worktrees/tweets-as-mode/src/pipeline.ts:1051), [src/store/artifacts.ts:981](/home/greg/code/spideryarn2/.claude/worktrees/tweets-as-mode/src/store/artifacts.ts:981)); `tweets/4 !== tweets/5`, even before considering the changed hash. That is consistent with the plan’s “outdated but not announced” intent, but not with “kept current through stamp/skip.” State the acceptance criteria as:

   - unchanged old thread: `loadTweets.stale === false`;
   - old thread: `stepIsDone === false` because its prompt is outdated;
   - matching `tweets/5` thread: both reader and pipeline agree it is current.

   Public DTOs deliberately strip `sourceHash` ([src/store/public-reader.ts:300](/home/greg/code/spideryarn2/.claude/worktrees/tweets-as-mode/src/store/public-reader.ts:300)); export writes the stored thread whole ([src/store/export.ts:438](/home/greg/code/spideryarn2/.claude/worktrees/tweets-as-mode/src/store/export.ts:438)). Neither performs a competing comparison. Also key the fingerprint family to a parsed producer version, not lexicographic comparison or merely the optional `blocks` field; test `tweets/4`, `tweets/5`, and `tweets/10`.
