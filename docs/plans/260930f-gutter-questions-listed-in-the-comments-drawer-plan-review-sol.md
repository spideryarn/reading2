1. **Opening a question is broken in Remember mode, and is not always floating.** `openChatThread` only clears the note and sets `?thread=`; it does not change mode ([Reader.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/reader/Reader.tsx:1381)). The floating overlay is suppressed in both Chat and Remember modes ([Reader.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/reader/Reader.tsx:673)). In Chat mode the conversation therefore opens in the full-width band, not the promised floating dialog. In Remember/Recall, the drawer bypasses the band’s mode-aware `onThread`, which normally switches a chat thread into Chat mode ([ConversationModes.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/modes/conversation/ConversationModes.tsx:586)); in Remember/Quiz, the cleanup effect immediately removes `?thread=` ([ConversationModes.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/modes/conversation/ConversationModes.tsx:102)). Suggested change: decide the intended surface explicitly. The least surprising rule is “Chat mode opens it in the Chat band; Remember switches to Chat; other modes use the floating dialog.” Hoist a mode-aware opener and test Plain, Chat, Remember/Recall, and Remember/Quiz, including history length.

2. **The proposed answer preview is stale in the exact reported sequence.** A newly created summary is inserted without `lastLine` ([ChatDialog.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/ChatDialog.tsx:561)), and although `useChatAnchors` exposes `touch`, `ChatDialog` has no completion callback that calls it ([useChatAnchors.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/useChatAnchors.ts:64)). Consequently, after receiving a good answer, closing it, and immediately opening Comments, the row says “thinking…” until reload. Moreover, server `lastLine` means “most recent finished answer,” not “status of the newest turn,” so a pending follow-up can display the previous answer ([routes.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/routes.ts:3880)). Suggested change: for the simpler v1, omit the preview and show only `Question` plus the passage. Otherwise add an explicit latest-turn status to `ThreadSummary` and update summaries when turns settle in both floating and full Chat surfaces.

3. **“Every anchored chat” also includes chats spawned by a comment, producing duplicate drawer rows.** Saving a comment with “Also ask the AI” creates an anchored chat carrying `sourceCommentId` ([Reader.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/reader/Reader.tsx:2389)), and the resulting comment records that conversation as `threadId` ([types.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/types.ts:2713)). The plan’s `kind === "chat" && anchor` rule therefore lists both the comment and its linked conversation, despite claiming the population consists of gutter-help and “Chat about this” threads. Suggested change: exclude summaries whose id appears in `comments[].threadId`, or merge the Question marker/open-chat action into that comment’s existing row. Add a test for the checkbox-created-chat path.

4. **Loading needs a fuller rule than the proposed empty-list test.** `useChatAnchors.loaded` becomes true on failure as well as success ([useChatAnchors.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/useChatAnchors.ts:289)), so consulting only `loaded` can turn a failed chat fetch into “no questions.” Its `error` also is not cleared when a new slug starts loading, making it unsafe to expose without a fix ([useChatAnchors.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/useChatAnchors.ts:284)). Finally, when comments already exist but chats are still loading, the current drawer logic renders a silently incomplete list because loading is shown only when the combined list is empty ([Dock.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/Dock.tsx:3611)). Suggested change: pass both chat `loaded` and `error`, clear `error` on a new fetch/success, and show a loading or failure line above any already-known rows. Test empty and non-empty partial states plus failure and slug change.

5. **Changing the visible count also requires changing the Dock’s fit signature.** The bar deliberately remeasures when its count changes width, but `fitSignature` still derives that count solely from `own.comments.length` ([Dock.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/Dock.tsx:1219)), while the visible chip is intended to use the combined row count ([Dock.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/Dock.tsx:3146)). Suggested change: compute one combined owner count and feed it to both `CommentsChip` and `fitSignature`; test a width-changing boundary such as 9→10 caused by a question arriving.

6. **The lost-vs-hidden diagnosis is correct for Greg’s report, but the history wording is too absolute.** The header X invokes only `onClose` ([ChatDialog.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/ChatDialog.tsx:643)); the controller deliberately survives unmount ([useChat.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/useChat.ts:412)), and the server continues and stores the answer after disconnect ([routes.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/routes.ts:2584)). Only the explicitly labelled Cancel control aborts and deletes the first-answer thread ([ChatDialog.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/ChatDialog.tsx:867)). Thus closing during “Starting…” does not delete it, and a question whose good answer was already visible was stored. Separately, `jumpToComment` pushes only when the passage is away; “here” and orphan rows merely replace the open-thread parameter and add no history entry ([comment-jump.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb6w-gutter-question-findable/src/web/comment-jump.ts:86)). Suggested change: keep the implementation, but change the plan to “at most one entry; exactly one when a scroll jump occurs.”

The simpler design is: list anchored, non-comment-linked chat threads with a `Question` label and passage text, omit live answer previews, and make opening mode-aware. That fully solves findability without adding a second store or a second live-status synchronization path. Reading-order logic and visitor gating otherwise look sound.
