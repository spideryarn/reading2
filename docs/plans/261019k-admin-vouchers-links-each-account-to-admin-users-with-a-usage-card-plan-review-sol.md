1. **P1 — Address fallback can link to the wrong account.** Two live Auth accounts may share the same trimmed, lower-cased address; the existing voucher lookup deliberately treats that as ambiguous ([admin-accounts.ts](/var/tmp/spideryarn-worktrees/fbqdd2vc-vouchers-user-links/src/store/admin-accounts.ts:511)). Resolve rows in this order: `claimedBy` always wins; revoked-and-unclaimed never matches; otherwise normalize both addresses with `normaliseEmail` and link only when exactly one `AdminUser` matches. Show ambiguity rather than choosing first/last. Test casing, whitespace, duplicates, and revoked-unclaimed rows.

2. **P2 — User-list failures silently remove all waiting-row links.** The proposed failure card is reachable only for claimed rows; an initial `/api/admin/users` failure makes every waiting row look exactly like “no account.” Also, `useAdminUsers` retains stale data after refresh failure ([useAdminUsers.ts](/var/tmp/spideryarn-worktrees/fbqdd2vc-vouchers-user-links/src/web/useAdminUsers.ts:57)). Surface the account-list error on the vouchers page, distinguish stale usage from unavailable usage, and make Refresh retry both lists—or add an explicit account-usage retry.

3. **P2 — The proposed link text can name a historical address as though it were the account.** The first column always renders `voucher.email` ([AdminVouchersPage.tsx](/var/tmp/spideryarn-worktrees/fbqdd2vc-vouchers-user-links/src/web/AdminVouchersPage.tsx:921)), while a claimed account’s current address is `claimantEmail` in Status. Prefer one conditional link: current claimant in Status for claimed rows, first-column address for uniquely matched waiting rows. This still gives one link per row and avoids a card headed `new@example.com` opening from `old@example.com`.

4. **P2 — The scroll can silently mark itself complete without scrolling.** The in-progress effect records the id before confirming that the row or `scrollIntoView` exists ([AdminPage.tsx](/var/tmp/spideryarn-worktrees/fbqdd2vc-vouchers-user-links/src/web/AdminPage.tsx:361)); the plan has no scroll assertion. Use a scoped row ref, record success only after the call, reset the one-shot guard when `?user` changes or clears, and add tests for delayed data, exactly one scroll, missing rows, and a changed target. Keep the guard in a ref so no render loop is introduced.

5. **P3 — The card misnames comments as questions.** `AdminUser.questions` is populated from `comments`, and `/admin/users` labels it “Comments / Passages they have marked” ([admin-columns.tsx](/var/tmp/spideryarn-worktrees/fbqdd2vc-vouchers-user-links/src/web/admin-columns.tsx:551)). Change the card’s “40 questions”/“Asked” wording to comments or passages marked.

6. **P3 — Make the tooltip action semantics explicit.** “Open in Users →” must remain static explanatory text because the trigger is already the link. A real link inside the card would require `Tooltip interactive={{label}}`, dialog semantics, and keyboard-focus tests—and would duplicate the destination. Add a focus test proving the trigger exposes the card as its accessible description.

No P0s. The proposed usage fields themselves remain within the existing admin-only metadata boundary.
