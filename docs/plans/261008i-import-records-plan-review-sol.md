1. **High — the plan overlooks a substantially simpler use of `jobs`.**  
   Evidence: reader-facing queries already hide rows with `dismissed_at` ([src/store/pg-jobs.ts:1127](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/src/store/pg-jobs.ts:1127)); Dismiss preserves a row by stamping that field ([src/store/pg-jobs.ts:2098](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/src/store/pg-jobs.ts:2098)); only `trimFinished` actually destroys the diagnostic record ([src/store/pg-jobs.ts:2173](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/src/store/pg-jobs.ts:2173)). The plan rejects keeping jobs because they would stay visible ([plan:135](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/docs/plans/261008i-a-failed-import-report-carries-the-address-and-a-record-of-every-import.md:135)), but `dismissed_at` already separates storage from visibility.  
   Recommended change: first evaluate changing `trimFinished` so doomed import jobs are stamped dismissed, while doomed mode jobs are deleted. Exclude already-dismissed rows from its ranking, or they will consume the fifty visible slots forever. The production script can then query `jobs` directly. This removes the new table, trigger, copied columns, FKs, and deletion synchronization while retaining every import. If the separate table is still preferred—for example because permanently retaining jobs also retains their upload FK and enlarges the live table—record that as the real reason.

   Recommended change: state explicitly that records with no resulting article remain until account deletion, or add an owner-facing erasure path for them. The privacy wording should distinguish “associated article deleted” from “failed before an article existed.”

3. **Medium — `ingest_event_id` should preserve the owner relationship, and every FK delete action must be explicit.**  
   Evidence: `jobs` deliberately uses a composite `(ingest_event_id, owner_id)` FK so a job cannot point at another owner’s reservation ([src/db/schema.ts:2814](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/src/db/schema.ts:2814)); `ingest_events` provides the corresponding unique pair specifically for that purpose ([src/db/schema.ts:6803](/var/tmp/spideryarn-worktrees/fba5gzb9-import-report-details/src/db/schema.ts:6803)).    Recommended change: if `import_records` remains, use a composite `(ingest_event_id, owner_id)` FK. Keep `upload_id ON DELETE SET NULL`; choose and state `NO ACTION/RESTRICT` for `ingest_event_id` and `owner_id`. Those restrictions will block direct ingest-event or Auth-user deletion until `import_records` is removed, which is appropriate only if the manual account-erasure procedure is updated accordingly.

   Recommended change: put the literal predicate in the plan—either `NEW.steps @> '[{"name":"fetch"}]'::jsonb` or an `EXISTS` over `jsonb_array_elements`. Add positive and negative database tests using the real object shape.
