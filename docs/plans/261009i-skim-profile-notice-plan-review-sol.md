1. **P1 — The hash pair does not invalidate every re-planned route.** Evidence: [plan:50](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/docs/plans/261009i-skim-profile-notice-can-be-dismissed.md:50), [useSkim.ts:240](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/src/web/useSkim.ts:240). Sequence: route planned for A → profile B → dismiss `(A,B)` → profile back to A → re-plan, still stamped A → profile back to B. The new route produces `(A,B)`, so the old dismissal wrongly hides its notice. `generatedAt` is already the route’s identity. Fix: bind dismissal to `route.generatedAt` plus the current profile hash, not the route’s profile hash. Use null-safe comparison (`IS NOT DISTINCT FROM`, JavaScript equality after selecting, or a canonical combined key), and explicitly test first profile `(route null, current hash)`, clearing `(route hash, current null)`, re-plan under the same profile, and changing away and back.

2. **P2 — A new table with a future-proof `mode` column is more machinery than the current feature needs.** Evidence: [plan:40](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/docs/plans/261009i-skim-profile-notice-can-be-dismissed.md:40), [schema.ts:226](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/src/db/schema.ts:226). The schema explicitly puts one-per-article owner state on `articles`; the proposal permits only `skim`, so `(article_id, mode)` currently models exactly one row per article while requiring another store, cascade registration, exports, and registries. Fix: prefer `articles.skim_profile_notice_key` plus `skim_profile_notice_dismissed_at`, where the key combines route identity and current-profile identity. If multi-mode dismissal becomes real, migrate to a table then.

4. **P2 — The 409 is unnecessary, while the stated no-body guarantee is false under races.** Evidence: [plan:56](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/docs/plans/261009i-skim-profile-notice-can-be-dismissed.md:56), [routes.ts:11190](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/src/routes.ts:11190). Between GET and POST, another tab can edit the profile or finish a re-plan; the server can therefore store a pair the browser never displayed. Conversely, “nothing currently to dismiss” is an idempotent success, not a conflict. Fix: keep “no route” as 404, but return 204 without writing when there is no current mismatch. If exact screen-state fencing is genuinely required, return an opaque notice key from GET and require it in POST; only a stale submitted key warrants 409. Ownership itself is sound provided the write goes through `articleIdForOwned` ([pg.ts:374](/var/tmp/spideryarn-worktrees/fbud2w92-dismiss-profile-notice/src/store/pg.ts:374)).
