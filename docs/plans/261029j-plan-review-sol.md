Verdict: not ready to build. I found one P1 and four P2 gaps.

1. **P1 — explanation touch handling would steal taps from comments and chat marks.** The plan adds `mark.explained` to `tapSelector` and only defines precedence for terms ([plan](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/docs/plans/261029j-explained-passages-underlined-in-the-prose.md:97)). On `mark.cmt.explained` or `mark.chat.explained`, `useHoverCard` claims the pointer and suppresses the later `mouseup`/`click` ([useHoverCard.ts](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/useHoverCard.ts:694), [suppression](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/useHoverCard.ts:763)). Consequently TableView’s existing comment/chat opener never runs ([TableView.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/TableView.tsx:1617)). Comment and chat marks need explicit touch precedence, plus regression tests for both overlaps.

2. **P2 — the proposed shared read can still disagree with the band and still performs two GETs.** `useStepFinished` deliberately misses jobs completed in another tab while this tab is idle ([useStepJob.ts](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/useStepJob.ts:416)). Meanwhile Explanations mode retains its separate `useExplanations(slug)` read ([ExplanationsMode.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/modes/explanations/ExplanationsMode.tsx:35)). Scenario: Reader initially gets no explanations; another tab generates them; opening the mode performs a fresh GET and shows them in the band, while prose and margin remain empty. The plan must include the mode in the shared-read design or define cache publication/revalidation that updates Reader too.

3. **P2 — lifting the read into Reader needs a concrete owner/feature-gated component boundary.** Reader serves owners and visitors ([Reader.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/reader/Reader.tsx:309)), while `useExplanationsRead` issues its GET whenever mounted ([useExplanations.ts](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/useExplanations.ts:124)). Calling it directly in Reader cannot be conditional under React’s hook rules. The current child feed is safely mounted only for owner plus experimental switch and clears its contribution on unmount ([MarginaliaColumn.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/marginalia/MarginaliaColumn.tsx:1389)). The plan should preserve an equivalent gated child/provider and test visitor, switch-off, and switch-on-then-off cases. Otherwise visitors make forbidden API requests or stale marks survive disabling the feature.

4. **P2 — neither card action is specified or tested to close the card.** `OpenInMode` only calls its callback ([ProseHoverCard.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/ProseHoverCard.tsx:1970)), and `openExplanationInBand` only changes focus and mode ([Reader.tsx](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/reader/Reader.tsx:3329)). Existing Quote and Term cards explicitly wrap actions with `onClose` ([QuoteCard](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/ProseHoverCard.tsx:2141)). Without the same wrapper, “Open in Explanations” or “Ask in chat” leaves the hover card floating over the newly opened destination. Tests should assert closure for both actions and second-tap commit.

5. **P2 — keyboard focus on links containing an explained mark is uncovered.** Keyboard focus lands on the `<a>`, not its nested `<mark>`. Existing term and citation readers therefore search both upward with `closest()` and downward with `querySelectorAll()` ([term read](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/ProseHoverCard.tsx:521), [citation read](/var/tmp/spideryarn-worktrees/fbnjkskc-explanations-underline/src/web/ProseHoverCard.tsx:538)). An explained implementation that only checks `closest("mark.explained")` works under the mouse but silently shows only the link card under keyboard focus. The plan should require the same descendant lookup and a focused-link regression test.

I found no fundamental problem with the proposed offset space: both existing annotation paths locate quotes in rendered text, matching the explanation quote validation. The fail-closed sanitizer approach and TableView memo-key additions are also sound if implemented exactly as planned.
