1. **Critical — the four-state table claims more than the evidence supports.** A gap cannot mean “nothing was running.” It can mean deliberate 5× backoff, a 120-second fleet-collection timeout, a long synchronous drain, event-loop starvation, failed persistence, or a dead dashboard. Because health collection currently follows fleet collection, the monitor is least likely to run precisely when the box is struggling. Also, two consecutive samples cannot detect an outage still in progress. Move the existing health collection into its own fixed-cadence loop—one collector, not a second collector—and label unexplained absence only as “no health sample recorded.” Return a predecessor sample for the window’s left edge and compare the newest sample with the response time for its trailing edge.

2. **Critical — “no point” is not enough; every unknown must break the line.** A typical implementation filters non-values before forming a `<polyline>`. If memory is 20%, then `free` fails during the crisis, then memory is 25%, that produces a calm line straight across the unreadable reading. The violet mark does not make the line honest. Split each series into contiguous segments at per-reading `unknown`, `collector-failed`, malformed records, and inferred missing coverage. Test SVG topology specifically—not merely that `unknown` and zero produce different markup.

3. **Critical — persistence failure currently becomes fake dashboard downtime.** The planned append catch only logs. If disk is full or the directory becomes unwritable, live health continues while the old files remain readable; the history route then returns old samples and the chart hatches “nothing was running.” Make retention health part of the route payload: last append attempt, last success, and the current failure. Render storage failure as its own state, never as collector silence.

4. **Critical — an append failure can poison subsequent lines.** `writeAll` can write part of a record and then throw. If the outer catch lets the loop continue, the next append is welded onto that torn text; `truncateToLastLine` only repairs at process startup. After any ambiguous/partial append, mark the writer poisoned, close it, and refuse further appends until the file has been repaired and reopened. A successful later write must not quietly imply recovery.

5. **High — the proposed “dead-feature” test bypasses the production join.** `refreshOnce → real store → route handler` remains green if somebody forgets to mount that handler in `server.ts`, or mounts it with a different store instance. That is exactly the failure class the test claims to catch. Extract the production handler/composition into an importable factory and test through it, then through the real client parser and mounted `HealthPanel`. Mutate the route mount or payload key and confirm the join test—not an earlier assertion—fails.

6. **High — count-and-discard corruption is not safe.** Your general instinct is right: a time series need not discard the entire window because one independent point is bad. But returning only valid samples plus `unreadableLines: 1` loses where the hole occurred, allowing the renderer to reconnect across it. The peer is right to reject that version. Preserve ordered hole sentinels or pre-split segments so corruption is a positional barrier. Unknown schemas and structurally invalid reports should follow the same path.

7. **High — the 8 MB retention invariant is false under unbounded rate and record size.** At one record per second, two 8 MB files hold only about 23.5 hours when a failure line is 198 bytes; a 348-byte line holds roughly 13.4 hours. `why` is unbounded, so even the per-record ceiling is unproved. A finite byte cap cannot guarantee 24 hours at every rate. Treat 16 MB as the hard disk ceiling and return explicit `coverageTruncated` metadata, or enforce both a maximum persistence rate and maximum record size. Never label the earliest retained point “history began” after rotation; say “retained data begins” unless first-ever collection is separately known.

8. **High — verbatim versus versioned is a false choice.** Verbatim storage is the right decision: a narrow write projection creates the irreversible lossy join you are trying to avoid. Wrap the complete report in an explicitly versioned sample envelope and strictly validate everything used on read. Meaning or unit changes require a schema bump; unknown versions become localized unrenderable intervals. The history response itself also needs a schema. Do not cast disk JSON to the current `HealthReport`.

9. **High — port binding does not construct a single writer.** Another dashboard can use a different `FLEET_PORT` or bind while sharing `FLEET_HEALTH_DIR`; startup races can also occur before asynchronous bind failure is observed. Concurrent startup repair and rotation can silently split or overwrite history even though individual `O_APPEND` writes remain intact. Use a kernel-backed exclusive writer lock. If it cannot be acquired, keep the dashboard usable but report retention as unavailable.

10. **Medium — importing `THRESHOLDS` does not unify the health judgment.** `health-view.ts` already copies the server thresholds, and constants alone do not encode operators or combined rules: load uses `>`, swap and disk use `>=`, memory reverses direction, and 50% IO wait is critical only when combined with active swapping. Extract pure classification functions into a node-free shared module used by collector, tiles, and charts. Also specify every arm: `swap.none` is known absence, `swapActivity.skipped` is deliberate non-measurement, and neither is `unknown` or zero. Ensure historical disk-critical samples remain visible even though the proposed four graphs omit disk.

11. **Medium — synchronous persistence is on the wrong side of the present-tense UI.** A small `writeSync` is normally cheap, but dirty-page throttling or `fsyncSync` can block badly on the exact swapping box being monitored. “Append before publish” does not provide atomicity—append failure is caught, and history is fetched separately anyway. Use one serialized asynchronous writer, publish current health first, and await persistence outside the HTTP event loop. Per-sample `fsync` is unnecessary for disposable telemetry.

The sound decisions are: dashboard-side ownership, retaining the full report, JSONL, explicit `collector-failed`, inline SVG, gzip, no averaging/downsampling, and a visible fresh-history boundary.

I would cut the `refreshOnce` health-history changes by giving health its own loop, cut the query/window clamp while v1 has exactly one 24-hour window, and remove the causal phrase “nothing was running.” Update the standing ownership document before implementation rather than in Stage 4; it currently directs parallel work toward the opposite owner.

**Verdict: rethink the absence model, then build with the named changes. Do not build this plan as-is.**
