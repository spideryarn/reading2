Verdict: **agree it should stop**, but the plan’s central argument needs revision. Reusing SSE on `/advance` is a plausible sub-budget near-route; it fails because only the tab that wins the job claim receives that response. Making intermediate levels and the preferred-first level reliable across the existing multi-tab job model requires shared persistence or another subscription channel, crossing the brief’s boundary.

1. **P1 — Streaming `/advance` is not itself a new transport, but it does not reliably reach the waiting reader.** The server already has a generic SSE writer and heartbeat, while the client already has a generic framed-event reader ([src/routes.ts:1275](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/routes.ts:1275), [src/web/lib/sse.ts:93](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/web/lib/sse.ts:93)). `/advance` could emit a `level` frame after `writeLevel` returns and a terminal `done` frame, without adding a route, runner, or artefact shape. However, the store grants exactly one claimant; concurrent advances receive `busy` ([src/jobs.ts:2284](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/jobs.ts:2284)). Jobs are deliberately observable and driveable from another tab ([src/web/useStepJob.ts:236](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/web/useStepJob.ts:236)). Consequently, an inactive tab can own the SSE response while the visible Summary panel receives no intermediate levels. Fixing that needs shared fan-out—persisted progress, pub/sub, or a separate subscription transport. The plan should reject the near-route for this reason, not because SSE is novel.

2. **P1 — “Reader’s level first” is not merely a 20-line `FIRST_LEVEL` change.** The selected level exists only in the mounted client controller ([src/web/modes/summary/SummaryMode.tsx:80](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/web/modes/summary/SummaryMode.tsx:80)); the engine’s advance operation carries only a job id ([src/web/jobEngine.ts:172](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/web/jobEngine.ts:172)), and `Job` stores no requested Simple level ([src/types.ts:2999](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/types.ts:2999)). A request-local hint would work only when that tab wins the claim. Preserving the choice through another tab, retry, or claimant handoff requires a job field—precisely the new storage shape the brief forbids. This independently supports stopping.

3. **P2 — The estimates are aimed at the wrong cheapest route.** The separate Simple streaming route’s 550–700 lines are plausible because it duplicates admission, metering, cancellation, and committing. A claimant-only `/advance` SSE implementation would likely be nearer **250–400 lines including focused tests**, because framing and parsing already exist and the panel’s current gating is compact ([src/web/SimplePanel.tsx:64](/home/greg/code/spideryarn2/.claude/worktrees/summaries-show-each-level-when-checked/src/web/SimplePanel.tsx:64)). It still does not meet the multi-tab requirement above. A correct fan-out implementation would likely exceed the budget or add storage/transport, so the verdict remains unchanged.
