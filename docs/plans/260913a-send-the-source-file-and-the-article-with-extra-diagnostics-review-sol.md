Reviewed commit `9c79abc`. The plan file acquired an unrelated unstaged edit during the review; findings below concern the committed HEAD version.

- R1 — P0 — Attaching `ArticleMetadata` wholesale sends undisclosed reader-authored text to Sentry. HEAD proposes `{ metadata, article }` (`HEAD:docs/plans/…:39-41`), but `ArticleMetadata` contains the reader’s global profile and per-article purpose ([src/types.ts:2099](../../src/types.ts:2099)); the implementation explicitly fetches both ([src/store/pg.ts:2916](../../src/store/pg.ts:2916)). Neither is disclosed by the proposed wording, violating the report rule that every open value must be disclosed ([feedback.md:313](../../docs/project/feedback.md:313)). Fix: build a dedicated diagnostics object field-by-field—article plus only the necessary stage/timing/visibility facts—and assert profile and purpose sentinels are absent from the final envelope. The current unstaged plan edit already moves in this direction.

- R2 — P1 — The unchanged envelope guard can cross-wire two owners’ reports. Expectations are stored globally under `reportId` alone ([feedback-envelope.ts:133](../../src/feedback-envelope.ts:133)), and the guard selects and consumes them using only the event’s `report_id` ([feedback-envelope.ts:223](../../src/feedback-envelope.ts:223)). But IDs are client-minted and unique only per owner: the database key is `(owner_id, id)` ([schema.ts:3731](../../src/db/schema.ts:3731)). Concurrent reports from two owners using the same valid ID can therefore substitute one expectation—including the new article attachments—for the other and leave the second envelope empty. Fix: key registrations with a server-generated high-entropy mirror nonce placed temporarily on the event and removed during rebuilding. Add a concurrent same-ID/different-owner test with distinct attachment sentinels.

- R3 — P1 — The reader-facing wording promises more, and different conditions, than the implementation. A slug is supplied for every `read` route ([FeedbackButton.tsx:207](../../src/web/FeedbackButton.tsx:207)), including the `article`, `metadata`, and `tweets` views ([read-address.ts:76](../../src/read-address.ts:76)); therefore “send the report from any other page” does not prevent attachment from metadata or tweets. “It also sends” is also false when either cap is exceeded or no source exists. “The page as we showed it, including what we had made” is broader than `loadArticle`: glossary, ideas, quotes, timeline, quiz, diagrams, debate, and citations are separate reads ([store/index.ts:222](../../src/store/index.ts:222)). Finally, “no article text goes with it” is absolute even though an independently consented screenshot may contain anything on screen ([PrivacyPage.tsx:473](../../src/web/PrivacyPage.tsx:473)). Fix: say “on a page for one of your own articles, we may attach the available source file and the base article payload, within size limits”; say “we do not automatically attach article text otherwise”; explicitly exclude profile and purpose alongside notes/comments/chats.

- R4 — P2 — The size arithmetic is sound only if the 5 MiB cap is measured after UTF-8 encoding. The guard converts strings with `TextEncoder` only when constructing attachment items ([feedback-envelope.ts:337](../../src/feedback-envelope.ts:337)); checking `json.length` earlier would undercount non-ASCII article text by up to roughly 3×. Sentry’s current limit is 20 MB compressed, and oversized envelopes are rejected whole ([official Sentry attachment documentation](https://docs.sentry.io/platforms/javascript/enriching-events/attachments/)). The installed SDK serializes `Uint8Array` attachments as raw bytes ([envelope.js:36](../../node_modules/@sentry/core/build/esm/utils/envelope.js:36)) and gzips the whole request ([http.js:51](../../node_modules/@sentry/node-core/build/esm/transports/http.js:51)); there is no base64 expansion. With true byte caps, the worst-case raw budget is about 16.34 MB, leaving roughly 3.66 MB below Sentry’s decimal 20 MB limit even without assuming JSON compresses well. Fix: encode once, cap `byteLength`, attach those exact bytes, and test non-ASCII JSON plus the worst-case serialized/gzipped envelope.

- R5 — P2 — The proposed `SourceStore.readDocument` is unnecessary duplication. `ArticleReader.loadSource` already returns PDF or HTML bytes and kind ([contracts.ts:135](../../src/store/contracts.ts:135)), is already exported ([store/index.ts:232](../../src/store/index.ts:232)), owner-filters through `currentRevision`, and reuses the shared rehashing resolver ([store/pg.ts:2363](../../src/store/pg.ts:2363)). `readPdf` is intentionally narrower because serving HTML inline from this origin would be stored XSS ([routes.ts:542](../../src/routes.ts:542)). Fix: use `loadSource` directly and leave the HTTP-specific `SourceStore.readPdf` contract alone. If avoiding a full read before identifying `too_large` is required, add an optional cap/preflight to the existing raw-document path rather than creating another resolver.

The two main ownership checks otherwise hold: `mirrorFeedback` is started before `send` and awaited afterwards ([routes.ts:6230](../../src/routes.ts:6230)), all of it remains inside `runInRequest` ([routes.ts:6370](../../src/routes.ts:6370)), and `loadArticle`/`articleMetadata` both go through the unconditional `ownedSlug` predicate ([pg.ts:1211](../../src/store/pg.ts:1211)). Public visibility and administrator status provide no bypass. A lost owner context would not run unfiltered, though outside request scope it could fall back to the configured environment owner—another reason R2’s explicit nonce and a route-level lifetime test are worthwhile.
