## Findings

1. **P1 — The evidence proves the `[chunk]` failure, but not the plan’s claim that it is “the whole of” the report.** The two-build reproduction, MIME error, fresh-build control, and repeated `3H` events make the stale lazy chunk diagnosis convincing. However, `BJ` occurred only 78 seconds before the report and is a different app-level render failure; the missing-module reproduction does not produce it. Calling it “the same family” is inference, not evidence ([plan:18](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:18>), [plan:56](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:56>), [AppBoundary.tsx:45](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/AppBoundary.tsx:45>)). Build this confirmed fix, but change the plan to say it fixes `3H`; do not close the feedback as wholly resolved until `BJ` is identified or Greg confirms he saw `[chunk]`, not `[render]`. Deferring `BJ`’s root cause is otherwise honest.

2. **P1 — A commit is not a sufficient build identity.** The plan treats a different SHA as a different deployment and the same SHA as the same deployment ([plan:69](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:69>)). The existing stamp explicitly records that `deploymentId` is stronger because the same commit can be redeployed and yield different bytes ([scripts/build-stamp.ts:46](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/scripts/build-stamp.ts:46>)); `build.json` already contains that full stamp ([vite.config.ts:406](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/vite.config.ts:406>)), while the running client exposes only commit and build time ([build-stamp.ts:29](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/build-stamp.ts:29>)). Compare and store a unique build identity—preferably compiled-in deployment ID, with build time as the non-Vercel fallback—and add “same commit, different deployment” coverage. Also call it a *different live build*, not necessarily a newer one; rollback needs the same recovery.

3. **P1 — The asynchronous recovery can reload a page other than the one that failed.** `recover` waits for `/build.json` and then performs the global reload, but the plan has no cancellation or “still on this failed navigation” check ([plan:94](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:94>), [plan:98](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:98>)). A reader can leave the spinner using Back or the sibling home logo; the old request can then finish and reload the new article or form. Abort on unmount/route change, or check that the captured URL/navigation token is still current before writing the guard and reloading. Test a delayed check, navigation away, then resolution: no marker and no reload.

4. **P1 — The build check needs a timeout.** “Never throws” does not cover a fetch that never settles. Since the lazy promise is waiting on that fetch, a partial network failure can replace today’s actionable `[chunk]` message with an indefinite spinner ([plan:65](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:65>), [tests/lazy-page.test.tsx:211](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/tests/lazy-page.test.tsx:211>)). Give `/build.json` a short abort deadline and then rethrow the original loader error. Test a build check that never resolves.

5. **P2 — The state-loss conclusion is right for this boundary, but its stated reason is false.** These are not all “plain pages”: `/admin/vouchers` has unsaved creation and editing fields ([AdminVouchersPage.tsx:70](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/AdminVouchersPage.tsx:70>)), Help has a query ([HelpPage.tsx:177](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/help/HelpPage.tsx:177>)), Changelog has expanded-release state ([ChangelogPage.tsx:689](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/ChangelogPage.tsx:689>)), and feedback has a filter ([AdminPage.tsx:412](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/src/web/AdminPage.tsx:412>)). Nothing is lost because a top-level lazy loader failure happens before the destination component mounts. Rewrite [plan:89](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/docs/plans/261003m-a-home-screen-app-reloads-itself-when-a-page-s-code-has-moved.md:89>) around that narrower fact. Finding 3 must also be fixed for it to remain true.

6. **P2 — Specify an uncached build check.** `vercel.json` sets no cache rule for `/build.json` ([vercel.json:23](</home/greg/code/spideryarn2/.claude/worktrees/fbu6uba0-changelog-errors-on-ipad/vercel.json:23>)). Vercel currently defaults to `public, max-age=0, must-revalidate`, so this is not presently broken, but the recovery contract should use and test `fetch("/build.json", { cache: "no-store" })` explicitly. [Vercel documents the default here](https://vercel.com/docs/caching/cache-control-headers).

The React mechanism itself is sound once findings 3–4 are addressed: React 19 caches the lazy promise, and a pending promise keeps the Suspense fallback visible; a fresh lazy type on retry or `routeKey` retains the existing retry semantics ([React `lazy`](https://react.dev/reference/react/lazy), [React `Suspense`](https://react.dev/reference/react/Suspense)). StrictMode does not create a production loop.

`sessionStorage` is also the right guard: it is scoped to the current page session, survives reloads in that session, and storage refusal is safely handled by not reloading. Private browsing makes it ephemeral, not normally unavailable; a resumed surviving context retains it, while a genuinely closed session starts by loading the current shell. A real installed-iPad smoke check would still be worthwhile because desktop WebKit plus `navigator.standalone` does not emulate process restoration. Multiple lazy failures are safe: after a successful reload the shell matches; after an unsuccessful one the stored build identity makes later failures show the boundary instead of reloading again.

The proactive foreground check can remain deferred. There is no materially simpler design that preserves all three properties—automatic recovery, no reload for ordinary failures, and a bounded no-loop fallback.

**Verdict:** build it with changes.
