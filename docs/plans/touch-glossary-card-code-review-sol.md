## Findings

1. **Must-fix — long press and selection are still not reliably excluded.** `Press` records neither start time, `isPrimary`, nor whether a selection existed at `pointerdown`; `isTap` asks only at `pointerup` ([useHoverCard.ts:98](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:98), [useHoverCard.ts:409](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:409), [useHoverCard.ts:451](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:451)). Worse, `contextmenu` merely clears the still-pending press ([useHoverCard.ts:444](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:444)). The Pointer Events specification explicitly leaves `contextmenu` ordering undefined—it may follow `pointerup`—so an allowed sequence is: long press → `pointerup` opens or commits and arms the swallower → `contextmenu` arrives too late. Likewise, a tap that collapses an existing selection before line 455 becomes a term tap. The prior #1 asked for one primary pointer; that check is also absent. Store `isPrimary`, selection-at-down, and elapsed duration, and make a late `contextmenu` undo any action/arm. [Pointer Events § compatibility mapping](https://www.w3.org/TR/pointerevents/#compatibility-mapping-with-mouse-events).

2. **Should-fix — touch can leak through the keyboard-focus path and become a “desktop” open.** `focusin` is not gated against an active/recent touch ([useHoverCard.ts:566](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:566)). On a touch browser that focuses the enclosing `<a>`, `arm(anchor, 0)` may run during the press and explicitly set `byTouch = false` ([useHoverCard.ts:349](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:349)). A drag/cancel can then leave a card open because scroll dismissal only accepts `byTouch` ([useHoverCard.ts:508](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:508)). If focus arrives after the term opened, it can replace the mark anchor with its enclosing link, remove the armed styling, and turn the next tap into another reveal instead of commit. The test never generates focus or even `mousedown`, so the explicit term-inside-link case does not cover this.

3. **Should-fix — `currentRef` fixed consumer-close, but introduced stale state across the effect’s other closing paths.** Normal hover reads were converted consistently, and the returned `close()` correctly clears `currentRef`. But listener cleanup claims to close while only calling `setShown(null)` ([useHoverCard.ts:573](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:573)); the anchor-replacement observer does the same ([useHoverCard.ts:638](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:638)). If `selector`, `focusable`, or `tapSelector` changes while the node remains connected, the next tap on that closed mark is treated as a commit. Also, hovering the same touch-opened mark takes the early return without transferring ownership to the pointer ([useHoverCard.ts:339](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:339)), so a subsequent scroll still dismisses it. All immediate closing paths need one operation that clears `currentRef`, both touch flags, and state.

4. **Should-fix — several tests still prove their setup rather than the claimed invariant.**

   - The requested third sleeping mutation is replacing the running maximum at [useHoverCard.ts:430](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:430) with the latest distance. Every current test remains green because the only drag ends far away ([hover-card-touch.test.tsx:252](/Users/greg/Dropbox/dev/experim/spideryarn2/tests/hover-card-touch.test.tsx:252)). Add down → move far → move/up back at the origin, asserting no card and no commit.
   - The scroll test dispatches directly on `document` ([hover-card-touch.test.tsx:330](/Users/greg/Dropbox/dev/experim/spideryarn2/tests/hover-card-touch.test.tsx:330)); it still passes if capture is removed. Dispatch a non-bubbling scroll from a nested scroller.
   - The cleanup test dispatches through a detached orphan, so leaked document listeners never see it; its later body click begins with no armed swallow ([hover-card-touch.test.tsx:360](/Users/greg/Dropbox/dev/experim/spideryarn2/tests/hover-card-touch.test.tsx:360)). Deleting all listener removals can still pass. After unmount, tap a newly connected matching mark and assert its click is untouched.
   - No test covers a multi-term mark or `isPrimary`.

   The capture-phase `mouseup`/`click` test itself is good: moving those listeners to bubble phase genuinely exposes the React ancestor.

5. **Note — the commit contract works here but is hazardous as a generic hook API.** `onCommit` is optional, yet the hook arms and swallows before invoking it ([useHoverCard.ts:473](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:473)). A missing or non-closing consumer silently makes every later tap a swallowed no-op. `ProseHoverCard` handles the current cases correctly: a single term closes before acting; a two-term mark remains open, and third and later taps intentionally do nothing ([ProseHoverCard.tsx:181](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/ProseHoverCard.tsx:181)). If a committed mark is not replaced, `close()` clears it correctly and the next tap reveals again.

The `TAP_ATTR` ordering is sound: the touch ref is written synchronously before `setShown`, and the effect reads it after commit ([useHoverCard.ts:488](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:488), [useHoverCard.ts:600](/Users/greg/Dropbox/dev/experim/spideryarn2/src/web/useHoverCard.ts:600)). StrictMode does not invert that ordering; commit, re-annotation, and unmount all run the attribute cleanup. The remaining replacement problem is the stale `currentRef`, not a leaked attribute.

For the real compatibility sequence, `mouseup` reaches browser default handling but no React descendant; `click` is stopped and cancelled, so neither TableView nor the enclosing link acts. A physical mouse click cannot normally be eaten because its new `pointerdown` disarms first. `autoUpdate` does not emit scroll events; actual nested/programmatic scrolling, rubber-band events, and window resize can close the card, which is conservative but consistent with the stated policy.

The targeted suite passes: 19/19.

**Verdict: not ready to land — the long-press/selection ordering hole remains must-fix.**
