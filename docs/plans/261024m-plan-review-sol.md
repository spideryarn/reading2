**F3 — P1 — The database key is right, but the fingerprint and tab-cache specification can still serve stale text.**

Evidence: `(owner, article, work_id, block_id)` is appropriate. Work IDs deliberately survive reruns through the work’s dedupe key ([types.ts:5263](/var/tmp/spideryarn-worktrees/fbmxk20e-source-hover-dive/src/types.ts:5263)); semantic changes therefore belong in fingerprints, not the primary key. The plan’s list mentions entry, note, paragraph, gist, profile, prompt and model ([plan:81](/var/tmp/spideryarn-worktrees/fbmxk20e-source-hover-dive/docs/plans/261024m-citation-card-streams-a-note-on-what-this-paragraph-cites-the-work-for.md:81)), but omits other likely prompt inputs: work title/authors/year, note quotes and provenance, article title/byline, and citation words if supplied. `rowIdentity` cannot stand in for this: it deliberately excludes `why` and mentions ([citation-blurbs-identity.ts:9](/var/tmp/spideryarn-worktrees/fbmxk20e-source-hover-dive/src/citation-blurbs-identity.ts:9)). ### Verdict

The core product idea is sound only as an evidence-backed comparison: it can add something the existing paragraph and abstract note do not say separately, and therefore passes the link mode’s “not a generic gist” test. I recommend approving a narrower v1—fresh owner data, one work, one citing body paragraph, checked abstract evidence required, timer bound to the open card, separate cache/store, and no automatic full chat—after fixing the cache and prompt boundaries and adding a small quality/cost evaluation. The current plan should not proceed unchanged because its evidence-free fallback revives a deliberately removed product failure, its trigger can multiply spend on compound citations, and its question to Greg does not yet present the actual chat choices cleanly.
