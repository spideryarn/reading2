No P0 findings. I found two likely regressions and five smaller issues.

1. **P1 — Unavailable actions become silent on the wide touch card.**  
   On a coarse-pointer card, [`pressCapture`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/ShelfEntry.tsx:860) bypasses reveal for every action, without consulting the existing `commits` value in [`ActionTip`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/ShelfEntry.tsx:1400). An unavailable [`IconButton`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/IconButton.tsx:98) then swallows the click. The result is a faded icon that does nothing and never explains why—the exact case the existing test calls out at [`shelf-action-touch.test.tsx:215`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/tests/shelf-action-touch.test.tsx:215).  
   **Fix:** propagate `commits` as a data attribute and preserve reveal-on-first-tap when it is false; direct-commit only enabled actions. Add a `fingerRow + coarse + NO_URL` test.

2. **P1 — The enlarged Annotate close target overlaps Copy.**  
   The close target extends 6px in every direction at [`close.css:44`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/styles/close.css:44), but the two buttons have only `0.15rem` between them at [`dialogs.css:93`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/styles/dialogs.css:93). Because Copy precedes Close in the DOM at [`AnnotateDialog.tsx:253`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/AnnotateDialog.tsx:253), their hit areas overlap by roughly 4px and the later Close target can steal taps from Copy. This also affects mouse hit-testing on hybrid devices because the media query is `any-pointer`.  
   **Fix:** make the gap at least 6px—preferably 8px—or give Close a physical 44px box here. Add a browser hit-test between the two controls; the current size test cannot catch overlap.

3. **P2 — The re-fetch safety claim understates the behavioral change.**  
   The plan says re-fetch is “also one tap in the menu today” at [`plan:62`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/docs/plans/261002i-ipad-touch-targets-shelf-card-actions-on-the-bottom-row-bigger-close-crosses-a-visible-band-scrollbar.md:62). From a closed card it is currently two taps: open the trigger at [`ShelfEntry.tsx:1214`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/ShelfEntry.tsx:1214), then select re-fetch. The change makes an unlabelled icon immediately queue paid work.  
   **Fix:** state the real two-to-one-tap trade-off. Either deliberately accept it, or keep re-fetch reveal-first/menu-only while letting reversible and free actions commit directly.

4. **P2 — The tests do not reproduce the WebKit event the implementation is designed around.**  
   The new direct-path tests at [`shelf-action-touch.test.tsx:437`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/tests/shelf-action-touch.test.tsx:437) send a `touch` click, whereas the cited iOS bug produces a click whose `pointerType` is `mouse`. They also do not assert that a tooltip remains closed after the compatibility mouse-event sequence.  
   **Fix:** under `matchMedia("(any-pointer: coarse)")`, test a `mouse`-typed click, the unavailable-action case, and pointer-enter/mouse-enter/click followed by the tooltip delay. The implementation’s controlled tooltip does use `mouseOnly` at [`Tooltip.tsx:263`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/Tooltip.tsx:263), which Floating UI documents as ignoring touch and pen, so I found no definite stuck-tooltip bug—just a missing regression check. [Floating UI documentation](https://floating-ui.com/docs/usehover)

6. **P2 — `scrollbar-color` shipped in Safari 26.2, not iPadOS 26 generally.**  
   Both [`mode-band.css:29`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/src/web/styles/mode-band.css:29) and [`plan:91`](/home/greg/code/spideryarn2/.claude/worktrees/fb9e-9f-9g-ipad-touch-targets/docs/plans/261002i-ipad-touch-targets-shelf-card-actions-on-the-bottom-row-bigger-close-crosses-a-visible-band-scrollbar.md:91) infer shipping from the August 2025 WebKit landing. Bug 258461 does specifically implement the thumb colour for iOS’s overlay indicator, but Apple lists `scrollbar-color` as new in Safari 26.2. [WebKit bug 258461](https://bugs.webkit.org/show_bug.cgi?id=258461), [Safari 26.2 release notes](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)  
   **Fix:** say “Safari/iPadOS 26.2” and confirm Greg’s installed version. For 26.0/26.1, this remains only progressive enhancement and the proposed fade fallback is still needed. On desktop the declaration should not move layout because `scrollbar-width` is untouched; it only recolours inherited band scrollbars.
