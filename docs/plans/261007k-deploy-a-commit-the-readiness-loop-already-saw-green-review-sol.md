1. **P1 — Runner path does not prove preparation.** A green record from before these fixes still qualifies for 24 hours. So does a hand-run `readiness-run.ts check` in the runner after its corpus was modified; that wrapper never refreshes it. **Fix:** record versioned preparation evidence bound to the run ID and SHA. Require it for reuse, reject legacy records, and make every qualifying entry point perform preparation.

2. **P1 — Clean test rows can cover stale bundles.** `check.ts` continues after build failures. If B’s client build fails before the API build, the runner can retain A’s `api-dist/vercel.js`; its trace test can pass against A. `readinessVerdict` accepts clean test/typecheck rows despite that build failure. Deploy then builds B successfully and skips testing B’s bundle. **Fix:** require explicit clean prerequisite rows from `SUITE_BUILDS` in the same record, and remove old build outputs before building. Missing rows must refuse reuse.

3. **P1 — Dependencies can differ on precisely the older commits `--ready` selects.** Production A and green candidate B use lockfile L1; newer dev C uses L2, installed in the primary. Deploy compares **A→B**, sees no lockfile change, and symlinks the primary’s **L2** dependencies. B’s readiness pass used L1. Successful builds do not prove its tests pass with L2. **Fix:** install candidate dependencies, or share only an installation demonstrably matching the candidate’s dependency inputs.

4. **P1 — “Stricter environment” and 24-hour freshness do not establish equivalence.** For example, readiness inherits `SPIDERYARN_CHROME` pointing to a missing executable, so browser suites skip; deploy’s shell finds Chrome and would run them. Linking `.env.local` also does not prove its contents stayed unchanged since the pass. **Fix:** use one canonical child environment for both paths and record/compare an environment and toolchain fingerprint. Keep the shared-database limitation explicit; age alone cannot prove equivalence.

5. **P2 — Corpus refresh needs ordering and exclusion.** `tick` prepares the runner **before** checking whether a manual run is active. Adding deletion there could erase `data/` and `output/` underneath that run. Also, `materialiseCorpus` reports missing halves rather than throwing. **Fix:** refresh immediately before an admitted check, under exclusion shared with manual runs, and refuse incomplete materialisation.

6. **P2 — Ancestor counts require a proven chain.** Fast-forward-only dev updates make historical **dev tips** comparable; they do not make every ancestor comparable. A hand-run green record on a side branch in the runner can later become reachable through a merge and qualify under §2. Counts then cannot establish which candidate is newest by ancestry. **Fix:** attest that qualifying runs observed actual fetched dev tips, or compare candidates by ancestry and refuse incomparable candidates.

7. **P3 — Changelog and trunk reasoning are substantially right.** With fresh fetches and unforced gates, candidate membership, production ancestry and `notesAt(candidate)` retain the relevant protections. Pending notes deliberately allow later commits. The weakened freshness guarantee is the explicitly requested omission of newer dev work. **Fix:** add integration cases for missing notes, candidates behind production, and failed fetches; make the production fetch fail closed—its result is currently ignored.

8. **P2 — A simpler implementation would share the preparation/check recipe.** One versioned prepared-check command used by readiness and deploy avoids proving equivalence between two recipes. Requiring its complete successful record also avoids partial-table inference, at the cost of rejecting checks whose only failure was an extra gate such as `cycles`. The current table additionally omits deploy’s `.vercelignore` pruning. **Fix:** share that recipe, or rerun the bundle-dependent tests against deploy’s freshly built artifacts.
