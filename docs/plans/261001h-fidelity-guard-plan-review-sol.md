Verdict: the prompt and Luna choice are reasonable, but the current scoring and corpus design cannot yet support the build decision. No P0s; four P1s.

- **P1 — The scorer does not implement the stated hand adjudication.** Every alarm on an unlabelled paragraph is unconditionally counted as false, regardless of whether `alarmsReadByHand` says “real other fault”, “borderline”, or “false alarm” ([probe.ts:294](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:294)). The deliberately borderline `pidpost5/fuller/3` is therefore also treated as a clean output and any alarm as false. Make adjudication structured, report the three categories separately, and exclude borderline cases from binary rates.

- **P1 — Unreadable-answer accounting is internally inconsistent.** Fail-closed currently counts one unreadable level as a false alarm on every paragraph ([probe.ts:292](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:292)). On a later invocation it is automatically called again, then the last result replaces the unreadable one for recall and availability while both calls remain in cost ([probe.ts:237](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:237), [probe.ts:275](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:275)). Count an unreadable response as one level-level retry/failure, preserve the first operational outcome, and do not turn it into N paragraph false positives.

- **P1 — The labels are adequate only for descriptive recall on this exact PID fault.** The 30 positives are keyword-selected variants of one distinction, mostly against one passage; they are not 30 independent contradiction types. Unflagged, unlabelled paragraphs are never reviewed, so “false-alarm rate” rests on the presumption that they are faithful. Call this a PID challenge-set result, not general fidelity recall. For deployment evidence, add the existing Olah and Gwern outputs, hand-adjudicate every alarm, and blind-read at least a sample of unflagged paragraphs. Also report classifier recall among the 27 evidence-supported faults separately from end-to-end guard recall across all 30.

- **P1 — Detector accuracy alone does not establish that the guard improves the final summary.** Greg also needs the probability that a fresh writer attempt fixes a caught fault, introduces a new fault after a false alarm, or fails validation/checking and stores nothing. This matters because validation and the guard share only two attempts ([simple-summary.ts:654](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/src/simple-summary.ts:654)). Run a small paired retry sample, or at minimum model the final residual-fault and lost-output rates using the current-production arm. Include writer retry cost and latency, not only checker cost.

- **P1 — Pooled output-level rates will not represent production.** The corpus mixes obsolete pitches, profiles, prompt experiments v1/v2, and current wording. That is useful diversity for classifier recall, but not for expected retries or false alarms. Report challenge-set recall across everything, then operational metrics on the current shipped configuration separately. There are also **51 successful arms**, not 56: 56 files exist, but five failed and are skipped at [probe.ts:87](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:87). Those baseline failures belong in the availability comparison.

- **P1 — Sonnet cost and latency are not representative of the proposed build.** Borrowing `quiz-mark` is acceptable for a rough accuracy comparison, but it uses the chat wire, no cache breakpoint, provider-default reasoning, and a 2,000-token ceiling ([probe.ts:145](/home/greg/code/spideryarn2/.claude/worktrees/fidelity-guard-probe/scripts/probes/261001h-fidelity-guard-probe.ts:145)). A Messages implementation would use different adaptive-thinking, streaming, caching, and failure behavior. Measure Sonnet through the intended production request. Also do not assume caching helps: the present per-level cited-passage packets differ, and parallel calls cannot generally reuse a cache one of them is still creating. Luna’s borrowed route is substantially representative of a Luna build.

- **P2 — The checker prompt is fair.** Naming the abstract failure class is appropriate because that is the proposed production rule; it does not reveal “feedback” or the expected verdict. Its “unsupported is OK” rule is intentionally lenient and explains the three evidence-absent misses. Keep it unchanged for this measurement so prompt tuning does not consume the test set.
