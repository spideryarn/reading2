## Findings

- **C-1 — P0: Cancellation does not bound encoding or storage, so a hung blob operation can prevent the manifest being written.** The signal is checked only before `storeOne`; neither `encodeFigurePng` nor `storeRawSource` receives a signal or participates in a race (`src/collect-pdf-figures.ts:195`, `src/collect-pdf-figures.ts:231`, `src/collect-pdf-figures.ts:250`). If `head`, `putIfAbsent`, or the dedup read hangs, aborting the job changes nothing: `collectPdfFigures` never returns, overflow markers are never finalized, and the process can die without any entries. An abort during encoding can also still store that figure afterward. The existing abort test starts already aborted, while the storage test rejects immediately, so both remain green under this bug.

- **C-2 — P1: Markers disappear when the raw manifest is absent or says anything other than PDF.** `recoverPdfFigures` checks `manifest?.kind !== "pdf"` and returns before discovering the markers (`src/pipeline.ts:1589`). Thus an inconsistent revision containing valid markers but a missing/non-PDF raw manifest produces no `pdfFigures` at all, indistinguishable from “nothing to look at.” This directly contradicts the requested invariant that the `kind !== "pdf"` early return must not lose markers. This pipeline-level branch has no test.

- **C-3 — P1: PDF figures have no aggregate byte budget.** The collector limits marker count and individual PNG size, but `run.bytes` is only accumulated after storage and never consulted (`src/collect-pdf-figures.ts:155`, `src/collect-pdf-figures.ts:240`, `src/collect-pdf-figures.ts:267`). At the committed limits, one document can store roughly 100 × 16 MiB. This does not require lowering the settled 16 MiB per-figure cap; it requires enforcing the planned shared article budget and recording every remaining marker once it is exhausted.

- **C-4 — P1: Permanent and transient source failures are falsely recorded as timeouts and hidden from operators.** `PdfFigureFailure` defines `out-of-time` as the wall clock expiring (`src/assets.ts:194`), but `recoverPdfFigures` maps every `readRawBytes` failure—including missing or hash-corrupt objects and Storage outages—to that reason with no logged diagnostic (`src/pipeline.ts:1594`). `readRasters` likewise catches every PDF-reader exception (`src/collect-pdf-figures.ts:294`), and the `MAX_FIGURES` overflow uses the same reason (`src/collect-pdf-figures.ts:202`). The hash verification itself is sound; the catch path erases what it established.

- **C-5 — P2: Marker validation mishandles duplicated and oversized hostile values.** Both marker walks silently deduplicate identical refs (`src/assets.ts:397`, `src/collect-assets.ts:331`), so the production path can never reach Stage A’s duplicate-ref assertion; two elements can consequently consume one manifest entry and later display the same picture twice. Separately, the regex accepts arbitrarily long decimal fields and converts them without a safe-integer check (`src/assets.ts:374`). I verified that a 400-digit page parses as `Infinity`, which serializes as `null` in JSON. Ordinary generated markers cannot reach either case, and malformed/truncated strings otherwise return `null`, hence P2.

- **C-6 — P2: The freshness tests do not prove that changing a PDF ref changes the hash.** The principal test changes from zero markers to one marker (`tests/collect-assets.test.ts:1345`); replacing every parsed ref with one constant token would still pass it and the framing test through `tests/collect-assets.test.ts:1386`. The Postgres carry-forward fixture changes a web-image URL, not a PDF marker. Add a same-count marker-ref change—the actual “different PDF” case.
