1. The plan has no safe height budget for a card that cannot scroll. `SPINE_LIMITS` permits six outline rows; `BandCard` can also contain a three-line gist, five child rows, footer, and touch hint. The proposed explanation and wrapping key can add five or more lines—not “about three”—making the card exceed a 400–600px viewport. Floating UI has no `size` middleware here, and scrolling cannot work while the tooltip ignores pointer events. Define a compact short-viewport form and require a browser check at 400px height with the worst-case card, all marks, and the tap hint fully visible. Preserve at least the short explanation/key on touch; compact lower-priority section detail first.

2. The key must not become part of every band button’s accessible description. `Tooltip` connects the card through `aria-describedby`, so keyboard navigation could announce the same legend after dozens of section names. Make the repeated visual key `aria-hidden="true"`, or provide a separate once-per-rail description. Also fix `ariaFor`: it currently always says “search match(es),” although `matches` can represent Ideas, Timeline, or Referee passages. Pass source-aware count copy into `Spine` and test both the visible key and accessible description.

3. “The full legend stays on `/help/spine`” is currently false. The help page omits the left-edge quote strip and incorrectly says Quotes and Skim draw right-edge passage lanes. `railFound` deliberately removes their quote passages; `quoteRailMarks` draws them separately on the left. Expand the help edit to add the quote strip and name the actual lane producers: Search, a selected Idea, a selected Timeline event, and Referee passages.

4. A second exhaustive `mode -> marksLabel` switch does not provide the claimed compile-time guarantee. It catches a newly added `BandMode`, but not an existing mode such as Chat or Sources beginning to publish passages while retaining a stale generic label. Return the rail copy alongside the slot from the existing `selectPassages` switch—ideally an object containing legend and count wording—so passage selection, key text, footer/count text, and accessible names share one decision.

5. The key does not yet explain the base structural colour accurately. Every `.spine-part` uses `--depth-1`; the current part is merely brighter, and `.spine-here` is a stronger nested fill. A solid swatch labelled only “you are here” can imply that all tan means the current location, while part bands and section-boundary hairlines remain unexplained. Say explicitly that tinted bands are article parts/sections sized to the rendered prose, hairlines divide sections, and brighter tint marks the reader’s location. For the adaptive promise, derive lanes from actual `marks`, not merely `laneOrder(matches)`, and count back matter only when its rendered band has positive height.

6. `More in Help › Reading the spine` looks like a link but is deliberately inoperable and consumes scarce height. Keep the rail cards non-interactive—their scrubbing behavior depends on it—but either omit this line or write `See Help: Reading the spine`, only in the roomy card variant.

The search claim is correct. `useSearchMode` applies `keepAbove(ordered, gate)` to produce `results`; that same array reaches `Reader`, then `blockMatches(railFound(passages))`, then `Spine`. The list, prose, and rail therefore follow the Prioritised threshold together. Preserve the qualification that rail marks are per visible `(block, run)`, not per occurrence, and folded or missing rows are skipped. Add one regression test that changes the gate and observes the matches passed to `Spine` or the rendered `.spine-match` set.

Deferring the other-modes half is reasonable: those modes require separate product rules about selection, prose marking, and—in Chat—several simultaneous result cards.

Dark mode has no architectural blocker if swatches reuse existing tokens. The browser pass should still check both themes because these marks are tiny and translucent.
