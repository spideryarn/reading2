Verdict: **rethink before building**. The feature is sound, but the proposed bookkeeping does not yet provide its central “at most once” guarantee.

1. **P1 — Recovering a stuck send can send the same email twice.**  
   Evidence: [plan:42](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:42>), [plan:49](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:49>), [email.ts:129](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/email.ts:129>).  
   Resend may accept an email and then the request may time out or the process may die before the final database update. Ten minutes later the proposed recovery sends it again. The database guard governs who calls Resend, not what Resend already accepted.  
   Concrete change: give every delivery event a persisted ID and pass it as Resend’s `Idempotency-Key`; make the completion update compare that event/attempt ID, not merely `status = 'sending'`. Resend supports this specifically for retries and duplicate submissions, but retains keys for only 24 hours, so an ambiguous event must not be silently retried outside that window ([Resend](https://resend.com/changelog/idempotency-keys)).

2. **P1 — Retrying the create request creates a second voucher and a second email.**  
   Evidence: [plan:49](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:49>), [routes.ts:7200](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/routes.ts:7200>), [pg-vouchers.ts:259](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/store/pg-vouchers.ts:259>).  
   `gift_mail IS NULL` protects only a retry against the same voucher ID. A replayed POST inserts a new UUID, granting another allowance and producing another email. Awaiting Resend makes an ambiguous client/proxy timeout more likely.  
   Concrete change: make voucher creation idempotent with a client-minted request/voucher UUID or persisted idempotency key. Concurrent and later replays must return the original voucher after verifying the payload matches. Test a concurrent duplicate POST and a retry after the first response is “lost.”

3. **P1 — “Send again” permits a sequential double-click to send twice.**  
   Evidence: [plan:49](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:49>), [plan:95](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:95>).  
   The predicate allows every state other than a current `sending`, including `sent`. If request A completes before request B reaches its `UPDATE`, both win in sequence. The proposed test covers simultaneous contenders, not that ordinary timing. Six “latest status” columns also do not identify which explicit resend event they describe.  
   Concrete change: distinguish “retry this delivery” from “start a new delivery.” Refuse retry once that delivery is `sent`; when an address is corrected, create a new delivery generation with a new event ID. Require a client-minted idempotency key for each explicit Send again action, and test both concurrent and sequential duplicates.

4. **P1 — Falling back to `adminAddress()` can disclose private data to someone other than the creator.**  
   Evidence: [plan:17](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:17>), [plan:20](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:20>), [admin-accounts.ts:442](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/store/admin-accounts.ts:442>), [email.ts:176](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/email.ts:176>).  
   “Creator lookup unavailable” does not establish that the shared/configured admin address belongs to that creator. The fallback email would contain claimant and voucher information, plus the proposed private note.  
   Concrete change: do not send the claim notice when the creator cannot be resolved. Record a safe failure such as `creator address unavailable` and surface it on the page. If a shared-inbox alert is wanted, send only a content-free operational alert, not the claimant, voucher address, or note.

5. **P2 — Database-bookkeeping failures are promised away but not designed or tested end to end.**  
   Evidence: [plan:57](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:57>), [plan:91](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:91>), [after-response.ts:32](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/after-response.ts:32>).  
   The tests cover provider 500s and thrown `fetch`, but not failure of the reservation update or final outcome update. A reservation failure leaves nullable state indistinguishable from a legacy/not-started email; a final-update failure leaves `sending`, activating the duplicate-prone recovery. A claim reservation failure also has no stated retry trigger or claim-mail action.  
   Concrete change: define the meaning and UI for `NULL`, and add injectable tests for both database writes. Assert create still returns 201, claim remains committed and the billing summary succeeds, safe metadata is logged, and the page exposes an actionable state.

6. **P2 — Awaiting Resend in the create request is the wrong exception.**  
   Evidence: [plan:63](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:63>), [email.md:103](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/project/email.md:103>), [email.ts:46](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/email.ts:46>), [AdminVouchersPage.tsx:346](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/web/AdminVouchersPage.tsx:346>).  
   Whether the caller is an admin does not remove provider latency or ambiguous HTTP retries. The plan already has a `Sending…` state, and the existing page already has Refresh, so waiting up to ten seconds avoids little.  
   Concrete change: persist/reserve the delivery, return 201 immediately with `mail: "sending"`, and use `afterResponse`. The success line can say “Voucher created; email sending,” with Refresh showing the outcome. A short poll is optional, not necessary.

7. **P2 — The creator’s private note should not be copied into the claim email.**  
   Evidence: [plan:17](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:17>), [gift-voucher plan:99](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001m-gift-vouchers-for-free-articles.md:99>), [email.md:138](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/project/email.md:138>).  
   The note may contain sensitive context and is not needed to identify the claim; emailing it creates copies in Resend, forwarding infrastructure, and an inbox. The `/admin/vouchers` link already provides access to it.  
   Concrete change: omit the note’s contents. Say “Private note recorded; view the voucher” if useful, followed by the admin link.

8. **P2 — Multi-voucher claims need independent failure handling and a test.**  
   Evidence: [pg-vouchers.ts:141](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/store/pg-vouchers.ts:141>), [pg-vouchers.ts:156](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/src/store/pg-vouchers.ts:156>), [plan:97](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-voucher-emails/docs/plans/261001p-voucher-emails-to-recipient-and-creator.md:97>).  
   One usage read can claim several vouchers, but the plan tests only one notice. A single after-response loop that throws on the first bookkeeping failure could abandon every later notice.  
   Concrete change: queue one settled task per returned voucher ID, or use `Promise.allSettled`, and test two vouchers where the first notice fails while the second still sends.
