The UI direction is sound, but the server-side dismissal design should change before building.

F1 — High: dismissal storage and prompt size are unbounded. The proposed primary key creates one row for every distinct value, while the route accepts arbitrary owner-supplied values. Repeated POSTs can grow both the table and every later model prompt without limit, contradicting the current route’s bounded-input argument ([routes.ts](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/routes.ts:8260)). Per-value length caps do not bound row count. Prefer the simpler v1: keep capped dismissal identities in `localStorage`, alongside collapse state. If cross-device persistence is required, use one bounded row per article with a fixed maximum and never interpolate an unbounded list into a prompt.

F2 — High: sending dismissed text back to the model is a privacy regression and is especially unwise here. Search and lens words are derived from the profile, and the project explicitly says personal details may leak into them despite the prompt ([reader-profile.md](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/docs/project/reader-profile.md:254)). Dismissing an embarrassing or sensitive suggestion would then store precisely those words and resend them to OpenRouter on future calls—even after the reader changes the profile or reason. That defeats the existing `readFrom` invalidation, which drops stale suggestions when either input changes ([CommandBar.tsx](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/web/CommandBar.tsx:1682)). Do exact filtering after the answer, but do not show dismissed strings to the model.

F3 — High: the proposed Guide ordering does not meet the second quoted ask. “First among ordinary rows, after the suggestions block” still makes Guide the fifth selectable row beneath as many as ten wrapped lines. It can remain below the fold—the exact problem Greg reported. On an empty box, Guide should be the first row overall, followed by the collapsible suggestions block. This can be a display-only reorder so typed ranking remains unchanged.

F4 — High: a real dismiss `<button>` inside the existing `role="option"` is not a valid listbox interaction. The bar deliberately keeps focus in the combobox and uses `aria-activedescendant` ([CommandBar.tsx](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/web/CommandBar.tsx:2469)); an independently focusable button inside an option creates nested interaction, and its click will also activate the suggestion unless propagation is carefully blocked. The plan must choose an accessible structure before implementation. The least disruptive option is one option action, with an announced `Delete` shortcut and a pointer-only × hit area; if the × must be a separately focusable button, the popup needs a grid/composite pattern rather than a listbox. Dismissal should also be announced through a live status.

F5 — Medium: collapse needs explicit focus and active-row rules. A button outside the listbox is valid, but it needs `aria-expanded`, `aria-controls`, and an accessible count. Collapsing while a suggestion is active must move `aria-activedescendant` to Guide or the first remaining ordinary row; merely clamping the numeric index can make the same index activate a different command. Keyboard activation of the collapse button must either return focus to the combobox or define how arrows resume list navigation.

F6 — Medium: `(article, kind, value)` is mechanically plausible but semantically inconsistent with the existing provenance rule. A mode dismissal keyed only by `mode:quiz`, for example, suppresses Quiz forever on that article even after the reason for reading changes completely, whereas the current list is deliberately discarded whenever `readFrom` changes ([command-suggest.ts](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/command-suggest.ts:228)). Either scope dismissals to `readFrom`, or explicitly obtain the product decision that “never suggest this action again on this article” is intended. Also carry a first-class shared `SuggestionIdentity` into `ShownRow`; the current row shape retains only `why` and optional model words ([CommandBar.tsx](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/web/CommandBar.tsx:942)), so deriving identities later from encoded action row IDs would be brittle.

F7 — Medium: the optimistic write has no failure contract. “The row goes at once” can silently claim a permanent dismissal when the POST failed, after which it reappears next visit. Specify rollback plus a failure sentence, or read back and reconcile as the existing dismissal stores do. Given the small × and permanent cross-device effect, an Undo affordance would also be proportionate; “no undo” is an added product decision, not required by Greg’s report.

F8 — Medium: ownership inheritance is sound, but the plan lacks the tests that prove it. No `owner_id` is needed when writes use the `article_id` returned by `ownedArticleIdentity`; do not perform an owner check and then re-resolve the article through an unscoped query. Add explicit unauthenticated `401`, other-owner `404`, malformed/extra-field, cascade-delete, and arbitrary-value/bound tests. The current route’s ownership check is the correct pattern ([routes.ts](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/routes.ts:8251)).

F9 — Medium: export is not actually an open question. Existing exports already carry per-article reader preferences, including hidden glossary entries and stale-notice dismissals, so a server table must be added to the article-row snapshot, rollback export, bundle export, import/round-trip coverage, schema drift, and table-coverage registries. The plan’s conditional wording ([plan](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/docs/plans/261010u-bar-suggestions-capped-dismissable-collapsible-and-the-guide-at-the-top.md:61)) understates the implementation scope. A new action table must also satisfy the repository’s timestamp rule.

F10 — Low: the cap pipeline must be stated precisely: resolve currently drawable rows, remove dismissals, interleave, then take four. Current resolution can drop a mode that no longer exists or a lens when Chat is unavailable ([CommandBar.tsx](/var/tmp/spideryarn-worktrees/fbyf23zk-bar-suggestions/src/web/CommandBar.tsx:956)). Capping before either filtering step breaks the promise that dismissing one reveals the next and can draw fewer than four despite usable suggestions remaining.

VERDICT: rethink
