RETHINK

1. **[P1] The trigger can destroy the evidence before recording starts — plan:99–104; CommandBar.tsx:2494–2503.** Opening the command bar explicitly focuses its input, invoking the iPad keyboard; typing *probe* guarantees further keyboard interaction. That is precisely the mechanism suspected of causing—or repairing—the faulty viewport. Bug 218983 reports that another focus/dismiss cycle can restore correct geometry. Use a one-tap admin action outside a text field/modal, such as an admin-only Dock drawer row. Otherwise the claimed `start` sample is not reliably the original broken state. [WebKit 218983](https://bugs.webkit.org/show_bug.cgi?id=218983)

2. **[P1] The trace narrows the states but cannot “separate” all three — plan:105–115.** It can identify `scale < 1`, expose a reported pan, and show disagreement between exposed geometry and a fixed sentinel. It cannot always distinguish stale `visualViewport.height` from stale fixed-position layout state because both the sentinel and viewport values may share the same stale internal geometry. A compositor-only fault may leave every CSSOM number apparently correct. Say “classifies observable signatures,” and keep the screenshot mandatory. [WebKit 312149](https://bugs.webkit.org/show_bug.cgi?id=312149)

3. **[P1] `hit` does not establish painting disagreement — plan:114–115.** `elementFromPoint()` at the CSSOM rectangle’s midpoint compares hit-testing with CSSOM geometry, not with where pixels were painted; failure could also mean another element covers the dock. Record the tested point, returned signature, and `dock.contains(hit)`, but describe it only as a CSSOM/hit-test comparison. Painting still requires the screenshot.

4. **[P1] Settled samples need coalescing and capacity protection — plan:116–118; ViewportProbe.tsx:83–95,402–443.** Scheduling two timers after every visual-viewport resize can create hundreds of delayed rows during keyboard animation. Because the probe keeps the oldest 600 samples, these can exhaust the trace before the final state or `mark`. Debounce/coalesce the 300/1000ms samples, cancel superseded timers, and always reserve or admit `mark`. Strict Mode also currently records `start` twice because its effect setup runs twice; make initial recording idempotent.

5. **[P2] The sentinel belongs inside `.reader`, not portalled — shell.css:121–138; Reader.tsx:5784–5790.** `.reader` currently has no transform/filter/contain fixed-containing-block trap, and `overflow-x: clip` does not create one. Keeping the sentinel as an untransformed sibling of the Dock best measures the Dock’s ancestry; a body portal could conceal a future ancestor-specific fault. Add root/body rectangles, scrolling-element position and scroll/client heights; `clientHeight` alone is insufficient evidence about which geometry is stale.

6. **[P2] The blind re-anchor should still be declined — plan:73–87.** WebKit explicitly chose to place `bottom:0` above iOS 26’s floating controls, so a positive screen-space gap can be healthy. The plan should say “screen pixels exist below WebKit’s CSS fixed-position floor,” not that the CSS visible viewport necessarily extends there, and “affected iPhones,” not “every iPhone.” An iPad-only gate avoids that iPhone case but not stale measurements, compositor faults, or iPad browser-chrome variants, so no behavioral partial fix is justified yet. [WebKit 297779 comment 23](https://bugs.webkit.org/show_bug.cgi?id=297779#c23)

7. **[P2] Scope the row to a mounted probe — Reader.tsx:5790; Metadata.tsx:1541–1557.** The same Dock/CommandBar also appears on Metadata, where no `ViewportProbe` exists. Pass an explicit probe action only from Reader rather than deriving availability merely from “has article.” The module store plus `useSyncExternalStore` is otherwise appropriate; update params.ts:150–155 because “off costs nothing” becomes “one inert subscription.”
