## Findings

- **P0 — The proposed owner partition is not atomic and can cross accounts.** The plan says to export the owner lookup and record the owner from the “same `accessToken()` answer `apiFetch` uses” ([plan:77](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/docs/plans/261003d-preload-recent-shelf-articles.md:77>)), but `apiFetch` performs that lookup internally and may change owner again during a 401 retry ([api.ts:465](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/lib/api.ts:465>), [api.ts:512](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/lib/api.ts:512>)). A separate lookup can label B’s response as A’s during an account switch. `findArticle` also receives only a boolean, despite `useArticleAccess` already having the exact `readerId` ([access.ts:185](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/article/access.ts:185>), [access.ts:476](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/article/access.ts:476>)). **Change:** introduce an atomic `apiFetchWithOwner(): { response, owner }` using the actual initial/retry credential, and thread `readerId` through `resolveAccess`/`findArticle` for comparison. Do not export and call `accessToken` separately.

- **P1 — “Only a 200 counts” admits an old IndexedDB copy.** On transport failure, `apiFetch` deliberately returns a synthetic 200 marked `x-spideryarn-offline: copy` ([api.ts:676](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/lib/api.ts:676>), [api.ts:691](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/lib/api.ts:691>)). The proposed status-only check would put that stale copy into the supposedly fresh slot, despite offline being explicitly deferred. **Change:** accept only status 200 without the offline-copy header; cancel/discard the body otherwise.

- **P1 — A two-minute TTL does not justify the plan’s “free of staleness” claim.** The payload resolves the current revision and mutable article fields ([pg.ts:2687](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/store/pg.ts:2687>), [pg.ts:2717](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/store/pg.ts:2717>)); a job later publishes by moving `currentRevisionId` ([pg-revisions.ts:2331](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/store/pg-revisions.ts:2331>)). A job already running in another tab/driver, or a rename/archive/share there, changes the payload without this page’s counter moving. The reader can therefore see two-minute-old prose or metadata with no refresh. **Change:** describe this honestly as bounded staleness and reduce the TTL to roughly 15–30 seconds; also invalidate on observed job completion and avoid prefetching candidates with active jobs. Cross-tab invalidation would require `BroadcastChannel`/storage events if two minutes must remain.

- **P1 — Waiting for `liveArticlesLoaded` can miss the exact “back, then straight back in” case.** `useShelf` paints the current reader’s IndexedDB shelf first ([useShelf.ts:362](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/useShelf.ts:362>)), while `liveArticlesLoaded` becomes true only after the network shelf returns ([useShelf.ts:255](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/useShelf.ts:255>), [useShelf.ts:273](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/useShelf.ts:273>)). The article link can therefore be clicked before any prefetch is even issued. **Change:** start from the owner-partitioned cached shelf as soon as `articles` exists; the article GET itself is still live. Reconcile or refresh candidates when the live shelf arrives.

- **P2 — The exemption list is safe today, but broad prefixes recreate the future omission risk it claims to avoid.** Current same-origin writes use `apiFetch`, `fetchOk` delegates to it, and the one raw XHR uploads only bytes to object storage ([upload.ts:94](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/upload.ts:94>)); none of the named exemptions currently changes `loadArticle`. However, exempting all of `/api/chat/`, `/api/comments/`, or `/api/quiz/` would silently exempt a future payload-changing subroute. Existing cache code already uses an exact anchored matcher for quiz marking ([api.ts:922](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/lib/api.ts:922>)). **Change:** match exact method-plus-route shapes, especially only `POST /api/quiz/:slug/mark`, rather than prefixes. Initially exempt only `POST …/open` and reading-time; extra harmless invalidations are safer than a larger policy.

- **P2 — A prefetched request no longer obeys the article load’s abort contract.** The present request receives `load.signal` specifically so leaving stops the 150KB download ([access.ts:464](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/article/access.ts:464>), [access.ts:496](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/article/access.ts:496>)). The `live` guard prevents a wrong paint ([access.ts:241](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/src/web/article/access.ts:241>)), but awaiting a pre-issued response cannot be aborted by that signal. **Change:** store an `AbortController`, transfer/link it when a slot is taken, cancel superseded/expired slots, and cancel scheduled idle work on Library cleanup.

- **P2 — The tests can all pass while the feature never improves navigation.** The proposed tests exercise the slot module and `findArticle`, but not the Library trigger, idle scheduling, candidate ordering, superseded batches, offline-copy rejection, or the actual request count across shelf → article ([plan:103](</home/greg/code/spideryarn2/.claude/worktrees/fbj78fff-snappier-article-loads/docs/plans/261003d-preload-recent-shelf-articles.md:103>)). The plan also does not say that a new shelf batch clears old non-top-five slots. **Change:** add an integration test that paints a cached shelf, verifies the newest candidates are issued, navigates before the live shelf completes, and observes exactly one article GET; separately assert a new batch clears old slots and `leavingFetch` really advances the generation.

**Verdict:** Do not build the plan as written: the atomic-owner gap is a privacy blocker, and the offline-copy, external-mutation, and late-trigger cases contradict its freshness and effectiveness claims. IndexedDB ordering itself is sound—tickets are reserved before requests and reject retired or older commits—so prefetching through `apiFetch` adds no ordering hazard. The simpler v1 is one slot for the single most recently opened article, started as soon as the current reader’s cached or live shelf paints, with a 15–30-second life and exact exemptions only for open-count and reading-time writes. That captures the reported reopen case without the five-slot scheduler, broad exemption policy, or most of the lifecycle complexity.
