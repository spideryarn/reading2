1. **P1 — “Active days” includes days the reader was not active.** [`job_step`](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/store/pg-admin.ts:792) records delayed/background execution and is also used by command-line stage runs; the spend predicate measures cost attribution, not reader causation. `reader_arrivals` was [backfilled from every shared Auth account’s creation date](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/drizzle/20260930144303_reader_arrivals.sql:22), including accounts that may never have used Spideryarn. This can fabricate both an active day and `lastActiveAt`. Fix: exclude both sources from v1, label the remaining proxy “Recorded action days”, or defer the column until an approved, explicit foreground-activity ledger exists. Do not backfill that ledger from these five sources.

2. **P2 — The lifetime `ai_calls` aggregation is unbounded and unsupported by the current indexes.** [`count(distinct UTC-day)`](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/store/pg-admin.ts:716) must process every product call, while the existing indexes cover `(owner, started_at)` or `(scope, started_at)`, not owner plus the day expression. It also processes the site account before `mergeUsers` discards it. Fix: add an `EXPLAIN (ANALYZE, BUFFERS)` acceptance check on production-scale data and, if retained, a partial covering expression index on owner and UTC date for the accepted scope; exclude `SITE_OWNER_ID` in SQL. Otherwise defer Active days to a daily ledger.

3. **P2 — “Last 30 days” includes future-dated rows.** The filter has only `day >= UTC-today - 29` ([query](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/store/pg-admin.ts:723)), so clock-skewed or manually inserted future rows count. Fix: use the closed range `day BETWEEN utc_today - 29 AND utc_today`, deriving `utc_today` once, and test days −30, −29, today, and +1.

4. **P2 — `FailureKind` is not severity.** Its contract describes retryability and next action—`blocked` means unchanged retry will fail, while null means unclassified—not high/medium/low impact ([definition](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/messages.ts:47)). Fix: display “Defect”, “App configuration”, “Request refused”, “Retry may help”, and “Unclassified”; remove severity colouring. Introduce a separate severity field only if something actually records impact.

5. **P2 — The failure details are mouse-only.** The essential explanation is attached to unfocusable `<span data-tip>` cells ([implementation](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/web/admin-columns.tsx:385)); delegated cards deliberately ignore touch, and the tooltip contract says spans need separate screen-reader text. Fix: make the count a real button wrapped in a controlled `Tooltip`, supporting focus, Enter/Space, tap, Escape, and `aria-describedby`; provide equivalent screen-reader text for the Active-days and Reading cells.

6. **P3 — “Failed imports ever” actually counts retained failed job attempts.** Retry creates a new job and therefore another record, while article/account deletion removes records ([schema contract](/var/tmp/spideryarn-worktrees/fbshf45w-admin-users-engagement/src/db/schema.ts:3451)). Fix: label it “Failed import attempts” and state that retries count separately and deleted records disappear; remove “ever” from `AdminUser`.
