The overall approach is sound, but the plan is not ready to build unchanged. No P0 findings.

1. **P1 — The cards promise movement that can be a no-op on stale routes.** The proposed copy unconditionally says the article scrolls to the previous/next passage ([plan:69](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/plans/260930h-trajectory-info-button-on-the-controls-row-and-shortcut-keys-in-tooltips.md:69)). But missing stops are explicitly represented ([TrajectoryMode.tsx:651](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/modes/trajectory/TrajectoryMode.tsx:651)); stepping selects the adjacent stored stop, then silently returns `false` if its block is gone ([TrajectoryMode.tsx:491](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/modes/trajectory/TrajectoryMode.tsx:491)). The buttons are disabled only at positional endpoints ([TrajectoryPanel.tsx:310](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/TrajectoryPanel.tsx:310)), and the door likewise targets the immediate next stored stop ([trajectory-route.ts:154](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/trajectory-route.ts:154)). Fix: make buttons, keys and door share a destination calculation that skips missing stops, or expose availability and disable/omit the corresponding control. Add tests with a missing adjacent stop before writing categorical card copy.

2. **P2 — “Or press ←/→” and the new documentation overstate when the keys work.** The global handler refuses modified, repeated, already-handled, and text-entry keypresses ([keynav.ts:446](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/keynav.ts:446)); Reader also suspends navigation while the Dock drawer is open ([Reader.tsx:1113](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/reader/Reader.tsx:1113)). Hovering an arrow does not blur a focused text box, so tooltips.md’s claim that the guard is “always” satisfied while hovering is false ([tooltips.md:218](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/project/tooltips.md:218)). Fix: use “While reading, press ←/→” and describe the standard guards in the documentation. Test that an arrow does nothing from a focused input and works again after focus leaves it.

3. **P2 — The touch rationale is false for the chosen uncontrolled tooltips.** The plan rejects `title` partly because touch cannot read it, but says only the sparkline and info cards remain controlled ([plan:75](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/plans/260930h-trajectory-info-button-on-the-controls-row-and-shortcut-keys-in-tooltips.md:75)). `Tooltip` makes touch hover mouse-only only for controlled cards ([Tooltip.tsx:182](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/Tooltip.tsx:182)); the repository already documents that an uncontrolled control card cannot be read on a phone because the same tap performs the action ([Dock.tsx:2894](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/Dock.tsx:2894)). Here a finger still steps immediately; the card may transiently open and close but is not readable. Fix: state that these are hover/focus cards and deliberately keep one-tap stepping. Do not add reveal-then-commit merely to expose keyboard advice on a device without those keys.

4. **P2 — Shrinking the info target to 28px is unnecessary.** Using the plan’s own measurements, changing the two gaps from about 11px to 6.4px and reducing the three depth buttons’ side padding saves about 24px: roughly `390 − 24 = 366px`, already inside the 377px head. The additional 8px target reduction and tighter label/count spacing are not needed ([plan:41](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/plans/260930h-trajectory-info-button-on-the-controls-row-and-shortcut-keys-in-tooltips.md:41)); today the info button deliberately uses the 36px house token ([trajectory.css:103](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/styles/trajectory.css:103)). Fix: keep it 36px wide and keep the label/count gap unless browser measurement proves otherwise. The non-wrapping end group is the part that solves longer routes.

5. **P2 — The tooltip placement and card styling need to be specified.** `Tooltip` defaults to `placement="right"` and `keepSide={false}` ([Tooltip.tsx:133](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/src/web/Tooltip.tsx:133)), which would put an arrow’s wide card across neighboring controls. The documented row idiom is `className="tip-soon"` plus `keepSide` ([tooltips.md:163](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/project/tooltips.md:163)). Fix: explicitly prescribe bottom placement for the head arrows, top for the prose door, `keepSide`, and `className="tip-soon"`.

6. **P2 — The promised interaction/layout tests are incomplete.** The plan says hover and focus will be tested, but the proposed tests exercise hover only ([trajectory-panel.test.tsx:987](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/tests/trajectory-panel.test.tsx:987)). They also use the first tooltip in the document without asserting only one exists, despite the documented stale-card trap. The browser matrix omits the one-depth and phone cases while claiming “any width” ([plan:120](/home/greg/code/spideryarn2/.claude/worktrees/fb73-trajectory-controls-row/docs/plans/260930h-trajectory-info-button-on-the-controls-row-and-shortcut-keys-in-tooltips.md:120)). Fix: test focus, focus retention and the Previous→Back-to-stop-1 content change; assert exactly one card; browser-check five-stop, maximum sparkline, one-depth, 288px band, and a narrow phone.

What does check out: for a valid stop, ← on stop 1 really revisits stop 1; the end-group idea prevents an orphaned info button across supported widths; mixing controlled and uncontrolled tooltips inside one `TooltipGroup` is sound; and `tooltips.md` is the right single home, with `keyboard.md` and `icons.md` as signposts. The disabled end-of-pass › and broader shortcut sweep are reasonable deferrals; the disabled button has no active → shortcut in that state anyway.
