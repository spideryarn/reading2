The plan should not be built unchanged. I found no P0, but five P1 issues and two P2 gaps.

### Findings

- **F1 — P1 — Established: `next` bypasses the existing freshness and one-use contract.**  
  The plan makes the signed-in `/login` branch navigate directly to the URL’s validated `next` ([plan](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/plans/261001m-a-sign-in-page-of-its-own-signposted-from-the-signed-out-pages.md:78)). Unlike `auth-return`, that value never expires and is not consumed ([auth-return.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/auth-return.ts:25)). A signed-in reader opening an old or shared `/login?next=…`, or an abandoned login tab receiving a later auth event, is redirected by a return destination unrelated to a fresh attempt. Immediate OAuth/sign-up failures also currently leave a remembered destination behind ([SignInControls.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/SignInControls.tsx:91), [SignInControls.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/SignInControls.tsx:130)).  
  **Fix:** Treat URL `next` only as a candidate. When the reader actually submits an auth attempt, write the validated candidate through the existing timestamped store. Have signed-in `/login` consume that one-shot value with `takeReturn`, falling back to the shelf. Add `forgetReturn()` and call it on every returned or thrown initiation failure. Test an already-signed-in visit, expiry, failed attempts, password success, and immediate-session sign-up.

- **F2 — P1 — Established: email confirmation in a new tab does not preserve `next`.**  
  The plan claims every deep-link CTA still returns the reader to the article ([plan](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/plans/261001m-a-sign-in-page-of-its-own-signposted-from-the-signed-out-pages.md:89)), but sign-up stores the destination in `sessionStorage`, which does not cross tabs. The existing pricing flow explicitly documents this limitation ([PricingPage.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/PricingPage.tsx:521)). A confirmation opened in a new tab therefore lands on the shelf.  
  **Fix:** For the simple version, keep the bare callback security property, qualify the guarantee as same-tab only, and make the confirmation message tell the reader to return to the original tab. If cross-tab return is required, design a separate opaque, expiring server-side return token; do not quietly put a raw destination into the callback URL.

- **F3 — P1 — Established: callback failures send “back to the sign-in screen” to a page that will no longer contain sign-in controls.**  
  `AuthCallback` labels its recovery action “back to the sign-in screen” but navigates to `/` ([AuthCallback.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/AuthCallback.tsx:276)). Once the landing form is removed, that action leads to the marketing homepage.  
  **Fix:** For unsigned callback failures, navigate to `LOGIN_HREF`; retain the shelf destination for the signed-in failure state. Add assertions for both branches to `auth-callback.test.ts`.

- **F4 — P1 — Reasoned: Create account can bypass the promised password validation.**  
  Today sign-up is a `type="button"` invoking `signUp` directly, outside native form submission ([SignInControls.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/SignInControls.tsx:308)). Merely retaining `required`, `minLength`, and adding “At least 8 characters” will not stop an empty or short password if this structure survives. The proposed test only checks that `signUp` is called.  
  **Fix:** Make both tabs submit the same form through an `onSubmit` handler that dispatches by tab, with a real submit button. Test that empty/short credentials do not call either Supabase method, and that valid Enter-key submission calls the correct method.

- **F5 — P1 — Reasoned: the page heading cannot “follow the tab” through the proposed API.**  
  The plan gives `SignInControls` only `initialTab` and `returnTo`, while requiring a heading owned by `SignInPage` to change when the internal tab changes ([plan](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/plans/261001m-a-sign-in-page-of-its-own-signposted-from-the-signed-out-pages.md:72)). No state seam connects them, and the tests omit the heading.  
  **Fix:** Lift the tab state into `SignInPage`, or add an explicit `onTabChange` callback. Test the heading on initial `?new` load and after both switch presses.

- **F6 — P2 — Established: the reason given for retaining the pricing form is false.**  
  The plan says moving the pricing panel would require new work to carry the chosen tier through `/login` ([plan](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/plans/261001m-a-sign-in-page-of-its-own-signposted-from-the-signed-out-pages.md:100)). That machinery already exists: `rememberBuyIntent` stores an expiring, tab-scoped marker ([buy-intent.ts](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/buy-intent.ts:109)), and the signed-in pricing page consumes it before checkout. Navigating through `/login?next=/pricing` neither loses the marker nor lets the URL authorize a purchase.  
  **Fix:** Prefer one sign-in location: have paid-plan presses store the existing marker and navigate to `/login?next=/pricing&new`; the free CTA navigates without a marker. Update the pricing test to assert marker plus navigation rather than marker plus inline panel. If the inline form is retained for conversion reasons, state that product reason instead of claiming missing transport machinery. The top-bar **Sign in** going to `/login` is otherwise correct.

- **F7 — P2 — Established: the documentation scope is incomplete and repeats an obsolete reset model.**  
  The plan omits `security-map.md`, whose authoritative row currently says returns are only ten-minute `sessionStorage` values ([security-map.md](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/project/security-map.md:93)), and `marketing-pages.md`, which inventories sign-in panels on both landing and pricing pages ([marketing-pages.md](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/docs/project/marketing-pages.md:24)). It also repeatedly calls `/login` the password-reset landing, but recovery is rendered directly by `AuthCallback`; `SetNewPassword` documents that it is not a route ([SetNewPassword.tsx](/home/greg/code/spideryarn2/.claude/worktrees/fb-sign-in-page/src/web/SetNewPassword.tsx:1)).  
  **Fix:** Add both authoritative docs and the relevant `AuthCallback` copy/header to the plan. Correct the description of `/login`, and keep the recovery callback test in the acceptance suite.

The proposed same-origin validator and bare `/auth/callback` preserve the open-redirect and one-time-code protections. The bare `?new` flag is also acceptable; `?tab=create` is clearer but not materially safer.
