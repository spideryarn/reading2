BUILD WITH CHANGES

### P0

None.

### P1

1. **“Upgrade” currently means “entitlement appeared,” which includes non-upgrades.** The proposed predicate treats every non-entitled status as free, so `unpaid → active`, an unknown status becoming `active`, or the start of a `trialing` subscription can be reported as a plan upgrade. It can also report an `active` subscription whose period is stale: `chooseSubscription` deliberately stores such a subscription for diagnosis, while the real entitlement function calls it stale ([plan:63](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/plans/260930i-email-admin-on-sign-up-and-plan-upgrade.md:63), [tiers.ts:88](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/tiers.ts:88), [subscription.ts:327](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/subscription.ts:327), [pg-billing.ts:316](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/store/pg-billing.ts:316)). `incomplete → active` is correctly detected, as is a first sync directly to `active`. Refine the state machine or explicitly rename the event to “paid entitlement began”; add cases for `trialing`, `unpaid → active`, stale periods, cancellation/resubscription, and `incomplete → active`.

2. **The promised email address is unavailable on the upgrade path.** The plan says upgrade mail includes the reader’s address ([plan:55](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/plans/260930i-email-admin-on-sign-up-and-plan-upgrade.md:55)), but `syncSubscriptionFromStripe` has only the owner ID and billing columns. Production’s `spideryarn_app` role is deliberately unable to read `auth.users` ([database.md:963](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/project/database.md:963), [admin-accounts.ts:9](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/store/admin-accounts.ts:9)), and Stripe customers are created without an email ([checkout.ts:438](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/checkout.ts:438)). The simpler fix is to send the account ID, tier names, and a link to `/admin`; do not add an Auth Admin API lookup solely for this mail.

3. **Putting the reader’s address in mail creates a retained copy the privacy change does not fully cover.** `hello@` is forwarded elsewhere ([email.md:19](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/project/email.md:19)), so the address and account event would persist in Resend, forwarding infrastructure, and the final mailbox. The privacy page currently enumerates what survives account erasure without mentioning administrative email ([PrivacyPage.tsx:550](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/web/PrivacyPage.tsx:550)). Either omit the address—preferred—or document the additional recipients, retention, and deletion procedure. Adding Resend to the subprocessor list is necessary regardless.

### P2

1. **The lock gives at-most-one notification attempt per stored transition, not reliable delivery.** All three callers converge on the locked read/write ([sync.ts:210](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/sync.ts:210), [webhook.ts:341](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/webhook.ts:341), [checkout.ts:665](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/checkout.ts:665), [admission.ts:216](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/admission.ts:216)). Therefore redelivery or caller races do not send twice. But a crash after commit, timeout, or Resend failure permanently loses the notice because the stored state already advanced ([plan:69](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/plans/260930i-email-admin-on-sign-up-and-plan-upgrade.md:69)). That is acceptable only if the requirement is explicitly “best-effort notification,” as the plan currently chooses.

2. **The route hook is editing a defence and can add up to ten seconds before dispatch.** `src/routes.ts` is explicitly listed as owning the one authentication gate ([security-map.md:77](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/project/security-map.md:77)); the insertion point is directly between `requireUser` and authenticated dispatch ([routes.ts:6724](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/routes.ts:6724)). Treat it as a defence edit and test that public routes, webhooks, and failed authentication never reach `noteArrival`. Prefer awaiting the notification after `serveAuthenticatedApi` has written the response, so Vercel remains alive without making the reader wait for Resend.

3. **The ledger is sound, but the migration/test details should be explicit.** The primary key plus `ON CONFLICT DO NOTHING RETURNING` correctly deduplicates across instances. Production migrations run as `postgres`, which can read and reference `auth.users` ([database.md:1025](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/project/database.md:1025)); local/private test databases contain `auth.users` ([db-test-create.ts:161](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/scripts/db-test-create.ts:161)). However:

   - The Auth FK must be appended by hand and added to the `pg_constraint` drift test; it must not be declared in Drizzle’s TypeScript schema ([schema.ts:27](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/db/schema.ts:27)).
   - Private test accounts are seeded after migrations, so merely running the migration there does not exercise the backfill ([private-db-global.ts:14](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/tests/setup/private-db-global.ts:14)). Add a focused backfill test.
   - Add IDs to the in-process `Set` only after the insert or conflict result succeeds; caching before a failed query would suppress retries for that instance.
   - The claimed migration/deploy gap is misstated: a user created after the backfill is not backfilled and will be noticed on their first request after deployment. Only users already visible to the backfill are intentionally classified as existing ([plan:98](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/plans/260930i-email-admin-on-sign-up-and-plan-upgrade.md:98)).

4. **`VERCEL_ENV === "production"` is the right default gate, but the override is a real dev-send path.** It matches the repository’s established production distinction ([stripe.ts:68](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/src/billing/stripe.ts:68)); Preview and ordinary local/test runs remain blocked. `SPIDERYARN_EMAIL_SEND=1` deliberately bypasses it, so “only production sends” is not literally true. Vitest currently scrubs secret values, but its network tripwire blocks Stripe, not Resend ([scrub-secrets.ts:120](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/tests/helpers/scrub-secrets.ts:120), [provider-guard.ts:194](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/tests/setup/provider-guard.ts:194)). Add `api.resend.com` to that tripwire and refuse the override when `NODE_ENV === "test"`.

No materially simpler architecture preserves fleet-wide sign-up deduplication: the small ledger is appropriate, and an outbox would need draining machinery the project does not have ([cron-scheduler.md:5](/home/greg/code/spideryarn2/.claude/worktrees/fb6t-admin-signup-email/docs/project/cron-scheduler.md:5)). The main simplifications are omitting the reader’s address and moving the awaited send off the reader-visible part of the request.
