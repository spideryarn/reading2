1. **P1 — The query widens a security boundary and keys on an identity that can be reused.** The plan deliberately aggregates every owner’s rows for any supplied slug (`docs/plans/260930f-article-cost-on-the-metadata-page.md:45-53`), but the admin contract says identifiers must not be followed into articles and “which articles they are” must remain inside the owner’s session (`docs/project/admin.md:195-198`, `docs/project/admin.md:229-245`). `security-map.md:53-56` explicitly treats that narrow exception as a defence. Slugs are unique only among current rows (`src/db/schema.ts:151-164`); the schema anticipates renaming (`src/db/schema.ts:166-184`), deletion removes the row (`src/store/pg-shelf.ts:509`), and the store explicitly discusses a slug being recreated (`src/store/pg-revisions.ts:680-689`). The public surface is read-only (`src/public/routes.ts:450-491`), so the claimed paid “visitor’s chat” does not currently justify cross-owner aggregation. **Fix:** resolve the slug through the existing owner-scoped article lookup, return 404 for missing/foreign articles, and query primarily by the current immutable `article_id`. If null-id rows must be recovered, include only `(owner_id, article_slug)` rows newer than that article row’s creation time. Add a two-owner negative test and a delete/recreate-same-slug test.

2. **P2 — The attribution machinery does not eliminate the omission class it claims to eliminate.** The only two known misses are exact routes—link summary and transcription (`docs/plans/260930f-article-cost-on-the-metadata-page.md:26-35`)—but the required field applies only to `PatternAuthRoute`; exact routes remain manual. `PatternAuthRoute` also cannot prove that `"none"` was the correct declaration (`src/routes.ts:6907-6912`). Make attribution required on every `AuthRoute`, with explicit variants such as capture-derived, handler-derived, and none; require the two exact routes to declare handler-derived attribution. Keep `slugPart` and ownership checks unchanged: they are security defences (`docs/project/security-map.md:87-90`). The wrapper itself is otherwise safe: it returns the handler’s original value or promise and only overlays async-local metadata (`src/ai-spend.ts:830-839`), while dispatch still awaits it (`src/routes.ts:9332-9343`), so errors, statuses, ordering, and streaming lifetime should be preserved. Treat the metadata strictly as accounting—not authorization—and test that a foreign slug causes no paid call.

3. **P1 — The paid check cannot prove its stated assertions through `spendForArticle`.** The proposed aggregate groups by scope, purpose, and step, not wire, and does not return individual `article_slug`, `wire`, `cost_source`, or `outcome` values; the existing aggregate shape demonstrates that limitation (`src/store/ai-calls-spend-pg.ts:88-121`, `src/store/ai-calls-spend-pg.ts:228-249`). Consequently, “exactly one persisted row per wire” and “each persisted row is provider-priced” cannot be established from that query; checking those fields only in `collectSpend`’s in-memory report could pass while persistence corrupted them. **Fix:** read the persisted rows independently by the collector’s unique `runId`, assert exactly three rows and the complete wire/source/outcome/scope/owner/slug tuple, then separately assert the admin aggregate equals those persisted rows. Also assert no pending calls. Use `EVAL_OWNER_ID`, verify it exists before spending, and print the database target. `scopeKind: "eval"` is safe for pricing: `costCategoryOf` classifies it as non-product (`src/cost-categories.ts:291-293`) and `/admin/users` filters to request/job-step scopes (`src/store/ai-calls-spend-pg.ts:269-286`); it will still appear intentionally in `npm run cost`’s Eval and raw breakdowns (`scripts/ai-cost.ts:1515-1558`).

4. **P2 — The 5.5% copy describes the wrong total.** The displayed total adds OpenRouter credits, BYOK upstream spend, and computed spend, but the purchase fee applies only to the credits pocket (`docs/project/ai-gateway.md:579-583`). Saying “these are OpenRouter credits; cash is about 5.5% more” over the combined total is false. **Fix:** either label the total “ledger estimate” and say the uplift applies only to its OpenRouter-credit portion, or calculate a separate cash estimate as `credits × 1.055 + BYOK + computed`, sharing and testing the existing `cashNanos` rule.

5. **P2 — The honesty markers still leave two material shortfalls invisible.** A sink failure creates no ledger row (`src/ai-spend.ts:1037-1044`, `src/ai-spend.ts:1109-1119`), and unscoped or late calls exist only as process counters (`src/ai-spend.ts:762-787`); an article query cannot count either. The aggregate also merges successful, failed, and aborted calls, whereas `npm run cost` explicitly reports non-success spend (`scripts/ai-cost.ts:1541-1550`). **Fix:** add a fixed disclaimer that this is recorded, attributed spend and cannot quantify failed writes/unscoped calls; aggregate and display `nonOkCalls` so retries and failed generation spend are visible. Test both with non-zero controls.

6. **P3 — The new lifetime lookups have no supporting index.** The append-only `ai_calls` table indexes owner/time, job, and scope/time, but neither article slug nor article id (`src/db/schema.ts:3021-3032`). The realtime article lookup is similarly unindexed. Both metadata queries therefore become full-ledger scans. **Fix:** add indexes matching the corrected predicates, preferably `ai_calls(article_id)` and `realtime_sessions(article_id)`; retain a slug index only if a justified fallback remains.
