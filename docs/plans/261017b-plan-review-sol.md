1. **F1 — P1 — established.** The measurement’s counts do not match its evidence. [The investigation claims 25 forbidden, 6 stubs, 6 imports, and 31 refusals](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/investigations/261017a-which-refused-paper-links-have-a-free-copy-the-server-can-read.md:38), and the [plan repeats those numbers](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:20). Running `jq` over `results2.json` gives **23** `fail:forbidden:403`, **6** stubs, and **8** normal HTML imports: **29**, not 31, refused. Of those, 15—not 18—have `oaStatus: closed`. Fix: derive the table mechanically from `results2.json`, make its categories exhaustive, and change every downstream denominator to 29, including “6 of 29”.

2. **F2 — P1 — established.** “Only six have a full text the server can read”, “nothing automatic will ever reach” the closed rows, and “about one refused link in five” are not conclusions this measurement supports. The sample was deliberately assembled roughly half OA and half closed rather than drawn from reader refusals ([investigation:16–25](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/investigations/261017a-which-refused-paper-links-have-a-free-copy-the-server-can-read.md:16)), so 6/29 is not an estimated user success rate or a demonstrated upper bound. More importantly, the seven OpenAlex repository candidates were never fetched: [epmc.ts retains only each repository’s display name](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/investigations/261017a-evidence/epmc.ts:16), while [probe.ts fetches only the publisher URL and Europe PMC XML](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/investigations/261017a-evidence/probe.ts:22). Licence and manuscript/version status were not recorded either, so “publisher’s own text, CC BY” is also unmeasured. Fix: state the narrow result—“Europe PMC’s fixed XML endpoint recovered 6 of 29 refusals in this constructed sample”—and either fetch and classify the repository candidates through the guarded path or leave broader A coverage unknown. A also need not widen the core `DocumentKind` union: a fixed-host, capped Europe PMC XML fetch followed by JATS→HTML conversion is the smaller future design, though it still edits `src/fetch.ts` and therefore remains outside this run.

3. **F3 — P1 — established.** Keeping an existing `<base>` verbatim breaks valid pages whose base is relative. The plan explicitly says [an existing base is kept](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:114), but an uploaded document has no JSDOM URL; [sourceDom documents that only a resolvable base works in that case](/var/tmp/spideryarn-worktrees/refused-site-open-copy/src/extract.ts:741). A direct run through `readArticle(html, null)` produced `https://wall.example/assets/figure.png` for an absolute base but left `figure.png` relative for `<base href="/assets/">`. The sanitiser is not the problem—the base has already done its work before Readability. Fix: capture the live page’s effective `document.baseURI`, remove existing base elements from the clone, and prepend exactly one absolute `<base href="…">`. Test relative, absolute, absent, and multiple bases through `url: null`.

4. **F4 — P1 — established.** The draggable link will perform the bookmarklet on Spideryarn itself when clicked or keyboard-activated, downloading the failed add page rather than merely installing the bookmark. The plan deliberately bypasses React’s `javascript:` refusal by assigning `href` after mount ([plan:124–127](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:124)); the app has [no CSP that would stop that execution](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/project/security.md:1308). The constant source means this is not an injection vulnerability, but it is wrong user-visible behavior. Fix: prevent ordinary and keyboard activation while preserving drag installation, give the control explicit installation semantics/instructions, and test that clicking creates no Blob or download while dragging retains the `javascript:` URL.

5. **F5 — P2 — established.** The proposed challenge counterfactuals cannot prove what the plan says. It promises that each captured page with one recogniser half removed “is an article” ([plan:94–96](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:94)). A direct run through base-commit `readArticle`/`runExtract` showed Springer/JSTOR remain `TooLittleTextToRead` and IEEE remains `ReadabilityRefused`; removing recogniser markup cannot make them articles. The Client Challenge’s second half is also left as “exact pair settled from the captures”, although that pair is the false-positive boundary. Fix: specify the exact structural predicates in the plan; parse raw `src`/`href` attributes against a dummy base so root-relative uploaded copies work; assert `challengeIn === null` with either half removed; separately put each half and both halves into a substantial real-article control; and test that `ChallengePage` wins over the existing generic refusal. JSTOR and Springer are byte-identical, so one corpus fixture is sufficient, with both observed hosts documented.

6. **F6 — P2 — reasoned.** “The file is an ordinary upload, sanitised like any other” understates the privacy boundary. The extracted artefact is sanitised, but [the decoded raw HTML is retained in the sources bucket](/var/tmp/spideryarn-worktrees/refused-site-open-copy/src/fetch.ts:281). A rendered signed-in page can contain account chrome, hidden form fields, CSRF values, drafts, or other personalised DOM outside `<script>`; the earlier question already records this exact concern ([q-fp8tqr:28](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/user-feedback/questions/q-fp8tqr.md:28)). Fix: say plainly that the whole rendered page is uploaded and stored, decide which credential-bearing controls can safely be removed before serialization, and verify that raw source is never exposed by public/private-link reads. Sanitisation should not be presented as data minimisation.

7. **F7 — P1 — reasoned.** The HTML path preserves image addresses, but it does not guarantee the images. A direct constructed upload was accepted as HTML and Readability emitted an absolute image URL, which `imageSourcesIn` selected. Stage 4.5 then fetches that URL from the server—the party the wall is refusing. On failure the reading view deliberately falls back to the publisher URL ([article-images.md:106–108](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/project/article-images.md:106)); that may work for the signed-in owner but fail for another device or a public reader. The proposed Nature/PLOS test does not exercise this because those hosts already load from the box. Fix: make image retention an explicit acceptance check on an actual walled capture, report the fallback limitation, and test a failed asset fetch. Also cover the [50 MiB upload cap](/var/tmp/spideryarn-worktrees/refused-site-open-copy/src/uploads.ts:38): either warn before saving an oversized Blob or explicitly accept the later upload refusal.

8. **F8 — P2 — reasoned.** “Not on touch devices” is the wrong capability cut. The authoritative map says [there is no single phone/touch switch](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/project/phone-and-touch.md:22), and specifically distinguishes phones, iPads, and touchscreen laptops ([phone-and-touch.md:216–220](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/project/phone-and-touch.md:216)). A wide touchscreen laptop has a bookmarks bar and should not lose the feature merely because it has touch. Fix: choose and name the actual condition—probably phone/small-screen presentation rather than touch—and test a wide coarse-pointer/hybrid device.

9. **F9 — P2 — established.** The AWS status evidence is not reproducible as written. The plan says “202 with an empty body” and then says `fetchDocument` received the 2 KB page ([plan:99–101](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/plans/261017b-a-refused-site-the-free-copy-and-the-bookmarklet-after-greg-s-reply.md:99)), but [readBody throws on an empty response](/var/tmp/spideryarn-worktrees/refused-site-open-copy/src/fetch.ts:2429). The probe had access to `FetchedDocument.status` but overwrote the result with `html:<length>` and did not record that status ([probe.ts:22–30](/var/tmp/spideryarn-worktrees/refused-site-open-copy/docs/investigations/261017a-evidence/probe.ts:22)). What is established is only that one `fetchDocument` run received 2,058 HTML bytes. Fix: record status, relevant headers, final URL, body length, and fixture hash in the evidence. If IEEE sometimes returns an empty 202, acknowledge that such a response stops in stage 1 and never reaches this recogniser.

The file handoff itself is a sound COOP-independent v1: there is no comparably simple full-document `postMessage` replacement that preserves the unchanged cross-site/authentication defence. The generated doctype HTML is accepted by stage 1, and the built stages need not edit any defence listed in `security-map.md`.
