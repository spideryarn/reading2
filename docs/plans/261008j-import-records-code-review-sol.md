# Code review: import report details and durable import records

Plan reviewed: [261008j](261008j-a-failed-import-report-carries-the-address-and-a-record-of-every-import.md)  
Commit reviewed: `937c73ca9`

1. **High — the audit insert depended on the application role's table grant, so a privilege drift could stop every import from ending.** At reviewed HEAD the trigger function was security-invoker and inserted into the new table inside the same statement that ends the job (`drizzle/20261008212426_import_records.sql:68-105`). Production is meant to grant all four DML verbs on future tables through default privileges, but the deploy gate currently proves only `SELECT` (`scripts/deploy.ts:1566-1606`). A missing `INSERT` grant would therefore pass that gate and make every terminal import update fail, rolling back publication or failure settlement with it. The copied data cannot violate the target constraints when the source `jobs` row is valid: the owner, upload and composite ingest-event keys duplicate constraints already holding on `jobs`; the target required columns copy required source columns; the status predicate implies the target check; and the primary-key conflict is ignored. **Fixed:** made this narrowly qualified trigger function `SECURITY DEFINER`, retained the empty `search_path` and schema-qualified names, revoked `PUBLIC` execution, and added a catalog assertion that those properties survive migration (`drizzle/20261008212426_import_records.sql:68-112`, `tests/import-records-pg.test.ts:127-144`). I did not swallow every insert error: that would turn a missing record into silent success.

2. **Medium — the hand-written foreign keys had no direct drift guard.** Drizzle's snapshot contains the generated upload key but cannot contain `import_records_owner_fk` or the composite `import_records_ingest_event_fk` appended by hand (`drizzle/meta/20261008212426_snapshot.json`, `drizzle/20261008212426_import_records.sql:25-46`). The focused tests exercised a valid reservation and its `SET NULL`, but did not prove that a record cannot name another owner's reservation, nor did the repository's catalog inventory name either constraint (`tests/db-schema.test.ts:1006-1085`). **Fixed:** added both constraint names to that inventory and behavioural coverage for the composite owner key and the owner's cascade (`tests/db-schema.test.ts:1011-1085`, `tests/import-records-pg.test.ts:127-155`).

3. **Medium — the public privacy policy changed without changing its displayed version.** The new import-record and failed-import-report paragraphs are dated 8 October (`src/web/PrivacyPage.tsx:229-240,665-673`), while `LAST_UPDATED` at reviewed HEAD still said 7 October (`src/web/PrivacyPage.tsx:51-58`), and its test pinned the stale date (`tests/privacy-page.test.ts:196-198`). **Fixed:** bumped the page and its test to 8 October 2026 (`src/web/PrivacyPage.tsx:58`, `tests/privacy-page.test.ts:196-198`).

4. **Low — the paste-safe list exposed the article slug outside its documented compact output.** The script says a listing is deliberately limited because it is likely to be pasted, and the plan describes time, job id, step, kind and host; `formatList` at reviewed HEAD additionally printed `slug` (`scripts/import-records.ts:18-22,109-122`). A slug is derived from a URL path or uploaded filename and can reveal a paper or private document's subject even though the full URL, filename and error are suppressed. **Fixed:** removed the slug from list output and asserted that the focused test's distinctive slug is absent (`scripts/import-records.ts:109-121`, `tests/import-records-pg.test.ts:290-309`). The allowed host remains explicit; the full address, upload filename and error remain absent.

5. **Low — the plan promised a `--local` CLI mode that the production-only script does not implement.** At reviewed HEAD the plan said `--local` reads `DATABASE_URL` and that the test uses it, but `parseArgs` rejects it and `main` always uses the guarded production connection (`scripts/import-records.ts:151-187`). The implementation's injected `Queryable` is the simpler and safer way for the test to read its minted database, and the requested tool is a production reader. **Fixed:** corrected the dated plan to record the implementation that was actually chosen rather than add an unnecessary second connection mode (`docs/plans/261008j-a-failed-import-report-carries-the-address-and-a-record-of-every-import.md:141-144,193-194`).

6. **Info — the trigger predicates, ordered failed-step selection and all terminal update paths are correct.** The trigger accepts only the first transition into `done`, `error` or `cancelled`, identifies imports with the correct object-array containment predicate, and uses `WITH ORDINALITY ... ORDER BY n LIMIT 1` to select the first errored step (`drizzle/20261008212426_import_records.sql:77-105`). Every relevant update includes `status` in its `SET` list, including the conditional branches: `settleExpired` (`src/store/pg-jobs.ts:1795-1840`), `requestCancel` (`src/store/pg-jobs.ts:2035-2083`), `releaseStepIn` (`src/store/pg-jobs.ts:2335-2362`), and `finishIn` (`src/store/pg-jobs.ts:2404-2424`), which `settleIn` calls (`src/store/pg-session.ts:470-481,605`). `UPDATE OF status` therefore misses none of them. No change recommended.

7. **Info — the read path and security-map boundary are sound.** `readRecords` opens `BEGIN READ ONLY`, executes only `SELECT`s, and rolls back in `finally`; it never uses session `SET` (`scripts/import-records.ts:62-92`). Production connection construction is reused from the verified-TLS feedback reader. There is no route or client type for `import_records`, so no reader-facing authorization boundary changes; the applicable security-map defence remains the verified database connection (`docs/project/security-map.md:111`). No security-map change recommended.
