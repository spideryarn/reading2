1. **P1 — `docs/plans/261021d…` §4 / `src/store/private-link-opens.ts`: the anonymous import graph would gain authority to write account identities.** The plan puts both the signed-out counter and the signed-in `(article_id, reader_id)` writer in the file imported by `src/public/routes.ts`. Thus the public graph reaches a function accepting an arbitrary reader id and the `private_link_openers` table, despite the current handler not calling that function. This weakens the structural defence in `tests/public-imports.test.ts`. Split it into an anonymous leaf that imports only `articles` and `private_link_signed_out_opens`, and a separate authenticated writer outside the public graph. Give the signed-out table a per-file `ALLOWED_IN` exception; never allow `private_link_openers` in the public graph.

2. **P1 — §4 “Abuse”: one row is not a meaningful abuse bound.** Option B is preferable to A—there is no honest signed-out count without some anonymous write, and counting in GET would count fetches rather than page opens. But every POST still takes a write lock on one hot row, produces WAL, and increments an `integer`; a link holder or cross-origin form can loop it indefinitely. The database work, count corruption, and eventual integer overflow are unbounded even though row cardinality is one. Add a deployment-layer request ceiling for this exact route, use a non-overflowing/saturating counter, and label the result as an unverified approximate count. If no rate bound is accepted, record that explicitly as a security risk rather than calling it bounded. The no-`req`, no-body, uniform-204 handler is otherwise the right privacy shape.

3. **P1 — §6–7 omit the reader-facing Help claim and its generated copy.** [`src/web/help/pages/sharing.md`](/var/tmp/spideryarn-worktrees/fbcf30ac-private-link-owner-opens/src/web/help/pages/sharing.md:24) says, “We cannot tell you who has opened it.” After this change Spideryarn can identify signed-in openers, although ordinary owners still cannot see them. Rewrite this plainly—e.g. that signed-in accounts are recorded for the administrator, signed-out opens are counted, and owners cannot see either—and regenerate [`src/help-corpus.generated.json`](/var/tmp/spideryarn-worktrees/fbcf30ac-private-link-owner-opens/src/help-corpus.generated.json). Otherwise Help and its chatbot preserve the old privacy promise.

4. **P2 — §5 / admin response DTO: the client cannot implement “is or has been link-shared.”** The proposed response contains owner and opens but no indication that a private link currently exists or existed. Empty opener rows cannot distinguish “never had a link,” “active link with no opens,” and “old link with no opens”; this especially affects a public article, whose `sharedBy` remains `"public"`. Either return a safe `hasPrivateLinkHistory` boolean derived from `article_share_link_events`—never the token—or simplify the UI to show a neutral “No private-link opens have been recorded” line on every administrator-only article view.

5. **P2 — §3 / [`src/web/public-api.ts`](/var/tmp/spideryarn-worktrees/fbcf30ac-private-link-owner-opens/src/web/public-api.ts): preserve the fixed-method client boundary.** `publicFetch` deliberately accepts only a path and signal so callers cannot add methods, credentials, or headers. Do not widen it to `RequestInit` to support this POST. Add a dedicated helper whose implementation hardcodes `POST`, `credentials: "omit"`, no body, and no headers. Preserve the existing network test proving an owner opening their own `?key=` address sends no request containing the key. The authenticated visitor POST through `apiFetch` is otherwise safe: its POST is not offline-cached, browser diagnostics strip queries, server logs use the query-free path, Sentry drops request URLs, and `madeFor: readerId` prevents account-switch misattribution.

6. **P2 — §2 store predicate: use the exact private-link predicate for writes.** `publicAccessWhere(link) AND visibility = 'private'` is currently equivalent to “this private link key matches,” but it expresses the broader “public or key” policy and then cancels its public arm. After rejecting a missing key, use `linkSharedSlug(slug, key)` plus `visibility = 'private'` directly. This makes the write remain exactly about private-link access if `publicAccessWhere` later gains another ownerless access mode.

7. **P2 — §7 / `src/store/pg-admin.ts` `activitySources`: state the deliberate exclusion.** That function currently documents itself as every timestamp showing account activity. The new signed-in opener table creates such timestamps, but adding them to Active days would be a further use beyond Greg’s exact 2C authorization. Record that private-link opener rows are deliberately excluded from Active days and narrow the “every timestamp” claim; treat counting them there as a separate decision.

No route or DTO in the proposed core design lets a non-admin read an owner, opener, or count, and `ownedSlug OR publicAccessWhere(slug, accessFor(key))` admits exactly the administrator’s own, public, or correctly keyed article.

**Verdict: Not ready—fix the public capability split, anonymous-write abuse bound, and stale Help privacy claim before building.**
