No P0 findings. The central 8K design is sound, but I would revise three details before building.

## Findings

- **P1 — The sampler can become stale when layout changes without a window scroll or resize.** The proposed effect only names scroll, resize, and `enabled` ([plan:60](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/docs/plans/261001n-trajectory-question-above-quote-and-highlight-on-screen-block-links.md:60)). However, switching between standard, Tweets, and Structure changes the prose width, and opening Annotations can rewrap it; those changes are deliberately captured by `layoutKey` ([Reader.tsx:438](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/reader/Reader.tsx:438), [Reader.tsx:494](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/reader/Reader.tsx:494)). Late images and font swaps can also change row positions without either event. The existing model the plan cites handles both: `layoutKey` restarts its measurement and a `ResizeObserver` watches the table ([useColumnContext.ts:47](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/useColumnContext.ts:47), [useColumnContext.ts:83](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/useColumnContext.ts:83)). Pass `layoutKey` to `OnScreenLinksStyle`, include it in the effect dependencies, and observe the table.

- **P1 — `bandOpen && !bandOverProse` enables the expensive sampler while the band is hidden.** `bandOverProse` becomes false when `bandAway` is true ([Reader.tsx:516](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/reader/Reader.tsx:516)), but on a narrow window that state hides `.mode-band` with `display: none` ([narrow-window.css:373](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/narrow-window.css:373)). Consequently, following a band link on a phone would start doing rect reads on every prose-scroll frame for a band with nothing visible to light. Use `bandOpen && fit.modeW > 0`, or equivalently exclude `bandBack`; that precisely means band and prose are visible together.

- **P2 — The viewport bottom should exclude the fixed Dock.** The reused code currently passes `window.innerHeight` as the bottom ([useReadingTime.ts:251](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/useReadingTime.ts:251)). A short row entirely behind the Dock could therefore satisfy the proposed “fully visible if shorter than 24px” rule and light its link despite being obscured. `dockOffset()` already exists specifically because a line underneath the Dock is not meaningfully on screen, and it follows the Dock as it slides away ([scroll.ts:56](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/scroll.ts:56), [scroll.ts:68](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/scroll.ts:68)). Use `window.innerHeight - dockOffset()` and test it.

- **P2 — “Full opacity” is not true for Summary ranges, and the CSS ownership is underspecified.** The plan says the highlighted link reaches full opacity while generated CSS “names only selectors” ([plan:65](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/docs/plans/261001n-trajectory-question-above-quote-and-highlight-on-screen-block-links.md:65)). But `.summ-range` applies `opacity: 0.75` to the parent of both links ([summary.css:388](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/summary.css:388)); child opacity cannot undo that. Also, a generated rule needs at least a custom-property declaration, so it cannot literally contain only selectors. Specify the bridge precisely and either move Summary’s baseline dimming onto its children or drop the full-opacity claim. Add one computed-style/browser check for a Summary range, not just string assertions.

## Answers to the questions

1. **The one-style-element architecture is right.** It avoids rerendering every link and only produces selectors for roughly a screenful of IDs. The scope is also coherent for “every band”:

   - Every actual mode surface is `.mode-band` ([ModeSurface.tsx:178](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/ModeSurface.tsx:178)); Summary, Tweets, and Structure all use it ([SummaryPanel.tsx:214](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/SummaryPanel.tsx:214), [Tweets.tsx:103](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/Tweets.tsx:103), [StructurePanel.tsx:588](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/StructurePanel.tsx:588)).
   - The standalone Chat dialog is deliberately outside that scope: it is `.chat-dialog`, not a band, and it can contain a `Conversation` with block citations ([ChatDialog.tsx:666](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/ChatDialog.tsx:666), [ChatDialog.tsx:751](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/ChatDialog.tsx:751)). Chat mode itself is covered. The plan should say “Chat band, not the passage Chat dialog.”
   - Annotations marginalia currently renders questions and idea buttons, not `BlockRef`s ([AnnotationsColumn.tsx:90](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/annotations/AnnotationsColumn.tsx:90)).
   - Structure is covered by the selector but currently contains no block links.
   - The selector correctly does not assume `<a>`: missing references are `<span data-block-link>` ([BlockRef.tsx:165](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/BlockRef.tsx:165)), while live references are anchors ([BlockRef.tsx:187](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/BlockRef.tsx:187)).
   - Bands are fixed while the prose remains window-scrolled ([mode-band.css:28](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/mode-band.css:28)); band jumps ultimately call the ordinary window-based `jumpTo` ([Reader.tsx:576](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/reader/Reader.tsx:576)). Window sampling is therefore the correct scroll source.

2. **The enabled gate is not quite right.** Use `bandOpen && fit.modeW > 0` so sampling occurs only when band and prose are simultaneously painted.

3. **There are layout reads per scroll frame, but not an O(2,000) pass or read/write thrash.** `rowsOnScreen` performs a binary search plus visible-row reads and caches each rect within the sample ([useReadingTime.ts:145](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/useReadingTime.ts:145)); `firstOnScreen` is logarithmic ([reading-time.ts:59](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/reading-time.ts:59)). For 2,000 rows that is about eleven probes plus a screenful. All reads happen before the conditional state write, so there is no synchronous read/write/read loop. The hidden-band gate is the avoidable expensive case.

4. **I do not see a simpler design that is as good.** Context rerenders every consumer; class toggling introduces imperative DOM writes; an observer per row adds thousands of registrations. Keep the style-element design and add the missing invalidation and visibility boundaries.

5. **8J’s reorder is correct.** `.traj-what` is a flex column, so DOM order is visual and accessible order ([trajectory.css:176](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/trajectory.css:176)). The current working-tree rendering is place → cue → words ([TrajectoryPanel.tsx:686](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/TrajectoryPanel.tsx:686)), and the proposed test checks exactly that order ([trajectory-panel.test.tsx:459](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/tests/trajectory-panel.test.tsx:459)). `voices.css` selects `.traj-cue` and `.traj-words` independently, so their order is irrelevant ([voices.css:51](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/voices.css:51), [voices.css:107](/home/greg/code/spideryarn2/.claude/worktrees/fb-trajectory-question-and-visible-block-links/src/web/styles/voices.css:107)). I found no other style or test dependent on the old order.

**Verdict:** revise before build. The style-element design should remain, but the layout invalidation and enabled gate are blocking correctness/performance fixes; Dock exclusion and CSS-opacity wording should be tightened in the same pass. No files were changed.
