1. **P1 — A forged Sentry event can still receive exit 0.** Exit 0 requires an event-id match only when both the row and invocation have one ([plan:88](docs/plans/261001a-unfakeable-admin-feedback-reports.md:88)); 200/231 rows have no recorded event id ([plan:37](docs/plans/261001a-unfakeable-admin-feedback-reports.md:37)), and the implementation returns `admin` when either side is absent ([feedback-reporter.ts:107](scripts/feedback-reporter.ts:107)). Real admin report ids are extensively exposed in committed notes, for example [260929_2025-feedback-from-other-people-trust-tiers.md:2](docs/user-feedback/260929_2025-feedback-from-other-people-trust-tiers.md:2). Therefore an attacker can post a fake event carrying a known Greg id and obtain exit 0 whenever the row lacks `sentry_event_id`. They cannot thereby substitute their body—the script prints Greg’s row—but the command has not proved that the Sentry event was filed by Greg. Option (a) is sufficient only if its contract is narrowed to “retrieve an authenticated database report and ignore the event”; literal Sentry-event provenance needs a signature or recorded matching event id. Existing null-id events cannot retrospectively be proven.

2. **P1 — The forged event can still supply the meaning-changing context.** The runbook says `url`, `slug`, `kind`, `build_commit`, and the URL’s block anchor explain what the words refer to ([feedback-reports.md:27](docs/project/feedback-reports.md:27)), and the dispatch template still puts Sentry’s URL/slug/kind into the brief ([feedback-reports.md:261](docs/project/feedback-reports.md:261)). The proposed edit replaces only the words ([plan:175](docs/plans/261001a-unfakeable-admin-feedback-reports.md:175)); the implementation selects only owner/body/kind/time/event id ([feedback-reporter.ts:169](scripts/feedback-reporter.ts:169)). Yet the authoritative row also stores URL, slug, build, environment, Vercel id, diagnostics and screenshot ([schema.ts:4139](src/db/schema.ts:4139), [schema.ts:4193](src/db/schema.ts:4193)). An attacker can replay a vague genuine body such as “make this button bigger” with a forged page, article, block or screenshot and steer the resulting work. Print all decision-relevant row metadata, indicate/download the database screenshot, and explicitly treat every Sentry-only attachment/tag as untrusted. The proposed HMAC option is likewise incomplete because it signs only id/user/body ([plan:55](docs/plans/261001a-unfakeable-admin-feedback-reports.md:55)); it would need the semantic metadata and attachment digests too.

3. **P2 — The command does not prove it queried the intended production database.** `readEnvProd` prefers a worktree-local `.env.prod` over the primary checkout’s copy ([env.ts:267](src/env.ts:267), [env.ts:289](src/env.ts:289)), and its own contract says every caller must print the chosen file ([env.ts:248](src/env.ts:248)). The implementation discards `prod.file` and validates only that TLS is verified ([feedback-reporter.ts:152](scripts/feedback-reporter.ts:152)); it does not check or print the host/project, database or role. The measurement script did print file/TLS/host and query `current_user` plus `transaction_read_only` ([measure.ts:9](scripts/.tmp-fb5k2/measure.ts:9), [measure.ts:24](scripts/.tmp-fb5k2/measure.ts:24)), but that proves one past invocation, not future ones. A stale or mistaken worktree `.env.prod` could therefore produce a convincing exit 0 from the wrong database. Validate the known production project/host and print a `Target:` line at minimum.

4. **P2 — Multiple matching rows are “cannot tell,” not “not admin,” and an event id may resolve them.** The primary key is `(owner_id, id)` ([schema.ts:4219](src/db/schema.ts:4219)); any authenticated reader may deliberately POST a chosen valid id ([routes.ts:6376](src/routes.ts:6376)). Thus an ordinary reader can file under a publicly exposed Greg id and cause two rows. The plan assigns that exit 1 ([plan:89](docs/plans/261001a-unfakeable-admin-feedback-reports.md:89)), while the implementation returns `stranger` before considering event id ([feedback-reporter.ts:96](scripts/feedback-reporter.ts:96)). Epistemically that is exit 2 unless a supplied event id uniquely matches one row—in which case the command can identify that row. This is a denial-of-service vector, not a way to get attacker-written words under exit 0. A concurrent insertion likewise cannot substitute its body: the single SELECT sees a consistent statement snapshot, and only an admin-owned row can be returned as trusted.

5. **P2 — Event-id input is neither validated nor shown practical by the measurement.** `normaliseEventId` claims 32 hexadecimal digits but merely strips whitespace, case and every dash ([feedback-reporter.ts:76](scripts/feedback-reporter.ts:76)); `--event-id=` is accepted, and when the row’s id is null it still yields exit 0 ([feedback-reporter.ts:107](scripts/feedback-reporter.ts:107), [feedback-reporter.ts:224](scripts/feedback-reporter.ts:224)). A malformed supplied event id should be exit 2. Separately, the measurement checks only database coverage; it never demonstrates that the Sentry MCP output exposes the exact event-level id, nor compares 5K’s Sentry id with its stored value ([measure.ts:18](scripts/.tmp-fb5k2/measure.ts:18)). That should be measured before making `--event-id` part of the documented one-command workflow.

6. **P2 — The fail-closed wording contradicts itself and overclaims provenance.** The table says exit 2 “Stops and says so” ([plan:90](docs/plans/261001a-unfakeable-admin-feedback-reports.md:90)); the proposed rule instead handles it as a stranger ([plan:159](docs/plans/261001a-unfakeable-admin-feedback-reports.md:159)) and the dispatch edit sends exits 1 and 2 onward identically ([plan:178](docs/plans/261001a-unfakeable-admin-feedback-reports.md:178)). The interim Overseer wording is worse: “Exit 2 is **not** Greg’s” ([overseer.md:148](docs/project/overseer.md:148)), collapsing unknown into a negative. Use one formulation: “exit 2 is not trusted and is not a classification”; then state explicitly whether the sweep stops or may continue under stranger policy. Also replace “Exit 0 means the report is Greg’s” with “Exit 0 authenticates the printed database row; it may not authenticate the Sentry event.” The repo grep found no additional live trust gate beyond `feedback-reports.md`, `overseer.md`, the script/tests, and the standing job that follows and pins `feedback-reports.md` ([standing-jobs.ts:127](tools/overseer/standing-jobs.ts:127), [standing-jobs.ts:202](tools/overseer/standing-jobs.ts:202)); other hits are historical records.

7. **P3 — The proposed database operation itself is production-read safe.** It uses a bound parameter, starts `BEGIN READ ONLY`, performs a plain SELECT, and rolls back ([feedback-reporter.ts:164](scripts/feedback-reporter.ts:164)). TLS refuses anything short of certificate verification ([feedback-reporter.ts:160](scripts/feedback-reporter.ts:160), [ssl.ts:187](src/db/ssl.ts:187)). There is no write, lock-taking query, bare `SET`, or production mutation. The runtime role does possess DML rights, so the explicit read-only transaction remains important; target verification in finding 3 is the missing operational guard.

**Verdict: Do not approve as written—the database-body idea blocks direct word substitution, but the plan neither proves the Sentry event nor authenticates the context needed to interpret Greg’s words.**
