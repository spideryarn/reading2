1. **High — `src/store/pg-share-link.ts:151` / `src/store/pg-author-gifts.ts:1200` — the link step had a time-of-check/time-of-use gap after `resolveGiftStarter`.** A gift's slug could be reassigned after the resolver approved the gift's article but before `pgShareLinkStore.create` locked the slug. Send would then enable a private link on the replacement article; the later voucher resolution refused the wrong article, but the wrong link and rights event remained. **Fixed:** the share-link store now locks the owner-scoped slug, verifies the expected article id under that lock, and returns no key. Both Send and the add-page ensure path use this article-pinned operation. `tests/author-gifts.test.ts:637` moves the slug in the exact gap and checks that neither replacement article nor audit ledger is touched.

2. **Medium — `src/store/pg-author-gifts.ts:1053` — a concurrent replay could make the voucher between the fresh request's first starter refusal and its link write.** If the owner then turned the link off, the older fresh request could turn it back on even though `createVoucher` should now be a replay. **Fixed:** Send asks `createVoucher` first, makes a link only for a fresh `link-off`, and retries the replay-first operation. Before writing the link it locks the gift, checks the attempt, then uses a separate READ COMMITTED statement to see any voucher committed by the previous gift-lock holder. A committed voucher is returned as a replay; a replaced attempt is `superseded`. `tests/author-gifts.test.ts:675` covers the committed-voucher/turned-off-link interleaving.

The next Send can then make the link, so the old wording sent the admin through an unnecessary manual step. **Fixed:** the rights-confirmed `link-off` path now says the attempt was released and to check the gift and press Send again; the no-tick path still asks for the rights tick. Added a database route test for the frozen recovery path.
