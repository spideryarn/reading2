No P0 findings. I found five P1s that make the design unsafe to implement as written. One operational Overseer is sound; one shared model conversation and the proposed three-class authority check are not yet sound.

## Findings

- **P1 — Owner/operator/product is neither exhaustive nor mutually exclusive, so Stage 3 cannot be “one function classifying an action.”** The plan says the answer follows from “the task’s owner and the action’s class” ([plan:87](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:87), [plan:208](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:208)). Three counterexamples:

  - Between the classes: Alice asks the Overseer to create and dispatch a new investigation. There is no task owner to look up yet; it is not box operation; and an investigation need not yet outlive a branch. The current queue separately requires work authorisation, but the new plan never assigns that authority.
  - Both owner and product: the product owner asks the Overseer to deploy Alice’s task. Product authority permits deployment, but Alice’s authority is still needed to repurpose her agent. Conversely, Alice’s approval does not authorise deployment. A single enum can only choose one.
  - Context-dependent: “pause Bob’s agent because load crossed the standing threshold” is operator action; “pause Bob so my task can run first” is an owner/priority request. Classifying the verb `pause` launders the latter through operator authority.

  Free text makes this worse: [`routes-actions.ts`](/home/greg/code/spideryarn2/tools/fleet/routes-actions.ts:623) and [`routes-steer.ts`](/home/greg/code/spideryarn2/tools/fleet/routes-steer.ts:692) can carry arbitrary prose, whose downstream effects are not program-classifiable. The implementable model is a set of required grants—possibly task owner plus product owner—along with a standing-policy ID and verified preconditions. It also needs separate work-origination and box-administration authority. Free text should always require task-owner authority and must not be treated as a typed operator action.

- **P1 — “Authority lives in the task” conflicts with copying `owner` onto sessions, queue items and decisions.** Rule 1 makes the task the source of truth ([plan:89](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:89)); Stage 1 then duplicates owner across three records ([plan:201](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:201)). Existing queued steering has session and conversation IDs but no task ID or authority revision ([wire.ts:172](/home/greg/code/spideryarn2/tools/fleet/wire.ts:172)). After Bob hands a task to Alice, Bob’s already-queued message can therefore still be delivered, a launch can finish on Bob’s account, and stale session metadata can continue authorising Bob. Every effect must carry a stable `taskId` and re-check the current ownership/grant version at delivery, not merely at enqueue.

  This also leaves absence and departure unresolved. An owner asleep for a week blocks every proposal and is the only person allowed to hand over. A departed owner cannot hand over after access is revoked. The design needs an explicit `orphaned`/`owner-unavailable` state, safe-stop policy, delegation expiry, and a named administrator/product-owner power to reassign with an audit record. It must not silently default abandoned work to Greg.

- **P1 — The plan settles one resource coordinator, but not one conversational Overseer.** The argument at [plan:117](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:117) addresses authority only. Today the Overseer is one long-lived model context backed by one global store ([overseer.md:15](/home/greg/code/spideryarn2/docs/project/overseer.md:15), [overseer.md:25](/home/greg/code/spideryarn2/docs/project/overseer.md:25)). Per-person views do not stop Alice’s preference, correction or private context influencing the answer to Bob.

  Pause/resume bookkeeping also needs multiple causes: an operator removing its load-pressure hold must not resume a task Alice paused herself, and Alice must not remove an operator hold. Decisions need requester, authoriser/policy, relay, task/product scope and reviewer; merely replacing `"greg"` with `Person` loses the proposed “Alice via Overseer” provenance. The clean version is one deterministic operational coordinator, but separate person/task conversation threads feeding it, plus durable multi-cause holds and structured request envelopes. Thus “one operational Overseer” is settled; “one model conversation” is not.

- **P1 — Personal account selection is incomplete across ownership changes and child work.** The plan covers initial `--account auto` selection ([plan:178](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:178)), but not:

  - a handover while the existing session continues spending the former owner’s account;
  - a helper steering or launching child work on the owner’s subscription;
  - reboot recovery via `claude --resume`, which must restore the original config directory;
  - a Claude agent launching its mandatory Codex review;
  - a task owner who has Claude capacity but no permitted Codex account;
  - the Overseer’s coordination, recovery and review sessions.

  The payer should be immutable per execution, separate from mutable task ownership. Handover should either retain that payer with explicit consent or stop and relaunch under the new owner. Child and resume paths must inherit `{taskId, accountId, payerGrantVersion}` and refuse ambiguity. A reserved coordination/review account is needed before the plan can promise that every stage ends in Sol review; leaving the Overseer account as an open question ([plan:237](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:237)) makes Stage 2 not implementation-ready.

- **P1 — The identity mechanism is plausible, but the proposed authorisation boundary is incomplete and the SSH setting is too broad.** Tailscale confirms that Serve supplies `Tailscale-User-Login`, strips incoming copies, omits identity headers for tagged devices, and recommends a loopback backend. It also says external users with a shared device can receive valid identity headers, so a non-empty header is not itself team membership. Serve requires HTTPS enablement and remains subject to tailnet access policy. [Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve)

  The plan must therefore map the header through an explicit active-person allowlist; a validated login string is insufficient. It must authenticate reads and streams as well as writes. [Plan line 168](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:168) says every headerless request fails closed, while Stage 1 only says writes do ([plan:203](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:203)); current `/api/live`, `/api/state`, recent messages, queue and decisions are unauthenticated reads ([server.ts:688](/home/greg/code/spideryarn2/tools/fleet/server.ts:688)). Funnel or an over-broad tailnet policy would otherwise expose transcripts even if writes fail closed. Direct loopback callers can also forge the header, which Tailscale explicitly acknowledges; with one shared Unix user, “only the owner steers” is enforcement only on supported remote routes, not a real boundary.

  For SSH, `PermitUserEnvironment yes` enables both authorized-key environment options and the shared user’s `~/.ssh/environment`, with OpenSSH warning that arbitrary variables can bypass restrictions through mechanisms such as `LD_PRELOAD`. Use the narrow pattern form `PermitUserEnvironment GJD_PRINCIPAL`, if the deployed OpenSSH supports it, and keep the authorized-key source root-owned. Even then `GJD_PRINCIPAL` remains attribution, because the shared user can overwrite its process environment or bypass `gjd-remote`. [OpenSSH `PermitUserEnvironment`](https://man.openbsd.org/sshd_config#PermitUserEnvironment)

- **P2 — The stages conceal several independently risky changes and are ordered around fields rather than invariants.** Stage 1 combines identity middleware, a people registry, wire-type migration, four durable-record migrations, tmux metadata and auditing across many write routes—not just steer/new. Stage 3 combines the task model, grant engine, natural-language-to-typed-action boundary, proposal storage and lifecycle, inbox delivery, handover concurrency, and every route’s enforcement. Stage 5 combines provisioning with an external-access rollout and a fortnight-long experiment.

  A safer order is: decide work/admin/departure authority; add a stable people registry and central authentication for every route; add durable tasks and `taskId` joins; implement compositional grants and proposals; implement account/payer propagation; add views; then provision and run the trial as a separate rollout stage.

- **P2 — “See all, steer all, stamped” really is simpler, including with the Overseer.** [Plan lines 220–226](/home/greg/code/spideryarn2/docs/plans/260909i-a-team-box-for-a-separate-product-one-overseer-that-carries-each-person-s-authority.md:220) claim the Overseer turns it into judgement calls. It does not: “any authenticated team member may steer any task, with attribution; product and box-admin actions retain their separate gates” is a mechanical rule with no ownership lookup, handover, proposals, orphan policy or delivery-time reauthorisation. Its genuine cost is that Alice can cause spend on Bob’s running account and can interfere with his work. Ownership may be the preferred product policy, but it is the more complex option; the plan should justify that cost rather than call it simpler.
