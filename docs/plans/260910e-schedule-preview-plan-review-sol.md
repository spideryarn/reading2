3. **P1 — `dispatch` cannot be outside the behaviour hash.** The existing split is principled: `JobBehaviour` is what the box does, while `ScheduleConfig` changes only when it does it ([jobs.ts:138](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/jobs.ts:138), [jobs.ts:162](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/jobs.ts:162), [schedules.ts:54](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/schedules.ts:54)). Dry-run → live changes whether an unattended Claude session may be launched, not its timing. Greg’s S8-1 decision protects cadence/lease/delay edits; it does not imply that an authority-enabling switch should be freely editable. Put `enabled`/`dispatch` in `JobBehaviour`, accept the one-time re-pin of existing jobs, and preserve all clock fields outside the hash. A dry-run/disabled job should indeed write no occurrence: recording a “last attempt” that never happened would corrupt the ledger. It should remain “due now if enabled” indefinitely. Prefer treating it as a disabled definition surfaced by preview, avoiding a `dry-run` report every daemon tick.

4. **P1 — D6 cannot claim the armed daemon’s exact answer from the proposed inputs.** There are two independent drifts:

   - The daemon’s definitions are fixed when `schedulerWiring()` runs ([overseer.ts:600](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/scripts/overseer.ts:600), [overseer.ts:1207](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/scripts/overseer.ts:1207)); the fleet server is another long-lived process. Calling `standingJobs()` on demand refreshes document bytes, but imported prompts, pins, schedule constants, and job membership remain the fleet process’s loaded module values, not necessarily the daemon’s. The checkpoint stores only a scheduler sentence, not its loaded list revision or capabilities ([store.ts:533](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/store.ts:533), [store.ts:611](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/store.ts:611)).
   - Scheduler writes and checkpoint writes run on separate timers ([daemon.ts:771](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/daemon.ts:771), [daemon.ts:987](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/daemon.ts:987)). A dispatch just after a checkpoint is absent from `jobs.occurrences` until the next checkpoint ([store.ts:3005](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/store.ts:3005)); the preview can therefore say “dispatch now” while the actual daemon sees an in-flight occurrence.

   The plan acknowledges only capability uncertainty ([plan:153](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/docs/plans/260910e-schedule-preview-make-periodic-work-inspectable-before-launch.md:153)). At minimum, store the daemon’s loaded `listRevision` and held capabilities in the scheduler checkpoint, compare them with the checkout forecast, and fold the event-log tail after `checkpoint.cursor` or checkpoint immediately after every scheduler tick. Otherwise label it “checkout forecast from checkpoint written at X,” not “what this armed daemon would do now.”

5. **P1 — The duplicate-id behavior must be fixed before sharing it with preview.** The current loop checks duplicates only after processing earlier definitions, so the first duplicate can dispatch and only the second is refused, despite the report claiming neither can be addressed ([scheduler.ts:412](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:412), [scheduler.ts:420](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:420), [scheduler.ts:435](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:435)). A per-job `planJob` cannot own this list-wide gate. Pre-scan all ids before any planning or dispatch and refuse every definition sharing an id; use that same preflight in preview. Add a test proving zero spawns, not merely that one refusal report exists.

6. **P2 — D2 is viable, but its purity and orchestration contract are underspecified.** The tick currently sweeps before the history-lost early return ([scheduler.ts:385](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:385), [scheduler.ts:389](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:389), [scheduler.ts:394](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:394)); spacing is checked after due ([scheduler.ts:519](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:519), [scheduler.ts:535](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:535)); and its in-loop clock advances only when a session actually or possibly launched ([scheduler.ts:435](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:435), [scheduler.ts:439](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/scheduler.ts:439)). The proposed success-assuming loop is faithful only as a conditional forecast: update simulated spacing after successful live session dispatches, never after rules, disabled jobs, reservation failures, or known refusals. It must say that later rows assume earlier proposed launches succeed. Also, a `planJob` that invokes `readDocument` is not pure; resolve current-document evidence outside it and pass a value in. Characterisation tests should compare old and refactored tick reports for sweep+dispatch, history lost, spacing, rule/session mixes, and duplicate ids—not just test `due()` boundaries.

7. **P2 — The roadmap’s timeout and no-overlap fields are being claimed rather than delivered.** A session occurrence settles when the short-lived `gjd-remote` launcher exits; the actual Claude session can continue for hours and overlap a later occurrence ([dispatch.ts:18](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/dispatch.ts:18), [dispatch.ts:20](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/dispatch.ts:20), [dispatch.ts:24](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/dispatch.ts:24)). The lease likewise monitors the launcher, not session runtime ([schedules.ts:84](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/schedules.ts:84), [schedules.ts:87](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/schedules.ts:87)). Therefore “no-overlap key = job id” and “timeout = lease” are misleading mappings. Show explicit values such as `launcher lease`, `session timeout: not built`, and `session no-overlap: not enforced`; the later Scheduled-dispatch stage can replace them. Resource class and the omitted timezone are honest derivations.

8. **P3 — D4 is worthwhile diagnostic duplication, not a blocker or authority mechanism.** The composite behavior pin currently cannot reveal which of several documents changed; rule jobs already carry three source documents ([rule-jobs.ts:149](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/rule-jobs.ts:149), [rule-jobs.ts:283](/home/greg/code/spideryarn2/.claude/worktrees/schedule-preview/tools/overseer/rule-jobs.ts:283)). Full authorised document digests let the preview make the roadmap’s “changed document is visible” concrete. Keep the composite behavior hash as the sole gate and make the pins-agree test non-vacuous. If scope pressure matters, D4 can be dropped in favor of naming current document digests plus the moved composite fingerprint, but the resulting diagnosis is materially poorer.

**Verdict:** build with these changes. D3’s central diagnosis is correct and its session/rule split is sound, but hash the live/disabled switch, eliminate the hidden `/loop` instruction, preflight duplicate ids, and stop presenting an independently loaded, checkpoint-lagged fleet forecast as the armed daemon’s exact state. The simplest acceptable shape is a hashed `enabled` field, fresh session-document evidence passed into a genuinely pure planner, one shared list-wide planning loop, and a checkpoint carrying the daemon’s loaded list revision/capabilities while the reader folds its event-log tail.
