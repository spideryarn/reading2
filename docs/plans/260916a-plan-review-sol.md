1. **P1 — The new stamp is unsafe after a rollback or an older bundle reloads it.** The plan writes `{ from, depth }` under the existing key and only considers old stamps being read by new code ([plan](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/docs/plans/260916a-back-to-where-you-were-survives-a-mode-change.md:81)). The old parser ignores unknown fields and accepts `from` ([jump-history.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/jump-history.ts:109)); the old chip then calls `history.back()` ([ReturnChip.tsx](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/ReturnChip.tsx:65)). Counterexample: new code creates `E1 depth=1`, then an inherited `E2 depth=2`; production rolls back and `E2` reloads old JavaScript; the old chip appears but returns only to `E1`, not the labelled origin `E0`. Use a versioned shape under the same `spya` key that old `readStamp` rejects—for example a non-string `from` plus `v`, `origin`, and `depth`. Keeping the same key matters because old `withStamp(..., null)` will delete it rather than unknowingly carrying an unfamiliar second key onwards. Test both old→new and new→old behavior; the latter must fail closed.

2. **P1 — Skipping Stage 3 while a glide is active leaves the exact rotation race unfixed.** `scrollToBlock` calculates one pixel destination before starting the animation ([scroll.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/scroll.ts:737)), and `glide` retains that pixel number until completion ([scroll.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/scroll.ts:641)). If rotation or a column change reflows the rows during those 200ms, the destination is stale. The plan then skips re-anchoring because `glideTarget() !== null` ([plan](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/docs/plans/260916a-back-to-where-you-were-survives-a-mode-change.md:184)); after the glide ends, the spy records wherever the stale pixel landed. Make block glides retain their block ID and retarget or snap to that block after layout changes. Add a red test that changes `layoutKey` midway through both a `beginJump` glide and an arrow/swipe glide.

3. **P1 — Same pathname plus same `?at=` does not mean “the reader has not moved.”** The position contract deliberately preserves a fine `?at=` while the reader moves anywhere within its section ([position.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/position.ts:174)), and position writes are debounced ([params.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/params.ts:150)). Concrete counterexample: jump to block T; scroll or arrow-step elsewhere within that section; press Plain; the URL still says T, so the new entry inherits the old stamp even though the plan says movement should strip it. Across a section boundary, pressing the mode during the debounce window produces the same result; if the queued `?at=` happens to merge into the push, the opposite result occurs. Inheritance therefore becomes timing-dependent. Use an explicit one-shot “carry this return stamp” handshake for the view-changing gesture. The smallest version arms it only when leaving a covering band for Plain/Hierarchy. If the desired rule is broader, explicitly choose “all unarmed same-article pushes preserve it”; do not infer physical movement from lossy URL state.

4. **P2 — Stage 3 has not separated layout correction from URL restoration.** The restore effect owns first load, Back/Forward, and pasted links—not merely the first run ([useReadingPosition.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/reader/useReadingPosition.ts:52)). Skipping only the hook’s first layout run still double-scrolls when a history traversal changes both `at` and mode/layout. Also, the current spy is a passive `useEffect`, so reusing it unchanged permits one paint at the wrong paragraph. Use a `useLayoutEffect` with previous `{layoutKey, at}` state: re-anchor only when layout changed while `at` stayed unchanged; when `at` changed, the existing restore path owns the move. Keep spy measurement separate and run it only after anchoring. Test a Back/Forward step that changes `at` and layout together, not only a pure layout-key change.

5. **P2 — The depth cap is an arbitrary disappearance rule, not a correctness mechanism.** At depth 10 the origin remains exactly reachable, yet the next view change silently removes the affordance ([plan](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/docs/plans/260916a-back-to-where-you-were-survives-a-mode-change.md:86)). That contradicts “robustly and universally,” and explicit dismissal already exists for a return that has outlived its usefulness ([router.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/router.ts:1452)). Remove the product cap and retain only technical integer/plausibility validation. If a cap is retained, dropping is honest; clamping is worse because the labelled button would deliberately land on the wrong entry. Add exact boundary tests either way.

6. **P2 — The planned data flow cannot leave `Spine.tsx` unchanged as claimed.** Today `readStamp` and `useJumpOrigin` expose a `JumpOrigin`; both ReturnChip and Spine consume it ([router.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/router.ts:1595), [Spine.tsx](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/Spine.tsx:700)). If `readStamp` now returns `JumpStamp`, ReturnChip can obtain `depth`, but Spine receives the wrong type. If `useJumpOrigin` continues unwrapping the origin, ReturnChip cannot obtain depth. Define a cached `useJumpStamp`; ReturnChip consumes the full stamp, while Spine either consumes `stamp?.origin` or retains a derived `useJumpOrigin`. The statement that Spine needs no change is false.

7. **P2 — The test plan does not establish the new history invariant.** The proposed tests cover one inherited push and parser shapes ([plan](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/docs/plans/260916a-back-to-where-you-were-survives-a-mode-change.md:158)). I found no arithmetic drift within one deploy for Back, Forward, Back-then-push truncation, replace, second jump, or per-entry dismissal—but none is pinned. Add sequence tests for: two inherited pushes; Back then push; Forward; second jump from an inherited entry followed by two chip presses; dismissal on an intermediate entry then Forward; legacy stamp inheritance; and the cap boundary if retained. The proposed happy-path tests genuinely fail red today—four intended assertions failed when run—but they would all remain green with several of these invariants broken.

8. **P3 — Conclusion 1 is literally false, although its product-relevant half is true.** All mode-panel deliberate jumps I found receive Reader’s `jumpTo`, so no new cross-mode jump machinery is needed. But keyboard ↑/↓ directly calls `scrollToBlock` ([keynav.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/keynav.ts:518)), and touch stepping does likewise ([swipe.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/swipe.ts:267)); both deliberately avoid history for the same traversal reason as comment stepping. Rewrite the audit as “every mode-originated deliberate jump uses `beginJump`,” and list keyboard, swipe, comment traversal, and arrival restoration as intentional non-pushing movers.

The other three source conclusions are true: an unarmed push currently strips the stamp ([router.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/router.ts:1426)); a narrow band covers the prose and Plain is a push ([narrow-window.css](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/styles/narrow-window.css:326), [Reader.tsx](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/reader/Reader.tsx:1822)); and width changes restart the spy, whose immediate `measure()` can overwrite `?at=` ([Reader.tsx](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/reader/Reader.tsx:460), [useReadingPosition.ts](/home/greg/code/spideryarn2/.claude/worktrees/wt-back-to-x/src/web/reader/useReadingPosition.ts:64)). Stage 3 alone would not answer the missing-return-chip complaint.
