1. **P1 — “Summary” is incorrectly treated as synonymous with “long.”** Evidence: `docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:37` says any summary disables the budget and permits “however long,” while the eval has no brief-summary case (`docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:74`). “Give me a quick summary” should remain short. The wording also risks overriding Chat’s principle not to replace reading (`src/chat-principles.ts:41`). **Fix:** make only an explicit request for detail override the default: “If they explicitly ask for a detailed, comprehensive, or step-by-step answer, the 300-word guideline does not apply.” Remove bare “summary” and “however long that takes”; add ordinary, brief-summary, and detailed-summary cases.

2. **P1 — The acceptance target rewards verbosity rather than demonstrating that the reader got needed detail.** Evidence: the plan requires requested-detail answers to be at least 1.5× longer (`docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:89`), although the cited smoke answer already exceeded 300 words, covered every section, and was explicitly recorded as evidence that the exception was working (`docs/plans/260930g-briefer-chat-and-explain-answers.md:185`). A padded answer can pass 1.5×; a much more complete answer at 1.4× fails. **Fix:** make blind requested-detail adequacy and article-grounded coverage the primary target, with no padding or repetition; use word count only as a diagnostic. First identify what the current detailed answers omit.

3. **P2 — The plan skips the simplest lever identified by its own diagnosis.** Evidence: it says the nearby line dominates because it starts “Keep it brief” and the model treats the number as a target (`docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:22`), yet rejects changing only that line because the more distant `SYSTEM` exception is weak (`docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:51`). That does not test the stated causal theory. **Fix:** add a `lengthLine`-only arm—e.g. “Follow an explicit request for length or detail; otherwise keep most answers under 300 words.” Change `SYSTEM` only if that arm fails. This also avoids a system-prefix cache rewrite.

4. **P1 — The sibling prompt creates unresolved precedence, and the eval excludes it.** Evidence: the plan claims the sections compose cleanly (`docs/plans/261020t-chat-length-flexes-when-the-reader-asks-for-detail.md:45`), but the sibling says a saved preference applies “in every answer” and wins over prompt length guidance (`(sibling) src/converse.ts:635`). That conflicts with “fit the length to what they asked” when a reader saved “brief answers” and now asks for the long version. The harness deliberately supplies no profile (`evals/chat-length/run.ts:27`). If the sibling lands between arms, it also becomes an uncontrolled prompt change. **Fix:** state one precedence explicitly—normally current explicit request, then standing preference, then the under-300 default—and test saved-brief/current-detailed plus saved-detailed/current-brief. Run every arm with the same sibling code present or absent.

5. **P2 — Blind judging of follow-ups lacks the context required to judge them.** Evidence: the generated pair says each answer followed a different first answer but intentionally does not show either one (`evals/chat-length/run.ts:154`). The follow-up asks for more detail “on that,” so a judge cannot know whether an answer expands, repeats, or omits the original subject. **Fix:** show each side’s complete two-turn transcript—ordinary question, that arm’s ordinary answer, follow-up, and follow-up answer—while keeping arm identity blinded.

7. **P2 — The harness cannot prove that only the prompt changed.** Evidence: result files store no article-content hash (`evals/chat-length/run.ts:101`); pairing checks only the question text (`evals/chat-length/run.ts:149`); and although the returned model is recorded, it is never reported or compared.
