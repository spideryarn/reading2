1. **P1 — A successful older send can delete a newer failed dictation.** Feedback deliberately lets an in-flight send survive close/reopen and resets the form to editing on reopen ([FeedbackDialog.tsx:479](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/FeedbackDialog.tsx:479)). Its completion decides `discard(false)` solely from whether the body changed ([FeedbackDialog.tsx:850](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/FeedbackDialog.tsx:850)). On Safari/Firefox, or after a silent/failed transcription, a newly attempted dictation can finish with an error and recording without changing the body ([useDictation.ts:922](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:922), [useDictation.ts:931](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:931)). It is then idle, so the planned `dismiss()` would erase and forget this newer recording when the older POST succeeds.  
   **Suggested fix:** give dictation artifacts an identity/generation. Capture it when Send starts, and dismiss only that same artifact; starting/recovering a different recording must advance the identity. Add a delayed-send test: close, reopen, make a new dictation fail without changing the body, resolve the old send, and require the new audio/error to survive.

2. **P1 — “Try again” can start during the feedback POST, defeating the planned no-op rule.** Only `DictationButton` receives `disabled={stage.kind === "sending"}` ([FeedbackDialog.tsx:1086](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/FeedbackDialog.tsx:1086)); `DictationStrip` receives no send state, and its retry button remains enabled ([DictationStrip.tsx:370](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/DictationStrip.tsx:370), [DictationStrip.tsx:488](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/DictationStrip.tsx:488)). If the report succeeds while retry is transcribing, the proposed `dismiss()` does nothing; the retry can subsequently insert its transcript into the newly emptied report or restore its error ([useDictation.ts:1583](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1583), [useDictation.ts:1621](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1621)).  
   **Suggested fix:** a terminal dismissal should cancel a retry belonging to the artifact that was present when Send began—abort `retryUpload`, increment `retryGeneration`, then clear it. Also disable Retry while that send is visibly pending. Test both success and failure arriving after the POST.

3. **P1 — The chime can manufacture its own repeated rising edges.** The plan says the tone is recorded and then resets the latch whenever quiet becomes false ([plan:75](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/docs/plans/261001k-dictation-silent-mic-warning-and-a-message-that-goes.md:75)). Any chime recaptured by speakers, or directly by a loopback input, will exceed the activity threshold, making `quiet` false; ten seconds later it becomes true and chimes again ([useAudioLevel.ts:174](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useAudioLevel.ts:174)). That creates a ten-second warning loop. Also, the tone is not intrinsically recorded: `MediaRecorder` receives the microphone track ([useDictation.ts:1813](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1813)); Web Audio output reaches it only acoustically or through a loopback device.  
   **Suggested fix:** chime at most once per dictation session, keyed by `startedAt`, rather than once per quiet stretch. Keep the visual warning edge-sensitive. Rewrite “is recorded” as “may be picked up by the microphone,” and test quiet → sound → quiet still produces only one chime in the same session.

4. **P2 — A separate delayed `AudioContext` contradicts the existing Safari design and may be silent.** The hook deliberately owns one page-long context because Safari has context limits and iOS requires audio activation ([useDictation.ts:174](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:174)); that context is private to this module. A new `quiet-chime.ts` therefore either creates a second context ten seconds after the gesture or needs an unstated refactor. Web Audio autoplay can leave a context suspended, while Apple recommends one long-lived context and explicit user activation. Active `getUserMedia` improves WebKit’s allowance, but does not justify a second context. [Apple Web Audio guidance](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/Using_HTML5_Audio_Video/PlayingandSynthesizingSounds/PlayingandSynthesizingSounds.html), [WebKit’s getUserMedia allowance](https://bugs.webkit.org/show_bug.cgi?id=180680), [W3C autoplay detection](https://www.w3.org/TR/autoplay-detection/).  
   **Suggested fix:** move the existing singleton into a shared audio module and synthesize the chime through it. `quiet` can only become true while that context is running, so this also removes the autoplay uncertainty. Verify the output route on a real iPhone/iPad; there is no inherent MediaRecorder conflict, but Safari audio-session routing is not established by the current code or plan.

5. **P2 — `forgetHeld()` is right for an already-shown recording, but the plan does not handle recovery already in flight.** Plain `release()` is not the answer for the recording attached to a completed report: released failed audio is explicitly offered as `[mic-recovered]` next time ([dictation.md:508](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/docs/project/dictation.md:508)), recreating the reported problem. Forgetting does irreversibly remove a failed recording whose report was typed by hand, but the reader was offered Save and successfully finishing the report is a reasonable terminal discard. That new deletion rule should be stated because current documentation says recordings remain until delivered or discarded ([dictation.md:534](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/docs/project/dictation.md:534)). Separately, an asynchronous `recover()` not yet placed in `held` cannot be touched by `dismiss()`; it may populate after dismissal or be released by effect cleanup and return on a later reopen ([useDictation.ts:1693](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1693), [useDictation.ts:1721](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1721)).  
   **Suggested fix:** forget only the displayed artifact associated with the sent report. Add a recovery-generation guard; an unseen recovery that loses the race should be released and legitimately offered later, not silently forgotten. Document that exception and test recovery resolving on both sides of successful send.

Clearing `error` in `clearRecording()` is otherwise safe: every path that displays a recording pairs it with an error about that recording—silent ([useDictation.ts:923](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:923)), failed ([useDictation.ts:931](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:931)), broken ([useDictation.ts:1011](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1011)), or recovered ([useDictation.ts:1711](/home/greg/code/spideryarn2/.claude/worktrees/fb7z-dictation-silent-mic/src/web/useDictation.ts:1711)).

Verdict: **Revise before build—the basic dismissal moment is sound, but it needs artifact ownership for races, and the chime must be once-per-session on the existing AudioContext.**
