# Plan review — say who owns an article on its details page

1. **P1 — Part 3 widens the admin privacy defence for private-link articles. The narrowest non-widening version is public-only.** The existing rule says identifiers may not be followed into articles and that *which* articles belong to an account is the reader’s reading (`docs/project/admin.md:204-221`, `docs/project/admin.md:277-290`). `/admin/articles` preserves this by exposing another owner’s email beside an opaque article id, while returning a slug/title only for admin-owned or public articles (`src/store/pg-article-transfer.ts:640-679`; `docs/project/admin.md:978-985`). Part 3 joins a private slug and article in Greg’s browser to that owner address (`docs/plans/261020j-say-who-owns-an-article-on-its-details-page.md:54-79`). Possessing a private key grants reading access; it does not grant disclosure of the owner’s account identity or prove the owner personally supplied the key. Reusing `publicAccessWhere`, itself catalogued as a defence (`docs/project/security-map.md:98-99`, `docs/project/security-map.md:130-133`), does not settle this separate policy question. The non-widening form is: owner details on the owner page; owner email on a visitor page only for public articles; private-link visitors see only “You don’t own this article” and “private link”. If Greg wants the private-link-to-account join, ask it explicitly as a defence change and document the exception in both `admin.md` and the security map.

2. **P1 — `publicAccessWhere(slug, key)` does not establish the claimed “could already read as a visitor” condition.** It checks only public visibility or the matching token (`src/store/public-access.ts:45-60`). The real public read also inner-joins a current revision and refuses an article without a tree or blocks (`src/store/public-reader.ts:601-619`, `src/store/public-reader.ts:923-942`); a matching public/keyed import may instead return “still being added” (`src/store/public-reader.ts:928-934`). A direct call to the proposed route could therefore disclose ownership for an article the public route does not return, contrary to the claim at `docs/plans/261020j-say-who-owns-an-article-on-its-details-page.md:62-65`. If approved, the query needs the same published/readable bar and must use `parseShareKey(query.get("key"))` before `accessFor`. Test public and keyed rows with no current revision, tree, or blocks and require 404.

3. **P1 — The deferred link-open question is not decision-ready.** “Each public read that matched by key” is not a definition of an open: the predicate serves article, head, asset, comment, search, and source-guess reads (`src/store/public-reader.ts:593-619`, `src/store/public-reader.ts:658-700`, `src/store/public-reader.ts:759-872`, `src/store/public-reader.ts:1163-1234`). Even if narrowed to one successful article-payload GET, reloads, retries, and repeat visits are loads—not people—so the counter cannot answer “how many people”. Signed-in tracking also cannot happen inside the anonymous read: the client deliberately sends no credentials (`src/web/public-api.ts:1-21`), and the public dispatcher is structurally denied the request and owner identity (`src/public/routes.ts:24-39`). It would require a separate authenticated, best-effort POST with validation and duplicate semantics.

   Present at least: do nothing; count successful payload loads for the current key, explicitly not people; or record signed-in accounts through that separate event, while signed-out people remain unknowable. For each, state who sees it, retention, whether owner/admin opens count, whether old key generations are retained, and that nothing is retroactive. Both tracking choices need privacy wording; the current privacy documentation says who opened a link is not recorded (`docs/project/privacy.md:843-864`), while the plan mentions a privacy change only for signed-in tracking (`docs/plans/261020j-say-who-owns-an-article-on-its-details-page.md:91-97`). “Either resets” is a retention choice, not an implementation detail.

4. **P2 — The ownership sentences are correct for a settled access result, but can become stale.** Ordinarily, the owner page is genuinely behind `access.kind === "owned"` (`src/web/article/ArticlePage.tsx:266-285`). That result requires a successful authenticated article request; 404 falls through to public access, while 401 produces `sessionUnconfirmed` (`src/web/article/access.ts:541-583`, `src/web/article/access.ts:603-618`). The generic article route has no admin bypass (`src/routes.ts:11226-11233`); the admin gate applies only under `/api/admin` (`src/routes.ts:14061-14110`). The fixture fallback is documented as dead and suppresses the sharing section if reached (`src/web/Metadata.tsx:743-787`, `src/web/Metadata.tsx:1329-1356`). Thus fixture/admin status is not a counterexample, and suppressing “You don’t own” when the session is unconfirmed is correct.

   The counterexample is a later transfer. The article is fetched once across views (`src/web/article/ArticlePage.tsx:64-71`), while transfer changes `owner_id`, makes it private, and clears its key (`src/store/pg-article-transfer.ts:585-610`). An old owner’s tab can continue saying “You own this article”. Conversely, a gift claim can transfer a visitor’s article while it remains on screen; the existing hook re-reads only after the claim request settles (`src/web/article/useClaimSharedArticle.ts:1-24`, `src/web/article/useClaimSharedArticle.ts:67-79`). Either acknowledge ordinary stale UI or perform a fresh owner check before categorical wording; at minimum test the known gift-claim transition.

5. **P2 — The admin visitor’s identity, key, and request lifetime need an explicit path.** `ArticlePage` already has the exact `readerId` used to key access (`src/web/article/ArticlePage.tsx:81-122`; `src/web/article/access.ts:254-324`), but `VisitorArticle` and `PublicMetadataPage` receive only `signedIn: boolean` (`src/web/article/ArticlePage.tsx:735-783`; `src/web/PublicPages.tsx:134-151`). The private `shareKey` likewise exists in `ArticlePage` but is not passed down (`src/web/article/ArticlePage.tsx:114-121`). `useSession()` is available—the owner metadata page uses it (`src/web/Metadata.tsx:535-541`)—but passing `readerId` is safer because it is the identity for which access was resolved. Pass both `readerId` and `shareKey`; require `!sessionUnconfirmed && isAdmin(readerId)`; bind the request to that id; and key/drop its response by slug, reader id, and key. Add a test that an unconfirmed admin session makes no admin request. The namespace gate remains the real authorization (`src/routes.ts:14080-14110`).

6. **P2 — Shared single-account lookup already exists: `accountEmail`. Preserve its failure state.** `accountEmail(ownerId)` calls `GET /auth/v1/admin/users/{id}`, applies a five-second deadline, verifies the returned id, and returns `found | unavailable` (`src/store/admin-accounts.ts:422-456`, `src/store/admin-accounts.ts:548-590`). Use it rather than listing every account and filtering, as `/admin/articles` currently does (`src/routes.ts:10262-10278`). Do not flatten `unavailable` into an unexplained `ownerEmail: null`; the list route exposes `emailsAvailable` specifically so an Auth outage does not resemble an account without an address (`src/routes.ts:10265-10278`). Also decide whether to match `/admin/articles` on soft-deleted accounts: `accountEmail` does not filter them, while `listAccounts` does through `accountFrom` (`src/store/admin-accounts.ts:243-263`).

7. **P3 — Parts 1–2 and the response can be simpler.** `PublicMetadataPage` already renders `SharedNotice` (`src/web/PublicPages.tsx:205-212`), which already prints `sharedSentence(sharedBy)` (`src/web/PublicChrome.tsx:227-229`, `src/web/PublicChrome.tsx:384-399`). A second Access section repeating that sentence duplicates public/private-link status and requires exporting a currently private helper. Add only “You don’t own this article” to the existing notice; signed-out and unconfirmed visitors need no new UI. On the owner side, reuse the `useSession()` already present in `Metadata`.

   For a confirmed visitor, `mine` is already false by the capability seam, and `sharedBy` determines visibility because public wins (`src/store/public-access.ts:11-16`; `src/store/public-reader.ts:700-702`). The only new server facts are owner address and, for a public article, whether a private link is also active. If part 3 becomes public-only, the existing `/api/admin/articles` response can already be matched by slug (`src/store/pg-article-transfer.ts:663-679`); reusing that list versus adding a small single-row endpoint is then a latency choice, not a new privacy capability.

**Verdict:** Parts 1–2 are sound after accounting for transfer staleness and avoiding duplicate visitor copy. Part 3 is not within the current defence for private-link articles: make it public-only or ask Greg to approve the explicit widening. Reframe link-open tracking before asking him to choose.
