1. **High — the hold has no single ownership/cancellation mechanism, so it can fight later programmatic arrivals.**  
   Evidence: the plan promises cancellation on “a newer arrival or jump” ([plan:50](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:50>)), but several arrivals call `scrollToBlock` directly rather than `jumpTo`: note-link arrival ([Reader.tsx:2360](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/reader/Reader.tsx:2360>)), Skim quote arrival ([SkimMode.tsx:975](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/modes/skim/SkimMode.tsx:975>)), and figure arrival ([walk.ts:84](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/modes/skim/walk.ts:84>)). A later resize/font event could therefore pull the page back to the restored `?at=` after Skim or a note deliberately centred somewhere else. There is also a commit-to-passive-effect window: `layoutKey` reacts in a layout effect ([useReadingPosition.ts:132](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/reader/useReadingPosition.ts:132>)), while URL restoration and its cleanup are passive ([useReadingPosition.ts:58](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/reader/useReadingPosition.ts:58>)); an old unbounded hold can fire between them.  
   **Fix:** make arrival holding scroll-owned, with one generation/token and alignment (`top` or `centre`). Every new `scrollToBlock`/`scrollToTop` invalidates the old owner automatically; the owner’s own re-alignment passes its token so it is preserved. Update/invalidate the desired token synchronously before passive effects. Extending the existing arrival-anchor machinery is simpler and safer than adding a second unrelated global hold.

2. **High — stopping `keepAligned` does not stop `scrollToBlock("auto")`’s corrective frame.**  
   Evidence: even an instant glide moves synchronously and then schedules one corrective animation frame ([scroll.ts:755](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/scroll.ts:755>), [scroll.ts:780](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/scroll.ts:780>), [scroll.ts:799](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/scroll.ts:799>)). The existing input cancellation for a glide covers wheel, touch and `pointercancel`, but not `keydown` or `pointerdown` ([scroll.ts:786](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/scroll.ts:786>)). Meanwhile `keepAligned` merely disconnects its own observers/listeners ([flash.ts:401](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/flash.ts:401>)). A reader can press a key or grab the scrollbar after the initial restore but before the corrective frame, end the proposed hold, and still be pulled back one frame later.  
   **Fix:** when reader input ends this arrival, cancel the corrective frame too—through an owner-aware cancellation operation, or `abandonScroll()` before releasing the hold. Add a test where `pointerdown`/`keydown` occurs between the synchronous move and the next animation frame.

3. **High — Stage 2 does not actually close the 300 ms departure window it claims to close.**  
   Evidence: `at` writes are debounced for 300 ms ([params.ts:53](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/params.ts:53>), [params.ts:116](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/params.ts:116>)); the spy updates `synced.current` immediately but the address later ([useReadingPosition.ts:231](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/reader/useReadingPosition.ts:231>)). Suppose the address still says section A, the reader crosses into B, and the note is `{at: B, block: B7}`. The plan says substitution occurs only when the address’s `at` matches the note ([plan:76](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:76>)); the immediate note-triggered save therefore stores A. Only the later address event would store B7. Leaving the SPA within 300 ms loses the precise position, contradicting “needs no unload hook.” Returning to the masthead has the analogous problem: there is no paragraph note to overwrite the previously stored paragraph before `at` is eventually removed.  
   **Fix:** distinguish the two save causes. On a fresh measurement, immediately build a remembered search from the current non-position parameters and set/remove `at` using the measured block/top regardless of whether the raw URL has caught up. On later address-change saves, substitute only when the address matches the note’s section/generation. Represent top explicitly, e.g. `{at: null, block: null}`, and save it immediately. Tests must cover navigating away before the debounce and returning to top before it.

4. **Medium — the proposed note is not scoped to a reader/article lifecycle.**  
   Evidence: the plan names only `{at, block}` ([plan:71](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:71>)). `useLastView` deliberately handles a reader changing while the same article remains mounted, strips reader A’s state, and restores reader B’s ([last-view.ts:755](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/last-view.ts:755>), [last-view.ts:774](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/last-view.ts:774>)). A stale note from A can match B’s coincidentally identical `at` and be saved under B. The same ambiguity exists across an article/metadata view transition because the save listener deliberately accepts whichever view this hook represents ([last-view.ts:844](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/last-view.ts:844>)).  
   **Fix:** scope the snapshot to `{slug, readerId, arrivalGeneration, at, block}` or register an active saver closure owned by the current `useLastView` instance. Clear/invalidate it before processing a reader or slug change. Carrying the same reader’s paragraph into Metadata is useful—Metadata already treats `at` as an exact block ([Metadata.tsx:725](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/Metadata.tsx:725>))—but that should be explicit. A first open at the masthead should create only the explicit top snapshot, never inherit an old note.

5. **Medium — “last visible row” plus `visibleNear` is insufficiently specified for hidden rows.**  
   Evidence: Stage 2 proposes a binary search followed by `visibleNear` ([plan:71](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:71>)). Hidden rows have zero height and tie the next visible row; `isRowHidden` is the established predicate for excluding them ([fold.ts:612](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/fold.ts:612>)). `visibleNear` handles folds and shut stretches, but it does not map a masthead echo encountered normally—it returns the id unchanged unless it is walking backward from a trailing stretch ([fold.ts:589](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/fold.ts:589>)). A naïve binary search can therefore remember the hidden title echo or a row inside a long folded run. A shut front-matter stub has separate semantics: its row is visible but its block content is not, and `visibleNear` intentionally maps it past the stretch.  
   **Fix:** define the sampler over rows for which `!isRowHidden(id)`, explicitly return top when no eligible row has crossed the reading line, then canonicalise the selected visible/stub row with `visibleNear`. Precompute eligible row indexes so binary search remains logarithmic despite long hidden runs. Test leading masthead echoes, real folds, an opening stretch stub, a trailing References stub, and all rows below the reading line.

6. **Medium — “no cap” is defensible, but not with `keepAligned` moved “unchanged.”**  
   Evidence: the existing helper reads `document.fonts.ready` and installs a timer ([flash.ts:375](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/flash.ts:375>), [flash.ts:398](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/flash.ts:398>)). The repository has a dedicated font subscription specifically because reading `fonts.ready` was 21.5% of script time in a long article and misses later batches ([fonts.ts:2](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/fonts.ts:2>), [fonts.ts:22](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/fonts.ts:22>)). With no deadline, every missed cancellation becomes a lifetime `ResizeObserver` and font/input listener. Also, a scroll event whose target is temporarily displaced by the very layout change the observer is meant to repair can end the hold before the resize/font callback runs; event ordering needs a real-browser check.  
   **Fix:** share a helper that uses `onFontsChanged`, takes `deadlineMs: number | null`, and has idempotent owner-aware teardown. Observe the table/body and target as required, disconnect on input, new arrival, missing target, identity change and unmount. “No cap” is then safe: an idle observer costs virtually nothing and is exactly what late images/fonts require. Prove the layout-scroll ordering in the cold-cache browser test rather than assuming it.

7. **Low — paragraph-valued `?at=` is compatible, but the plan describes its URL contract incorrectly.**  
   Evidence: the plan says “`?at=` in the address stays a section” ([plan:67](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:67>)) and later says restoration puts a paragraph into `?at=` ([plan:79](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/docs/plans/261019a-reopen-lands-on-the-paragraph-you-were-reading.md:79>)). Once restored, copying the address shares that paragraph, not merely a local-storage-only refinement. That is probably desirable and is already a supported state: `positionToWrite` preserves a fine block inside its section ([position.ts:210](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/position.ts:210>)). I found no bad consumer: Diagram maps any block to its row ([DiagramMode.tsx:103](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/modes/diagram/DiagramMode.tsx:103>)); Marginalia resolves a tree path from it ([Reader.tsx:4062](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/reader/Reader.tsx:4062>)); Feedback and Chat benefit from the finer block; ReturnChip reads its history stamp, not current `at`; and Skim tests only whether `at` is present ([SkimMode.tsx:172](</var/tmp/spideryarn-worktrees/fbqspg5a-reopen-where-you-were/src/web/modes/skim/SkimMode.tsx:172>)).  
   **Fix:** state the real contract: ordinary scrolling keeps the public URL section-granular, while jumps and local restoration may place a paragraph in `?at=`; once present, reloads and copied links preserve that paragraph. Add one shared-link/Skim-presence regression test.

A simpler design is available for Stage 1: generalise the existing arrival anchor into one scroll-owned arrival object with `align: "top" | "centre"` and optional active alignment, rather than introducing a parallel hold with separate cancellation rules. For Stage 2, keep the paragraph snapshot inside the existing last-view subsystem, scoped to its current reader/article generation, and make the measurement-triggered save authoritative immediately; do not add another storage key or write every paragraph into the live URL.

The measured diagnosis and the overall two-stage direction are sound. The missing pieces are lifecycle and timing contracts, not a reason to abandon the feature.
