1. **High — the proposed response is rejected by the client as internally inconsistent.** The client requires `more === (counts[show] > reports.length)` ([FeedbackEarlier.tsx](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/src/web/FeedbackEarlier.tsx:199)). The proposed route test returns one row, `counts.waiting: 3`, and `more: false` after filtering ([feedback-route.test.ts](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/tests/feedback-route.test.ts:795)). That fails validation, so the real *Needs a decision* request becomes `[fb-list]` rather than removing the stray row. The plan’s “no wire-shape change” is not enough: it changes the envelope’s semantics without updating its invariants.

2. **High — filtering after the store’s limit can hide genuine orphans and makes the “more” line false.** `listMineByStatus` selects only the newest `limit + 1` waiting reports before the route sees them ([pg-feedback.ts](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/src/store/pg-feedback.ts:532)). If the newest 50 are covered by questions and report 51 is a real orphan, route filtering returns no rows while the orphan is never examined. With a nonempty remainder, the UI can say “Showing 1 … of your 51 waiting reports” even though 50 are threads, not omitted orphan rows ([FeedbackEarlier.tsx](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/src/web/FeedbackEarlier.tsx:1860)). Filtering must happen before pagination with its own orphan count/`more`, or the unfiltered rows must remain on the wire.

3. **Medium — the rule is sensible for this repeat, but the proposed data cannot actually establish “the question about that note.”** A question records only one report id; its free-form `refs` is optional and deliberately not compiled ([feedback-reports.md](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/docs/project/feedback-reports.md:534)). Meanwhile, endings allow one report to occur in several notes ([feedback-endings.ts](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/scripts/feedback-endings.ts:275)). If A and B share awaiting note 1, but A’s open question concerns a separate note 2, the proposed rule hides B even though nobody asked about note 1. Either document and enforce that a multi-report awaiting note represents inseparable whole-report repeats, or encode which note/question establishes the coverage.

4. **Medium — “not transitive” needs a direct test.** The new test covers one awaiting pair and a shipped pair, but not two awaiting groups `A–B` and `B–C` ([feedback-questions.test.ts](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/tests/feedback-questions.test.ts:443)). An implementation that grows the set while traversing groups would silently mark C asked. The intended conservative one-hop rule is right and should be pinned explicitly.

5. **Low — the two owning docs would become stale.** Both currently define an orphan as a waiting report that no open question is directly about ([feedback.md](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/docs/project/feedback.md:396), [feedback-reports.md](/var/tmp/spideryarn-worktrees/qi7j8d72p9-repeat-covered-by-question/docs/project/feedback-reports.md:574)). They should state the shared-awaiting-note rule. The Overseer needs no separate logic change because it invokes `feedback-questions.ts`; `feedback-unswept.ts` is unaffected because the shared note already covers both report ids.

The simpler safe design is to keep the status page’s rows, counts and `more` untouched, add a versioned `coveredReportIds`/per-question coverage field to the admin response, and let the existing client orphan filter use it. Pager and auto-switch already depend on question state, not rows; the pill already counts waiting threads. If orphan pagination itself must be exact, it needs a distinct server-side orphan query with its own count and `more`.

VERDICT: reject
