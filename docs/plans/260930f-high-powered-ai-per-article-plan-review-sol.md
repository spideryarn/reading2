## Findings

**F1 — P1 — Citation lookup freshness bypasses `sameGenerator`.**  
The plan says the standard/high models are freshness-equivalent through `sameStamp` and `arc.ts` ([plan:90](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/docs/plans/260930f-high-powered-ai-per-article.md:90)). But citation lookup and investigation fingerprints include the exact configured model ([citation-lookup.ts:149](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/citation-lookup.ts:149), [citation-investigate-context.ts:132](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/citation-investigate-context.ts:132)). `loadCitations` recomputes both with the current model ([pg.ts:3638](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/store/pg.ts:3638), [pg.ts:3675](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/store/pg.ts:3675)). After either toggle, the stored hashes no longer match and the lookup/investigation is detached from the article. This is user-visible disappearance and may make Investigate repeat its lookup.

Proposed fix: give these two hashes a canonical generation key that maps only the four standard/high wire and stored spellings to one value, while retaining exact matching for overrides and unrelated models. Use it at write and read time. Add toggle-on and toggle-off attachment tests for both lookup and investigation. Keep checkpoint fingerprints exact—the labels and hierarchy checkpoints correctly need different keys.

**F2 — P2 — The effort decision promised by the plan is absent.**  
The plan correctly notes that an unspecified effort changes from Sonnet’s `high` to Opus’s `medium`, then promises Stage 1 will enumerate and decide those calls ([plan:50](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/docs/plans/260930f-high-powered-ai-per-article.md:50)). Stage 1 does not do so. Most chat-wire capable jobs explicitly choose `providerDefault` ([ai-call.ts:798](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/ai-call.ts:798)); the Messages-wire `illustrated` call also sends adaptive thinking without `output_config.effort` ([illustrated.ts:903](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/illustrated.ts:903)). Therefore “high-powered” silently lowers effort for chat, explain, search, debate, quiz marking, citation work, PDF frontmatter, source guessing, and Illustrated.

Proposed fix: add the promised task-by-task matrix and make each change—or deliberate use of medium—explicit. Do not blanket-set `high`: `max_tokens` includes reasoning tokens ([ai-call.ts:768](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/ai-call.ts:768)), so each high-effort choice needs its ceiling checked.

**F3 — P2 — The deferred billing recommendation charges the wrong period.**  
The recommended sticky column is described as “the same query” with no ledger row ([plan:171](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/docs/plans/260930f-high-powered-ai-per-article.md:171)). The existing query counts `ingest_events` and filters paid accounts by the event’s `succeeded_at` period ([pg-billing.ts:395](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/store/pg-billing.ts:395), [pg-billing.ts:450](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/store/pg-billing.ts:450)). Switching an older article on this month would therefore create no current-period charge; multiplying its old ingest row either backdates the charge or leaves it outside the window. It also retroactively multiplies every ingest row associated with the article, while the current contract is explicitly N ingest rows to one article ([billing.md:658](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/docs/project/billing.md:658)).

Proposed fix: recommend a one-time, article-unique high-power charge event timestamped when the switch is first enabled. Its price can still be recomputed from live visibility, with deletion freezing analogous to ingest charges. Decide explicitly whether duplicate ingests should affect that single upgrade charge. `high_power_charged_at` may record state, but cannot be the accounting event by itself.

**F4 — P2 — Two reachable request paths are missing from the Stage 2 checklist, and the compiler guarantee is incomplete.**  
Stage 2’s request-path list omits the legacy-but-reachable citation `/find` route and the active upload source-guess route ([routes.ts:7974](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/routes.ts:7974), [routes.ts:8024](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/routes.ts:8024)). Stage 1 names their tasks, but misclassifies them as pipeline calls ([plan:128](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/docs/plans/260930f-high-powered-ai-per-article.md:128)). Moreover, high-level helpers retain optional model defaults ([citation-find.ts:542](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/citation-find.ts:542), [source-guess-run.ts:158](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/source-guess-run.ts:158)), so making `modelFor` require power does not itself force the route to supply the article’s power.

Proposed fix: add both routes explicitly, including citation investigation’s nested find-first path. Require `power` or `model` at production entry points, leaving standard-default wrappers only for scripts/evals. Test these routes separately rather than testing just one representative request path.

**F5 — P2 — Prompt-cache compatibility needs an Opus 5.5 check.**  
The cache threshold is hard-coded for Sonnet 5, and its own comment explicitly says a model change must revisit it because floors are non-monotonic ([article-prompt.ts:225](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/article-prompt.ts:225)). The plan does not. OpenRouter’s current [prompt-caching documentation](https://openrouter.ai/docs/guides/best-practices/prompt-caching) does not yet state Opus 5.5’s minimum and lists several recent Opus models at 4,096 tokens, versus the app’s 1,024. If 5.5 differs, short high-power prompts will accept `cache_control` but silently receive no cache.

Proposed fix: live-probe Opus 5.5’s cache floor on both wires and make `underCacheFloor` model-aware if it differs.

## Checks that passed

- The admin-only v1 needs no new billing defence. The namespace gate precedes dispatch ([routes.ts:9399](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/routes.ts:9399)), `ownedSlug` enforces both slug and caller owner ([owned-slug.ts:45](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/store/owned-slug.ts:45)), and bare-slug re-runs already bypass ingest reservations ([routes.ts:9041](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/routes.ts:9041)). The planned second `isAdmin(owner)` check prevents hand-edited non-admin rows from enabling Opus.
- Per-step reading is coherent: one `StepContext.power` can govern preflight, all calls, provenance, and commit for that step. Successors, retries, resets, hierarchy structure/deepening, and forced re-runs all pass through `runStep`. Treat “missing article means standard” only for a genuinely new ingest; an unexpectedly missing reset/retry article should fail rather than silently downgrade.
- The AsyncLocalStorage concern is real: an async generator constructed inside `run()` and iterated after the callback returns executes outside that context. Required arguments are proportionate and safer. A strict ALS that throws when unset would be smaller, but it trades compile-time completeness for runtime failures and is not equally safe.
- Opus 5.5 supports the existing `max_tokens`, tools, adaptive effort, and 128K completion ceiling; Anthropic Messages supports `output_config`, provider routing, and `cache_control`. Anthropic’s native web search covers current Opus models. See OpenRouter’s [model page](https://openrouter.ai/anthropic/claude-opus-5.5), [Messages API](https://openrouter.ai/docs/api/api-reference/anthropic-messages/create-messages?explorer=true), and [web-search documentation](https://openrouter.ai/docs/guides/features/server-tools/web-search). Existing `max_uses` is already known not to cap searches ([converse.ts:243](/home/greg/code/spideryarn2/.claude/worktrees/fb6c-high-powered-ai/src/converse.ts:243)); that pre-existing cleanup can stay outside this v1.
