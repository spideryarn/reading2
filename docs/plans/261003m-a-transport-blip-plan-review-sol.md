The root cause is right, and `streamMessage` is the right retry boundary. The SDK retry and whole-step retry remain worse options. The plan needs several changes first.

1. **P1 — A generic 429 retry would bypass and multiply the existing rate-limit policy.** The plan retries 429 internally ([plan:85](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/docs/plans/261003m-a-transport-blip-fails-an-import-one-countable-retry-on-the-messages-wire.md:85>)), but Structure deepening already turns a 429 into `ExpansionRateLimited`, preserves `Retry-After`, and feeds it to a shared `WidthGate` ([structure-deepen.ts:826](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/structure-deepen.ts:826>), [structure-deepen.ts:1428](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/structure-deepen.ts:1428>)). With both loops, one logical expansion can make up to nine requests; the gate sees only every third 429, after two retries have ignored the provider’s delay. The PDF precedent explicitly honours `Retry-After` and coordinates concurrency ([pdf-read.ts:1270](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/pdf-read.ts:1270>)); `ai-call` likewise leaves 429 policy to its caller ([ai-call.ts:801](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/ai-call.ts:801>)). Cut 429 from this generic retry. Handling it globally would require a larger refactor of the existing gate and caller retry.

2. **P1 — Two callers’ published call counts would become false.** `SimpleRun.calls` promises “writer requests made, across every level and retry,” but increments once per `streamMessage` ([simple-summary.ts:795](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/simple-summary.ts:795>), [simple-summary.ts:934](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/simple-summary.ts:934>)). Labels similarly says `calls` is the number of requests and stamps each invocation as exactly one request ([labels.ts:1796](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/labels.ts:1796>), [labels.ts:1957](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/labels.ts:1957>)). An internal retry would leave both artifacts saying one while the ledger correctly says two. Expose an attempt count from `MeteredCall` and consume it in these two callers, or explicitly redefine and rename those fields; silently changing their meaning is not acceptable.

3. **P1 — “No `message_start`” proves nothing was shown, but not that nothing was generated or billed.** The log inference itself is sound: `safeError` copies numeric statuses ([log.ts:105](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/log.ts:105>)), while `anthropicCallFailed` attaches one only when the SDK supplied one ([anthropic-call.ts:90](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/anthropic-call.ts:90>)). Therefore the production error had no numeric HTTP status. But the stronger assertion that nothing was generated is unsupported ([plan:42](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/docs/plans/261003m-a-transport-blip-fails-an-import-one-countable-retry-on-the-messages-wire.md:42>)). The SDK receives a successful HTTP response before consuming events ([MessageStream.ts:209](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/node_modules/@anthropic-ai/sdk/src/lib/MessageStream.ts:209>)), and an SSE `error` becomes an `APIError` with undefined status ([streaming.ts:139](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/node_modules/@anthropic-ai/sdk/src/core/streaming.ts:139>)). A dropped response can also happen after the server accepted work. The safe claim is: no exposed listener saw a start or text, while the first attempt’s cost is unknown and may have been billed. Keep `message_start` as the retry boundary, but document that retrying accepts a possible duplicate charge and records the first attempt as unpriced.

4. **P1 — “Any status-less APIError” includes deterministic streamed failures.** The SDK preserves an SSE error’s `type`, whose closed union includes authentication, permission, invalid-request, not-found, billing, rate-limit, timeout, overload, and API errors ([shared.ts:40](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/node_modules/@anthropic-ai/sdk/src/resources/shared.ts:40>)). Retrying all status-less `APIError`s ([plan:85](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/docs/plans/261003m-a-transport-blip-fails-an-import-one-countable-retry-on-the-messages-wire.md:85>)) therefore asks deterministic streamed failures three times. Retry connection/timeout classes and explicitly transient SSE types such as `timeout_error`, `overloaded_error`, and `api_error`; decide deliberately what to do with a missing type. Also either add 409 or document its omission: the installed SDK treats 409 as a retryable lock timeout ([client.ts:1439](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/node_modules/@anthropic-ai/sdk/src/client.ts:1439>)).

5. **P2 — The proposed `aborted()` semantics contradict the backoff test and its public contract.** During backoff, the current stream is the already-failed, non-aborted attempt, so “reports the current attempt’s stream” ([plan:94](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/docs/plans/261003m-a-transport-blip-fails-an-import-one-countable-retry-on-the-messages-wire.md:94>)) would return false, while the planned test expects true ([messages-stream.test.ts:711](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/tests/messages-stream.test.ts:711>)). Define it as whether the logical `MeteredCall` ended by abort, including an abort during backoff. No production caller currently invokes `aborted()`, but the exported interface promises that meaning ([messages-stream.ts:410](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/messages-stream.ts:410>)).

6. **P2 — Strengthen the tests around the exact boundary and accounting lifecycle.** The proposed post-start test includes text ([messages-stream.test.ts:697](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/tests/messages-stream.test.ts:697>)), so an incorrect implementation that retries until the first text—rather than until `message_start`—would pass. Add a `message_start` followed immediately by failure, with no text, and assert one request. Also assert `report.pending` is empty after a retry; `beginSpend` mints each pending call and row ID ([ai-spend.ts:811](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/ai-spend.ts:811>)), and `recordSpend` clears it by call ID ([ai-spend.ts:987](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/ai-spend.ts:987>)). The same collector naturally gives attempts one `runId` and distinct row IDs, so the accounting design is otherwise correct. The 400 and current post-start tests pass before the fix; that is acceptable negative coverage, but only the first test is the stated reproduction.

7. **P2 — Update the remaining “one `streamMessage`, one record/request” claims.** The function documentation still says one finished call produces exactly one `SpendRecord` ([messages-stream.ts:441](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/src/messages-stream.ts:441>)), and an existing test is named “calls the transport once per streamMessage” ([messages-stream.test.ts:427](</home/greg/code/spideryarn2/.claude/worktrees/fbx4zut6-import-failed-at-arc/tests/messages-stream.test.ts:427>)). The new invariant is one network attempt, one record. The plan mentions updating only the `maxRetries` comment and gateway documentation, so these stale claims should be added.

The deferrals for the other wire and failures after `message_start` are correct; neither should be pulled into this change.
