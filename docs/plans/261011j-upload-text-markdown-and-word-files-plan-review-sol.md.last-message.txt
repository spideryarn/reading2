1. **High — Converted HTML is sound as the pipeline input, but not as the only retained source.**

   **Evidence:** The plan explicitly discards the uploaded bytes and stores only the conversion ([plan:20](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/plans/261011j-upload-text-markdown-and-word-files.md:20>), [plan:50](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/plans/261011j-upload-text-markdown-and-word-files.md:50>)). That conflicts with “Never lose what the reader gave us” ([vision.md:121](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/project/vision.md:121>)) and makes several downstream claims false:

   - Feedback promises “the file it was made from” but would attach converted `source.html` ([feedback-article.ts:2](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/feedback-article.ts:2>), [feedback-article.ts:77](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/feedback-article.ts:77>)).
   - Rollback export writes the canonical HTML, not the uploaded `.docx`/Markdown ([export.ts:251](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/store/export.ts:251>)).
   - Rebuild works, but permanently reuses the derivative, so a corrected converter cannot improve the article ([jobs.ts:3739](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/jobs.ts:3739>)).
   - The injection scan claims to inspect raw source because conversion loses hiding evidence ([source-scan.ts:16](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/source-scan.ts:16>), [security-map.md:19](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/docs/project/security-map.md:19>)). Mammoth deliberately discards Word colours and layout, so a white/zero-size/off-page instruction can become ordinary converted HTML and yield a misleading “HTML examined” result.

   The ordinary downstream HTML path otherwise fits: extraction already handles uploaded HTML without a URL ([pipeline.ts:2873](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/pipeline.ts:2873>)); masthead/metadata use the retained filename ([SourceLink.tsx:117](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/web/SourceLink.tsx:117>)); slugging still uses that filename ([routes.ts:7412](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/routes.ts:7412>)); and the CLI’s wider classification/content-type mapping is the right shape ([stage.ts:475](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/stage.ts:475>), [stage.ts:497](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/stage.ts:497>)).

   **Fix:** Keep the original as a separate content-addressed object with durable source-format provenance; keep converted HTML as the stage-2 derivative and `DocumentKind: "html"`. Feedback/export should include the original. Until DOCX hidden-content scanning exists, report DOCX as unexamined rather than scanning its derivative as “raw”. If that is too much for this iteration, defer DOCX—but text and Markdown originals still need retaining.

2. **High — The `fflate.unzipSync` ZIP-bomb guard is not sound as described.**

   **Evidence:** Deflated entries do receive `new Uint8Array(originalSize)` ([fflate index.mjs:2693](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:2693>), [fflate index.mjs:2704](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:2704>)), but the inflate loop continues to the stream’s real expanded length after the buffer is full; out-of-bounds typed-array writes are merely discarded ([fflate index.mjs:395](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:395>), [fflate index.mjs:403](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:403>)). Thus the proposed “output is ≤1 KB” test can pass while 100 MB—or far more—was still inflated, leaving the CPU bomb intact.

   Stored entries are another hole: method 0 copies the declared compressed size, not the checked `originalSize` ([fflate index.mjs:2701](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:2701>)). That is bounded by the 50 MiB upload, but defeats the promised 32 MiB guard.

   Central-directory sizes and names are authoritative; the local header is used mainly to locate payload bytes ([fflate index.mjs:1851](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:1851>), [fflate index.mjs:1853](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:1853>)). Data descriptors therefore do not strengthen the bound, and ZIP64 merely supplies larger declared values ([fflate index.mjs:1859](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/fflate/esm/index.mjs:1859>)).

   **Fix:** Stream entries and abort based on actual emitted uncompressed bytes, per entry and cumulatively. Skip media without opening it; reject unsupported/encrypted methods, duplicate names, stored-size disagreement, excessive entries, and malformed central/local metadata. Re-zip only fully validated parts. Tests must prove early abort—not merely truncated output—for lying deflate sizes, stored entries, data descriptors, ZIP64, duplicates and header disagreement.

3. **Medium — Billion-laughs is not reachable, but Mammoth still needs isolation and a stronger security floor.**

   **Evidence:** xmldom uses only its fixed predefined XML entity map ([dom-parser.js:75](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/dom-parser.js:75>), [entities.js:12](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/entities.js:12>)); its DTD handling records the declaration without installing or recursively expanding internal entities ([sax.js:590](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/@xmldom/xmldom/lib/sax.js:590>)). Billion-laughs/XXE is therefore not the problem.

   Mammoth itself warns that malicious documents can cause pathological CPU or memory use and recommends a separate thread with a timeout ([README.md:548](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/README.md:548>)). Its 1.12.3 release fixed another denial-of-service case ([NEWS:1](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/NEWS:1>)). Also, “≥1.11.0” is not a sufficient external-file security floor: 1.12.2 fixed prototype pollution that could turn `externalFileAccess` back on ([NEWS:13](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/node_modules/mammoth/NEWS:13>)). The lock currently resolves safe versions—Mammoth 1.12.3 and xmldom 0.8.15 ([package-lock.json:9121](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/package-lock.json:9121>), [package-lock.json:6839](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/package-lock.json:6839>)).

   **Fix:** Run DOCX preflight and conversion in a terminable worker/process with timeout and memory limits. Require at least 1.12.3, keep `externalFileAccess: false` explicit, disable `includeEmbeddedStyleMap`, and use an image converter that never invokes an image read. Test the timeout and an external-image document.

4. **Medium — The plan lacks a bound on converted HTML itself.**

   **Evidence:** Escaping can expand plain text several-fold, and Markdown conversion can likewise produce output larger than its input ([upload-convert.ts:98](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/upload-convert.ts:98>), [upload-convert.ts:123](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/upload-convert.ts:123>)). Stage 1 then stores that entire derivative ([pipeline.ts:1718](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/pipeline.ts:1718>)), while the `sources` bucket still has a 50 MiB object limit ([config.toml:162](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/supabase/config.toml:162>)). An accepted 11 MiB file consisting mostly of `&` can already cross that storage limit after escaping; a 50 MiB Markdown file can consume much more memory before the PUT fails.

   **Fix:** Give conversion an explicit UTF-8 output cap and a reader-facing refusal; never truncate. Bound conversion CPU/memory as well—preferably through the same isolated worker—and add positive-control tests showing an expanding input is refused before canonical storage.

5. **Low — `text/plain` staging is fine; deployment wording and tests need tightening.**

   **Evidence:** The staging MIME is only a private bucket allowlist claim. The supported converted extension wins before browser MIME guesses ([uploads.ts:250](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/uploads.ts:250>)), the server later verifies bytes, and canonical output remains `text/html`. So using `text/plain` for `.txt` and Markdown is harmless and keeps the allowlist smaller ([uploads.ts:307](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/src/uploads.ts:307>)).

   The deploy does not apply bucket changes; it only reports/refuses drift ([deploy.ts:1412](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/deploy.ts:1412>)). The separate `check-buckets --prod --apply` command performs and verifies the mutation ([check-buckets.ts:146](</var/tmp/spideryarn-worktrees/fbqxh28e-upload-txt-md-docx/scripts/check-buckets.ts:146>)).

   **Fix:** Say explicitly that the production bucket must be updated before the deploy gate can pass. Expand acceptance tests to cover Markdown end-to-end, realistic browser MIME guesses, CLI staging types, retained-original export/feedback, source-scan coverage, rebuild semantics, converted-output overflow, and the adversarial ZIP cases above.
