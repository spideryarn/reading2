# The regenerate hook says when it declines a commit that names its sources

Fixed under Greg's standing rule for bugs (2026-10-09: *"You are definitely authorised to fix bugs
any time you notice them"*). Found by the 261009p session and its postmortem,
[261009j](../postmortems/261009j-a-hook-that-cannot-read-the-command-does-nothing-and-says-nothing.md),
which named this as the right default for the regenerate hook and left it as a separate change.
Builds on [261007q](261007q-generated-files-regenerate-on-commit.md), which added the hook, and
[261009p](261009p-the-commit-hook-reads-only-one-commit-command-in-seven.md), which fixed its
sibling.

## The problem

`.claude/hooks/regenerate-commit-generated.sh` regenerates `src/help-corpus.generated.json` and the
two `src/feedback-*.generated.ts` files when a commit carries one of their sources, and appends the
output to the commit. It reads the command through `commit_command.parse(…, approval=True)` and acts
only on the house recipe with the commit last, because it rewrites the command and grants it
permission. That strictness is right and stays.

What was wrong is that it declined **silently**. On a commit whose text plainly names a Help page or
a feedback note, it said nothing, the generated file could go in stale, and the help-corpus or
feedback test went red later, on the full suite or the deploy gate — the delay the hook was built to
remove.

Counted over every Bash `tool_use` in the last three days of transcripts on the box, with
[`261009t-measure.py`](261009t-measure.py) (the 261009p regex; the text-only parts of the hook's
decision, replayed with each transcript's `cwd`):

| | commit commands | the hook acts | it declines, silently |
|---|---|---|---|
| any `git commit` | 917 | 123 | 794 |
| naming a source or a generated file, by substring | 174 | 37 | **137** |

That is command-shape evidence, not a count of stale commits: the worktrees those commands ran in
are gone, so whether each named source was still changed, or already regenerated by hand, cannot be
recovered.

## What we do

**Status: built, 2026-10-09.**

**When the hook declines a `git commit` whose text names a source file that differs from `HEAD`, it
says so** — `additionalContext` only, never `updatedInput` or a permission decision, so what it
approves is unchanged and the parser is untouched. The line names the set, the source it saw, the
command to run, and every output:

> Commit hook (never blocks): did not regenerate the feedback endings and questions automatically,
> because this command is not the one form the hook can safely extend ([cd <dir> &&] [git add --
> <files> &&] git commit … -- <paths>, the commit last), although it names
> docs/user-feedback/x.md, which feeds it. After this command finishes, run `npx tsx
> scripts/feedback-endings.ts` from the repository root, and commit
> src/feedback-endings.generated.ts and src/feedback-questions.generated.ts if it changes them

- **A decline** is every return before the hook would regenerate: the parser's `None`, a `#`, a
  command that is not the house recipe (`house_recipe()`), a path outside the repository. Not the
  "did not regenerate … because …" cases, which already speak.
- **A commit**: the hint first checks the same matcher as the screenshot hook's `is_commit`
  (`commit_command.COMMIT`), then conservatively checks that the match is an executable shell
  command, so `git log --grep commit -- <page>` and commit text in a quote, comment or heredoc stay
  silent.
- **Names**, and the command's directory, are read exactly as the screenshot hook's fallback reads
  them (261009p): the file, its folder as a whole word or as the base of a glob, or a further
  ancestor as a whole word; repo-relative, relative to the command's directory, or absolute; the
  directory from a leading literal `cd`. `leading_cd` and `named` move from `compress-commit-pngs.sh`
  into `commit_command.py`, unchanged, so the two hooks cannot disagree about what a command names.
  A leading `cd` with a `..` in it stays silent, quoted or not: Bash follows a logical `..`,
  `leading_cd` a physical one, and the strict parser refuses the same case. A later `cd`, `pushd`,
  or Git directory environment variable stays silent rather than inspecting the payload's
  repository.
- **Differs from `HEAD`**: the candidates are the files on disk under each set's sources plus those
  in `HEAD`'s tree, compared by Git object kind and raw hash (`hash-object --no-filters` against
  `ls-tree`), not by `git status`, which assume-unchanged and skip-worktree can blind. A deleted
  source counts. A source named only in a message but unchanged says nothing.
- **Bounded**: the hint runs under the hook's existing 25-second alarm and 3-second per-call limit,
  which now start before any decision. About 0.7 s on this repository.

Replayed over the same transcripts, with the hook's own `executable_commit`, the hint would name a source on **114 of the 137**. The other
23 are almost all commits of the generated files themselves (`git add -- src/help-corpus.generated.json
&& git commit --no-edit`) or merges — sessions that had already regenerated, where silence is right.

**What it still misses:** a commit that does not name the source in its text (`git commit -a`, a
bare commit of staged sources, `$P.md`, braces, escapes, a pieced-together name), or whose execution
directory cannot be established conservatively (`git -C <dir>`, `--git-dir`, a later `cd`, or a
shell wrapper). A bare commit is the obvious next one, but it would mean reading the index to guess
what the commit carries, and in the shared primary that is a peer's staging. Left to the test, as
before.

**What it can wrongly say:** a changed source named somewhere other than the pathspec (a message, a
`git diff` before the commit). The cost is one advisory line, and the action it asks for is harmless.

## Why this and not the other candidates

- **Loosen the parser, or approve more shapes.** Ruled out by the brief and by 261007q: the approval
  covers the whole command, and the hook must read it for certain to grant it.
- **Regenerate on decline without touching the command** (write the file, tell the session to add
  it). Writes into the working tree on a command it could not read, possibly over a peer's work in the
  shared primary, to save the session one command. Not simpler.
- **Block the commit on decline.** Every hook here is contracted never to block, and a false
  positive would stop a real commit.
- **A git `pre-commit` hook.** Still the long-term answer for both hooks (261009j), still Greg's call
  because of `core.hooksPath`.

The simpler option passed over: **say something on every declined commit that names a source,
changed or not.** Fewer git calls, but it would fire on every commit message that mentions a Help
page, and a hint that is usually wrong stops being read.

## Stages

1. Red first. The "left alone" cases in `regenerate-commit-generated.test.sh` that named a changed
   source asserted *silence*, which was the bug; they now assert no approval plus a hint naming the
   generator command and the source, alongside the measured shapes (a `$SP` message file, a trailing
   `; git log -1 | cat`, a glob, an ancestor folder, a leading `cd`, a heredoc message). 19 failed on
   the old hook. Done.
2. Helpers moved (the screenshot hook's test `ALL PASS` unchanged); the hint; tests for
   assume-unchanged and skip-worktree, a deleted source, an unchanged named source, a `cd …/..`, and a
   hung `git`. Hook test `ALL PASS`. Done.
3. GPT Sol code review (fixes in place), gates, commit, push to `dev`. Done.

## Review

GPT Sol's plan review ([prompt](261009t-plan-review-prompt.md), [answer](261009t-plan-review-sol.md)):
APPROVE WITH CHANGES, all six taken. Gate the hint on a real `git commit`, not the substring; compare
with `HEAD` by raw hash, since `git status` hides flagged sources; put the hint under the existing
deadline, with a hung-`git` test; stay silent on `cd symlink/..` and list the forms `named()` cannot
resolve; reword the message (it is not always "could not read", and it should say *after* the
command); and present the measurement as textual evidence rather than a replay of the full decision
or a count of stale commits.

GPT Sol's code review ([prompt](261009t-code-review-prompt.md),
[answer](261009t-code-review-sol.md)): LAND WITH FIXES. It found three classes in the advisory
path, all fixed: commit-looking text in quotes, comments and heredocs could produce a false hint;
unsupported directory-changing forms could inspect the payload repository instead of the commit's;
and the raw comparison treated an unchanged symlink as changed while missing newline-named sources
and new symlink directories, and it could miss a file-to-symlink change when their blob hashes
matched. The added regressions failed before each fix, and both hook suites pass.

One fix went too far and was narrowed afterwards: `executable_commit` gave up at the first `<<`,
which silenced the common `cat > msg <<'EOF' … EOF` then `git commit -F msg -- …`. It now drops a
here-document's body up to its terminator and reads on; an unterminated one is still all data. Two
tests cover both. The replay above uses the final `executable_commit`, lifted from the hook.
