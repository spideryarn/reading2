### F1 — P0: the voucher sum can become a string and grant the wrong allowance

**Evidence:** The plan puts a correlated `sum(articles)` into `BILLING_COLUMNS` and adds it to the free limit ([plan:63](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:63>)). In this codebase, Postgres `sum()` arrives as a string unless explicitly mapped; a TypeScript `sql<number>` annotation does no runtime conversion ([pg-admin.ts:439](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/store/pg-admin.ts:439>)). Naively adding `3 + "20"` produces `"320"`, which later numeric multiplication would treat as an allowance of 320.

**Fix:** Specify `.mapWith(Number)` or an explicit integer cast, then validate that the result is a non-negative safe integer before constructing `Articles`. Add a test using a real claimed voucher that asserts the exact numeric limit, not only whether a fourth ingest passes. Also make one `freeEntitlement(row)` helper and use it for both free-return branches in `entitlementFromRow`; currently unentitled and unrecognised-price rows return the bare `FREE` constant separately ([pg-billing.ts:332](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/store/pg-billing.ts:332>)).

Structurally, the projection is otherwise sound: admission, eligibility, account summary and `/admin/users` all reach `entitlementFromRow` through `BILLING_COLUMNS`. `sync.ts` has its own select, but it computes subscription transitions rather than entitlement, so it does not need the bonus. Creating an anchor is sufficient for legitimate “no row” cases.

### F2 — P1: revocation and downward edits are not serialized with admission

**Evidence:** The plan gives claims no billing lock and says admission reads the aggregate in the same statement that locks the billing row ([plan:63](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:63>)), while promising revocation takes effect immediately ([plan:71](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:71>)). Admission currently locks the account and derives entitlement from that locked read ([pg-billing.ts:837](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/store/pg-billing.ts:837>), [pg-billing.ts:887](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/store/pg-billing.ts:887>)). A concurrent revoke or reduction can therefore commit after admission read the old bonus, admitting one extra ingest. Merely taking the account lock in the voucher transaction is insufficient if the correlated aggregate remains in the same statement that waits for that lock, because its statement snapshot may predate the wait.

**Fix:** For every claimed-voucher mutation that can reduce allowance—revoke and decreasing `articles`—lock the claimant’s `billing_accounts` row first. In admission, acquire that lock in one statement, then read `BILLING_COLUMNS` including the aggregate in a second statement, so READ COMMITTED obtains a post-lock snapshot. Add a real two-connection test racing revocation/downsize against admission. Claim and restore only increase allowance, so their current race fails safely, but using the same order everywhere is simpler.

Revoking after articles have already been used is otherwise sound: no usage is refunded or deleted; the lower live limit simply blocks later admissions.

### F3 — P1: the proposed homepage ratio and “remaining” count are false for existing billing states

**Evidence:** The plan specifies “N of M free articles used · K remaining” unconditionally ([plan:39](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:39>)). The billing contract explicitly says `used` and `limit` cease to be a ratio when public or high-powered charges exist ([billing-plan.ts:67](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing-plan.ts:67>)); `isRatio` permits that headline only when nothing is public, no high-powered charge exists, and `used <= limit` ([billing-plan.ts:447](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing-plan.ts:447>)). The repository records the exact bad result—“6 of 3”—that this rule prevents ([billing.md:716](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/project/billing.md:716>)).

**Fix:** Reuse `describePlan`/`isRatio`’s distinction. When it is not a ratio, show separate facts such as “6 articles added · allowance 23.” If the box must show remaining capacity, have the server return `remainingPrivate` computed with `privateHeadroom`, whose meaning is specifically “further private articles the wall would admit” ([half-units.ts:119](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing/half-units.ts:119>)). Label it accordingly; do not compute `limit - used`.

### F4 — P1: lapsed readers receive the allowance but cannot receive the gift status or copy

**Evidence:** The plan says lapsed readers regain the gift bonus ([plan:31](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:31>)), but adds `gifts` only to the `free` arm ([plan:94](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:94>)) and later claims `/profile` will mention gifts through that arm ([plan:111](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:111>)). A lapsed reader is a distinct union arm with no `used` or gift field ([billing-plan.ts:143](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing-plan.ts:143>)), built separately by the summary ([summary.ts:255](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing/summary.ts:255>)).

**Fix:** Put gift metadata on both `free` and `lapsed`, or at `BillingSummary` level when the effective entitlement is free. Keep `used` absent from `lapsed`; its existing `remaining` calculation remains correct after the limit includes the gift. Treat lapsed readers as eligible for the homepage free-allowance box.

### F5 — P2: the GET is acceptable, but its contract and notice identity are inconsistent

**Evidence:** The current route is explicitly documented as a GET because it creates nothing and touches no network ([summary.ts:25](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/src/billing/summary.ts:25>)); the plan changes both facts ([plan:25](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:25>)). The claim itself is idempotent, so React double-fetching is safe, but the plan simultaneously withholds voucher IDs from the reader ([plan:94](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:94>)) and keys dismissal in `localStorage` by voucher ID ([plan:104](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:104>)).

**Fix:** Keep the claim in this GET for v1; a separate POST followed by GET is more choreography and introduces its own race. Mark this as an intentional idempotent exception, change the route/docs comments, send `private, no-store`, and claim using the route’s `VerifiedUser` so both ID and JWT email are available. Drive the notice from persisted `claimedAt`, never from “this request claimed it,” so either double-fetch response is correct. Add a harmless stable `noticeKey` to `Gift`, or explicitly allow the random voucher UUID on the reader wire.

### F6 — P2: the anchor guarantee is not enforced by the schema

**Evidence:** The plan depends on every claimed voucher having a `billing_accounts` anchor ([plan:68](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:68>)), but the proposed schema lists `claimed_by` only as a nullable UUID and names no foreign key ([plan:76](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:76>)).

**Fix:** Make `claimed_by` reference `billing_accounts(owner_id)` and insert the anchor before stamping the claim. That makes orphaned claimed vouchers impossible for every writer, including admin scripts and future maintenance code.

### F7 — P2: the full request the plan says it relies on is absent

**Evidence:** The plan says Greg’s full text is in `docs/user-feedback/` ([plan:18](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:18>)), but the same plan records that no note was found ([plan:132](</home/greg/code/spideryarn2/.claude/worktrees/fb-vp4mdn-gift-vouchers/docs/plans/261001m-gift-vouchers-for-free-articles.md:132>)); commit `751aa69b` contains only the plan. **Verdict:** **Build with these changes.** The identity design does not expose a non-admin self-grant path: a signed JWT alone is insufficient, an email change or sign-up using another address still needs that address confirmed in the current Auth record, and Google accounts carry confirmed email; after claim, intentionally binding to the immutable account ID makes later email changes irrelevant. The correlated entitlement projection covers the named consumers, while `sync.ts` is not an entitlement reader, but the numeric mapping is a P0 implementation trap and the revocation race, invalid homepage arithmetic, and missing lapsed metadata should be corrected in the plan before building.
