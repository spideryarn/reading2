1. **BLOCKER — Option B does not provide the security boundary it claims.** The same agents can still read `.env.prod` and use its `spideryarn_app` credential, which has DML on every `spideryarn` table, including `feedback_question_answers`. Putting `QUESTIONS_DATABASE_URL` beside it changes the script’s default, not the agent’s capability; an injected agent can ignore the narrow credential and forge Greg’s words with `DATABASE_URL`. **Fix:** either describe B honestly as protection against accidental misuse only, or remove `spideryarn_app` from agent-readable environments and expose required production reads through a genuinely isolated broker/service. Only the latter supports “the database refuses” and “an injected agent can at worst put words in front of Greg.”

2. **HIGH — “Nothing on any other table” is false for a fresh Supabase role without a privilege audit.** Every new role inherits `PUBLIC` privileges regardless of `NOINHERIT`; Supabase documents access to `public`, system catalogs, temporary tables, large objects, and—when enabled—`net`, including queued request headers and outbound HTTP. [Supabase’s custom-role warning](https://supabase.com/docs/guides/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted-ddaa1c) directly contradicts plan lines 108–118. **Fix:** replace the absolute claim with the exact residual capability, and require an inventory of schema, table, sequence, function, database, role-membership, role-attribute, large-object, and `pg_net` privileges. Test the full negative matrix, not only inserts into `feedback` and `feedback_question_answers`. Global `PUBLIC` revocations need their own impact assessment; `NOINHERIT` cannot remove them.

3. **HIGH — Option B’s explicit grants are broader than the command requires.** Table-wide `UPDATE` on `feedback_questions` lets the role rewrite titles, bodies, references, report links, claimed session names, and environment—not merely close a question—and it can close any question. Because all agents share one login, there is no row-level identity with which to restrict “its” questions. RLS is currently absent, so grants apply to every row. **Fix:** grant column-level update only for the fields required by the close transition, or preferably grant `EXECUTE` on narrowly checked database routines while withholding base-table DML. Add database constraints for IDs, lengths, status transitions, timestamps, and open-question/flood limits; treat `asked_by` and `environment` as unverified claims unless derived outside agent input.

4. **HIGH — The role/grant order cannot work as written.** The plan runs “Migration: two tables (+ grants under B)” before creating `spideryarn_questions`; `GRANT … TO spideryarn_questions` will fail when the role does not exist. The promised role-creation statement is also not actually present, and project policy says production SQL is run through `supabase db query`, not pasted into the editor. **Fix:** either create the role before the migration on both local and production databases, or create the tables first and apply a separately verified grant script afterward. Production migrations run as `postgres`, not the unused `spideryarn_migrator`, so `postgres` can create the tables, their mutual FK, and their grants; the runtime role needs no `REFERENCES` privilege merely to insert a child row. Specify whether reply IDs are client-minted; if a sequence supplies them, grant that sequence’s `USAGE`. The pooler URL must use `spideryarn_questions.<project-ref>` on port 6543, which Supavisor supports for custom roles. [Supabase connection format](https://supabase.com/docs/guides/database/connecting-to-postgres#shared-pooler-transaction-mode)

5. **HIGH — The cutover order creates the outage it claims to avoid.** Deploying the database-reading server before copying rows makes every existing question disappear until the copy completes. Copying beforehand would not duplicate anything because the old server does not read the new table. Copying only open files also leaves answered questions absent while their answer rows remain, breaking the claimed “one home” history and late-reply handling. A rollback after new database-only questions arrive likewise restores an old server that cannot see or accept replies for them. **Fix:** migrate all question files, with statuses, before switching reads; verify row/reply/deferral reconciliation; then deploy. Keep a deduplicating compiled fallback for a transition release or document and automate a rollback export/freeze. Remove the generated path only after the rollback window closes.

6. **HIGH — Greg’s POST routes are not unchanged.** Both answer and deferral parsing currently call `feedbackQuestionStatus`, which reads the compiled file map; deferral additionally checks `open` before writing. Removing the generated file without replacing these checks makes new database questions unanswerable. Moving status into a writable table also introduces a close-versus-defer race that the immutable compiled state does not have. **Fix:** include both POST handlers and their stores in the plan. Validate question existence from the database; preserve late answers to closed questions; make “defer only if open” one conditional transaction rather than a route check followed by a separate write.

7. **HIGH — `acts_on` and the proposed state rule disagree, leaving trust handling underspecified.** The schema records which admin replies an agent reply acts on, but plan lines 129–132 derive state only by comparing newest timestamps. A later agent message that does not answer Greg would therefore mark his reply handled. Conversely, if `acts_on` is an array, it has no FK and can name another owner’s answer; answer IDs are unique only with `owner_id`. A forged `acts_on` value could suppress Greg’s trusted words from later agents even though it cannot forge them. **Fix:** either intentionally discard `acts_on` and document the weaker “any later agent message counts” rule, or normalize it into a relation keyed to `(owner_id, answer_id)` and derive `responded` from admin replies with no valid acting relation. The CLI must read Greg’s words only from `feedback_question_answers`, label agent text as untrusted agent-authored context, and retain an audit view of all admin replies even after an agent marks them acted on.

8. **MEDIUM — Prompt-injected output reaching Greg is bounded per message but not in volume.** Plain-text rendering, admin-only visibility, and a 6,000-character cap limit content execution, but a direct database role can bypass script-only validation and insert unlimited questions/replies, making the dialog response and database grow without bound. **Fix:** put hard length and shape checks in PostgreSQL, add a database-enforced open/daily limit or execute-only routine, and cap/page the server response. Do not present the free-text session label as authenticated provenance.

9. **MEDIUM — The A–D comparison is not fair enough for Greg’s decision.** C does buy something B’s raw SQL login does not: an application boundary that can validate transitions, rate-limit, audit, and expose no general SQL capability; both secrets are remotely usable if exfiltrated because Supavisor is internet-reachable. D is broader in account/admin actions, but A is broader over database data, so “far wider than A” is not a sound total ordering. A narrower missed option is a database login granted only execution of checked routines and reads through scoped views. **Fix:** compare options by accidental blast radius, prompt-injection resistance, internet reachability, validation/rate limiting, revocation, setup cost, and the pre-existing `spideryarn_app` exposure. Correct A’s “only inserts” wording because `close` necessarily updates state.
