I found four substantive issues; F1 and F2 should be fixed before building.

- **F1 — P1: the pre-`begin` path can lose the rewrite or submit it with provisional IDs.**  
  Evidence: the open editor is tracked by message ID and rendered under `key={m.id}` ([ChatPanel.tsx:1669](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:1669), [ChatPanel.tsx:2109](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:2109), [ChatPanel.tsx:2134](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:2134)). The `begin` frame replaces both the provisional question and answer IDs ([model.ts:1135](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/model.ts:1135), [reduce.ts:1067](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:1067)). Therefore, editing the newest question before `begin` causes its `Turn` and locally owned `EditQuestion` state to unmount when `begin` arrives; `editing` still names the old ID, so the editor, its text, and its queued submission disappear while the newly named answer is stopped.  
  If the turn instead fails or disconnects before `begin`, `stranded` drops the waiting stop and the provisional answer becomes `error`, making `busy` false ([reduce.ts:865](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:865), [reduce.ts:1176](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:1176), [reduce.ts:1204](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:1204)). The queued effect then edits using the provisional target/tail read by `useChat.edit` ([ChatPanel.tsx:3108](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:3108), [useChat.ts:982](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/useChat.ts:982)); the server cannot match those IDs, so the promised edit is refused. The tests avoid both cases by delivering `begin` before opening the editor ([learn-edit-asks-again.test.tsx:281](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/tests/learn-edit-asks-again.test.tsx:281)).  
  **Suggested fix:** preserve the editor draft/queue across the provisional-to-server ID swap, or withhold the newest provisional question’s pencil until its IDs are authoritative. Do not treat `busy === false` alone as permission to auto-edit after a pre-`begin` failure; reconcile/remap first. Add tests for queuing before `begin`, `begin` renaming the current question, and failure/disconnection before `begin`.

- **F2 — P1: an unchanged or blank rewrite stops the answer and then asks nothing.**  
  Evidence: while busy, `ask` queues and calls Stop without validating the text ([ChatPanel.tsx:3114](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:3114)). Validation happens later in the parent, after the editor is closed: blank or unchanged text deliberately does not call `onEdit` ([ChatPanel.tsx:2556](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/ChatPanel.tsx:2556)). Thus an accidental Enter on an unchanged editor stops a useful answer, closes the editor when `busy` clears, and produces no replacement.  
  **Suggested fix:** determine `trimmed !== "" && trimmed !== original.trim()` inside `EditQuestion` before queuing or stopping. Disable or explain an invalid Ask-again press, and test unchanged and whitespace-only text while busy.

- **F3 — P2: the plan’s reason for rejecting immediate edit is incorrect.**  
  The reducer would indeed contain two turn operations, but it already defines their ordering: projections are applied by `seq` ([project.ts:219](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/project.ts:219)); `startTurn` explicitly allows multiple turns without supersession ([reduce.ts:961](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:961)); and edit repair explicitly distinguishes an in-flight provisional send from rows the edit owns ([reduce.ts:1033](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:1033)). The server also checks `expectedTailId` before aborting, then aborts and waits before performing the edit ([routes.ts:3687](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/routes.ts:3687), [routes.ts:3700](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/routes.ts:3700)).  
  Immediate edit is therefore sound once `begin` has supplied authoritative IDs. It is not sound before `begin`, because the edit target/tail may still be client-minted—the real reason some waiting is required.  
  **Suggested fix:** correct the plan’s rationale. Either send the edit directly for a begun turn and hold only the pre-`begin` case, or retain stop-first sequencing specifically as the mechanism that waits for authoritative IDs. In either case, add a reducer/controller test for an old turn finishing after an edit has registered.

- **F4 — P2: the documented stop-failure path leaves a misleading error after the edit succeeds.**  
  A failed stop stores `Couldn't stop that answer…` globally ([reduce.ts:1592](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:1592)). If the original answer subsequently finishes, the queued edit starts, but `startTurn` does not clear that error ([reduce.ts:897](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/chat/reduce.ts:897)). The reader can therefore be looking at a successful replacement answer beneath a stale stop-failure banner.  
  **Suggested fix:** clear the transient stop error when the queued edit starts, or otherwise retire it once the requested replacement operation is underway. Test “stop fails, old answer finishes, edit succeeds.”

- **F5 — P2: the Help work omits the generated corpus and its gate.**  
  The plan names only `src/web/help/pages/modes/chat.md`, but every Help-page edit requires regenerating `src/help-corpus.generated.json`; `tests/help-corpus.test.ts` deliberately fails otherwise ([help-page.md:112](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/docs/project/help-page.md:112)).  
  **Suggested fix:** add the corpus regeneration command and Help tests to the plan. Also note that the shared `Conversation` covers Tutorial and Explore as well as the listed kinds ([ConversationModes.tsx:178](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/web/modes/conversation/ConversationModes.tsx:178)); decide whether their Help wording needs the same clarification.

The ordinary post-`begin` sequence is otherwise sound. A successful Stop waits for the server writer to finish ([routes.ts:4182](/var/tmp/spideryarn-worktrees/fbyur0eq-edit-while-thinking/src/routes.ts:4182)); if the SSE connection was lost, recovery retains the attempt and eventually adopts the stored stopped answer. I found no additional Live-specific race: Live cannot start while `busy`, and typed sending already finishes an active Live handoff first. Focus returns to the rewritten question’s pencil after normal submission; only F1’s ID-remount path breaks that behavior.
