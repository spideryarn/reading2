The overall direction is right: keep TanStack Table, stay on v8 for this work, migrate Articles and Vouchers, and retain `renderRow` rather than lifting voucher edit state into context. The plan needs correction before implementation, however.

- **F1 — P1: Total-cost sorting would regress existing ordering and misclassify unknown costs.**  
  Today, equal costs retain newest-first order ([AdminArticlesPage.tsx:90](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminArticlesPage.tsx:90)), and the test explicitly requires that tie-break ([admin-articles-page.test.tsx:231](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/tests/admin-articles-page.test.tsx:231)). `useSortedTable` first orders data by row ID ([DataTable.tsx:283](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/lib/DataTable.tsx:283)), so a cost comparator returning zero for ties changes them to ID order. In addition, the plan only makes `calls === 0` missing ([plan:62](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/plans/261021i-admin-tables-share-one-sortable-hideable-table.md:62)); an article whose every call is unpriced also displays `—`/“No recorded amount” ([admin-articles-page.test.tsx:220](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/tests/admin-articles-page.test.tsx:220)) but would sort as a real zero.  
  **Fix:** make the accessor missing whenever `calls - unpricedCalls === 0`; retain zero when at least one priced call recorded `$0.00`; give the cost comparator a creation-time tie-break. Test no calls, all-unpriced calls, priced zero, mixed floor, and equal-cost rows in both directions.

- **F2 — P1: `renderRow` does not specify the keyed reconciliation boundary required to keep edits attached to the correct voucher.**  
  `VoucherRow` owns draft fields in local state and saves using its current `voucher.id` ([AdminVouchersPage.tsx:1043](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminVouchersPage.tsx:1043)). The current map deliberately keys `VoucherRow` by voucher ID ([AdminVouchersPage.tsx:1605](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminVouchersPage.tsx:1605)); the proposed callback merely says `renderRow(row, cellClass)` ([plan:89](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/plans/261021i-admin-tables-share-one-sortable-hideable-table.md:89)). If rows are reconciled by position after sorting, a draft can move onto another voucher and PATCH the wrong ID.  
  **Fix:** have `DataTable` enforce identity, for example with a `Fragment key={row.id}` around every custom result, rather than relying on each caller. Test by beginning an edit, changing a value, sorting so the row moves, then saving and asserting both the PATCH URL and body still belong to the original voucher. Repeat while hiding another column.

- **F3 — P2: the promised exhaustive voucher switch is not exhaustive with TanStack’s types.**  
  `cell.column.id` is typed as plain `string` ([table-core types:76](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/node_modules/@tanstack/table-core/build/lib/types.d.ts:76)), so a `switch` plus `never` does not automatically fail when a column is added.  
  **Fix:** derive a `VoucherColumnId` union from one ordered ID tuple, and require both the column definitions and cell renderers to satisfy `Record<VoucherColumnId, …>`. Add a runtime assertion before narrowing an external string.

- **F4 — P2: the hook’s identity contract is incomplete.**  
  The hook can memoise URL-derived sorting, but it cannot repair a fresh `data`, `columns`, or `rowId` supplied by its caller. `useSortedTable` keys its pre-ordering on `data` and `rowId` ([DataTable.tsx:267](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/lib/DataTable.tsx:267)), and the postmortem names unstable data/sorting as the dangerous inputs. The plan only explicitly requires a module-scoped `rowId` ([plan:125](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/plans/261021i-admin-tables-share-one-sortable-hideable-table.md:125)).  
  **Fix:** make the hook accept `data: T[] | null` and normalize null through a stable empty constant, require memoised columns, and document stable `rowId`. Keeping `admin-page.test.tsx` green checks behavior, not identity.

- **F5 — P2: voucher sorting semantics and URL behavior remain undecided.**  
  “Waiting, claimed, revoked…, whatever `Status` already distinguishes” is not an implementable rank ([plan:96](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/plans/261021i-admin-tables-share-one-sortable-hideable-table.md:96)), and no order at all is defined for the composite Claimant’s free usage values. The existing caption also says “newest first” unconditionally ([AdminVouchersPage.tsx:96](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminVouchersPage.tsx:96)), which becomes false after sorting.  
  **Fix:** define the exact status accessor and precedence—revoked should win because that is what `Status` displays—or make it non-sortable. Make claimant usage non-sortable unless one honest scalar and missing-value rule can be named. Change the caption to order-neutral wording. Test that changing `by`/`dir` preserves `tab=given`, changing tabs preserves sort state, and a reload restores all three.

- **F6 — P2: the costs exclusion counts the failure tables incorrectly.**  
  There are three: by day, by task, and causes ([AdminCostsPage.tsx:1163](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminCostsPage.tsx:1163), [AdminCostsPage.tsx:1168](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/web/AdminCostsPage.tsx:1168)). The plan reasons about only “one” and “the other” ([plan:114](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/plans/261021i-admin-tables-share-one-sortable-hideable-table.md:114)). Leaving all three hand-drawn is defensible: day is chronological, task is ranked by total trouble, and causes are commonest first ([cost-cube.ts:595](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/cost-cube.ts:595), [cost-cube.ts:639](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/src/cost-cube.ts:639)).  
  **Fix:** explicitly account for all three and preserve those meaningful fixed orders. No extra migration stage is necessary.

- **F7 — P2: required reference-doc updates are absent.**  
  `admin.md` explicitly says Vouchers is a plain table rather than `DataTable` ([admin.md:990](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/project/admin.md:990)), and `web-client.md` owns the shared table signpost ([web-client.md:217](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/project/web-client.md:217)).  
  **Fix:** add both documents to the relevant stages, documenting the row-rendering exception and the shared URL/visibility hook.

- **F8 — P3: the research verdict is sound, but several supporting claims need correction.**  
  The repository is indeed pinned to v8.21.3, and separating the v9 migration from this adoption work is sensible. However, the research says it could not confirm `sortUndefined` or `enableSortingRemoval` in v9 ([research:86](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/research/261021a-table-library-for-sortable-hideable-columns.md:86)); both are now documented in the official [v9 sorting guide](https://tanstack.com/table/latest/docs/framework/react/guide/sorting), while pagination is an opt-in feature under the official [v9 migration guide](https://tanstack.com/table/latest/docs/framework/react/guide/migrating). It also calls April 2025 “six months ago” in October 2026 ([research:102](/var/tmp/spideryarn-worktrees/fbk8mka5-admin-tables-library/docs/research/261021a-table-library-for-sortable-hideable-columns.md:102)); it is about eighteen months. Finally, “only `DataTable.tsx` and column callers touch TanStack types” is contradicted by `Library.tsx`, `AdminPage.tsx`, `AdminCostsPage.tsx`, `ShelfControls.tsx`, `table-sort.ts`, and `shelf-hidden-columns.ts`.  
  **Fix:** correct those claims and qualify the unsupported assertion about LLM pretraining data. None of these corrections overturns “keep TanStack, stay on v8 for this job.”

The simpler design is the plan’s basic one: retain row-local voucher state and add a narrowly keyed `renderRow` escape hatch. A voucher-edit context keyed by ID introduces more state ownership and synchronization without buying functionality.

VERDICT: REJECT
