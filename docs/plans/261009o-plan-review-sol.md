1. **High — `expectedTailId` must not be optional.** The plan promises that deletion is guarded by the observed tail, but both the store and route accept an omitted tail ([plan:61](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/docs/plans/261009o-delete-a-chat-question-and-what-follows.md:61), [plan:71](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/docs/plans/261009o-delete-a-chat-question-and-what-follows.md:71), [plan:76](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/docs/plans/261009o-delete-a-chat-question-and-what-follows.md:76)). A buggy or stale caller could therefore delete turns it never saw. The existing edit route permits omission solely for compatibility with old clients ([src/routes.ts:3619](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/routes.ts:3619)); a new endpoint needs no such concession. Make the field required in the HTTP schema and store contract, return 400 when missing, and always call `requireTail`.

2. **High — replacing `base` with the returned server thread can erase a newer send.** Sends place their provisional rows directly into `base` ([src/web/chat/model.ts:210](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/model.ts:210), [src/web/useChat.ts:713](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/useChat.ts:713)); their operation projection only redraws the answer ([src/web/chat/project.ts:46](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/project.ts:46)). If prune finishes server-side, then a new send begins before the prune response is reduced, the plan’s whole-thread replacement ([plan:88](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/docs/plans/261009o-delete-a-chat-question-and-what-follows.md:88)) removes that new question locally. The reducer already documents this exact class of server-snapshot race for rename/send ([src/web/chat/reduce.ts:1175](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/reduce.ts:1175)).

   Fix: have `PruneOperation` capture the exact deleted message IDs at registration. Its projection filters only those IDs. On success, merge the server snapshot underneath the current base—preserving the current title and locally added rows except captured deleted IDs—using the same principles as `merged`/`underneath` ([src/web/chat/reduce.ts:1208](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/reduce.ts:1208)). Full-thread delete should supersede prune as it does other same-thread operations.

3. **Medium — unnamed and provisional threads need an explicit rule.** Mutations against an unconfirmed thread are normally held because the server cannot address it yet ([src/web/chat/model.ts:394](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/model.ts:394)); provisional message IDs likewise do not exist server-side until `begin` succeeds ([src/web/chat/model.ts:302](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/chat/model.ts:302)). After a failed send, the proposed bin can therefore target a thread or question the server cannot find. Holding prune is insufficient because its provisional target ID might never acquire a server identity. Hide prune until `named(threadId)` is true, and do not offer it on unconfirmed failed-send rows; require recovery/reload first.

4. **Medium — `canEdit` does not protect an active live conversation.** Ordinary `busy` only reflects a stored pending tail ([src/web/ChatPanel.tsx:1550](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatPanel.tsx:1550)), while the live tail is separate ([src/web/ChatPanel.tsx:2038](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatPanel.tsx:2038)). Spoken appends carry their previously observed tail ([src/web/useChat.ts:545](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/useChat.ts:545)); pruning that tail makes the next spoken append fail stale-tail validation. Hide deletion while live conversation is active, or explicitly stop live before opening confirmation. Hiding it is the simpler choice.

5. **Medium — leaving `updated_at` unchanged makes the sidebar metadata false.** The schema defines it as being bumped for every stored message ([src/db/schema.ts:4261](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/db/schema.ts:4261)), and the UI sorts by it and labels it “Last message” ([src/web/ChatPanel.tsx:1001](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatPanel.tsx:1001), [src/web/ChatPanel.tsx:1385](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatPanel.tsx:1385)). After pruning, it would describe a deleted message and preserve ordering caused by erased activity. Rename is not a good analogy because it does not change the last message. Set `updated_at` to the retained tail’s `finished_at`, falling back to its `created_at` and then the thread’s creation time.

6. **Medium — “everywhere the pencil is offered” omits the dialog call site.** `Conversation` is instantiated both in the main panel ([src/web/ChatPanel.tsx:735](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatPanel.tsx:735)) and in `ChatDialog` ([src/web/ChatDialog.tsx:1295](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/src/web/ChatDialog.tsx:1295)). The implementation checklist names `Turn`, `ConversationModes`, and `ChatPanel`, but not `ChatDialog`. Thread a required delete callback and eligibility state through both call sites so the compiler catches omissions.

7. **Medium — the proposed tests miss the risky cases.** Beyond the tests at [plan:97](/var/tmp/spideryarn-worktrees/fbmx423m-delete-chat-message/docs/plans/261009o-delete-a-chat-question-and-what-follows.md:97), add:

   - Missing `expectedTailId` is rejected; answer IDs, first-question IDs, and pending threads are rejected at the route and store layers.
   - Append-before-prune refuses deletion; prune-before-append preserves the append.
   - Finish and pending-sweep races preserve the attempt fence and never resurrect deleted rows.
   - Prune overlaps send, rename, load, recovery, and full-thread delete in both completion orders.
   - Failure retires only prune and restores its rows without undoing another operation.
   - Unnamed/provisional and active-live threads do not offer deletion.
   - Both `Conversation` call sites render the control.
   - `updated_at` becomes the retained tail’s time.
   - Store deletion cannot affect the same-looking ID outside the addressed article/thread.
   - Confirmation copy covers zero, one, and plural trailing messages.
