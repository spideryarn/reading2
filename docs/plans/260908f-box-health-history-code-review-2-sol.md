## Findings

1. **Critical — the coverage timeline is still overlapping, so the clamp moved the bug.** Inferred gaps still begin at the preceding sample timestamp ([history-series.ts:426](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:426), [history-series.ts:457](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:457)), while that sample claims coverage until `atMs + gapAfterMs` ([history-series.ts:633](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:633)). I executed the four-hour failure case: it produced a gap `[t0, t0+4h]` and an unknown span `[t0, t0+182.5s]`. The hatch hides the known collector failure and the prose overstates the break by 182.5 seconds. Marks and over-ceiling bars are drawn after the hatch, so other layers resolve the same overlap in the opposite direction ([HealthHistory.tsx:381](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:381)). The test asserts the clamp and gap count, but never asserts non-overlap. Build the normalized sequence: inferred silence begins at `min(next.atMs, sample.atMs + gapAfterMs)`, holes override intersecting coverage, and every drawable layer derives from those mutually exclusive spans.

2. **Critical — `latestIsCurrent` is correct for later parsed samples but wrong across holes.** A valid value at `t0` followed by a rejected trailing sample creates `{afterAtMs: t0, beforeAtMs: null}`, yet `plotSeries` never uses holes when calculating `latestCoveredUntil` ([history-series.ts:649](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:649)). I reproduced a window ending at `t0+60s`: it contained a full trailing gap and still returned `latestIsCurrent: true`. The card therefore says “now 1.0× cores” while simultaneously admitting that the record after that value is unreadable. Determine currentness from the final normalized coverage span, not from `until` alone.

3. **Critical — lock ordering is improved, but startup ownership is still incomplete and the new order leaks locks on repair failure.** The normal locked-out opener now repairs nothing, and per-append `stillOurs` is correct. But after claiming, startup calls `truncateToLastLine` without checking ownership immediately before and after it ([health-history.ts:475](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:475)); that is precisely the race the shared lock’s contract and `openStore` guard against. Also, if repair throws, the function returns `refused` without releasing the acquired lock ([health-history.ts:478](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:478)). I reproduced this with `health.jsonl` as a directory: the first open refused, left `writer.lock` behind naming the live process, and the second opener was locked out by a writer that did not exist. Follow `openStore`’s pattern: release on every post-claim failure and check `stillOurs` around repair.

4. **High — the client boundary remains permissive outside the three tested mutations.** Missing or malformed `predecessor`, `holes`, `earliestAt`, `rotated`, `retention`, `unreadableLines`, and `refreshMs` are silently defaulted ([health-history-client.ts:262](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/health-history-client.ts:262)). Concrete failures:

   - Rename `predecessor` on a response with no in-window samples and an old `earliestAt`: the parser accepts it, produces no gaps, and the panel takes its reassuring empty-store branch.
   - Rename `holes`: the parser accepts `[]` and can reconnect across corruption.
   - Rename `lockedOutBy` inside `retention`: the parser constructs an apparently healthy retention status.
   - A schema-2 sample is accepted because `parseSample` does not inspect its schema; a schema-2 `unreadable` envelope is also accepted because that arm is handled before the schema check.

   The history-arm schema and required `samples` checks are good, as is converting rejected runs into barriers. Finish the boundary by validating every required envelope field, sample schema/order, hole endpoints, predecessor, and retention shape.

5. **High — an oversized sample is only temporarily reported, then can disappear from history entirely.** The byte measurement and 64 KiB ceiling are correct. But rejection only sets in-memory `failure` ([health-history.ts:627](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:627)); the next successful append clears it ([health-history.ts:687](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:687)). I reproduced: healthy at `t0`, oversized critical at `t0+73s`, healthy at `t0+146s`; afterward `failure` was null and disk contained only the two healthy samples. Since 146 seconds is within the 182.5-second allowance, the chart reconnects them and can erase the critical turn. Persist a compact `sample-omitted`/retention-failed sentinel, or otherwise preserve a durable positional barrier.

6. **High — the separate-health-loop decline still leaves the original six/seven-minute false reassurance.** The cap reduces the blind window but does not remove it. A healthy sample after a fleet failure records `nextDueMs ≈ 313s`; another sample at six or seven minutes is still below the 433-second threshold and is deliberately asserted as “no gap” ([fleet-history-series.test.ts:224](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tests/fleet-history-series.test.ts:224)). If the dashboard actually disappears during that interval and returns before 7.2 minutes, the line connects and the page says there were no breaks. The cap is not the wrong number; `nextDueMs` is the wrong fact to treat as continuous health coverage. Either separate the loop or store a distinct health-coverage horizon and render the scheduled non-observation explicitly. I would not leave both alternatives as follow-ups.

7. **Medium — a fast phone clock manufactures an ongoing outage.** The route deliberately timestamps the window with the server clock, but `plotHistory` replaces its right edge with `Math.max(view.toMs, nowMs)` ([history-series.ts:404](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:404)), and `nowMs` is the phone’s `Date.now()` ([HealthPanel.tsx:207](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthPanel.tsx:207)). A phone one hour fast turns a current server sample into a one-hour ongoing break. Advance from server `toMs` using monotonic elapsed time since receipt, or simply use the server edge until the next 60-second poll.

8. **Medium — a locked-out reader can take a non-atomic snapshot across rotation.** `read()` reads `prev` and then `live` by pathname ([health-history.ts:695](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:695)). A second, read-only dashboard can read the old `prev`; meanwhile the owner rotates `live → prev` and creates a new `live`; the reader then reads only the new live file, omitting the entire just-rotated file and drawing a large false break for one poll. Use stable open file descriptors or detect identity changes and retry.

9. **Low — IO is visually amber-only, but its tooltip now says “red past Infinity.”** `Number.POSITIVE_INFINITY` correctly produces a zero-height red band, but the generic prose formats that value literally and also claims the tiles use the same cutoff ([HealthHistory.tsx:307](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:307), [HealthHistory.tsx:331](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:331)). Special-case the explanation.

The targeted 115 tests pass, and all TypeScript projects pass. The full suite could not start because the local database was unavailable. Lint additionally reports `parseHistory` over the configured cognitive-complexity limit.

**Verdict: do not ship.** The mutually exclusive timeline, hole-aware currentness, startup lock protocol, strict boundary, and durable oversized-record barrier need fixing first.
