1. **High — The unmarked push can discard the very mode state it promises to preserve.** The plan builds the return URL from `location.search`, then makes an unmarked history write ([plan](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/docs/plans/261008g-the-way-back-chip-moves-the-position-and-leaves-the-modes-alone.md:26)). nuqs updates hook state immediately but flushes the URL later; its external-write `sync()` resets all pending queues before comparing addresses ([patch-history](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/node_modules/nuqs/dist/patch-history-Bze7i4qB.js:38), [reset](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/node_modules/nuqs/dist/reset-Cwe7SWyj.js:14)). Thus: press Glossary, then quickly press the return chip; Glossary may already be visible while `location.search` still names the old mode. The return copies that old address and aborts the queued Glossary push. The marked rewrite underneath nuqs is safe by itself, but the preceding unmarked push is not. It also is not one unobservable operation: the outer wrapper emits `NAVIGATED` after the push before the stamp rewrite, followed by another event after the rewrite ([router.ts](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/src/web/router.ts:1715)). Revise this around a nuqs `setAt(..., {history:"push"})` plus a return-arm consumed by the wrapper, analogous to the jump handshake, so pending mode keys coalesce and the final stamp is written in the push itself. Add a real queued-mode race test; a fully committed raw `history.pushState` test misses the bug.

2. **High — The restore effect will not reliably move the page when the origin equals `synced.current`.** It exits solely on value equality ([useReadingPosition.ts](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/src/web/reader/useReadingPosition.ts:57)). That equality does not prove the page is at the origin: `?at=` is section-granular and can remain the section-start id while the reader moves far within that section. If the jump originated at that id, returning pushes the same `at`; nuqs may emit no changed snapshot, and even a render would hit the guard. The chip visibly does nothing. The plan needs an explicit return/re-anchor signal or a single coordinated mover that always scrolls on this deliberate action. Test actual scrolling with `origin === synced.current`, not only the resulting URL; cover `top` similarly.

3. **Medium — The covering-band visual case is right, but keyboard focus is lost.** Stepping aside when `bandOverProse` is the correct visibility predicate, and I found no other pressable state that completely hides the landing: modal surfaces prevent pressing the chip, while Marginalia and desktop bands leave prose visible. However, `bandStepsAside` only remembers focus when it was inside `.mode-band` ([Reader.tsx](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/src/web/reader/Reader.tsx:812)). Here focus is on the ReturnChip outside the band; it is then replaced by `BandBackChip`, whose `takeFocus` is false. A keyboard or screen-reader user falls back to the document. The covering-band test must assert focus transfer and a sensible destination when the band returns.

4. **Medium — The affected documentation and spine tests are incomplete.** Help currently says the chip and browser Back “do the same” ([jumping-around.md](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/src/web/help/pages/jumping-around.md:15)); after this change, Back restores the earlier whole address while the chip preserves current modes. Update that page and the generated Help corpus. `useJumpOrigin` remains the correct projection for the spine, but the plan should name [spine-jump-origin.test.ts](/var/tmp/spideryarn-worktrees/fbq3dfmw-back-chip-position-only/tests/spine-jump-origin.test.ts:301): replace its depth-specific invariant and test that successive returns move the mark through `earlier`, then remove it. No new keyboard shortcut or keyboard-help copy is required, but the focus behaviour above is required.

5. **Info — The v3 `earlier` model is otherwise sound, and dropping the chain is not the better simplification.** Nearest-first `[current.origin, ...current.earlier]`, capped by discarding the oldest entries, preserves repeated-return semantics without stack traversal. v2 and legacy entries can safely supply one origin and no earlier journeys; old v2 readers reject unknown `v:3`, while pre-v2 readers find no `from`, so both fail closed. Losing journeys behind an old v2 entry is unavoidable because they live in inaccessible history entries. The chain is modest, preserves an explicit earlier requirement, and is not responsible for the two blocking defects above.
