## Findings

- **R2-F1 — P1 — A repeated Send does not currently resume an email stranded between voucher commit and task registration.** The plan claims both `created` and `replayed` “send the email after the response” and therefore guarantee one email ([plan:135](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:135), [plan:144](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:144)). But `createVoucher` returns a delivery ID only for `created`; `replayed` carries only the voucher ID ([pg-vouchers.ts:471](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:471)). The existing route returns immediately on replay and schedules only a newly created delivery ([routes.ts:9686](/var/tmp/spideryarn-worktrees/author-gift/src/routes.ts:9686), [routes.ts:9690](/var/tmp/spideryarn-worktrees/author-gift/src/routes.ts:9690)). Therefore, if the voucher/email transaction commits and the process dies before `afterResponse` is registered, later Send presses never attempt that queued email. **Fix:** after either `created` or `replayed`, resolve the voucher’s gift-delivery ID and schedule `sendQueuedVoucherEmail`. Its atomic queued reservation already makes duplicate scheduling harmless ([pg-voucher-emails.ts:702](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-voucher-emails.ts:702)). Test a simulated death after `createVoucher` commits, plus two concurrent retries, asserting one provider send.

- **R2-F2 — P1 — The create endpoint is not replay-safe for either access or spend.** Revision 2 says an existing gift may start a fresh lookup ([plan:118](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:118)), while the route is described as creating the private link before finding/creating the gift ([plan:42](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:42), [plan:57](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:57)). Once the first lookup has finished, a lost-response replay can therefore buy another search. Worse, after a sent gift’s private link is deliberately turned off, a delayed replay can turn it back on: `keepExisting` preserves only a link that is currently on; otherwise `create` mints one ([pg-share-link.ts:123](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-share-link.ts:123), [pg-share-link.ts:163](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-share-link.ts:163)). **Fix:** make `POST /author-gifts` an idempotent ensure operation: an existing gift returns without touching the link or starting paid work. Create the first pending lookup exactly once with the new gift. Give explicit reruns their own `POST /author-gifts/:id/lookups` route. This is also simpler than making one endpoint mean create, replay, restore access, and rerun lookup.

- **R2-F3 — P1 — `starter-refused` can unfreeze a newer Send attempt.** The plan clears `send_started_at` after refusal without a compare-and-swap ([plan:127](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:127), [plan:139](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:139)). Two callers can resume the same frozen attempt while `createVoucher` performs starter and audience work outside its transaction ([pg-vouchers.ts:508](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:508)). One can refuse and unfreeze; Greg fixes the link and starts a new attempt; then the older caller can clear the new freeze, allowing PATCH to race the successful create. **Fix:** treat the freeze value as an attempt token—prefer a UUID, or at least the returned timestamp—and clear only `WHERE send_attempt = $attempt AND NOT EXISTS (voucher_id)`. Test two delayed refusals around a repaired-link retry.

- **R2-F4 — P1 — The exact `createVoucher` replay body is not actually frozen.** `author_gifts` stores neither the voucher’s private note nor a starter slug snapshot ([plan:89](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:89)), yet Send derives `note` from the article title and passes the current `adminId` as creator ([plan:135](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:135)). Replay identity compares the note, starter slug, and creator exactly ([pg-vouchers.ts:563](/var/tmp/spideryarn-worktrees/author-gift/src/store/pg-vouchers.ts:563)). A title change, slug change, or a different administrator retrying after a lost response can therefore produce `conflict`, potentially leaving the only queued delivery in R2-F1 unsent. **Fix:** freeze every field of `NewVoucher`, not just the editable recipient fields. The simplest version is a stable private note such as `Author gift`, the gift row’s `created_by`, and a stored starter slug. Test a committed create followed by a title change and lost-response retry.

- **R2-F5 — P1 — The lookup’s begin transaction is sound, but its worker claim and finish transaction are missing.** The plan serializes lookup creation and stale replacement ([plan:154](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:154)), but it does not require the deferred worker to claim an exact still-pending row, nor require finish to update only a still-pending lookup. It also says lookup completion fills fields and appends notes without conditioning that mutation on the gift still being a draft ([plan:193](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:193)). An old task marked stale can consequently start or finish later, and a lookup already running can alter name/provenance/notes after Send froze the row or after Discard. **Fix:** at task start, conditionally claim that lookup and persist its run ID before spending. At finish, lock gift then lookup in the same order as begin, CAS `outcome IS NULL`, and apply fields/provenance only while `send_started_at` and `discarded_at` are null. A stale loser records/applies nothing; a result that lost to Send remains visible as “found, not applied.” Test finish versus stale replacement, PATCH, Discard, and Send.

- **R2-F6 — P2 — The separate spend collector works, but the run-ID lifecycle needs to be designed explicitly.** Production after-response tasks drain only after `collectSpend(serveApi)` has returned ([routes.ts:9020](/var/tmp/spideryarn-worktrees/author-gift/src/routes.ts:9020), [after-response.ts:45](/var/tmp/spideryarn-worktrees/author-gift/src/after-response.ts:45)). Thus this is not actually a nested collector at execution time: the request collector correctly sees none of the lookup calls. The outer owner scope remains alive, so owner lookup would work. However, the pending lookup exists before its collector, while `collectSpend` mints its run ID internally ([ai-spend.ts:1041](/var/tmp/spideryarn-worktrees/author-gift/src/ai-spend.ts:1041)); `run_id` therefore must initially be nullable and must be persisted before the first provider request, or a crash can leave paid ledger rows unjoinable to the lookup. There is no existing after-response paid-collector precedent; the documented nested precedent is only `runStep` ([ai-spend.ts:1035](/var/tmp/spideryarn-worktrees/author-gift/src/ai-spend.ts:1035)). **Fix:** specify `run_id NULL` until claimed, then inside the fresh collector read/persist its ID before calling the gateway. Supply `{ scopeKind: "request", ownerId, articleSlug }` explicitly and use `sink: row => costStore.record(row)`. Test that the outer request report remains empty while the inner row has the exact owner, article, and lookup run ID on success and failure.

- **R2-F7 — P2 — Notes lack a complete lifecycle and capacity rule.** All PATCHes are refused after Send ([plan:129](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:129)), although notes are admin-only metadata that the plan says Greg and MCP edit and that remain listed after Send ([plan:222](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:222)). Repeated automatic appends also have no defined behavior when the 20,000-character limit is reached; a constraint failure must not roll back lookup completion and leave it pending. **Fix:** freeze only voucher-bound fields; permit a notes-only update after Send. Append under the gift lock, with an explicit bounded behavior—skip/truncate the automatic block while still completing the lookup—and test a full notes field. The routes do provide the real admin boundary. For MCP completeness, also add both tool names to the existing `ADMIN_ONLY` diagnostic set, not merely `TOOLS` ([mcp/tools.ts:738](/var/tmp/spideryarn-worktrees/author-gift/src/mcp/tools.ts:738)); otherwise access is still refused, but the error loses its admin-only explanation.

- **R2-F8 — P2 — The add-page/API completion contract remains contradictory and needs an asynchronous once-guard.** D4 says a running or non-draft lookup returns 409 ([plan:154](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:154)), while the route table says the same outcomes are values inside a `202` response ([plan:273](/var/tmp/spideryarn-worktrees/author-gift/docs/plans/261010c-author-gift-draft-voucher-from-the-add-page.md:273)). The current common exit takes its once-guard, marks the page opened, and navigates synchronously ([AddPage.tsx:1230](/var/tmp/spideryarn-worktrees/author-gift/src/web/AddPage.tsx:1230)); the automatic exit duplicates that transition ([AddPage.tsx:1295](/var/tmp/spideryarn-worktrees/author-gift/src/web/AddPage.tsx:1295)). Merely inserting an `await` risks two submissions or an old completion navigating after the source/session changed, and a failure cannot be visibly shown on the add page if navigation immediately follows it. **Fix:** define `202` only for a newly accepted lookup and `200` for an already-existing gift; use the separate rerun route from R2-F2. Refactor both exits through one async, reader-bound, single-flight transition that rechecks completion/source after the await. On failure, remain on the page with the promised explanation and an explicit **Open article anyway** action.

The admin namespace, exact evidence matching, separate-table isolation, and after-response owner scope are otherwise correctly chosen. No files were changed.
