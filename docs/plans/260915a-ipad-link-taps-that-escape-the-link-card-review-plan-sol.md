1. **P1 — The plan rejects the simpler design for a reason that is no longer true.** [plan:65](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:65), [TableView.tsx:1490](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/TableView.tsx:1490). `TableView.onMouseUp` now handles a selection first, then explicitly returns for anything inside `a[href]` before opening a comment at line 1512. Therefore anchor-contained targets can be decided exclusively at capture-phase `click`; only bare terms still need `pointerup`. Concrete scenario: a `mark.term.chat` inside a link will not open chat on `mouseup`, so processing that link once at `click` avoids the entire pointerup-plus-swallow duplication. Suggested change: keep `pointerup` for non-link marks, but defer terms inside links, footnote markers, and outbound links to one capture-click path.

2. **P1 — One “most recent press” record cannot guarantee that a handled first tap never escapes.** [plan:43](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:43), [plan:69](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:69), [test:247](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/tests/link-tap-escapes.test.tsx:247). A click after 1000ms simply escapes; more subtly, a second pointerdown can replace the first tap’s record before its delayed click arrives. The Pointer Events specification permits compatibility mouse events to be delayed or grouped after the last `pointerup`, so `down A → up A → down B → up B → click A → click B` is an ordering the state machine must survive. If the first arriving click consumes the one-shot record, the second can navigate; if B was otherwise declined, click A can be misread as B and commit the already-open card. [Pointer Events § compatibility mapping](https://www.w3.org/TR/pointerevents/#compatibility-mapping-with-mouse-events). Suggested change: use the click-only anchor design above. Otherwise the plan needs a multi-press state machine and tests for grouped, missing, reordered, and out-of-window clicks—and must drop the word “never.”

3. **P1 — The net reverses the deliberate selection guards and can turn selection into commit.** [useHoverCard.ts:154](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/useHoverCard.ts:154), [TableView.tsx:1451](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/TableView.tsx:1451), [plan:53](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:53). Concrete scenario: with a card already open, the reader drags a short selection within that link. `pointerUp` declines because the selection is live; `onMouseUp` opens the annotation flow; then the capture net sees the same open target and commits it, opening the external page. Even without an open card, it can add a hover card over the annotation dialog. A live selection was not an escape—TableView already cancels its click. Suggested change: preserve why `pointerUp` declined. For a live selection, do not run the net; for a tap dismissing an earlier selection, cancel navigation without revealing or committing.

4. **P1 — Time and distance do not establish that the click came from the recorded tap.** [plan:46](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:46), [plan:150](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:150), [test:274](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/tests/link-tap-escapes.test.tsx:274). Concrete scenario: a touch produces no click, then within one second the reader presses Enter on the same focused link. Enter has no new pointerdown and may carry usable element coordinates, so the stale touch record can swallow it or treat it as reveal/commit. Programmatic `.click()` and assistive activation have the same ambiguity. A normal trackpad click is safer because its mouse pointerdown replaces the record; `pointercancel` or a pointerdown with no matching pointerup must explicitly invalidate it. Suggested change: require a completed, primary press; exclude keyboard/programmatic activation using appropriate click metadata such as `detail`, `isTrusted`, and direct `pointerType` when reliable. Do not rely solely on click `pointerType`: WebKit only changed `click` to `PointerEvent` in Safari 18.2, and its touch-as-`mouse` bug remains reopened. [Safari 18.2 release notes](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/), [WebKit bug 282988](https://bugs.webkit.org/show_bug.cgi?id=282988).

5. **P2 — The widened click window exceeds the touch-focus window.** [useHoverCard.ts:118](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/useHoverCard.ts:118), [useHoverCard.ts:719](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/useHoverCard.ts:719), [plan:150](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:150). Concrete scenario: compatibility `mousedown`/focus arrives 800ms after lift, still inside the new 1000ms swallow but outside `TOUCH_FOCUS_MS = 700`. `focusIn` treats it as keyboard focus; `arm()` on the current element changes `byTouchRef` to false, so the touch-opened card no longer dismisses on scroll even though its click is swallowed. The test helper emits only `mouseup` and `click`, so it cannot catch this. Suggested change: key focus suppression to the outstanding touch/pen activation record, or align the horizons, and test the full compatibility sequence including focus.

7. **P2 — “Every escape” omits other first-tap external links already served by this card.** [ProseHoverCard.tsx:309](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/src/web/ProseHoverCard.tsx:309), [plan:157](/home/greg/code/spideryarn2/.claude/worktrees/ipad-link-card-escape/docs/plans/260915a-ipad-link-taps-that-escape-the-link-card.md:157). External links in chat prose (`a.cited-link`) and `.chat-sources` receive hover cards but are excluded from `tapSelector`, so they still open on the first finger tap. The acknowledged lightbox/note-preview gap is therefore not the whole remaining scope; `<area target="_blank">` in prose is another low-frequency case. Suggested change: either explicitly scope the promise to prose `<a>` links or inventory all card-enabled external-link sinks and decide them deliberately.

Terms and footnote markers inside links should remain covered, not only `a[target="_blank"]`; otherwise the same target-adjustment disagreement bypasses their established reveal-first behavior. The necessary exception is selection, not link kind.

Verdict: **rethink — use click-only handling for anchor-contained tap targets, retain pointerup only for non-link marks, and add the ordering/input/selection tests above.**
