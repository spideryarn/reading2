1. **P1 — Make the active-run append atomic.** Both searches can run, but `setActive([...panel.active, ask(...)])` derives the next URL value from a render snapshot ([SearchMode.tsx:108](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/modes/search/SearchMode.tsx:108), [SearchMode.tsx:404](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/modes/search/SearchMode.tsx:404)). If two asks reach that callback before a render, the later write can omit the first id; both POSTs continue, but the first search becomes unticked and disappears from the merged results because those are filtered through `active` ([SearchMode.tsx:271](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/modes/search/SearchMode.tsx:271)). Stream-driven renders normally refresh the closure, so interleaving frames are safe; the unsafe case is specifically two same-render writes. Use `setRunIds(old => [...resolveRuns(old, run1), id])`, exposed as an `activate(id)` operation, and test two appends sharing one render snapshot.

2. **P2 — The shared transport-error banner has order-dependent behavior under parallel requests.** Every `send` clears the one global error ([useSearch.ts:311](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/useSearch.ts:311)), while a stream/transport failure sets it and also stores the failure on that run ([useSearch.ts:406](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/useSearch.ts:406)). Therefore starting Q2 after Q1 fails removes Q1’s detailed banner, while Q1 failing after Q2 starts leaves its banner visible even after Q2 succeeds. No result data is lost—the failed row remains—but the banner is unscoped and timing-dependent. Prefer keeping search failures solely on their run and reserving the global slot for delete/recolour failures, or explicitly accept and test the current behavior.

3. **P2 — The tests do not exercise the concurrency seams most likely to regress.** The proposed test completes streams in reverse order, but its `done` frames replace streamed hits authoritatively ([useSearch.ts:380](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/useSearch.ts:380)), so final-state assertions can pass even if live hits were routed incorrectly. Add assertions after alternating distinct `hit` frames, before either `done`, verifying each saved row/result’s run provenance and the exact “1 still searching” count ([SearchPanel.tsx:1167](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/SearchPanel.tsx:1167)). Also cover one stream failing while the other succeeds, and duplicate refusal after the pending run has been unticked—the plan explicitly promises ticked or not ([260930f-parallel-searches.md:49](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/docs/plans/260930f-parallel-searches.md:49)).

4. **P2 — The `MAX_RUNS` defer should state the visible failure, not merely the deletion.** `begin` protects only the newly inserted row; trimming may delete another pending run ([pg-searches.ts:236](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/store/pg-searches.ts:236)). Its eventual fenced `finish` then updates no row ([pg-searches.ts:353](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/store/pg-searches.ts:353)); the route sends no `done`, and the client reports “The search stopped arriving” ([routes.ts:4192](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/routes.ts:4192), [useSearch.ts:399](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/useSearch.ts:399)). That means a paid search can appear failed and vanish on reload. This does not block the ordinary two-search case, but “no cap” makes it an accepted product boundary that should be documented accurately; protecting pending rows during trim would be the stronger fix.

The core claim is otherwise correct: `put` and hit accumulation use functional, run-id-keyed updates; tombstones and colour/PATCH state are per id; the route creates independent streams; `begin` holds the article lock only for its transaction; and `finish` is fenced by run plus attempt ([useSearch.ts:273](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/web/useSearch.ts:273), [routes.ts:4137](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/routes.ts:4137), [pg-searches.ts:144](/home/greg/code/spideryarn2/.claude/worktrees/fb-5v-parallel-searches/src/store/pg-searches.ts:144)).

The exact trimmed, case-sensitive pending-question refusal is the right minimal guard. A server guard would complicate cross-tab behavior and could not attach the second client to the first client’s stream; broader case or semantic normalization would reject legitimately distinct questions.
