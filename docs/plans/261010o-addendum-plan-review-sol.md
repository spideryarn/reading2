The overall architecture is sound: a separate append-only table is appropriate, the composite FK is valid because `feedback` has primary key `(owner_id, id)`, and an uncovered-addenda queue is necessary for late additions. I found several blocking gaps.

- **F1 — P1 — Unbounded addenda break the response byte guarantee.** The plan permits unlimited 20,000-character addenda with no rate/count limit, while claiming each report plus all addenda remains within `FEEDBACK_LIST_BYTES` ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:96), [plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:102)). `prefixWithinBytes` deliberately always keeps the first item, even when it alone exceeds the budget ([json-budget.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/json-budget.ts:20)); its safety depends on each item being independently bounded. Roughly 27 worst-case addenda can exceed 3 MiB, and enough can exceed Vercel’s 4.5 MiB limit.  
  **Fix:** Bound the aggregate addenda payload per report inside the locked insertion transaction, or make the simplest version one addendum per report. Add a test proving the largest permitted report-plus-addenda item remains bounded.

- **F2 — P1 — Coverage can silently confuse a report ID with an addendum ID.** Both use browser-minted `spya-` IDs ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:61)), and the plan explicitly relies on the existing generic `spya-` regex in queue sources ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:128)). That regex feeds one untyped set ([feedback-unswept.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/scripts/feedback-unswept.ts:95), [feedback-unswept.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/scripts/feedback-unswept.ts:111)). If an addendum ID equals its parent report ID—or any covered report ID—the addendum appears covered without anyone reading it. IDs are also only owner-unique, and the plan lacks the existing report ambiguity check.  
  **Fix:** Give addendum coverage a typed identity. Parse `reports:` and `addenda:` into separate sets, require an explicit addendum marker in queue sources including an unambiguous parent identity such as the globally unique report number, and detect cross-owner duplicate addendum IDs. Test same-ID report/addendum and duplicate IDs across owners.

- **F3 — P1 — “Same transaction” does not close the status race.** The plan checks Open and inserts in one transaction ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:89)), but a normal read does not prevent the existing Ignore update from committing between that read and the insert ([pg-admin-feedback.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/store/pg-admin-feedback.ts:368)). The compiled endings are stable for the process, but `ignored_at` is not. The plan also says the FK “or a read” can produce 404; an unhandled FK violation produces a 500, not a classified 404.  
  **Fix:** In the store transaction, first handle an existing idempotent row, then lock the owner-scoped parent report with `SELECT … FOR UPDATE`, distinguish missing from closed, compute the shared `statusOf`, and insert with conflict handling. Add a concurrent Ignore-versus-addendum test.

- **F4 — P1 — The production-reading scripts will fail before the migration deploys.** The plan adds unconditional addenda reads to `feedback-reporter.ts` and `feedback-unswept.ts` ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:124)). Those scripts run from `dev` against production before deployment; the existing replies reader therefore probes with `to_regclass` first ([feedback-questions.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/scripts/feedback-questions.ts:148)). Without the same treatment, every sweep and provenance check will fail between the dev push and production migration.  
  **Fix:** Probe `to_regclass('spideryarn.feedback_addenda')` within the read-only transaction. When absent, state explicitly that addenda are not deployed and continue the existing report read. Test both present and absent tables.

- **F5 — P1 — The proposed dictation keeper is not bound to its report.** The plan specifies the single keeper name `feedback-addendum` while preserving drafts across navigation ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:114)). The existing reply implementation keys drafts and retry attempts by question ([FeedbackEarlier.tsx](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/web/FeedbackEarlier.tsx:499), [FeedbackEarlier.tsx](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/web/FeedbackEarlier.tsx:577)) and deliberately uses `feedback-reply:${question.id}` so recovered speech cannot reach another destination ([FeedbackEarlier.tsx](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/web/FeedbackEarlier.tsx:1306)).  
  **Fix:** Key drafts, retry attempts, local receipts, and the keeper by report ID: `feedback-addendum:${report.id}`. Test drafts and recovered dictation across two reports.

- **F6 — P1 — The in-flight-session handoff is not operationally specified.** The plan says to find a live `fb<short-id>` session and `SendMessage` it ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:139)), but the addendum supplies a report ID, while `fb<short-id>` is the Sentry issue naming convention ([feedback-reports.md](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/project/feedback-reports.md:393)). The queue already records the exact dispatched session in `dispatchedTo` ([idea-queue.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/tools/overseer/idea-queue.ts:432)). Without a deterministic lookup, the core “report’s session must see it” requirement remains procedural hope.  
  **Fix:** Specify: find the queue item whose typed source names the parent report; use its `dispatchedTo`; verify it is live; send the addendum and require acknowledgement. If lookup or delivery fails, leave the addendum uncovered and queue it next run. Test/render enough identifiers for the sweep to perform this mapping.

- **F7 — P2 — The request byte limit is omitted.** A 20,000-character body can exceed the default 64 KiB request limit ([routes.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/routes.ts:570)). The answers endpoint avoids this with a six-bytes-per-character envelope limit ([routes.ts](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/src/routes.ts:8917)).  
  **Fix:** Give addenda the same explicit request-byte calculation and test a maximum-length heavily escaped body.

- **F8 — P2 — “Open only” rests on an incomplete premise.** The plan says Needs a decision reports already have a reply box ([plan](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/plans/261010o-addendum-to-an-earlier-feedback-report.md:40)), but the current UI explicitly has waiting reports with no open question and therefore nothing to answer ([feedback.md](/var/tmp/spideryarn-worktrees/fbsaz0yw-addendum/docs/project/feedback.md:390)). A question reply is also not necessarily an addendum to the report.  
  **Fix:** Either define “open” as the exact Open pill with Greg’s explicit agreement, or accept addenda for both `open` and `waiting`; at minimum, expose it on waiting reports that have no question.

VERDICT: REVISE
