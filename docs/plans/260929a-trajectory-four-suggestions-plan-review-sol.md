1. **F1 — P1: §3’s centring arithmetic is sound, but the deferred “known cost” is not small enough to accept.** `stickyDestination()` correctly predicts the moving top bar, `dockOffset()` measures the live bottom obstruction, and `glide()` re-aims through the 200ms journey; I would keep that design. The problem is that every other notion of “where the reader is” remains tied to the top reading line: `positionToWrite()` can replace the destination with the preceding section, `measureOrigin()` records the preceding block for the next ReturnChip, and a repeated link no longer satisfies `beginJump`’s same-target check. Large-but-fitting centred rows can also change `isBlockOnScreen`/`whereIsBlock` from “here” to “away” because their bottom enters the 10% margin while their top no longer crosses the reading line. This affects URL restoration, Back/chip correctness, duplicate history entries, and comment navigation—not just the spine label. 2. **F2 — P1: `beginJump` can suppress the passage-centred movement entirely.** Its “already there” branch compares only the block under the reading line with the target block. If the requested quote is near the bottom of that same long paragraph, opening Trajectory or pressing its row flashes the quote without scrolling to it—even if the quote itself is off-screen. Separately, `glide()` immediately settles when its first fallback aim is within one pixel, so the plan’s claim that marks appearing mid-glide are always picked up is false in that no-op case. Evidence: [keynav.ts:318](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/keynav.ts:318), [keynav.ts:364](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/keynav.ts:364), [scroll.ts:689](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/scroll.ts:689), [postmortem:109](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/docs/postmortems/260928c-a-scroll-aimed-at-a-pixel-not-at-the-element.md:109). **Instead:** make “already there” alignment-aware and passage-aware: refuse the jump only when the resolved passage is already at its centred destination. When a requested passage is not yet drawn, force the existing corrective frame before declaring the movement settled.

3. **F3 — P1: a literal `mark.hit[data-hit=…]` lookup will miss overlapping marks.** `data-hit` is a space-separated list because one generated `<mark>` can carry several hits; the existing flash code deliberately queries `[data-hit]`, splits the value, and tests token membership. Quotes split by inline markup also produce several matching marks, which should be vertically unioned. Evidence: [annotate.ts:457](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/annotate.ts:457), [flash.ts:83](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/flash.ts:83). **Instead:** scope the lookup to the target row’s `td.text`, reuse the token-matching rule from `passageMarks`, and union all matching fragments. A quote itself cannot span blocks: its key and resolver bind it to one `blockId`.

4. **F4 — P1: the opening one-shot cannot live solely in the remounted band.** The existing arrival token lives above the mode boundary specifically because changing modes remounts the band. A local ref therefore re-arms when Back or Forward re-enters Trajectory; calling `onJump` then pushes a new entry, truncates Forward history, and turns traversal into a fresh jump. Two independent effects are also unsafe for deep-link precedence: the existing effect mutates `arrival.stop` to `null`, so the opening effect can subsequently fire too; conversely, treating any non-null arrival as consumed leaves a stale `?stop=` motionless because `currentStop` falls back to stop 1 while the deep-link effect declines the mismatch. Evidence: [Reader.tsx:337](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/reader/Reader.tsx:337), [TrajectoryMode.tsx:384](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/modes/trajectory/TrajectoryMode.tsx:384), [trajectory-route.ts:78](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/trajectory-route.ts:78), [useReadingPosition.ts:248](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/reader/useReadingPosition.ts:248), [params.ts:333](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/src/web/params.ts:333). **Instead:** keep an activation token above the keyed mode boundary, armed only on initial Trajectory arrival without a valid deep link or a direct UI activation—not on `popstate`. Consume deep-link and opening precedence in one effect/state machine, falling back to the resolved first stop for a stale token. Direct activation will then coherently create two entries—mode, then automatic jump—so first Back returns to the origin while remaining in Trajectory and second Back leaves the mode; document and test that explicitly. The mounted-band suite already exists, so add unit coverage there for late data, valid/stale deep links, StrictMode, remount, Back, and Forward rather than leaving opening behavior to browser checks: [trajectory-panel.test.tsx:890](/home/greg/code/spideryarn2/.claude/worktrees/trajectory-four-suggestions/tests/trajectory-panel.test.tsx:890).
