The product design is right. The simpler implementation is to reuse one article-level `useSearch` controller for Search mode and chat, rather than build a second miniature search client. Paying one indexed GET per owner article is probably the cleanest trade-off; alternatively start the controller lazily on first Search/card use and retain it for the Reader’s lifetime.

1. **High — two independent search clients will lose or duplicate live runs.** The plan gives `ChatSearchCard` its own POST, stream, and saved-list read ([plan:91](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/docs/plans/261011aa-guide-and-chat-run-in-article-searches-in-place-and-link-the-article-readily.md:91)), while Search mode mounts a separate `useSearch` ([SearchMode.tsx:126](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/modes/search/SearchMode.tsx:126)). An already-mounted Search mode never hears about the card’s new run; one mounted mid-stream may load a `pending` snapshot and never receive its hits or completion. Its opening GET also replaces the whole local list ([useSearch.ts:385](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:385)). The server’s article lock only serialises short database writes ([pg-searches.ts:33](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/store/pg-searches.ts:33)); it does not deduplicate equal criteria, and a different valid client ID mints another run ([searches.ts:252](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/searches.ts:252)).  
   **Fix:** lift one `useSearch` instance into an owner-only Reader/provider and pass its `runs`, `ask`, `retry`, `isRunning`, and rename notifications to both SearchBand and every card. Do not allow a card press until the opening list has settled—the existing contract explicitly relies on callers waiting because a late GET can erase a later write ([useSearch.ts:78](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:78)).

2. **Medium — “read begin/hit/done” understates the protocol the new client would have to reproduce.** `begin` may replace the proposed ID, and the existing hook migrates every per-ID fact when that happens ([useSearch.ts:622](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:622)). Streamed hits are previews; `done.hits` must replace them, not be merged with them ([useSearch.ts:748](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:748)). Deletion may legitimately end with no `done` ([routes.ts:5316](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/routes.ts:5316)), and late work must remain bound to the reader for whom it began ([useSearch.ts:195](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:195)). Local card state is especially fragile because `CommandChip` owns state inside the streamed answer ([CommandChip.tsx:105](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/CommandChip.tsx:105)); the editable next-step chip is deliberately remounted whenever its words change ([GuideNextSteps.tsx:240](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/GuideNextSteps.tsx:240)).  
   **Fix:** let cards render the shared controller’s run, keyed by its live server ID. Keep the request above the answer/dialog lifecycle, replace previews on `done`, treat a `done` error separately from transport failure, and retry the real returned ID. This avoids copying the rename, tombstone, stall, final-authority, and `madeFor` machinery.

3. **Medium — saved-run reuse needs a precise identity and staleness rule.** The token parser collapses whitespace ([command-proposal.ts:132](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/command-proposal.ts:132)), while the current duplicate guard compares case-sensitive, trimmed criteria and kind ([useSearch.ts:220](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:220)). More importantly, the owner GET currently sends no current article fingerprint, so old runs cannot be judged stale ([useSearch.ts:393](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/useSearch.ts:393)); the shared rule says an unknown fingerprint is stale ([search-stale.ts:38](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/search-stale.ts:38)).  
   **Fix:** introduce one shared search-identity helper used by reuse and duplicate detection. Conservatively, retain today’s semantics: same `kind`, exact case and internal whitespace after outer trimming; therefore a card reuses only a `done`, non-stale `quick` run with that identity, choosing the newest if duplicates exist. Extend the GET to return the current `sourceHash`, then either label stale results “older version” or leave the runnable button in place. Never reuse a `meaning`, `pending`, or `error` row as a completed quick result. Showing a valid saved result without a press does **not** break the consent rule: it is a read and display, not a write or model run.

4. **Medium — the typed and spoken prompt paths need a sharper distinction.** The typed guide already has article-search tools ([converse.ts:1826](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/converse.ts:1826)). If “run searches” encourages it to call those tools and also offer saved quick-search buttons, one request can spend twice. Meanwhile the spoken base prompt says ordinary article lookup is worse than reading the supplied article and prefers `show_passage` ([live.ts:341](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/live.ts:341)), so the new exception must be explicit. The actual chip tooltips also still promise “Search mode” ([command-proposal.ts:361](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/command-proposal.ts:361), [command-proposal.ts:403](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/command-proposal.ts:403)).  
   **Fix:** tell the typed guide that a request to create/run searches is fulfilled with buttons, not its private lookup tools; those tools remain for evidence needed to compose an answer. Tell the spoken guide, which has no buttons, to search only on an explicit request and then call `show_passage`, while retaining “never say IDs aloud” ([live.ts:311](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/live.ts:311)). Make `proposalWords` descriptions neutral enough for both surfaces—e.g. “Every place these words appear” and “A fast first pass”—or override them in the card context.

5. **Low — the security boundary is sound, provided the card does not bypass the second check.** `quick-search` is already an allowed, spending proposal and `find` is already allowed; this changes where their existing capability is displayed, not what a model token can request. The defence remains `chipFor` at draw and press, plus the reader’s press ([security-map.md:118](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/docs/project/security-map.md:118), [CommandChip.tsx:131](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/CommandChip.tsx:131)).  
   **Fix:** keep initiation inside `CommandChip` or a shared press function that reruns `chipFor`; never POST from render or merely from receiving card context. No change to `chat-commands.ts`, `command-proposal.ts`, or the security-map defence is needed.

6. **Low — define passage counting and canonical links.** `findLiteral` emits one result for every occurrence, including several in the same block ([search-hits.ts:354](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/search-hits.ts:354)). Repeating the same block chip is not useful if the card says “passages.” Also, the proposed quick URL omits `match=quick`, whose absence defaults to meaning ([params.ts:813](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/params.ts:813)).  
   **Fix:** deduplicate literal hits by block ID in document order and count unique passages; test multiple occurrences in one paragraph. Build exact-word links with the existing `findHref` ([CommandBar.tsx:1111](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/src/web/CommandBar.tsx:1111)). Build quick links from the actual `begin` ID as `mode=search&match=quick&runs=<id>`, preserving the same carried URL state as existing navigation helpers.

7. **Medium — the planned tests miss the failure modes above.** The current list tests ordinary rendering but not the two-controller race ([plan:140](/var/tmp/spideryarn-worktrees/fbmpg67x-guide-block-links-and-searches/docs/plans/261011aa-guide-and-chat-run-in-article-searches-in-place-and-link-the-article-readily.md:140)).  
   **Fix:** add tests for:

   - Search mode already mounted, mounted during the card stream, and mounted after completion.
   - Two identical cards pressed in one React batch producing one POST; different criteria still run concurrently.
   - `begin` returning a different ID, with the card and Open link following it.
   - Streamed hits differing from—and being replaced by—a zero-hit or smaller `done`.
   - Card/answer/dialog unmount and remount mid-stream, including a reader change and the frozen `madeFor`.
   - Saved-run selection across case, whitespace, quick versus meaning, pending/error, duplicate finished rows, and stale/current fingerprints.
   - Deleting the run from Search while its chat stream is active.
   - Repeated literal matches in one block.
   - Composed Realtime and GPT-Live guide prompts containing no command tokens, retaining “never speak IDs,” and distinguishing article links, block links, and explicit web requests.

**Verdict: build with these changes.**
