2. **High — the iOS claims are too categorical.** It is sound that Apple documents no developer-supplied dark/clear/tinted variants for web-clip icons; `apple-touch-icon` still takes precedence over manifest icons ([WebKit](https://webkit.org/blog/13878/)). But iOS can itself transform Home Screen icons, and current PWA reports describe tinted treatment and automatic replacement of white backgrounds—not one immutable raw colour. The “transparent becomes fixed black even in light mode” evidence is an unresolved iOS 16 report, not iOS 26 behavior ([WebKit bug 255596](https://bugs.webkit.org/show_bug.cgi?id=255596)); iOS 18 reports already describe appearance-dependent behavior ([Apple forum](https://developer.apple.com/forums/thread/761615)). Likewise, selecting a light/dark touch-icon with JavaScript at installation time is reported to work, although it does not subsequently switch. Rewrite lines 77–88 as “no documented, reliable developer-controlled live variant” and treat automatic treatment, transparency, and refresh-after-install as device-test findings rather than settled rules. An adaptive SVG is not a dependable escape hatch either: Safari 26.3 has an open bug for ignoring `prefers-color-scheme` inside SVG favicons ([WebKit bug 309949](https://bugs.webkit.org/show_bug.cgi?id=309949)).

Also split the history accurately: iOS 18 introduced dark/tinted native icons; iOS 26 added clear appearances.

4. **Medium — the proposed implementation has undisclosed scope and cache claims.** The note proposes changing Android icons too, although the question only asks about iPhone, and `/apple-touch-icon.png` is also used in the dark email header at [email-frame.ts](/home/greg/code/spideryarn2/src/email-frame.ts:42).
