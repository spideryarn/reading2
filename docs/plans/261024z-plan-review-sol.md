I would not build the plan as written. The synchronous request is a sensible defensive fix, but the cached device listing and Live handoff need revising first.

1. **P1 — The remembered listing can recreate the exact stale-device failure this change is meant to prevent.** The plan treats a prior device list as sufficient to issue an early `exact` request ([plan:77](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/docs/plans/261024z-dictation-asks-for-the-microphone-inside-the-press.md:77>)), but availability can change after that list and before `getUserMedia`. If a cached “listed” device disappears, the early `exact` request rejects and spends the gesture; the fallback at [useDictation.ts:2497](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/useDictation.ts:2497>) is then the unprivileged second request. Conversely, a cached “missing” result can open the default even though the chosen device has returned. `devicechange` reduces but cannot remove that race, and “no listing only on the first press” at plan:80 is false after device changes, failed enumeration, or missed events. Use `{ deviceId: { ideal: preferred } }` for the early, non-Chromium path and determine `honoured` afterwards with `openedId(track) === preferred`; then retain the existing label-based warning/adoption check. The prior objection to `ideal` was measured on Chromium ([mic-devices.ts:173](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/mic-devices.ts:173>)), while this path expressly excludes Chromium. That removes the listing cache, listener, refresh, and stale-exact race altogether. Measure Safari and Firefox once before landing.

2. **P1 — The early request must be placed under the microphone claim synchronously, not merely cleaned up later.** The lock’s contract says the claim precedes `getUserMedia` ([mic-lock.ts:68](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/mic-lock.ts:68>)); the plan currently describes checking `microphoneFree()` and issuing the request, without pinning the ordering. Do this in `start()`:

   - Check whether the lock was free.
   - Call `claimMicrophone(s.claim)` without awaiting it; that function installs the claim synchronously before reaching its internal `await`.
   - If it had been free, call `getUserMedia` immediately afterward, still in the click stack.
   - Attach an ownership handler to the promise immediately. Until `beginCapture` explicitly adopts the stream, Stop, unmount, a newer claimant, or a stale session must stop every returned track.

   This is necessary because `finish()` can only stop `s.track` ([useDictation.ts:965](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/useDictation.ts:965>)); while the early promise is pending, that field is null. The existing stale-claim guard at [useDictation.ts:1437](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/useDictation.ts:1437>) is otherwise suitable. A device change during capture is also safe: `chooseDevice` starts again before the old recorder has released its claim ([useDictation.ts:1830](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/useDictation.ts:1830>)), so the restart should deliberately take the ordinary waiting path. On non-Chromium, skipping the probe is behavior-neutral because `probeTrackOverload` already returns false immediately ([useDictation.ts:2335](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/useDictation.ts:2335>)); Firefox is safe and should receive the early path too.

3. **P1 — Chat’s pending-Live path still does not call `getUserMedia` inside the press.** `toggleDictation` waits for `live.stop()` and invokes dictation from `.then(...)` ([ChatPanel.tsx:3625](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/ChatPanel.tsx:3625>), [ChatPanel.tsx:3645](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/src/web/ChatPanel.tsx:3645>)). That contradicts plan:65’s unqualified claim that `start()` runs synchronously inside the click. Waiting is required when Live owns a track, but not while a ticket is pending before Live has claimed the microphone. Add an explicit Live API state/result meaning “startup was synchronously cancelled before microphone ownership”; in that case call dictation immediately in the original click. Continue awaiting an active Live capture. The existing test substitutes a fake dictation hook and checks only eventual arming ([chat-live-dictation.test.tsx:148](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/tests/chat-live-dictation.test.tsx:148>)), so it cannot prove synchronous `getUserMedia`.

4. **P2 — The timings support a non-gesture one-minute timeout, but do not establish that the two awaits caused it on Greg’s shipped WebKit.** Feedback almost certainly did not remember a separate permission: its press was only ten seconds after chat, as the plan says ([plan:26](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/docs/plans/261024z-dictation-asks-for-the-microphone-inside-the-press.md:26>)). But the table also fits a page/web-process recreation between the earlier presses, or Chat’s asynchronous Live handoff. Current WebKit `main` is stronger than “probably carries it”: `enumerateDevices` captures the gesture token, re-enters it as media-only, and explicitly propagates it to the promise microtask; blame dates that logic to 20 May 2025. [`getUserMedia` then reads the current token directly](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/mediastream/MediaDevices.cpp), and [`UserGesturePromisePropagation` is enabled in current main](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml). The one-minute grant rule itself is real in the [permission manager](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/UserMediaPermissionRequestManagerProxy.cpp). Therefore:

   - On current `main`, the no-holder path is intended to remain privileged.
   - Upstream source does not prove which implementation Greg’s iPadOS build contains.
   - The diagnosis should say “consistent with loss of gesture,” not “the logs say the awaits lost it.”

   Record the exact iPadOS build and repeat two idle-Chat presses 70–120 seconds apart without backgrounding or using Live. The synchronous workaround remains worthwhile because it removes this version-dependent uncertainty.

5. **P2 — The proposed tests need stronger ownership fakes and several race cases.** The fixture currently creates a different fake track for `getAudioTracks()` and `getTracks()` ([dictation-phases.test.ts:335](</var/tmp/spideryarn-worktrees/fbwembb7-dictation-permission/tests/dictation-phases.test.ts:335>)). An early-cleanup test could therefore “stop” a track other than the one capture handed out and pass falsely. Construct one track per fake stream and return that same object from both methods. Also add tests for:

   - Stop and unmount while early `getUserMedia` is pending, then resolve it.
   - A second claimant arriving while the early request is pending.
   - Early rejection releasing the claim without an unhandled rejection.
   - Claim registration occurring before the synchronous `getUserMedia` call.
   - `chooseDevice` not opening the replacement until the old tape has stopped its track.
   - Firefox’s synchronous path and Chromium’s deliberately deferred path.
   - The pending-Live-ticket Chat path with a real call-order assertion.
   - If the cache design is retained, device changes in both directions and a device disappearing between cached listing and capture.

The core early-request idea is sound after these changes. The simplest version is: claim synchronously, make one early non-Chromium request, use an `ideal` preferred device, determine what actually opened afterward, and keep explicit ownership until transfer.
