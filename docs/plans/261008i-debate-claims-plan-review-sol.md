## Findings

- **F1 — P0 — Established: Claims can spend without the intended press, and its press currently buys Reception.** The plan makes claim listing automatic on arrival ([plan:59](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:59)), while the mode contract says arrival does not run work ([mode.md:506](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/mode.md:506)). More seriously, both Debate sub-modes currently arm the `debate` target ([activation.ts:682](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/activation.ts:682)), and `useDebate` consumes that token by starting the existing pipeline step ([useDebate.ts:257](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/useReception.ts:257)). Therefore pressing Claims with no stored debate would buy the Reception search, while a pasted URL, Back, or another mount could buy the list. **Change:** give the list its own auto-run target; make Debate’s mode target depend on the sub-mode; update `PressContext`, `subModeTarget`, `bandTarget`, the command row, and `DebateViews` together. Only an actual Claims control press may arm the list. Direct links, Back, reload, and last-view restoration must only GET.

- **F2 — P0 — Established: “one pending check per article” and one list call are not atomic.** The proposed check key is `(article_id, id)` ([plan:121](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:121)), so it permits any number of pending rows. An application-level “look, then insert” races; the SQL rules call that out explicitly ([sql.md:49](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/sql.md:49)). Copying Referee’s list lifecycle also does not deduplicate calls: its two-tab design deliberately allows both calls and merely prevents the older answer landing ([pg-referee-claims.ts:27](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/store/pg-referee-claims.ts:27)). **Change:** enforce the check invariant in PostgreSQL, preferably with a partial unique index on `article_id WHERE status='pending'`, and use an atomic reservation before the model call. If the list remains custom, its begin operation must return “already pending” instead of replacing the attempt; making it a pipeline job, as F11 recommends, provides the better lifecycle. Add a real two-connection concurrency test for both operations.

- **F3 — P1 — Established: keeping `debate/6` makes the stamp lie, and the proposed new artifacts have no prompt version.** Removing pass B changes what the prompt asks for and what a stored Debate means, despite the plan’s contrary decision ([plan:47](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:47)). The repository requires a prompt-version bump whenever that changes ([mode.md:515](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/mode.md:515)). The stated reason is also false: the store computes `stale` from the source and `outdated` from the prompt version separately ([pg.ts:4134](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/store/pg.ts:4134)), and the panel deliberately does not show an outdated banner ([DebatePanel.tsx:1253](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/ReceptionAndClaimsPanel.tsx:1253)). **Change:** bump to `debate/7`. Give the claim-list prompt its own stamped version; give immutable check records a format/prompt version so old JSON can be read deliberately rather than as today’s output.

- **F4 — P1 — Established: an empty claims group currently means “a search ran and found nothing,” not “we skipped the search.”** The plan stores an empty `claims` group after removing pass B ([plan:47](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:47)). Current counts say `webSearches` is always positive for a completed group ([types.ts:6785](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/types.ts:6785)), and an empty group makes the UI tell owners and visitors that the claims search found nothing ([DebatePanel.tsx:599](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/ReceptionAndClaimsPanel.tsx:599), [messages.ts:5415](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/messages.ts:5415)). That would be false for every new debate. **Change:** represent pass B explicitly as `not-run`—for example, a discriminated group state or a dedicated field whose absence means legacy “searched.” Update the owner DTO, public DTO, provenance, empty-state copy, and compatibility tests. Do not encode “not run” as zeroed search counts.

- **F5 — P1 — Reasoned: a flat row array cannot prove that every selected claim was checked.** The plan treats the absence of rows for a target as “checked and found nothing” ([plan:109](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:109)), but its answer protocol contains only rows carrying `claimId` ([plan:113](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:113)). A target the model ignored is indistinguishable from one it searched and found nothing on. Current Debate deliberately refuses analogous ambiguity between an unusable answer and an honest empty result ([debate.ts:1056](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/reception.ts:1056)); its search accounting is only global to the call ([debate.ts:1720](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/reception.ts:1720)). **Change:** require one explicit result group per requested target, such as `{claimId, rows: []}`. Validate exactly one group for every requested ID and reject or mark incomplete answers with missing, duplicate, or unknown IDs. Only an explicit empty group may produce “found nothing.”

- **F6 — P1 — Established: stale lists remain actionable and can create broken block anchors.** The plan shows a stale list but does not disable Check or require freshness ([plan:69](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:69)). Block IDs survive only while the relevant text survives; changed passages need not retain the old ID ([block-ids.md:90](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/block-ids.md:90)). A check could therefore search an obsolete claim and store a jump target absent from the current article. **Change:** make stale lists read-only, disable Check and Dig further, and have the server compare the stored list hash with the exact article loaded for the call. Return 409 before allowance or model use on mismatch. Test re-extraction both before the POST and while a previous check is completing.

- **F7 — P0 — Established: the spending limiter is left undecided and the experimental switch is incorrectly named as a defence.** The plan defers whether the routes join a limiter and lists the switch among safeguards ([plan:128](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:128)). The security contract says the switch changes discoverability, never authority ([security-map.md:382](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/security-map.md:382)). The existing `dig-deeper` allowance already bounds paid “tell me more about this” actions and states its required placement before the paid call ([dig-deeper.ts:117](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/dig-deeper.ts:117), [dig-deeper.ts:166](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/dig-deeper.ts:166)). **Change:** decide this in the plan. The simplest choice is the shared `dig-deeper` bucket, after free ownership/input/staleness/in-flight refusals and before the model. If measurements justify a separate bucket, specify its hourly, daily, concurrent, global, and lease limits now. Add tests proving limiter refusal starts no model call.

- **F8 — P1 — Established: withholding the generated claim list from visitors breaks the default artifact contract.** The plan hides both list and checks ([plan:136](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:136)). The mode contract says stored model-generated output is public by default; owners-only applies to the reader’s own writing ([mode.md:445](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/mode.md:445)). Current Debate follows that rule through the public reader and sanitizing DTO ([public-reader.ts:426](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/store/public-reader.ts:426)). **Change:** publish a sanitized, read-only claim list—article quote, anchor, and model statement—with no controls. Keep typed claims and all check history private pending Greg’s separate decision. The existing question should ask only about publishing checked results, not silently override the list’s established policy.

- **F9 — P1 — Established: the owner UI cannot currently host this feature independently of a stored Debate, and the state matrix is missing.** The panel explicitly says no Claims sub-mode exists before a debate is stored ([DebatePanel.tsx:1147](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/ReceptionAndClaimsPanel.tsx:1147)), and the complete segmented control and Claims body are under `debate && ready` ([DebatePanel.tsx:1232](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/web/ReceptionAndClaimsPanel.tsx:1232)). The plan’s generic “useDebate-style hooks” does not resolve that coupling ([plan:158](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:158)). **Change:** specify independent Reception, claim-list, and check controllers. Claims must work with no stored Debate and while Reception is loading or failed. Name and test list `none/pending/done-empty/error/stale/swept`, check `pending/done-empty/error/swept`, two tabs, and an old debate with legacy claims. Scope relevance/threads to legacy rows unless deliberately extended; compute the segment count from final deduplicated visible rows, not the raw sum in plan line 146.

- **F10 — P1 — Reasoned: “POST to start, GET to read” is ambiguous about the lifetime of the paid call.** A serverless handler must not respond and assume another 90 seconds of work will continue. The existing Referee call keeps an SSE request open, stores pending before the call, attempt-fences completion, and ends only after storage ([routes.ts:5662](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/routes.ts:5662)); its GET also sweeps abandoned pending rows ([routes.ts:11613](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/routes.ts:11613)). Vercel permits 800 seconds, so the estimated 90 seconds fits ([vercel.json:16](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/vercel.json:16)). **Change:** state that check POST is a long-lived SSE request following that pattern; GET is for recovery, polling, and other tabs. Specify disconnect behavior and ensure an orphan is swept so it cannot block all later checks. A general pipeline job is not required for the check.

- **F11 — P2 — Established: the claim list is on the wrong storage and stage boundary.** The plan introduces another bespoke one-row article-derived table ([plan:73](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:73)), even though the schema calls that exact Referee design interim and says such reusable article output belongs in a pipeline artifact ([schema.ts:2106](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/db/schema.ts:2106)). The artifact checklist already supplies prompt stamping, job deduplication, revision carry policy, export, and public projection obligations ([mode.md:415](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/project/mode.md:415)). **Change:** make the list a pipeline step/revision artifact; keep checks as reader-action rows. Recut the stages vertically: (1) `debate/7`, explicit pass-B-not-run semantics, and legacy compatibility; (2) claim-list artifact end to end, including activation and public DTO; (3) checked claims end to end, including atomic reservation, allowance, streaming, sweep, and UI; (4) Dig further/aggregation. The present “all server, then all client” stage postpones the load-bearing spend and state contracts until after the server design is fixed.

- **F12 — P2 — Established: the validation/type reuse needs an explicit shape, or it will fork the refusal rules.** `ClaimDebateRow` requires both `blockId` and `claimQuote` ([types.ts:6691](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/types.ts:6691)), while the plan says typed-target rows carry no block ([plan:168](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/docs/plans/261008i-debate-claims-picked-by-the-reader.md:168)). `readClaimGroup` reads both fields from model output ([debate.ts:1028](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/reception.ts:1028)); `readShared` and `readGroupWith` are private precisely to keep one implementation of the refusals ([debate.ts:1047](/var/tmp/spideryarn-worktrees/fbcaue42-debate-pick-claims/src/reception.ts:1047)). **Change:** define discriminated listed/own target and result-row types, then add `readCheckedClaimGroup` inside `src/debate.ts` on top of the existing private `readGroupWith`. It should resolve listed anchors from server-loaded targets and use dedicated `unknownTarget`, `duplicateTarget`, and `missingTarget` outcomes. Do not copy `readShared`, and do not trust client-supplied anchors or “known addresses”; the server derives both from stored IDs.
