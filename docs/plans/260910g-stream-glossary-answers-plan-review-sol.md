1. **P1 — Partial provider completions can become `done` and, in stage 2, be saved.** The plan’s signal check only catches reader abandonment ([src/term-lookup.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/term-lookup.ts:552)). `explainStream` deliberately accepts `length` and `content_filter` as success, then yields `done` ([src/explain.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/explain.ts:727), [src/explain.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/explain.ts:826)). It also accepts `tool_calls` and unknown finish reasons. Because `ExplainEvent.done` does not expose the classified ending, the glossary wrapper cannot distinguish these from a genuinely finished answer and emits its own `done` ([src/term-lookup.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/term-lookup.ts:590)). A response cut off by the 1,500-token limit can therefore be presented—and later persisted—as complete. The glossary path needs its own strict completion policy inside `explainStream`, or the classified outcome must travel to the wrapper.

   The other endings are sound:

   - Provider error data or `finish_reason: "error"` throws, so the route emits `error`.
   - EOF without `[DONE]` throws as `unterminated`.
   - Deadline and stall throw.
   - Reader abort becomes `abandoned`; the wrapper’s signal check suppresses `done`.
   - Changed term, changed slug, and unmount abort the client request and prevent terminal state from committing, assuming the generation guard covers every provisional update as noted next.

4. **P2 — A rejected `lookups.save()` does not prove that nothing was saved.** The Postgres implementation commits its upsert and then performs a separate read of the whole lookup map ([src/store/pg-lookups.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/store/pg-lookups.ts:80), [src/store/pg-lookups.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/store/pg-lookups.ts:102)). If that trailing read fails, `save()` rejects and stage 2 emits `error`, although the lookup is already durable. Likewise, the process/socket can die between the successful write and `done`. The one-way promise “never claim kept before persistence” works, but an error/EOF cannot mean “not kept”; without a refresh, the reader may pay for an unnecessary retry. An atomic `INSERT … RETURNING` result would narrow the first ambiguity; the post-save/pre-frame uncertainty must be accepted and tested.

5. **P2 — Entry removal can produce a successful save and a client-side no-op.** Lookup rows have no foreign key to a glossary entry, deliberately permitting orphan IDs ([src/db/schema.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/db/schema.ts:3360)). If regeneration removes the entry while its answer streams, `save` still succeeds and the route can emit `done`; `patchEntry` then maps over the current entries and silently changes nothing when the ID is absent ([src/web/useGlossary.ts](/home/greg/code/spideryarn2/.claude/worktrees/glossary-streaming/src/web/useGlossary.ts:290)). Thus “saved against this entry” can finish with neither a visible answer nor a currently attachable entry. Stage 2 should explicitly choose between revalidating/declining the save and accepting the existing orphan-row semantics. The ordinary happy path—save, then `patchEntry(id, lookup)`—is otherwise compatible with the current store and merge.
