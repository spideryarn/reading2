The plan is not safe to implement as written; the unconditional second capture and deferred `AudioContext` setup are blockers.

1. **Blocker — The second stream is not defensibly safe on iPadOS.** WebKit supports only one microphone source at a time; capturing a different microphone can kill the previous capture. Worse, an open iOS bug shows `getUserMedia({audio:true})` choosing the built-in mic instead of the selected headset and changing audio routing. The meter could therefore animate from one microphone while recognition receives another—or interrupt recognition. [WebKit microphone limitation](https://bugs.webkit.org/show_bug.cgi?id=253834), [iOS device/routing bug](https://bugs.webkit.org/show_bug.cgi?id=282939). Remove the claim at [260827f-microphone-level-meter.md:125](260827f-microphone-level-meter.md) and do not ship this path on Safari without a real-iPad test matrix covering Safari/PWA, built-in mic, wired headset, AirPods, repeated starts, and pauses.

2. **Blocker — There is no cross-browser one-stream alternative while retaining Web Speech.** The specification now allows `recognition.start(audioTrack)`, and Chromium implements it, so desktop Chromium can use one `getUserMedia` track for both the analyser and recognition. [Specification](https://webaudio.github.io/web-speech-api/#dom-speechrecognition-start-audiotrack), [Chromium implementation](https://chromium.googlesource.com/chromium/src/+/99e74c70784b2b25182a05fff268a7ff8ac416f0%5E%21/). Current WebKit still exposes only `start()` with no track argument. [WebKit IDL](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/speech/SpeechRecognition.idl). For Safari, choose explicitly:

   - Keep Web Speech and use `audiostart` plus `soundstart`/`soundend` as a real but binary “sound detected” indicator.
   - Or, if a numerical level is non-negotiable, capture one stream yourself and move Safari transcription to a service consuming that same stream.

   There is no reliable third option that exposes Safari Web Speech’s audio samples.

3. **Blocker — An effect-driven `AudioContext` will miss the initiating gesture.** If `useAudioLevel` starts after `setListening(true)` causes a render, context creation/resumption occurs outside the click. iOS requires Web Audio to be started from an explicit user action, and Apple recommends one long-lived context per page. [Apple Web Audio guidance](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/Using_HTML5_Audio_Video/PlayingandSynthesizingSounds/PlayingandSynthesizingSounds.html). Create/reuse the context and call `resume()` synchronously inside `toggle()` before the first `await`; verify `state === "running"` before trusting samples.

4. **Should-fix — Specify one lifecycle owner and handle late acquisition.** The proposed hook owns acquisition and a level ref while the component owns the rAF, leaving cleanup and the silence clock ambiguous. Make `useAudioLevel` own the context, stream, analyser, rAF, timeout, and session token; let `MicLevel` be markup. If `getUserMedia()` resolves after stop or unmount, immediately stop the returned track rather than installing it. Reuse the context across cycles, cancel rAF first, stop tracks immediately, disconnect nodes, and close the context only on unmount. Do not await `close()` before stopping tracks.

5. **Should-fix — Suspended/interrupted capture must not be classified as silence.** A suspended `AudioContext` returns the same analyser data repeatedly, which could look like a flat microphone. [Web Audio specification](https://webaudio.github.io/web-audio-api/#dom-audiocontext-suspend). Only assess samples while the context is running and the track is live and unmuted; handle `statechange`, `mute`, `unmute`, and `ended`. rAF is normally paused in hidden documents, so the CPU loop is not the main hidden-tab problem; an elapsed-time silence clock may jump straight to failure when the tab returns. Reset that clock on `visibilitychange`.

6. **Should-fix — Four seconds cannot support the proposed accusation.** A person may press the button, think, then speak. Heavy noise gating may also produce exact silence until speech starts. Replace “No sound reaching the microphone” with no automatic fault verdict. Keep “Listening” and the visible meter; after perhaps 8–10 seconds, a neutral “No sound detected yet” is acceptable. Only `audio-capture`, a dead track, or an acquisition failure justifies saying the input failed.

7. **Should-fix — Byte-domain RMS is too coarse for a silence threshold.** The byte conversion is `floor(128 × (1 + sample))`, giving roughly 1/128 amplitude resolution and awkward behaviour around zero. [Web Audio analyser definition](https://webaudio.github.io/web-audio-api/#dom-analysernode-getbytetimedomaindata). Use `getFloatTimeDomainData()`, calculate RMS and dBFS, and map roughly −60 dBFS to empty and −12 dBFS to full with attack/release smoothing. A −50 dBFS activity threshold is a plausible heuristic, not evidence of a broken microphone; do not attach fault copy to it.

8. **Should-fix — Direct DOM updates are fine, but animate transforms.** `element.style.setProperty()` does not itself force synchronous layout unless code subsequently reads layout. Using that property for `height`, however, causes layout on every frame. Give each bar fixed dimensions and `transform-origin: bottom; transform: scaleY(var(--level))`. Scope the property to the meter root and cap updates around 30 Hz so 120 Hz screens do not double the work. React state would not necessarily rerender “the whole page,” but avoiding React for this signal is still reasonable.

9. **Should-fix — Model three phases; the current timing description is factually wrong.** The current hook calls `setListening(true)` immediately after `r.start()`, not when the recognition `start` event fires. See [useDictation.ts:181](../../src/web/useDictation.ts). Use `idle | opening | capturing`: show a pending stop-capable button and “Opening…” immediately, but apply the orange `.on` state only on `audiostart`. Reset to opening on Safari’s automatic restart until the next `audiostart`. Give the text strip `role="status"` and make decorative bars `aria-hidden`.

10. **Should-fix — Error handling should be semantic, not exhaustive enumeration.** Explicitly map only errors needing distinct action: permission, network, audio capture, and unsupported language; let a default message cover everything else. The current specification adds `phrases-not-supported`; `bad-grammar` is legacy. Also, `service-not-allowed` means the requested recognition service was refused, not necessarily that the microphone permission was blocked. [Current error definitions](https://webaudio.github.io/web-speech-api/#speechrecognitionerrorcode). Do not swallow every `aborted`: ignore it only when this app already disarmed or replaced that recogniser. An unexpected `aborted` while armed should stop and report generically.

11. **Should-fix — The meter introduces a second error channel the plan omits.** `getUserMedia` can reject while SpeechRecognition continues successfully. Meter failure must not disarm or obscure dictation; show “Listening — level unavailable” and continue. Permission reuse is a browser choice, not a guarantee, so “there is no second prompt” is too strong. [Media Capture permission rules](https://www.w3.org/TR/mediacapture-streams/#dom-mediadevices-getusermedia). Test first-use prompts rather than assuming recognition permission and `getUserMedia` permission are interchangeable.

12. **Should-fix — Automatic termination currently risks losing dictated text.** `ProfileBox` commits only when the reader presses Stop at [ProfileBox.tsx:111](../../src/web/ProfileBox.tsx). A network error, unexpected abort, failed Safari restart, or other disarming path can leave confirmed text uncommitted. Add an explicit terminal callback/reason from `useDictation`, or commit on an armed-to-idle transition after confirmed text has changed.

13. **Should-fix — The test plan is much too narrow.** Deterministically test in jsdom with fake globals:

   - Pure float RMS/dB mapping, clamping, and smoothing.
   - Error mapping, default fallback, and own-versus-external `aborted`.
   - `opening → capturing → idle`, `audiostart`, `audioend`, Safari restart, and errors.
   - Late `getUserMedia` resolution after stop/unmount.
   - Track/rAF/context cleanup and context reuse across cycles.
   - Hidden-tab timer reset.
   - Pending/listening/error markup, ARIA, and CSS-property updates.

   Leave actual permission behaviour, nonzero analyser samples, device identity/routing, AudioContext gesture unlocking, Bluetooth/headset behaviour, and Safari/PWA restart interactions to Chrome plus physical-iPad browser passes.

14. **Should-fix — Do not repeat the claim that Safari is always on-device.** The plan says Safari cannot produce `network` because it is on-device at [260827f-microphone-level-meter.md:83](260827f-microphone-level-meter.md). Apple says Safari uses the Siri speech engine, but does not promise that Web Speech always remains local; Apple’s underlying speech framework explicitly distinguishes on-device-capable and server-backed recognition. [WebKit announcement](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/), [Apple speech documentation](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition). Change the documentation to “implementation-defined; may be local or remote.”
