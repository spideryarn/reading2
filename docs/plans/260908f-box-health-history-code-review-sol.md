I verified three cases:

   - `schema: 2` was accepted as current history.
   - Renaming/removing `samples` produced a valid empty history.
   - A malformed middle sample between two healthy readings produced one continuous line and no gap.

   If every sample is rejected, [`HealthHistory`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:147) takes the empty-window branch before displaying `unreadableSamples`, making corruption look like a fresh store. The composition test in [`fleet-health-wiring.test.ts`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tests/fleet-health-wiring.test.ts:106) still stops at raw JSON casts; it never drives `parseHistory`, `plotHistory`, or the mounted panel. Strictly validate schema 1 and every required payload field, preserve rejected samples as ordered barriers, and add the promised route → JSON → real parser → mounted panel mutation test.

2. **Critical — finding 9’s lock is present, but its safety protocol is not.** [`openHealthHistory`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:411) repairs the live file before trying to take the lock, and [`append`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:525) never calls `stillOurs`. I opened a second store while the first held the lock: the second correctly reported itself locked out, but nevertheless truncated the first writer’s live file from 105 to 100 bytes. During a short write, that can damage the active writer’s record. The stale-lock race documented in `lock.ts` can also leave two successful claimants, and this store will never notice. Take the lock before repair; a refused/read-only opener must not repair anything; check `stillOurs` before and after repair and before every rotate/append, turning loss into retention failure.

3. **Critical — the chart does not yet have one mutually exclusive absence timeline.** [`plotSeries`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:525) extends unknown/absent/over-ceiling spans all the way to the next sample. The SVG draws the gap first and then draws unknown/absent rectangles over it in [`HealthHistory.tsx`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:328). Therefore an unknown or `collector-failed` sample followed by four hours without samples paints those four hours violet, hiding the hatch and assigning the silence a cause. Separately, `latest` means “latest value anywhere”, but [`summarise`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:408) labels it “now” even when later samples are unknown or the writer is overdue. Build one normalized sequence of mutually exclusive coverage spans, derive every layer from it, render gaps last as a backstop, and only say “now” when the right edge is covered by that value. The currently uncommitted swapping marks inherit the same span bug.

4. **High — finding 1c misses the most important predecessor case.** Predecessor logic requires an in-window `first` sample, while ongoing-gap logic uses only the in-window `last` sample in [`plotHistory`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:375). If the last recorded sample is just before the 24-hour window and nothing has been written since, the result has zero gaps and the page says “Nothing recorded … empty after a restart.” Use the predecessor as the effective last sample when the window is empty and the retained record predates the window; do not take the empty-state shortcut when gaps, holes, or rejected samples exist.

5. **High — the declined half of finding 1 can make the picture wrong, not merely coarse.** After an unrelated fleet-collection failure, health can succeed, but [`refreshOnce`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/refresh.ts:171) records the five-minute fleet backoff as health’s expected cadence. `gapAfterMs` then allows 12.5 minutes, so a six- or seven-minute interval with no health sample is drawn as continuous and described as “a sample was recorded throughout.” `nextDueMs` also adds this turn’s collection duration even though the next interval contains the next turn’s duration, and omits the drain that occurs after the stamp. It is not “told”; it is the wrong estimate. The clean fix remains one health loop on its own cadence. The minimum honest fix is to treat fleet-driven skipped health intervals as absence instead of redefining them as coverage.

6. **High — finding 3’s telemetry is implemented, but the banner makes a forbidden causal claim.** “Any break after that is this, not the box” at [`HealthHistory.tsx:585`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:585) is unknowable. If persistence fails and the box subsequently crashes, both happened. Say that history after the last successful write is unavailable and cannot support conclusions about the box. Also treat `lockedOutBy` itself as trouble immediately; currently the banner waits until the first append copies it into `failure`.

7. **High — finding 7’s hard ceiling is still false.** Only the top-level `collector-failed.why` is bounded. A reading’s several `why` and verdict strings remain unbounded, and rotation compares filesystem bytes with JavaScript `line.length` at [`health-history.ts:557`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:557). A type-valid report produced a 40,000,420-byte live file against the claimed 8,388,608-byte cap. Measure `Buffer.byteLength`; enforce a maximum serialized record before writing; and represent an oversized sample explicitly or report a non-poisoning retention failure.

8. **Medium — `collapseVerdict` has half-open interval errors.** At [`history-series.ts:615`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/history-series.ts:615), flooring both endpoints and including both columns means:

   - a band ending exactly at the window start paints column 0;
   - a zero-width band inside the window paints a whole column;
   - a critical band ending on a column boundary contaminates the following column.

   On a 24-hour/360-column strip that shifts severity by about four minutes. Intersect each band with the window, skip `end <= start`, and use half-open columns: floor the start and `ceil(end) - 1`.

9. **Medium — finding 10’s claimed containment is false for IO wait.** The chart does encode a verdict through its red/amber backgrounds. `SERIES` assigns both IO thresholds to 50, so 50%+ IO is red; the collector and live tile call high IO without active swapping merely strained/amber. A disk-bound, non-swapping sample therefore produces an amber verdict strip over a red chart. Until the shared classifier lands, make 50%+ IO amber and reserve critical presentation for the stored verdict’s combined swapping rule.

10. **Medium — polling can replace a newer picture with an older one.** [`setInterval(load)`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/web/src/HealthHistory.tsx:103) ignores each interval call’s cleanup. Two slow requests can overlap and resolve out of order; an older response can erase a newly arrived retention warning for another minute. Poll serially after each request, or use an abort/generation token.

What is fine and should not be changed:

- Finding 4’s poison narrowing is sound. `openSync` cannot partially append application data; it may at worst create an empty inode. Every production content write goes through `writeAll`, whose throws poison and close the writer. I found no unpoisoned partial-write path.
- Per-reading unknowns do break polyline topology correctly.
- The single composition factory is the right design; only its test stops too early.
- Reading while locked out, idempotent `close()`, positional store holes, the stored schema envelope, fixed axes, gzip, and the query clamp are good decisions.
- The current `mergeGaps` fix is correct: strictly overlapping gaps merge, while merely touching gaps remain separate because a sample exists at the boundary. The targeted suite now passes 91/91.
- Keeping the append synchronous after `publish`, without `fsync`, is defensible for v1 given the measurements. It remains an availability risk under pathological dirty-page throttling, but it does not create a false chart by itself.

The code is over-written rather than structurally over-built: roughly 4,000 lines across the core and four test files repeat the same rationale many times. That repetition has already drifted—[`health-history.ts:29`](/home/greg/code/spideryarn2/.claude/worktrees/health-history/tools/fleet/health-history.ts:29) still says “Nothing was running,” despite the plan claiming every such statement was removed. Trim duplicated narrative after the correctness fixes; the store/composition/chart split itself is reasonable.

**Verdict: do not ship.** The strict client boundary, lock ordering/ownership checks, and mutually exclusive coverage timeline are blockers; otherwise the page can still present an empty or continuous, plausible, wrong day.
