- **F1 — P1 — Established. The reported Rovelli glossary will not receive the proposed treatment.** The stretch path is explicitly only for a first run, while *Find more* remains one whole-piece call and `/9` remains appendable ([plan:40](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:40), [plan:62](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:62), [plan:70](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:70)). `existingFor` will therefore accept Rovelli’s `/9` list under `/10`, and `generateGlossary` will append rather than rewrite it ([glossary.ts:446](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:446), [glossary.ts:494](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:494), [glossary.ts:1655](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:1655)). - **F2 — P1 — Established. Publishing successful stretches after one fails is a silent success.** The proposed artefact carries the ordinary current `/10` stamp and has no “stretch 3 missing” state; future freshness checks therefore skip it as complete ([plan:66](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:66), [pipeline.ts:4556](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/pipeline.ts:4556), [glossary.ts:958](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:958)). A job-detail sentence is not durable provenance, and unchanged *Find more* is a global ranking pass, not a retry of the missing range. The same policy can turn Stop into success when one stretch finishes before the shared abort signal cancels the rest. Either fail without publishing, or checkpoint successful stretch responses while leaving the step incomplete and retry only missing stretches. Abort must always drain all started calls for accounting and then propagate cancellation.

- **F3 — P1 — Reasoned from established mechanisms. Cross-stretch duplicates are likely, and the proposed guard is weaker than the guard the current design says is necessary.** Parallel calls cannot put one another’s answers into the FORBIDDEN list. The project specifically records that a plain instruction does not prevent synonyms, plurals, subcategories, or overlapping concepts ([glossary.md:319](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/project/glossary.md:319)). `dedupe` deliberately merges only name/name and name/alias collisions, not synonyms or merely shared aliases ([glossary.ts:755](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:755)). “First used in PART a–b” is also weakly grounded: `articleText` contains bare prose with no `PART n` boundaries, while the numbered parts exist only in a separate title/gist skeleton ([article-prompt.ts:190](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/article-prompt.ts:190), [glossary.ts:1401](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:1401)). Entropy-like central terms, alternate names, and related concepts can therefore recur. One hand-read run is insufficient; this needs repeated runs and an acceptance criterion for semantic duplicates.

- **F4 — P1 — Established. The design still has fixed caps and therefore does not fix the stated bug class.** Five stretches cap the list at roughly 100, so beyond roughly 40,000 words the density declines again ([plan:40](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:40), [plan:54](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:54)). More seriously, the plan refuses to make more stretches than top-level parts. `partsOf` merely returns the root’s children and provides no lower bound tied to article length ([tree-parts.ts:34](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/tree-parts.ts:34)). A 40,000-word piece represented as one top-level part still gets one call and 20 entries; one enormous part also prevents roughly equal partitioning. Either permit cuts inside top-level parts using their block ranges, or narrow the claim from “scales with length.”

- **F5 — P1 — Established. `passes` becomes false, and the plan does not specify the other required aggregation semantics.** `Glossary.passes` means “how many model calls have contributed to this list” ([types.ts:782](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/types.ts:782)), but one invocation of `buildGlossary` increments it by exactly one ([glossary.ts:970](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:970)). Five successful stretch calls merged through one existing `buildGlossary` would therefore say one pass. The plan also needs to require:

  - merge validated raw entries, then call `buildGlossary` once, so ids are minted against one shared `taken` set;
  - preserve `idsByTerm` on rewrites;
  - compute occurrences once against the whole article;
  - sum score-drop and token counters, count successful contributing calls for `passes`, and compute `lastAdded` after the final dedupe;
  - run `finishedText` separately on every response, so one truncated response is classified as that stretch’s failure;
  - aggregate progress across stretches instead of letting five local character counters overwrite one job line;
  - test all of those, plus the frozen profile on every call.

  The proposed tests cover only partitioning, prompt presence, one exact duplicate, and partial failure ([plan:139](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:139)).

- **F6 — P2 — Reasoned. The cache, ledger, and concurrency design is missing, so the cost and latency claims are not yet credible.** A glossary-only job currently sets no article breakpoint because the stage used to make one call ([glossary.ts:1553](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:1553)). Leaving that unchanged pays for the entire book five times. Marking all five simultaneous calls is also wasteful: the cache manual explicitly says simultaneous fan-out calls all pay the write and none reads it ([prompt-caching.md:540](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/project/prompt-caching.md:540)). The established solution is to start one marked call, wait for `MeteredCall.onStart`, then release the remaining calls. Every started call must have `finalMessage()` awaited inside the spend collector; otherwise an early rejected `Promise.all` can leave paid calls finishing after the ledger scope closes. Finally, the global six-job cap exists partly to ration provider rate limits, but this turns one glossary job into five full-book calls, potentially 30 alongside six jobs ([jobs.ts:511](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/jobs.ts:511)). That may be acceptable, but it needs a bounded width and a measured 429/cost run. The quoted `$0.70–1.40` is an Opus design estimate, not an engineering measurement.

- **F7 — P2 — Established arithmetic; outcome requires evaluation. The simpler one-call design was dismissed too quickly.** Today’s streaming and budgeting machinery is specifically stronger than the original system that hit 504s. Asking for 100 entries gives `answerTokens = 600 + 100×340 = 34,600`; with the standard 40,000-token reasoning allowance, `budgetFor` requests 74,600, below the 128,000 response ceiling ([glossary.ts:1692](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/glossary.ts:1692), [token-budget.ts:53](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/token-budget.ts:53), [token-budget.ts:198](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/token-budget.ts:198)). One call can ask for the unclamped desired count, distributed across named part ranges. It avoids cross-call duplicates, cache coordination, partial completion, rate-limit fan-out, and false pass accounting. The global-ranking concern is real, but should be tested before rejecting the much simpler design. The specific claim that Torricelli lost to the quota is plausible, not yet established by the read-only production observation; the planned counterfactual eval is what can establish it.

- **F8 — P2 — Reasoned. The plan acknowledges but does not evaluate the largest reader-facing trade-off: five times as many standing underlines.** The factual threshold claims are correct: the default gate is `0.10`, it hides rows from the prioritised band, and gate-hidden terms remain underlined. But that means the threshold does not protect the prose from a roughly 100-entry list ([plan:84](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/plans/261022f-explain-this-and-a-glossary-that-scales-with-length.md:84), [GlossaryPanel.tsx:776](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/web/GlossaryPanel.tsx:776), [Reader.tsx:1440](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/src/web/reader/Reader.tsx:1440)). The accompanying research says underlines alter perceived importance and that an incomplete list is read as complete ([evidence:40](/var/tmp/spideryarn-worktrees/fbe5t77w-explain-names-glossary/docs/research/261022b-explain-this-evidence.md:40)). The eval examines entries but not underline/occurrence density or an actual rendered chapter. That should be part of the acceptance evidence.

The fixed 20-entry clamp is real, and the threshold/underline description is factually accurate. The proposed solution, however, does not reliably scale, does not reach the existing glossary that prompted it, and would certify partial output as complete.
