Revise the plan before implementation. The server-side save/queue ordering is sound, but the add-page completion state and Trajectory auto-run contain real races.

## Findings

- **F1 — P0: A touched-but-empty re-add can silently delete an existing purpose.**  
  The plan sends `{ purpose }` whenever the field was touched, while `purpose: null` explicitly clears the stored value ([plan:55](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/docs/plans/260930e-ask-why-you-are-reading-and-a-trajectory-for-that-intent.md:55), [routes.ts:4817](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/routes.ts:4817)). On a re-add, the box starts blank even if the article already has a purpose. Merely focusing it—or typing and deleting—then pressing Save would erase words the reader cannot see. Whitespace also normalises to null ([pg-shelf.ts:349](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/store/pg-shelf.ts:349)).  
  **Fix:** never PATCH a normalised-empty add-page draft. Treat it as “leave the stored purpose alone,” or fetch and display the existing purpose before permitting an explicit clear. Test re-add + focus/type/delete + Save.

- **F2 — P1: The shared completion function needs a real state machine, not merely `queueModesOnce`.**  
  The `{article}` promise callback is created by the posting effect and can capture the initial untouched draft while the reader types during the request ([AddPage.tsx:328](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:328), [AddPage.tsx:371](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:371)). The existing auto-mode choice uses refs specifically to avoid this stale-closure problem ([AddPage.tsx:277](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:277)). Also, `queueModesOnce` guards only the POSTs; navigation remains outside the guard, so StrictMode can still navigate twice ([AddPage.tsx:119](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:119), [AddPage.tsx:470](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:470)). Finally, Save and Open-without-it can race: the latter can queue jobs while the PATCH is still pending.  
  **Fix:** have all completion producers record `{key, slug}` into state; let one render-driven transition inspect current draft/focus state. Use a discriminated state such as `running | ready | saving | opened`, plus a synchronous ref guarding the terminal decision. Disable both actions while saving; restore `ready` if saving fails.

- **F3 — P1: A failed ingest’s Retry is not followed to completion.**  
  `AddPage` continues selecting the original `started` id ([AddPage.tsx:468](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:468)). But Retry creates a new job ([jobs.ts:4140](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/jobs.ts:4140)), and the client discards the returned job ([useJobs.ts:402](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/useJobs.ts:402)). Therefore a retry can succeed while the add page remains attached to the failed job and never reaches Ready/navigation. The plan does not address this.  
  **Fix:** make `retry` return `Job | null`; let `JobCard` report the replacement to `AddPage`, which updates `started`. Test error → retry → done with the purpose draft preserved.

- **F4 — P1: `offerAutoModes` cannot also own the purpose box through Ready.**  
  The plan says the box is shown during `offerAutoModes`, but that predicate is false for a done job and deliberately excludes `alreadyArticle` ([AddPage.tsx:137](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/AddPage.tsx:137)). Those are precisely the states where the plan needs the box plus Save/Open controls.  
  **Fix:** use `offerAutoModes` only for the running choice. Render the purpose area from the new completion state, including `ready` and `saving`.

- **F5 — P1: `ProfileBox` cannot provide the interaction the plan specifies.**  
  `ProfileBox` deliberately maps both blur and ⌘/Ctrl+Enter to the same `onCommit` ([ProfileBox.tsx:117](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/ProfileBox.tsx:117)). The plan requires blur to do nothing while the shortcut means Save and open. It also says dictation is deferred, but `ProfileBox` always instantiates and may render dictation ([ProfileBox.tsx:75](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/ProfileBox.tsx:75), [ProfileBox.tsx:97](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/ProfileBox.tsx:97)).  
  **Fix:** either add explicit `commitOnBlur`/`onShortcut`/`dictation` options to `ProfileBox`, or use a small textarea with the shared visual classes. Record this extra component change in Stage 1.

- **F6 — P1: The Stage-2 press can race Trajectory’s automatic unprofiled run and spend twice.**  
  When Trajectory reads `none`, `useTrajectory` hands that state directly to `useAutoRun` ([useTrajectory.ts:242](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/useTrajectory.ts:242)), which calls `ensure()` automatically after a mode press ([useAutoRun.ts:159](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/web/useAutoRun.ts:159)). The reader can then save a purpose and call `ensure()` again. Jobs freeze the profile at POST time, and the profile is part of the work key ([routes.ts:9017](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/routes.ts:9017), [jobs.ts:3108](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/jobs.ts:3108)); therefore old-profile and new-profile requests do not deduplicate.  
  **Fix:** wait for the purpose read before allowing auto-run. If purpose is absent, consume/suppress the activation without starting a job and let the explicit “Plan the route for this” action be the only starter. Test with a deferred PATCH and assert zero job POSTs before it resolves and exactly one afterwards.

- **F7 — P2: Save-then-queue is not an absolute guarantee because profile resolution fails open.**  
  On the normal path it is correct: `patchShelf` awaits the write before answering, and every job POST reads the current profile directly from the stores. The browser cache is not involved. However, `resolveProfileParts` catches a shelf-read failure and substitutes no purpose, while `resolveProfile` ignores `purposeFailed` ([routes.ts:5733](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/routes.ts:5733), [routes.ts:5752](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/src/routes.ts:5752)). A successful PATCH followed by a transient purpose-read failure can therefore queue unprofiled jobs.  
  **Fix:** if the promise is literal, add a safe boolean such as `requirePurpose: true` to these job requests and refuse the POST when the server cannot read a non-empty purpose. Otherwise narrow the plan’s claim to the successful-read path.

- **F8 — P2: The proposed tests do not cover the named completion matrix.**  
  The test section mentions only one “existing-article completion path” and omits ingest failure/retry, the distinct promise `{article}` path, touched-empty re-add, cross-clicking the two Ready actions, and exactly-once navigation under StrictMode ([plan:147](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/docs/plans/260930e-ask-why-you-are-reading-and-a-trajectory-for-that-intent.md:147)). The existing StrictMode test checks queued jobs but not navigation count ([auto-modes.test.tsx:256](/home/greg/code/spideryarn2/.claude/worktrees/fb60-reading-intent/tests/auto-modes.test.tsx:256)).  
  **Fix:** make the three completion producers a table-driven suite and run each through untouched, typed, save failure, Open-without, and StrictMode where applicable.
