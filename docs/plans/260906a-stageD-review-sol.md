Authorization is sound: I found no route that lets a reader obtain another article’s bytes, and no P0 or current security vulnerability. I did find three P1 reader/test issues and two P2 weaknesses.

## Findings

- **D-1 — P1: Public asset failures leave a broken figure, unlike owned failures.** The public branch inserts `/api/public/asset/...` without observing the response (`src/web/rehost.ts:344`), whereas `Promise.allSettled` and the “insert only after a successful fetch” behavior apply only to the owned branch (`src/web/rehost.ts:355`). A 404 after un-sharing, a 500 from a dangling blob, or a network failure therefore leaves an `<img>` with fixed dimensions pointing at a failed request—typically a large blank/broken-image area. This contradicts the stated behavior that an unloadable figure remains caption-only (`src/web/rehost.ts:252`). The public test only checks that the URL was inserted (`tests/rehost.test.ts:180`); it cannot exercise failure.

- **D-2 — P1: Owned object URLs are not released when the next article has no drawable figures.** `rehostImages` returns before `releasePrevious()` whenever `wanted.size === 0` (`src/web/rehost.ts:265`, `src/web/rehost.ts:268`). Thus navigating from an owned PDF with figures to an ordinary article, an old PDF without a manifest, or one containing only failed figures retains every previous blob indefinitely. A stale in-flight article load can also finish after navigation and mint more unused URLs because the fetches are not cancelled (`src/web/rehost.ts:355`). The current DOM sequencing does prevent already-revoked URLs remaining visibly mounted (`src/web/App.tsx:850`, `src/web/App.tsx:877`); this is a memory/lifecycle leak, not a broken-current-image bug. No test observes creation or revocation.

- **D-3 — P1: The security-critical “un-sharing takes effect on the next asset request” behavior has no behavioral test.** The implementation is correct: every `loadAsset` call issues `publicCurrentRevisionQuery` afresh (`src/store/public-reader.ts:855`, `src/store/public-reader.ts:858`), whose own SQL includes `visibility = 'public'` (`src/store/public-reader.ts:436`, `src/store/public-reader.ts:448`). But the route test seeds one permanently public article and one permanently private article (`tests/asset-route.test.ts:204`, `tests/asset-route.test.ts:215`); it never fetches an asset, changes that same article to private, and fetches again. Memoizing the projection or entitlement would therefore leave the route tests green. Given that revocation is why this route deliberately uses `no-store`, this deserves a same-slug public→private regression test.

- **D-4 — P2: The cancellation result is not completely snapshotted.** The entries array and numeric counters are safe: entries are copied synchronously after finalization (`src/collect-pdf-figures.ts:379`, `src/collect-pdf-figures.ts:383`). But the returned result exposes `book.storageErrors` by reference (`src/collect-pdf-figures.ts:394`). A storage operation that rejects after the race has returned can still push into that array (`src/collect-pdf-figures.ts:506`, `src/collect-pdf-figures.ts:511`), mutating an object already held by the caller. Returning a copied array would make the stated snapshot guarantee complete. The composed signal otherwise reaches `readPdfRasters`, and the pre-storage abort check is correctly placed.

- **D-5 — P2: Several `storedAssetFor` claims are correct but not isolated by the tests.** All route fixtures leave `Assets.entries` empty (`tests/asset-route.test.ts:194`), so deleting the generic web-image half of the lookup would pass. The wrong-extension fixture contains no second stored extension (`tests/asset-route.test.ts:385`), so it does not distinguish the correct same-entry conjunction from a wrong “hash exists somewhere and extension exists somewhere” implementation. Also, changing the route’s final key construction from `canonicalKey(found.sha256, found.ext)` to `canonicalKey(hash, ext)` would pass every test: after the exact manifest match those values are necessarily equal (`src/asset-delivery.ts:96`, `src/routes.ts:708`). The cross-article tests prove the important security property—manifest membership before storage access—but not the stronger “which variable supplied the identical key” assertion claimed in their commentary.

## Verified sound

- **Authorization:** The owned route checks ownership before reading the manifest (`src/routes.ts:706`) and `loadAssets` independently uses the owner-filtered current revision (`src/store/pg.ts:3190`). The public route rechecks current public visibility on every request. Both rebuild storage keys from matched entries (`src/routes.ts:711`, `src/store/public-reader.ts:864`). A hash valid only for another article returns 404.

- **`storedAssetFor`:** Only `status: "stored"` entries are reachable, and hash plus extension are compared on the same entry (`src/asset-delivery.ts:95`). Neither can be mixed across `entries` and `pdfFigures`. A URL caller cannot forge `Content-Type`; both production writers derive extension and content type together from `sniffImage` (`src/collect-assets.ts:867`, `src/collect-assets.ts:881`, `src/collect-pdf-figures.ts:478`, `src/collect-pdf-figures.ts:495`). A manually corrupted JSONB manifest could make them disagree because the runtime route trusts `contentType`, but I found no untrusted write path capable of doing that.

- **Sanitization:** The sole production call performs `sanitizeArticle` before `rehostImages`, on both owned and public branches (`src/web/App.tsx:901`, `src/web/App.tsx:918`). Insertions use `createElement` and `setAttribute`, not string interpolation (`src/web/rehost.ts:192`), and marker parsing admits only a narrow grammar. A hostile marker cannot reintroduce markup.

- **Annotation offsets:** The image adds no `textContent`, and the failure/source UI is a sibling outside `.prose` (`src/web/TableView.tsx:1461`, `src/web/TableView.tsx:1481`). Existing offsets are resolved against block HTML text nodes (`src/web/annotate.ts:236`), while new selections root specifically inside `td.text .prose` (`src/web/selection.ts:47`). The anchor claim is sound.

- **Downscale:** Partial edge boxes use their actual width and height; destination dimensions remain positive; valid classified rasters cannot read out of bounds (`src/pdf-figures.ts:356`, `src/pdf-figures.ts:384`). RGBA color averaging is mathematically equivalent to premultiply-average-unpremultiply, with one final rounding; alpha is averaged independently (`src/pdf-figures.ts:443`). I found no arithmetic defect.

- **Checks:** From an isolated archive of `1b8fdc30`, 184/184 selected unit tests passed, including rehosting, asset/public dispatch, downscaling, and cancellation. All three TypeScript projects passed, covering 1,402 source files. No files were changed.
