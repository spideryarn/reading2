# Code review findings — 261015a Part 1

1. **Medium — A stopped transfer and a newly chosen recovery file can occupy `UploadPicker` at the same time.** `take` blocks only the four active transfer phases. With a `failed`, `cancelled`, `queued`, or `article` transfer still in the tab-wide engine, it accepts a new file without forgetting the old transfer. The row then shows the new filename while `failureOf(transfer)` can still show the old file's failure, and its X button forgets the old transfer and also clears the new choice. This contradicts the component's own `chosen || transfer` invariant and is particularly confusing on the failed URL page, where that transfer belongs to another article. Forget a terminal transfer when a valid new file replaces it; keep refusing while a transfer is active.

2. **Low — An unrelated tab-wide transfer is drawn as though it were the replacement file.** On a URL add page `mine` is correctly `null`, but the nested `UploadPicker` still subscribes to the singleton and renders whatever file the tab is uploading. The plan-review finding asked for that file to be labelled as unrelated; a filename and link alone do not explain why it is under this failed address. Prefix the transfer row in `single` recovery mode with plain copy such as “Another upload”.

3. **Low — The nearby recovery copy drops the PDF constraint, and Help still recommends the route this change rejected.** `UploadInstead` asks “Saved the page or its PDF?”, which can mean an HTML/Web Archive save even though the failure sentence deliberately says PDF. `src/web/help/pages/adding-articles.md` still tells a reader behind a login wall, paywall, error page, or script-filled page to save HTML; that is now stale against the documented reason for changing `[jb-bot-check]`. Name both reliable actions explicitly—download the site's PDF, or save the page as a PDF—and regenerate the Help corpus.

4. **Low — The component tests do not prove two claims the implementation makes.** The multi-file test exercises only the hidden input, not `onDrop`, even though a drop commits immediately and is therefore the higher-risk branch. The predicate tests cover status, import-vs-mode, and `failureSuggestsUpload`, but never remove `job.url`, so they do not pin the fourth guard called out in the plan. Add a multi-file drop test and a no-URL import test. The shared `take` implementation is correct for drops today; the missing evidence is the issue.

No finding on `LIMITS_ID`: only one `UploadPicker` can mount on the current mutually exclusive shelf and add routes, and `UploadInstead` does not create a second picker beside another one on `AddPage`.
