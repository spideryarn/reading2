2. **P1 — `latexmlAuthorNames` is not a sufficient safety gate for rewriting the surrounding details.**

   The helper proves only that each creator has one readable name and that its other direct children have an allowed class. It does not inspect or validate anything inside `ltx_author_notes` or the `\thanks` node ([latexml.ts:694](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/latexml.ts:694), [latexml.ts:697](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/latexml.ts:697)). Accepted contacts already include multi-sentence disclaimers ([authors-2605-20355v1.html:19](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/tests/fixtures/latexml/authors-2605-20355v1.html:19)). Therefore, “the names parsed” does not prove that rebuilding the rest from selected contacts and notes cannot omit words or markup.

   Plain-text reconstruction also unnecessarily discards useful links: `oneName` explicitly accepts a name linked to ORCID ([latexml.ts:744](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/latexml.ts:744)), and the fixture contains that link ([authors-2610-08750.html:16](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/tests/fixtures/latexml/authors-2610-08750.html:16)); other accepted fixtures have working `mailto:` links ([authors-2610-01658v1.html:8](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/tests/fixtures/latexml/authors-2610-01658v1.html:8)).

   Rule 3 also needs an explicit implementation: `prepareLatexml` already computes all fragment targets once ([latexml.ts:86](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/latexml.ts:86)), while the module contract requires every referenced descendant ID or name to survive or the rewrite to refuse ([latexml.ts:30](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/latexml.ts:30)).

   Fix: introduce one all-or-nothing parser that returns structured author rows—name nodes, contacts, local/shared notes—and validates every consumed child before mutation. Reuse it for both `latexmlAuthorNames` and the rewrite. Prefer moving validated nodes into the new paragraphs, removing only the known labels and duplicate furniture; that retains links, IDs, and formatting. Refuse if an unknown node or an unhomed fragment target would be discarded. Add adversarial tests for words inside an accepted contact and links to descendant IDs.

3. **P2 — Moving all of `metaAuthors` before `prepareDocument` is broader than necessary.**

   Today the whole preparation pass runs before `metaAuthors` ([extract.ts:493](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/extract.ts:493), [extract.ts:501](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/extract.ts:501)). Normal `<head>` metadata is unaffected, so the move would work on ordinary pages. It is not strictly behaviour-preserving, however: `metaAuthors` queries metadata across the entire document ([meta-authors.ts:48](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/meta-authors.ts:48)), while preparation deliberately deletes recognised furniture and comment containers before the current read ([extract.ts:795](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/extract.ts:795), [extract.ts:801](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/src/extract.ts:801)). A body `<meta>` inside something removed would newly become authoritative.

   Fix: parse or snapshot only the LaTeXML fallback before preparation, then let `metaAuthors` read metadata at its existing point and use that snapshot only if metadata supplies no authors. Having `prepareLatexml` leave the old author classes readable is not simpler: those are precisely the classes that trigger Readability. Returning or sharing the pre-rewrite structured parse is narrower.

4. **P2 — The Readability diagnosis is substantively correct, but should not say it deletes “the first author.”**

   The installed version accepts the first node whose `rel`, `itemprop`, class, or ID looks like a byline and whose text is under 100 characters ([Readability.js:995](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/node_modules/@mozilla/readability/Readability.js:995)); it records that node’s text and removes the node ([Readability.js:1081](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/node_modules/@mozilla/readability/Readability.js:1081), [Readability.js:1100](/var/tmp/spideryarn-worktrees/fbxg4jyr-arxiv-authors/node_modules/@mozilla/readability/Readability.js:1100)). Thus the plan’s general destructive-side-effect diagnosis is confirmed.

   On this paper, however, Ashish’s creator is over 100 characters because it contains the long contribution note. The first valid match is his shorter `ltx_author_notes`, so his name and contribution note remain while his affiliation and email are removed ([live HTML:242](</tmp/claude-1000/-home-greg-code-spideryarn2/a73041af-eace-477f-bcd6-b46598a13780/scratchpad/attn-1706.03762v7.html:242>), [live HTML:246](</tmp/claude-1000/-home-greg-code-spideryarn2/a73041af-eace-477f-bcd6-b46598a13780/scratchpad/attn-1706.03762v7.html:246>)). On shorter creators, the whole creator can indeed disappear.

   Fix: describe the fault as “Readability removes the first short byline-shaped LaTeXML element,” with the contact block and whole-creator cases as its two manifestations. Also, the failure to fold is a client presentation fault, not itself stage 2.

5. **P2 — Declining a fold change is right, but the plan gives only one of the two reasons this paper will not fold.**

Keep folding out of v1; structural import-time marking remains the sound solution. Declining the model call is also right: the displayed rows are explicitly marked up, so a model would add cost and unverifiable rewriting without fixing either blocker.
