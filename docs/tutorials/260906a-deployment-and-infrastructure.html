Shipping Spideryarn

A commit on somebody's laptop becomes www.spideryarn.com. This is what sits in between — four machines, one command, and a long list of things that report success while being wrong.

8 minutes to skim · ~30 to read everything · written 2026-09-06, against dev at f31dea63, with production serving 39282f8c

TL;DR

One command ships: npm run deploy. It runs the tests against a clean copy of the exact commit rather than against the files on your disk, applies any pending database migrations to production, pushes that commit to main — which is the only thing Vercel watches — waits for the build, and then asks the live site a series of questions whose answers it compares against the commit it just shipped.

There are three long-lived pieces of infrastructure and they are all rented: Vercel runs the app in London as one serverless function, Supabase holds the Postgres database and the stored files in eu-west-2, and a Hetzner box exists so that AI coding sessions keep working when a laptop sleeps. Only that last one is a machine anybody has to administer, and it serves no reader.

The interesting part is not the pipeline. It is that a serverless host takes away three things a program normally assumes — a writable disk, memory between requests, and a runtime you can test on — and that nearly every failure this has caused arrived reporting success. Most of the deploy script is not deploying. It is refusing to believe a green light.

Four ways to picture it

1 · Two computers that disagree about what your code is

Your laptop knows about every file on its disk. Vercel's build machine only knows about the files in the commit. Those are different programs, and the second one is the one that ships. main has been broken three times by a commit that imported a file still sitting untracked on somebody's disk — the build was green locally every time.

2 · A hotel room, not a flat

The production app runs in a rented room that is cleaned between guests. There is no writable disk that survives a request, no shelf to leave something on for the next one, and you may get a different room each time. Anything that must persist goes to Postgres or to file storage. This is not a detail: it is why adding an article on the live site was broken for three days, and why /tmp — which really is writable — is not the shortcut it looks like.

3 · A pre-flight checklist for a plane whose instruments sometimes lie

Every item on the deploy checklist exists because something once said OK while being wrong: a build that succeeded and shipped a function failing on every request; a health check that returned green with the fault printed four lines lower; a migration command that printed ✓ migrations applied having migrated the wrong database. So the checks are written to be hard to please, and an empty result is treated as a failure rather than as good news.

4 · One front door and three peepholes

When something is wrong in production there are exactly three places to look and they answer different questions. /api/health says what the deployment is, right now. Vercel's logs say what happened during a request, for one day. Sentry says something broke while nobody was watching, for thirty days. Going in that order is most of the skill.

Pass 1 The whole thing, in one page

Three machines matter, and they are in three different places.

The path from an edit to a live site is short. You commit on dev — the trunk, which several agents push to all day and which builds nothing. When a batch of work is ready, one person runs npm run deploy. That command is the only thing that writes to main, and main is the only branch Vercel deploys. So a deploy is a deliberate act, and every other push is free.

A version is a deploy, and there is no version number

No semver, no tag, nothing in package.json to bump. One production deploy is one version and its name is its timestamp. That has a consequence worth knowing: git alone cannot tell you which commits were deploy points, because main is fast-forwarded one sha at a time. Vercel's own deployment list is the only record. Deploys are frequent — twenty in the 42 hours to 2026-09-06, most of them containing nothing a reader would notice.

If you stop reading here, the three things to carry away are: what ships is the commit, not your disk; the database schema moves before the code does, deliberately, because code arriving ahead of its schema is the failure, and the reverse usually is not; and the checks after the deploy are anchored to the commit, not to whether the site is up — because almost any check you could write passes happily over a perfectly healthy deployment that is three commits old.

Seven things, and only three of them cost real money.

Vercel, in more depth — one function, and why the API is not TypeScript

The whole API is a single serverless function. Vercel's file-system routing would ordinarily give you one function per file under api/, but there is exactly one file there and it is plain JavaScript. Two reasons, both learned by shipping the alternative:

Vercel's builder compiles any TypeScript it finds under api/ with this repo's own TypeScript, which it cannot drive. It prints an error, then succeeds, then uploads a function that fails on every request with the reason in no log at all. So the real handler lives in src/ and is compiled by the same tool that compiles the client.

A file called [...path].js is not a catch-all here. Vercel treats every bracketed filename as exactly one path segment; the ... is a Next.js convention and is not honoured. Measured on a real deployment: /api/library arrived, /api/article/writes and /api/jobs/abc/retry returned a platform 404 — which is nearly every route in the app, failing before any of our code ran and therefore appearing in no log we write. The catch-all is an explicit rewrite in vercel.json instead, which smuggles the real path through in a query parameter that the function puts back together.

One more deliberate oddity: the single file imports the compiled bundle inside the request handler rather than at the top. A module-level import that throws takes the function down before anything of ours runs, and you get an opaque platform error. Inside a try, the same failure produces a stack you can read. That is the only reason the Node-runtime bug below was ever found.

Supabase, in more depth — two roles, three ways to connect, and one bucket

There are two database roles that matter. postgres applies migrations, from a laptop, over the session pooler. spideryarn_app is what the running server uses, over the transaction pooler, and it can do data operations on our schema and nothing else — it cannot read the auth tables, cannot create objects, and is invisible to Supabase's own auto-generated REST API. Only that second credential is ever given to Vercel.

A third role, spideryarn_migrator, exists and is unused. It was meant to be the one that applies migrations, and it cannot be: seven columns reference Supabase's own auth.users table, granting that permission needs a grant option nobody can reach, and Postgres answers a grant you lack the option for with a warning rather than an error. The statement is correct SQL that the platform will never obey. It was caught only by asking afterwards whether the permission had actually arrived.

File storage is one bucket called sources, and it holds more than its name suggests: uploaded PDFs, the raw HTML of every page the pipeline fetched, and the images an article came with. A single object may be 50 MiB, which is the free plan's ceiling and also the product's.

A reader's upload never passes through the app. Vercel refuses a request body over 4.5 MB before any of our code runs, so the browser asks the API for a short-lived signed URL and then PUTs the file straight to Supabase Storage. That is why an upload can fail with a perfectly healthy app — and it is the failure the missing-bucket story below describes.

The bucket's settings are declared in a config file, and that file creates a bucket that does not exist while doing nothing at all to one that does — anywhere, including locally. Editing it is therefore not a change to any running system. That has cost real outages twice, so there is now a read-only checker that prints which project it reached above its verdict, and the deploy refuses to proceed if the live bucket and the file disagree.

The local stack — why a developer needs no accounts at all

Setting this up is npm run setup, and the only true prerequisites are Node, Docker running, and an OpenRouter key. There is no cloud project to create, no supabase link, and no remote credentials: the Supabase CLI mints its own keys and the database is a container.

The one awkward part is a chicken-and-egg: seeding the account needs keys that do not exist until the stack has started, so the stack goes up first, three values get copied into .env.local, and then setup runs. Sign-in is an email and a password that a script generates and prints — no Google step, nothing to click on a dashboard, which is what makes a machine you can only reach over ssh usable at all.

Two things bite. The dev server must be on port 5273, because that port is baked into the auth redirect allow-list; if it is taken, Vite silently picks 5274 and sign-in fails for a reason unrelated to your code. And .env.local deliberately beats what your shell exported, so FOO=… npm run dev does not do what it looks like.

The Hetzner box — a disposable server bolted to a permanent disk

It exists for one reason: a Claude Code session that dies when the laptop sleeps is not much use. Sessions run in tmux so they survive disconnection, one session each, driven by a single command from the laptop.

The shape worth knowing is that the server is disposable and the volume is not. A separate volume is mounted over /home, so checkouts, agent state and browser profiles survive destroying and recreating the machine. The machine itself is described in Terraform and built by a provisioning script that is safe to re-run — which is the point: a change to the box is supposed to be a change to a file, not a thing somebody typed once.

The server is €29.49/month net and there is nothing above it in that line — the next rung with more memory is nine times the price. So the plan when it is outgrown is to swap the server under the volume rather than expect a bigger one.

Pass 3 One commit, followed all the way to the live site

Take the deploy that is live as this is written: commit 39282f8c, built at 09:49 UTC on 2026-09-06, deployment dpl_5CkF27c3GPHGz47wiHd1EsReP1YP. Somebody on dev, with the work committed and pushed, typed:

npm run deploy

Seven steps follow. Four of them happen before anything at all has shipped.

What each step is really asking

Preflight asks whether this machine should be deploying at all. It refuses any branch but dev. It refuses a commit that is behind origin/main, and separately one that is behind origin/dev — two different questions since the trunk moved off main, and collapsing them would let somebody promote a commit missing the last two days of work while every light stayed green. It also asks Vercel a question nobody would think of: are you still assigning production domains automatically? A rollback turns that off, and until somebody promotes a deployment, every push builds and goes live nowhere, silently.

The gates are the interesting one. They run build, typecheck and test — but not in your working directory. The script makes a throwaway clean copy of the exact commit and runs them there, which costs about two seconds and is the only check that can catch the failure that has broken main three times: a committed file importing something whose definition is still uncommitted on somebody's disk. Locally it builds perfectly, because locally the file is there.

The copy is of the source, not of the machine, and the difference is worth being honest about. The tracked files and the test fixtures come from the commit; your .env.local is linked in from this machine — the documented remaining honesty limit — and so, normally, are the installed dependencies, which are only reinstalled when the lockfile changed. So the gate answers "does this commit hold together", not "would this pass on a machine that is not yours".

The gate needs a corpus, and for a day it could not go green

The test suite is not hermetic — it reads article fixtures from disk — and a clean copy of a commit has none of the gitignored files. For its first day the gate copied only half of what the tests read, producing 13 failures at every single commit, which meant the only way anybody deployed was by forcing the test gate. The fixtures now live in git and are copied out of the gate's own copy, so a commit that deletes a fixture cannot pass on the strength of your laptop still having one. The real cost of a genuinely fresh clone was measured at 50 failures — two smaller numbers were in circulation and both described something else, which is why they agreed with each other and neither was right.

Migrations is where a specific piece of discipline lives. The list of pending migrations is read from production's own ledger, never inferred from your laptop. On 2026-09-02 somebody counted local rows and told Greg the deploy would apply four migrations; it applied fifteen, because production was a long way further behind than the laptop was. The answer was arrived at honestly. It was just the wrong database's rows. So: never quote a pending count for production from anything local, and read the Target: line the migration command prints rather than its success line.

Four checks the summary above skipped, because each guards something a reader should know is guarded. Before anything else the script takes a lock covering every checkout on the machine — the migration tool takes no lock of its own, so two agents deploying at once would both find the same pending migrations and both try to apply them. Preflight asks the migration tool whether the history itself is consistent, which catches two agents having generated migrations from a diverged snapshot. After migrating, it checks that the application's own database role can actually read every table — a migration succeeds for the migrating role and leaves a table the running app cannot see, and those two look identical from the migrator's side. And it compares the resulting ledger entry by entry rather than counting rows.

Push, verify, logs. The push names the commit explicitly rather than pushing a branch, because several agents commit into this tree and a plain push would gate one commit and ship another. Then the script waits for Vercel and asks the live site five questions: is it healthy, does a POST body arrive intact, does an unauthenticated API request get refused, is the page our own index.html rather than Vercel's failure page, and does robots.txt answer as a real file. It also downloads every asset that page names and scans it for a leaked secret. Note what it does not do: it never runs the bundle, so a client that throws at module load passes every one of these. And finally it reads the logs — but not for errors. It makes its own request with a unique path first, and looks for that line; only once it is found does the absence of errors beside it mean anything.

And one thing it cannot tell you: whether the page renders

/api/health is served by the API. The reading view is a separate bundle, and it has thrown at module load — a completely blank site — while every line of that response stayed green. A healthy health check and a blank site are perfectly compatible. Load it in a browser.

Pass 4 What the host takes away

This is the part with product consequences, so it is not behind a fold.

A serverless host gives you a program that starts fresh, runs for a moment, and disappears. Three assumptions ordinary code makes are false there, and each one has cost this project real time:

1 · There is no writable disk

The pipeline that turns a URL into a readable article was written to write files. On the live site step one said ENOENT: no such file or directory, mkdir '/var/data' and stopped — for every URL and every PDF, for three days. Adding an article, the product's central action, did not work in production while everything else did.

/tmp looks like the fix and is not, and this is written down because it is the first idea everybody has. /tmp genuinely is writable — but each pipeline step runs in a separate HTTP request, so step 2 lands somewhere else and finds nothing. Worse, on a reused instance it would sometimes find a stale file and skip real work, which is the failure you cannot see.

What actually fixed it, on 2026-08-30, was not the storage rewrite everyone had been pointing at for three days: the working directory became explicit and scoped to one job rather than derived from where a bundled file happened to sit; one claim — a lease on the job, taken in the database so that only one server may work it — now walks the whole job in a single invocation, so the steps share a scratch directory; and the result is published in the same transaction that finishes the job — because until then a job could report done having published nothing at all, and nothing noticed.

What is still broken, stated plainly: re-running one step against an existing article. That gets its own job and therefore its own empty scratch space, and fails. The article reads fine without it, which is why this is a known limitation rather than an outage.

And a fourth: a request may not run for more than 800 seconds

That ceiling is set as high as the platform allows and is still a ceiling. It shapes the product rather than the plumbing: an ingest has to fit inside it, or be cut into steps that each fit, and no amount of fixing the storage problem above makes an arbitrarily long job possible in one go. A longer article, a slower model, or a step that retries can all walk into it.

2 · There is nothing left over between requests

One instance serves several requests at once, so there is no "current request" at module scope — a logger created once at the top of a file would attribute lines to the wrong article, intermittently. And there is no affinity between requests: a warm instance is an optimisation, never a place to keep something.

3 · You cannot test the runtime you ship to

A dependency chain three libraries deep threw ERR_REQUIRE_ESM in the deployed function and worked on every version of Node available to test locally — 22, 24 and 26 alike. The difference was Vercel's runtime configuration, not the code, and nothing on a laptop will ever reproduce it. The fix is one environment variable. The lesson is the shape: some faults exist only in production, so a deployment has to be able to tell you what it is, from the inside.

That vertical arrow is worth a product sentence. A log line reading GET /api/library 200 10ms is true and is not the wait: the clock starts after the bundle has loaded. Everything any of the ~200 modules in that bundle imports at the top level is paid for by the first request to a fresh instance, whether or not the request could ever use it. Three libraries have been moved to load only when something needs them, which took about 940 ms off a ~2,400 ms module import, measured. Two more are deliberately left at the top — the database driver, because the shelf's own query needs it, and error reporting, because it has to be up before the code that might fail.

The failures that reported success

Every item here said OK while being wrong. They are grouped because the shape repeats, and recognising the shape is worth more than remembering any one of them.

The health check that was green with the fault printed four lines lower

The health endpoint listed environment variables as booleans, and nothing ever compared one of those booleans against anything. So production served { "ok": true, "warnings": [], "env": { "SUPABASE_SERVICE_ROLE_KEY": false } } for a day. Healthy on line one; the fault in full on line four; the endpoint had no opinion about the contradiction.

A boolean nobody reads is not a check — it is a report that looks like one, which is worse, because that list is exactly what you scroll to in order to reassure yourself. Each entry now carries a description of what stops working without it, and anything in warnings makes the endpoint return 503 rather than 200. A cross-family review of the fix then found three more lies in it: a required need is not a required name (a variable with a legitimate fallback was being demanded); presence is not correctness (one variable has to be the exact string 0); and a wrong consequence is worse than none, because it sends you to the wrong file.

The migration command that migrated the laptop and printed success

DATABASE_URL=<remote> npm run db:migrate applied migrations to the local Docker container and printed ✓ migrations applied, while the remote it named stayed four migrations behind. The cause: .env.local deliberately beats the shell — right for the app — so the URL you typed was replaced before the "am I pointed at production?" guard ever ran. The guard agreed with itself and the wrong database moved forward.

The fix is structural and generalisable: the target of a command is an argument, not configuration, so the few scripts whose target is a real argument now read the shell first, and every one of them prints a password-stripped Target: line whatever happens. Read that line, not the tick.

The URL that was public the whole time the dashboard said "Protected"

Vercel's deployment protection was on and working: per-deployment URLs redirected to a login. But Vercel generates two automatic production hostnames and only one had been removed, and production hostnames cannot be covered by that protection on this plan at all. So the setting reported itself as enabled, and was, while the app was served to anybody with the second address. The dashboard said "Protected". The per-deployment URL really did ask for a login. The obvious check shared its assumption with the thing it was checking.

It was found with an unauthenticated curl from outside — the check nobody had run. The real answer, and the one that made a custom domain safe, is that authentication is enforced by the application itself, which no hosting plan can take away.

The file storage bucket that was declared, never created, and discovered by a reader

Uploading a PDF puts bytes in a bucket that a config file declares. That file creates the bucket locally and does nothing at all to the remote project. Nothing checks for it at boot: the API mints a perfectly valid-looking signed upload URL against a bucket that is not there, and the browser's upload is what discovers it. The reader sees an upload failure on a file that is fine.

It happened twice. The second time, production had been refusing every image upload for five days while the checking script — run by somebody explicitly asking whether production had drifted — answered ✓ every declared bucket matches the running project, because it had quietly been talking to the Docker container on the asker's laptop.

The three log traps, one of which answers an outage with silence

Vercel's error dashboard does not show application failures. It reports uncaught errors — the ones that became a 5xx. A failed pipeline step here is caught, recorded on the job, and answered with HTTP 200, deliberately: the call did what it was asked, and returning 500 would make the client retry a recorded application failure as though it were a network blip. So the dashboard listed one cluster from two days earlier and nothing else, while every ingest on the site was dying at step 1. Use it to rule things in, never to rule them out.

Never filter logs by level. Filtering for errors returns nothing over a window containing lines whose body reads "level":"error" — because everything goes to standard output and Vercel classifies the stream, not our JSON. Search for the string instead. This is the dangerous one: it answers a real outage with silence, and silence reads as health.

Scope every query to a deployment or it times out and returns no logs, which looks exactly like finding nothing.

The shape, in one sentence

In every case the check shared an assumption with the thing it was checking, so it agreed. The practical rule the project runs on: a check you have never seen fail is not evidence — and an empty result is a failed check, not a quiet pass.

Trade-offs, risks and open questions

Trade-offs, where reasonable people could choose differently

The choiceWhat it buysWhat it costs
One rented serverless host rather than a server we run Nothing to patch, nothing to monitor, no on-call. Global edge for free. For a beta with a small readership this is close to the right answer by default. Everything in §4. A pipeline that would be trivial on one machine with a disk cost three days of production breakage, and one part of it is still broken. There is an always-on box already paid for that could run this work — using it would mean a second deployment target and a second thing to keep alive.
Migrations applied before the push Code never arrives ahead of the schema it needs, which is the failure that actually hurts. A failure between the migration and a successful deploy leaves production one build behind a newer schema. That is harmless only while the migration is backward-compatible with the old code, and six of the 79 migrations drop a column. The deploy prints destructive statements and ships anyway — a report, not a gate, deliberately. So the trade-off is real and the wrong instinct is still to roll the schema back.
One production database and no staging copy No second environment to keep in sync, no drift between them, no cost. Preview deployments deliberately have no database at all, so they fail loudly rather than serving an empty shelf. There is nowhere to rehearse a migration against real data, and a preview build cannot exercise anything that touches the database. Every risky change is rehearsed against a laptop's container, which is a different shape of data.
Deploying is one person's command, not automatic on merge The trunk (dev) stays free — thirteen agents can push all day and nothing builds. A deploy is a deliberate act with a checklist attached. It only happens when somebody runs it, and the checklist takes minutes. In practice deploys are frequent enough (twenty in 42 hours) that this has not bitten.
Everything through one AI gateway One key, one bill, one place to set a spending cap, and model choice becomes configuration. npm run cost can read every call that goes through it. A single point of failure for the entire product — and the word "everything" is already false. Live conversation goes direct to OpenAI on a separate account, so it is invisible to npm run cost and uncovered by the OpenRouter spend cap; capping it means a second dashboard.

Risks and fragilities

  • Nothing alerts. Sentry receives errors and waits for somebody to open a dashboard. On 2026-08-28 every ingest on the live site had been failing for hours and the way it was found was Greg trying to read an article. This is the largest open gap on this page and the fix is small.
  • The health check cannot see the error monitor. The monitoring DSN is not in the list of variables the health endpoint reports, and monitoring returns silently when it is absent. So "monitoring is switched off" and "monitoring found nothing" are the same picture from outside. One entry would fix it.
  • Vercel's logs are kept one day. Long enough for "I deployed and something is wrong", useless for "a reader hit a bug on Tuesday" — and a failed pipeline step's diagnostic sentence exists only in that log, by design. Thirty-day retention is a paid add-on that has not been bought.
  • Development runs Node 26 and production runs Node 24.18. The infrastructure config pins the box to match the laptop with the note "a major-version gap between the two is where 'works on my machine' comes from" — and there is now a two-major gap between every development machine and production. Nothing states it. Note what this is not evidence of: the ERR_REQUIRE_ESM bug below reproduced on none of Node 22, 24 or 26, so that incident was the host's runtime configuration rather than the version gap. The risk here is the plainer one — a whole major version of behaviour that no test on any of our machines exercises.
  • The development box is the one machine somebody has to look after. It runs no reader traffic, so it is absent from every risk list above — but it is an Ubuntu server whose ssh and mosh ports default to the whole internet (a dynamic home IP is why, and narrowing it is one config change), whose single account is shared by every agent, and whose persistent volume holds the checkouts, the agent state and the credentials pushed to it. Nothing a reader can see depends on it; quite a lot of what a developer can reach does.
  • One local database per machine, shared by every agent on it. Several sessions work the same box at once, and they share one Supabase stack, one job queue and one set of ports. A lease serialises the commands that take part, but it cannot exclude a running dev server — so tests go red for reasons that are not yours, and telling those apart from a real failure costs time.
  • Anybody with the address can read the app shell. Not the data — application authentication stands in front of that, and an unauthenticated API request returns 401. But the automatic .vercel.app hostnames cannot be protected on this plan without a $150/month add-on, so the shell is public, and robots.txt is a request rather than a fence.
  • Re-running a single pipeline step against an existing article still fails in production. Known, written down, and the article reads fine without it.
  • One person can deploy. Deploying needs a Vercel credential and the ability to reach the production database; the docs are explicit that some machines have neither. That is a bus-factor question rather than a technical one.

Open questions

  • Should preview deployments get a database? Today they have none and fail at the store — deliberately, since pointing them at the one real database would let every branch build write to readers' data. A second Supabase project would make previews genuinely useful and would add a schema to keep in sync.
  • Is the log retention gap worth paying for? The step-failure diagnostic exists in exactly one place for exactly one day. Thirty days is an add-on. This is a cost question with a clear product consequence: how often a reader's bug report can actually be diagnosed.
  • Where should the pipeline run? The serverless constraint has been worked around rather than removed, and the workaround is one job per invocation with a shared scratch space. A long-lived worker would make the whole class go away, and would be a second thing to operate.
  • Alerting on failed steps. The events are structured and tagged. Nothing reads them.

FAQ

Something is broken in production. Where do I look?

In this order. curl -sL https://www.spideryarn.com/api/health — one command, rules out the commonest and dullest cause and tells you which commit is running, which has been the answer more than once. Then Vercel's runtime logs, scoped to the deployment id that health response gave you, searching for a string rather than filtering by level. Then Sentry, for anything older than a day. And check the deployment doc's list of what is known to be broken before debugging something already written down.

How do I roll back?

Carefully, and usually you should not. A Vercel rollback silently turns off automatic assignment of production domains, so until a deployment is promoted, every subsequent push builds and goes live nowhere. The deploy script checks for exactly this state before it touches anything. Rolling the schema back is the more dangerous instinct: a schema ahead of the code is usually survivable, and reversing it is what turns a half-deploy into an outage. "Usually" is doing work — six migrations drop a column, and the old code may want it. The deploy names destructive statements in its plan; read that list rather than assuming.

Can I deploy something that is not committed?

Yes — vercel deploy --prod uploads your working directory. It is kept for exactly that reason. Know what it means: whatever is on disk ships, including somebody else's half-finished edit, since several agents work in the same tree. It also skips every gate and every migration.

Why is the whole API one function instead of one per route?

Because the platform's per-file routing does not support the path shapes this app has — a bracketed filename is one segment, not a catch-all — and because the platform's TypeScript builder cannot compile this repo's TypeScript, and reports success rather than failing when it tries. One hand-written JavaScript entry file and an explicit rewrite avoids both. The cost is that every cold start pays for everything that file's bundle imports at the top level — once per fresh instance, not once per request.

What does it cost to run?

Vercel Pro and a Supabase project, plus the Hetzner box — €29.49 net for the server, nearer €38 once its 50 GB volume and UK VAT are in — plus usage-based AI spend through OpenRouter which is the variable and the one that matters — npm run cost reads it back per month. Sentry is on the free tier.

Do I need any of this to work on the app?

No. Node, Docker running, and an OpenRouter key. No accounts on anybody's dashboard, no cloud project, no Vercel. The database is a container that mints its own keys and the sign-in account is seeded by a script that prints its own password.

Glossary of internal nouns

the trunkdev. Everyone pushes here; nothing builds. main is production and is written only by the deploy command.
a gateA check the deploy refuses to continue past. Overriding one is possible, must be named individually, and is printed in red in the summary.
the build stampThe commit, build time and deployment id compiled into both artefacts, so a check can ask "is this the code I shipped" rather than "is the site up". Two stamps rather than one, because the failure worth catching is them disagreeing: an old page in front of a new API loads perfectly and calls endpoints that have moved.
the gate (auth)Application-level authentication. Distinct from a deploy gate; the word is overloaded in the docs.
the poolerSupabase's connection multiplexer. Two of them: the session pooler for migrations, the transaction pooler for the running app. Using the wrong one fails in ways that read as a wrong password.
silent successThe project's name for something reporting success while doing nothing, with the obvious check agreeing because it shares an assumption with the code. Most of §5.
a claimA lease on a queued job, held in the database, so that only one server works it at a time. Before there was one, several servers ran the same job — which cost about a third of all the AI spend the project has ever made.
a worktreeA second checkout of the same repository on one machine, so agents do not edit each other's files. The deploy gates use a throwaway one.
