The import pipeline and its database

How a pasted URL becomes an article you can read — and why, on spideryarn.com today, it doesn't.

8 minutes to skim · ~30 to read everything · written 2026-08-30, against the tree at commit 80ff5b4

TL;DR

Pasting a URL creates a job: a list of six steps that run one at a time, each turning what the last one made into something a bit more useful — raw bytes, then clean HTML, then numbered paragraphs, then a table of contents, then a one-line summary of each part.

Every step writes its result as a JSON file on a disk. That is the whole design, and it is also the whole problem: Vercel has no disk. So all nine imports ever attempted on production have failed, in about sixteen milliseconds, on the first step.

Meanwhile the reading side of the product already runs on Postgres and works fine. There are effectively two stores — files and a database — and today the only bridge between them is a human running npm run db:import at a terminal. Closing that gap is the single biggest piece of unfinished work in the product.

Five mental models

Everything below is an elaboration of these. If you read nothing else, read these.

🏭 The assembly line

An import is a line of six stations. Each takes the part the station before it made, does one thing, and puts the result on the bench. Nothing is done in parallel, and any station can be re-run on its own. If a station finds its part already on the bench, it skips — which is what makes re-adding the same article take a second instead of two minutes.

🪑 The workbench and the display case

The workbench is a folder of scratch files, one per article. Messy, rewritable, and where all the work happens. The display case is Postgres: what readers actually see, versioned, owned, and never half-finished. Today somebody carries finished pieces from one to the other by hand. The plan is for the line to build directly into the case.

🎫 The cloakroom ticket

Every paragraph gets a random id like spya-k3m9qt the first time we see it, and keeps it for ever. A reader's comment holds the ticket, not the coat. So the article can be re-extracted, re-worded, even lose that paragraph entirely, and the comment survives and knows what it was about. Everything in the product — table of contents, scroll position, highlights, search results — addresses text by ticket, never by "the 14th paragraph".

👷 The browser is the foreman

Nothing slow happens inside a web request. You paste a URL, the server says "accepted, here's a receipt", and then your browser pokes the server once per step and polls for progress. That is why the progress list names each stage as it runs, and why a job survives you closing the tab on a laptop but not on production.

🎟️ A claim, not a lock

Only one job may run at a time. That used to be a promise one server process made to itself. Now it is a rule the database enforces, and a runner "claims" a job with a token and a time-limited lease. If the runner dies, the lease lapses and the job becomes a visible failure with a Retry button — never a spinner that spins for ever.

Pass 1What happens when you paste a URL

No detail at all. Just the shape.

In words, the same thing:

  1. You paste a URL. The app works out what to call the article — its slug, taken from the last bit of the address — and checks whether it already has one.
  2. The server writes down a job and immediately answers, without doing any of the work. The answer is a receipt.
  3. Your browser drives the job forward, one step per request, polling for progress in between. The progress panel names the stage that's running.
  4. Each step writes a file and the next one reads it. A step whose file is already there skips itself.
  5. The last step finishes, and the article is on the shelf.
Step 5 is not actually true yet

Finishing the last step does not put the article in the database. Publication is a separate command a human runs. On a laptop this is invisible — the app can read straight off the workbench. In production it is the difference between a green tick and a shelf that never changes. §5.

Pass 2The pieces

A job is a list, not a function

The obvious way to build an importer is four function calls in a row. Spideryarn doesn't, and the reason is worth knowing because it explains most of the product's flexibility.

A job is a slug plus a list of step names. That one decision gives you, with no special cases:

What the reader doesWhat the job is
Add an articlethe six default steps
Refresh it from the sourcethe same six, with fetch forced
Re-run one stage after a prompt changejust that stage, forced
Write the tweet thread (a button on its own page)one step, tweets

There are ten steps in existence and only six run by default. The other four — the tweet thread, the glossary, the longer summaries, and the "ideas" the piece assumes — each cost a model call, so nobody gets one unless they ask.

The full step list, and the difference between order and default

Two lists, deliberately not the same list:

STEP_ORDER          fetch  extract  blocks  toc  assets  arc  tweets  glossary  summary  ideas
DEFAULT_INGEST_STEPS fetch  extract  blocks  toc  assets  arc

STEP_ORDER answers two questions — what order do steps run in, and which names will the API accept — and DEFAULT_INGEST_STEPS answers a third: what does a plain "add this URL" do. They were one array until the tweet thread arrived and needed to be a valid, orderable step that nobody pays for by accident.

assets is in the default despite not being needed to read the article, and the reason is privacy rather than completeness: an article whose images are still hot-linked to the publisher announces the reader's IP address to that publisher on every single read.

The two stores

This is the single most important thing to hold in your head about the architecture. There are two places an article can live, they hold different things, and the app can be pointed at either one.

Three facts about this picture carry most of the consequences:

  • Reads are abstracted; writes are not. One interface answers "give me this article" from either store. But there is no equivalent for writing — every step opens a file and writes it. So "move to Postgres" is a change in ten places, not one.
  • There is no fallback, on purpose. If Postgres errors, the app does not quietly read a file instead. A fallback would hide exactly the divergence you built two stores to notice, and it would hide it in production, where nobody is comparing.
  • Files have no owner column. That is why the whole multi-reader story — accounts, sharing, public links — is a Postgres story by nature and not by preference. A folder named after a slug has nowhere to record who may read it.

The shape of the database

The interesting part of the schema is one decision, made early and defended repeatedly: an article's identity and an article's content are different tables with different lifetimes.

The rule that everything else rests on

A block id is an identity; a block's text is a revision. If comments pointed at the current text rows, then re-extracting an article — which happens whenever the publisher edits their page, or we improve the extractor — would delete the reader's questions along with the paragraphs. Instead the reader keeps a pointer to something that is never deleted, and the app can show them "you asked about a paragraph that isn't in this version any more".

Two smaller schema decisions with outsized consequences

Block ids are unique only within an article. Every key that touches one is composite on (article_id, block_id). Making them globally unique looks tidier and starts silently rejecting valid rows at around a hundred articles — and a global upsert would overwrite one article's paragraph with another's. Nobody may "tidy" these into single-column keys.

Document order is a written-down number, not an insertion order. revision_blocks.ordinal is set explicitly from the array index. Block ids are random and carry no position, so if that column were ever wrong there would be nothing left to recover the order of the article from.

Search is per paragraph, not per article. Each block row carries its own full-text index, generated by the database rather than filled in by the pipeline. A search hit therefore deep-links to the paragraph — which is the entire point of the feature — and a column the pipeline had to remember to fill would be empty for exactly the article somebody just re-ran.

Who is allowed to run a job

One job at a time, globally. Not one per server — one, full stop. Three of the ten steps are long model calls billed by the token and one is a fetch of somebody else's server, so running two articles at once would double the spend rate, halve the politeness, and turn the progress display into a race.

That used to be a promise a single server process made to itself. It stopped being true the moment there could be two servers, so it moved into the database as an index that permits at most one running row. A second claim comes back as a constraint violation and the caller is told busy.

The claim, the lease, and why a dead runner becomes a visible failure

A runner claims a job with an attempt token and a lease — a deadline. Every subsequent write is conditional on id = $id AND attempt_id = $attempt AND status = 'running', so a runner that has been superseded cannot write anything, even if it is still alive and confused.

The claimant also sets its own timer, slightly shorter than the lease, and aborts its own work when it fires. That is what makes an expired lease mean something: it says the process is gone, not the process is slow.

An expired lease does not get taken over by another runner. It gets marked failed, with a sentence saying it was interrupted and a Retry button. Guessing that an owner is dead is how two runners end up writing one article, and that only becomes safe once every durable write is inside one fenced transaction — which is the work described in §6.

The expiry sweep runs at the top of every advance rather than on a timer, because there is no scheduler on Vercel, and because that is the exact moment somebody wants the slot.

Pass 3One article, all the way through

Take a real one. You paste:

https://www.noemamag.com/the-mythology-of-conscious-ai/

It's a long essay, about 54 minutes of reading, and almost entirely without headings — the deliberate hard case this project tests against.

Before anything is queued

The app derives a slug from the last path segment: the-mythology-of-conscious-ai. Then it asks two questions that look like one:

QuestionAnswered byMay it change the address?
What do we fetch and store?normaliseUrl No. Whatever comes out is what gets fetched.
Is this the article we already have?urlKey It is never fetched, so yes — freely.

The second one is why pasting http://noemamag.com/the-mythology-of-conscious-ai tomorrow finds the same article rather than paying for a second copy. It strips the scheme, a leading www., a trailing slash, and the tracking parameters a share button staples on.

The asymmetry this is designed around

Failing to merge two spellings of one article costs a duplicate — a second card on the shelf, visible, deletable, paid for once. Merging two different articles costs the wrong article, silently, under the headline the reader pasted, with nothing anywhere saying so. So a merge is only made where the URL specification or universal practice actually guarantees it — never where it is merely usually right.

Which is why /Why-Trees and /why-trees are not merged (plenty of servers are case-sensitive and mean it), and neither are ?tag=a&tag=b and ?tag=b&tag=a (a repeated parameter's order is part of the request).

The six steps

>>> WE ARE HERE >>> — the job has been accepted and your browser has started poking.

#StepWhat actually happensTime
1fetch Downloads the page. Counts bytes on the decompressed stream, honours the page's own declared encoding rather than assuming UTF-8, tells a PDF from HTML by its bytes rather than the server's claim, and re-checks the address at every redirect hop. Writes the bytes, plus a small manifest saying which file is authoritative and where it came from.~10s
2extract Mozilla Readability strips the navigation, the ads and the newsletter box, leaving the article. Also writes the article's identity — title, byline, site, language, the final URL.~5s
3blocks Sanitises the HTML, then splits it into blocks and gives each one a permanent random id. This is the step that mints the tickets.~5s
4toc 🟢 A model reads the whole article and returns a deeply nested table of contents — down to paragraph level. The most expensive step in the product by a wide margin.up to 5½ min
5assets Copies the article's images to our own storage, so reading it doesn't tell the publisher who is reading.~30s
6arc 🟢 A model writes one sentence per part of the article: where the argument stands there.~30s

Total, worst case measured: about seven minutes, of which the table of contents is 80%.

Why a block is the smallest readable unit

A list item is a block; the list around it is not. That looks like a detail and is actually a product decision. If the whole list were one block, there would be no id pointing at an individual item — so no reader could ever comment on one, and no table of contents could ever give one a row. Making blocks the finest unit costs nothing and turns "how much detail does this list deserve?" into a choice the table of contents makes per list, rather than one the splitter makes for everybody in advance.

What you now have, and what you don't

On a laptop: an article on the shelf, fully readable, with a zoomable table of contents and an arc. On production: nothing. The job would have died at step 1.

What happens on the second run — and why re-adding is instant

Each step declares the files it produces, and a step whose files are all present skips itself. So re-adding the same URL takes about a second: six steps, six skips, and the article.

"Present" is more careful than it sounds. The store answers by parsing the file, not by checking it exists — a write killed halfway leaves a file that exists and won't parse, and that used to report its step done for ever.

And presence is not the only question. A step also records that it started, in a marker that only the success path removes. A marker still sitting there means a run that did not finish, and a run that did not finish is not done however good its files look. That catches the case existence checks cannot: a rerun that overwrote one of three outputs with a perfectly good new generation and then died, leaving every file present, parseable, individually beyond reproach — and two different generations of the article on disk at once.

Pass 4The parts that are genuinely hard

Everything above is the happy path. This section is the four things that make this system harder than it looks. All four are collapsed; none is needed to understand the rest of the document.

1. "Already done" and "still correct" are different questions

A step that checks only whether its file exists will happily skip a file describing last week's version of the article — and report a green tick while doing it. The reading view then serves a table of contents for text that has since changed, and nothing anywhere says so.

So steps are moving from presence to a freshness stamp: a hash of the inputs, plus the prompt version and the model id. Change any of the three and the step re-runs on its own, with nobody having to remember.

Where this stands is uneven, and that unevenness is the interesting part. Four steps stamp; the table of contents does not. That is deliberate rather than pending — a stamp on toc needs consumer invalidation first, because the tree is the thing five other artefacts are joined to. A stamp landed there once and was withdrawn.

The hash input matters more than the idea. It hashes each block's id and text, deliberately not the bytes of the file — because those bytes change when an unread field is recomputed, and don't change when two blocks swap ids.

2. Forcing one step forces every step after it

"Refresh from source" was originally written as: force the two steps that touch the outside world, leave the rest alone. Which produced a freshly fetched article under last week's table of contents and last week's arc — every summary describing paragraphs that had moved, three green ticks, and nothing saying anything was wrong.

So forcing a step now expands to include everything downstream of it. The pipeline is a chain; invalidating a link invalidates what comes after it, by definition.

With one exception, and it is about money. The tweet thread isn't a link in that chain — it reads the same inputs the arc reads and nothing reads what it writes. Its position in the list is about running order, not dependency, and reading it as dependency would spend a model call rewriting a thread whose inputs never moved. So a small list holds the steps the positional cascade may not speak for.

3. Retry is not always offered, and that is a feature

Until a fix in August, the Retry button appeared under every failure — including the ones that are arithmetic. A long article was pasted, the table-of-contents step worked out that its answer would not fit in one model response, said so clearly, and offered a Retry that made the identical call and failed identically.

A failure now says what kind it is, and the card asks before drawing the button. Roughly:

Cannot come out differentlyMight
an answer too long for one responsea model answer that would not parse
a page Readability already refused, over bytes we still havean empty answer, a refusal, a timeout
a PDF over the page capa fetch that failed at somebody else's server

The direction of the doubt is chosen: a failure that says nothing gets the button. Not because a wasted click is cheap — here a false retry costs minutes of pipeline and another billed model call — but because every job recorded before the field existed carries nothing, and so does one that a restart swept up, which really is worth another go.

What makes any of this trustworthy is that a retry never re-runs a step that already succeeded. So a step that failed while reading an artefact an earlier step wrote will read that identical artefact again — which is precisely why the left-hand column is certain.

4. Silent success — the failure mode this codebase is organised around

Most of the hard-won detail in this system is defence against one shape of bug: something reports success while doing nothing, and the check you would naturally run agrees with it, because it shares an assumption with the code.

A partial list from this pipeline alone, every one of them real:

  • A refresh that fetched new bytes and left the old tree, reporting three green ticks.
  • Two URL spellings of one article read as two articles: a second fetch, a second tree, a second arc, two cards under one headline, nothing errored.
  • A migration command that migrated the laptop instead of the remote database and printed ✓ migrations applied.
  • A GRANT that is correct SQL the platform will never obey — Postgres answers a grant you lack permission for with a warning, not an error.
  • An export that read a directory that had never held the source documents, and wrote a backup that looks complete and is not — in the one command anybody runs after losing something.
  • An importer that read the comments file with the wrong shape and imported 17 KB of the reader's questions as zero comments, while printing a tick.

The recurring lesson is the same each time: prove it rather than reading it back. A grant is verified by creating a table and asking whether the app role can see it. A test that has never been watched go red is not evidence.

Why it does not work on production

Signed in at spideryarn.com on 2026-08-29, the shelf said "9 earlier imports · 9 failed". Every one stopped at step 1 with the same line:

ENOENT: no such file or directory, mkdir '/var/data'

Reading works fine. The shelf renders out of Postgres and the reading view is healthy. It is only ingest that has nowhere to put anything. There are three causes, and they stack.

Cause 1 — a path that bundling invalidates

Two files work out where to write by asking "where am I, and go up two directories". That is correct for a file living in the source tree. It ships bundled into a single file, and where am I is a fact about where the code ended up, not where it was written. Two levels up from there is /var, which is not writable.

No local test can catch this, because the arithmetic is right on a laptop and wrong in the bundle — the check and the thing it checks share the assumption.

Cause 2 — six steps, six machines

Why "just point it at /tmp" is worse than the bug

Sequential requests often do land on the same warm machine. So imports would succeed in testing and fail unpredictably in use — and when they failed, the step-skipping logic would find no artefacts and silently re-run a step that had already been paid for. A reliable loud failure would become an intermittent quiet one, which is strictly the worse trade.

Cause 3 — a finished job publishes nothing

This is the one that decides the size of the job, and it was missed in the first plan written about this. Even with perfectly durable artefacts, a green ingest leaves the production shelf unchanged, because the function that publishes a revision is not called from the pipeline at all. It is called by the importer and by tests. Publication today is a person running a command.

So there is no route to working imports that does not also build the publication bridge.

The ceiling nobody had measured

While planning the fix, somebody grouped the recorded model calls into per-article totals. The result changed the plan's order:

StepCallsTotal
toc3324 seconds
summarise10240 seconds
toc (another article)1163 seconds
arc110 seconds

The lease was four minutes with a twenty-second margin, so every step aborted itself at 220 seconds — on a laptop too. A 324-second table of contents therefore could not complete through a job at all, on any machine. It had only ever succeeded when run directly from the command line, which takes no lease.

That was a live bug that predated the whole Vercel question, and fixing it went first: the lease is now seven minutes and the platform limit 800 seconds. It is the only stage of the current plan that has landed.

Trade-offs, risks and open questions

This section is written to be read on its own.

The decision that is live right now

Two plans were written for making imports work. The first proposed giving the pipeline a durable artefact store built on the object storage that already works in production. It was reviewed by a different model family before anything was built, came back NO-SHIP with three criticals, and was withdrawn the same day. The criticals are worth knowing because they generalise:

  1. All ten steps still write their own files directly. So no storage adapter can intercept them, whatever you plug in. The plan had written down the condition that should kill it — "if most of the ingest path bypasses the seam, this is not a store-adapter job" — and the condition was met.
  2. A finished job doesn't publish, so durable artefacts alone change nothing a reader can see.
  3. The object store has the wrong semantics. It is content-addressed and create-only; artefacts need mutable, retryable, attempt-fenced generations.

The replacement plan is deliberately smaller and explicitly temporary: run the whole job in one invocation on an injected writable root, and publish by calling the existing importer as a real pipeline step. Five stages, each ending committable. Stage 0 (the time budget) has landed; stages 1–5 have not.

The trade-off worth having an opinion about

The long-term-right answer is to make every step write into a database transaction, delete the importer entirely, and stop having a workbench at all. That is 2–3 weeks and gated on the largest unstarted piece of it.

The v1 above works in days and throws away roughly fifteen lines of glue when the real thing lands. Everything expensive it builds — the store-backed identity checks, the injected root, the end-to-end tests, and the position of publication inside the job machinery — survives into the end state.

Greg's framing, 2026-08-29: "Look for simplicity, and getting to a v1 now, while being aware of the long-term-best eventual state and choosing stepping stones towards that."

The risks, and how bad each one is

RiskWhat it costsWhere it stands
Slug identity asks the filesystem The worst one. Three functions on the live path decide "does this slug already exist?" by reading a file. On production that read can never succeed, so every slug reads as free — and a different URL deriving the same slug could be handed an existing article's identity. If it is the same owner's article, the import replaces it and deletes its reader state. Every write reports success. Harmless today only because nothing can be ingested at all. Reachable the moment imports start working. This is why "slug identity asks Postgres" is its own stage, before publication.
Re-publishing deletes reader state The importer treats the files win as its contract. Re-importing an article whose temporary disk has no comments file deletes the reader's real comments and reinserts nothing. Contained by publishing first ingests only, until the stage that copies the database back onto the disk before a job starts.
Repeat model spend on retry A retry on a cold machine re-runs everything, including the 5-minute table of contents. Real money. Accepted for v1 and stated rather than discovered. On a warm machine the skip logic resumes real artefacts for free.
Stop gets slower A cancel arriving at a different machine can't abort the work in flight, so it is read at the next step boundary. Stopping mid-table-of-contents means waiting for it. Acceptable, and said out loud. Stop is two halves: a flag everybody can see, and a local abort that only helps when the runner happens to be here.
Deleting a user is impossible All seven owner foreign keys refuse deletion while any row is owned. That is inherited from a default rather than chosen. Defensible for a reading library, but it needs an export-and-delete workflow rather than silence. Open.
Row-level security is deferred Database permissions carry the whole weight of keeping one reader out of another's library. Structurally rather than carefully: the schema is simply not exposed through the public data API, so it cannot be served whatever key is presented. Verified with a real anonymous request, not by reading a settings page.
The uplink can be the constraint On a slow connection a single large insert blew a two-minute database timeout; the next morning the same import took under two minutes. Known. Measure the upload before blaming the database.

Open questions worth a product opinion

  • Uploaded PDFs get their slug from the filename. paper.pdf becomes paper, then paper-2. document.pdf and download.pdf are extremely common and the counters will pile up. The alternative is to store under a provisional id and rename from the title once we know it — but renames here are expensive for exactly the reasons in the identity model above.
  • Canonical URLs aren't read. Two genuinely different addresses that serve the same piece — a syndication, an AMP page, a link shortener — are two articles. The <link rel="canonical"> tag is sitting in HTML we already fetch and would close most of that gap.
  • Should the queue become a library? A mature Postgres job library was reconsidered honestly and rejected again, for a weaker reason than last time: our job records are unusually rich — per-step state, a cancellation that must not release the global slot — and would have to exist beside the library's own, leaving two sources of truth about the same work. Revisit when redelivery or backoff becomes a requirement rather than a nicety.
  • Concurrency 1 is a real product decision, not a limitation. Raising it doubles the spend rate and halves the politeness to publishers, for a single reader adding a handful of articles a day. It is changed by editing a database index, not a constant.

Common questions

If reading already works on Postgres, why is importing so much harder?

Because reading needed one seam and writing needs ten. There is a single interface that answers "give me this article", and pointing it at the database was one implementation behind it. There is no equivalent for writing: every step opens a file and writes it, inside its own function. Ten stages have to move behind a boundary that has been built and is currently empty.

Why does the browser drive the job instead of the server?

On a laptop, the server does drive it — there is a loop that keeps a job going after you close the tab. On production that loop cannot exist, because it can't outlive the request that created it; all it could produce is a job marked running whose owner is already frozen. So the browser is the only driver in production, which is what the "advance" endpoint was built for. It is also why the current plan's fix is to loop that endpoint server-side until the time budget runs out, rather than rewriting the runner.

Why polling rather than a live connection?

A job is six steps over one or two minutes, so a one-second poll is at worst a second behind something that changes every twenty; nobody can tell. What it buys is that the client holds no connection: it survives the dev server restarting, it is the same three lines against a serverless host, and there is no reconnect logic to get wrong. The failure mode of a dropped live connection is a progress panel that quietly stops updating — which looks exactly like a stuck job.

What actually happens if the same article is added twice at once?

The second request is handed the job already working on that article rather than starting a second one. That is also why the add page can be reloaded, bookmarked and shared: reloading picks up the same job where it was.

The claim check consults the stored article and the live queue — because a job that is queued has taken a slug and not yet written anything for it. Without that second half, two different articles with the same last path segment added within a minute of each other both get the bare slug, and the later one is quietly handed the earlier one's job and never happens.

Can we run migrations against production safely?

Yes, and there is one line to read. The documented command used to migrate the laptop while printing ✓ migrations applied, because the local environment file is deliberately allowed to beat the shell. Four migrations were missing from production for a day because of it, and the homepage rendered a failed SQL query in red.

The migration script now prints a password-stripped Target: line whatever happens. Read that line, not the success line. And verify afterwards as the application's own role, not as the admin — they are different roles over different connections, and a migration that succeeds for one while leaving a table the app cannot see looks identical from the migrator's side.

What is the "arc", and why does it join to the tree by range?

The arc is one sentence per part of the article saying where the argument stands there — the thing that makes a long unstructured essay navigable. It is joined to the table of contents by range of blocks, never by node id, exactly as the longer summaries are. Node ids are regenerated when the tree is re-cut; a range of block ids is stable, because block ids are stable. Same principle as everything else: address text by ticket.

running, or errorPublication refused outright.

Vocabulary

WordMeans
slugThe article's short name in the URL, derived from the last part of the address. Globally unique.
blockThe finest unit a reader takes in as one thing — a paragraph, a list item, a heading. Never a container.
block idA random permanent handle like spya-k3m9qt. Everything addresses text by these.
artefactA file (or, later, a set of rows) a step produces: blocks.json, tree.json.
the treeOne structure serving two purposes: rendered as navigation it is the table of contents; rendered as text it is the zoomable article. They must never diverge into two trees.
step / stageSame thing. One station on the line.
forceRun a step even though its artefact is there — and everything after it.
stampA step's freshness record: a hash of its inputs, plus the prompt version and model id.
the storeWhichever of files-or-Postgres the app is pointed at.
revisionOne extraction of an article. Articles have many; exactly one is published.
