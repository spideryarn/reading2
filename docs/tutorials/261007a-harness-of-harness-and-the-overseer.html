Harness-of-Harness vs the Overseer

A paper that wraps a coding agent in a planner → developer → tester loop and lets it build a game for days with nobody watching, set beside the machinery that runs Spideryarn's own fleet of coding agents. Where they line up, where they part, and what is worth borrowing.

Skim: 8 minutes (TL;DR, mental models, Pass 1, the comparison table, judgement). Deep dive: 25 minutes. Written 2026-10-07 against dev at 71f95f5.

TL;DR

The paper's Harness-of-Harness (HoH) takes one ordinary coding agent and runs it three times per round — once to plan a small increment, once to build it, once to test it independently — and passes the test report forward to the next round's planner. Over three rounds that lifts benchmark scores by 52% on average (a relative gain). In a separate case, given game-specific tools as well, 70 rounds built a playable shooter; people only restored the network when it dropped.

Our equivalent of one HoH loop is a single job run the way engineering-manager.md says: plan doc → build → GPT Sol review. The Overseer sits a layer above that — it runs 20–35 such jobs at once and handles what the paper never faces: shared machines, usage limits, deploys, and a human who keeps the consequential product calls. Within the loop, the sharpest difference is the tester: HoH's may not touch the code it judges, and ours fixes what it finds.

Mental models

HoH is a three-person studio working in shifts on one game

The producer reads the brief and last night's bug report and writes today's to-do sheet. The programmer is the only one allowed to touch the code. The tester gets a locked copy, plays it, and writes the bug report. Then they swap the sheet and go round again. None of them remembers yesterday — everything they know is in the folder they pass along.

The Overseer is the site foreman of thirty contractors, each running their own studio

The foreman does almost no building. They decide who starts when, keep two crews off the same wall, ration the electricity, check finished crews actually tidied up before leaving, and are the only one allowed to hand the keys to the client. What gets built is the client's call — the foreman's job list comes from the client's queue, not from the foreman's own ideas.

Both of them keep their memory in the folder, not in their head

HoH's agents forget everything between invocations; the plan, the code and the test evidence carry the project. The Overseer runbook says the same thing of itself: "Your context is a cache, not the record." The record is files on disk. This is the deepest thing the two share.

Pass 1The two shapes

HoH: one agent, three hats, round and round

HoH does not change the coding agent at all. It takes an off-the-shelf one (Codex, OpenCode or Pi in the paper) and calls it three separate times per round, each time with a different role prompt and different permissions. The paper calls each round a loop.

Two things cross from one loop to the next: the code (the next developer starts from where the last one stopped, rather than from scratch) and the evidence (the tester's report of what works, what doesn't, and what must not break). The human writes the spec once and is then out of the picture.

Ours: three layers, and the loop is the middle one

At the top is Greg, who has the ideas and makes the product calls. At the bottom are the jobs — each one a single Claude Code session working in its own copy of the repository, running its own version of the HoH loop: write a plan doc, have GPT Sol review it, build, have Sol review the code, commit, push.

In the middle is the Overseer: one permanently running Claude session plus a small background program that keeps a log on disk. It starts jobs from Greg's queue, nudges stuck ones, pauses the fleet before the usage limits run out, removes finished worktrees, and is the only thing allowed to deploy to production.

The one-sentence comparison

HoH is a loop. The Overseer is a scheduler and safety officer for many loops. The fair comparison is HoH against one of our jobs; the Overseer is the part of our system the paper has no counterpart for.

The three HoH roles, in a little more detail

Project Planner. Reads the fixed spec and the previous loop's evidence. (The main text says it reads the code for context too; the benchmark prompt in the appendix says the opposite — "do not … inspect production code" — and has it pick at most three priorities, blockers and regressions first.) Writes a development document: a small set of related tasks, the existing behaviour that must be preserved, and observable checks for "done". It is told to be bounded (not too much at once, so failures are easy to localise) but locally complete (include every change needed for the new thing to actually work and be testable).

Developer. Starts from the previous loop's code ("warm start"), implements the dev doc, and tests as it goes: baseline the behaviour, change, re-run, look at nearby things that might have broken. Its own tests only decide whether it is ready to hand over — they do not count as acceptance.

QA Tester. Gets the code frozen and read-only, plus the results of build and smoke checks. Turns the spec and the dev doc into specific checkable claims, then tests each one from outside (play the game, press the keys, look at the screen) and from inside (read the code, logs, config). A claim is "verified" only if a recorded observation supports it; anything else is logged as a gap, never assumed to pass. Its report is the next loop's evidence.

A small deterministic Runtime wraps all three: it fixes what each may read and write, and checks the output against a schema (retrying if it doesn't match). In the long game run, code and each role's output were also committed after every stage; the benchmark runs had no extra version control.

The Overseer's parts, in a little more detail

The store, not the transcript, is the memory. A daemon owns a clock and writes ~/.overseer/: which sessions exist, an event log, a decision log. The Overseer session auto-compacts, and compaction drops the boring bookkeeping first — "which is exactly the pause you issued forty minutes ago". So it reads the store rather than remembering.

Four gates bound what it may decide for Greg: (1) never hide who decided — every message it sends is stamped as its own, never Greg's; (2) answer facts, route judgement (technical to Sol, wording to Opus), default low-stakes product calls and log them for veto — except anything that outlives the branch, which waits; (3) never the irreversible, and never work of its own devising; (4) never spend what it is rationing.

The tick, every half hour or so: read usage and box load; close out finished jobs (debrief first); then pull from the queue if there is room. Usage-wise the instruction is to "surf close to the edge" — use the limits, not hoard them — and slow down only if a window won't last until it resets.

Deterministic rules before judgement: a session stuck in the wrong permission mode, a shell command unchanged for hours, box pressure. These need no model call and account for most of the fleet time actually lost.

Deploying: pull, read every new migration, write release notes, check /help, npm run deploy, and then check that three things agree — exit code, target database, and the commit production reports serving.

Pass 3One real job, through both lenses

On 2026-10-01 Greg filed a feedback report from inside Spideryarn (report spya-yj2vdr): the Earlier tab of the Feedback dialog said "Showing your 50 most recent" — was that true? And could the Shipped / Not shipped pills show a count? Here is what happened, with the HoH role each step corresponds to.

  1. Greg files the report. In HoH terms this is the spec — but note how small it is. HoH specs are whole products ("a five-minute bomb-defusal mission with 18 enemies"); ours are one question and one suggestion.
  2. The Overseer picks it up. A sweep of the feedback queue checks the report really is Greg's (a script proves it against the production database, because anyone can forge a Sentry event), adds it to the queue, and schedules a session named fb95-earlier-tab-counts to start later in a wave so it doesn't collide with others. HoH has nothing here: it only ever runs one project, so there is nothing to schedule.
  3. The job agent plans. It answers Greg's question first — yes, the line was true, because it only appears when the filtered query finds a 51st row. Reading production (read-only) on 3 October with the shipped list from Greg's build gave 115 not shipped. Then it writes the plan: a count on each pill, and the cap line rewritten to say "of your 115". This is HoH's Planner, including its insistence on checkable acceptance conditions.
  4. Sol reviews the plan and finds two serious problems. The sharp one: the list and the counts would come from two separate database queries, so a report filed between them could make the screen say "Showing your 50 most recent of 50" — conspicuously false. Fix: one transaction. HoH has no review of the plan itself; its QA only looks at built code.
  5. The agent builds and commits (157a4c7), testing as it goes. HoH's Developer.
  6. Sol reviews the code — and fixes it. It found that a repository-wide test would fail on the new kind of transaction, that the client accepted an impossible combination ("50 most recent of your 45"), and that the pill's text read Not shipped1 to a screen reader. It fixed all of these in place, with tests (f9935b4). This is HoH's QA, with the one thing HoH forbids — the tester repairing the candidate. Our rules call for a second round that treats those fixes as unreviewed code; this job's record shows one code review.
  7. The Overseer deploys. Both commits are on main. HoH has no deploy: its artifact is a repository at the end of the run.

What this example shows

The middle four steps are recognisably the HoH loop, run once. What we add around it — provenance checks, scheduling, a plan review, a cross-family reviewer, a deploy gate — is where most of our machinery lives. What HoH adds that we don't have is the second, third … seventieth loop on the same thing: our jobs typically run the loop once per stage and stop.

Pass 4The evidence, and the hard parts

What the paper measured

Three benchmarks (games in Godot; open-ended software tasks; rebuilding a program from its binary), three agent/model pairs, and a comparison of "run the agent once" against "run HoH for three loops".

  • Every configuration improved on every benchmark. Codex + GPT-5.5 on the game benchmark went from 49.6 to 71.5 (out of 100); the weakest pair, OpenCode + DeepSeek, from 26.9 to 49.0.
  • It keeps improving past three loops, at least on one benchmark. Comparing Codex's own checkpoints against each other on FrontierSWE, its "dominance" (how often it beats a randomly picked other checkpoint) rose from 39% at loop 3 to 73% at loop 10, peaking at 76% at loop 9. That is a different comparison pool from the main table, so the numbers don't line up with it.
  • It isn't just "more turns". The same agent told to "keep going" for three passes reached 58.2; HoH reached 64.8 in two loops, using fewer tokens (5.7M vs 6.3M per task).
  • Each carried-over ingredient matters about equally. Freezing the first plan cost 8 points; replanning without the test evidence cost 6; rebuilding from scratch each loop cost 8 — and a third more tokens.
  • The 70-loop game: 81 issues recorded, 65 closed, 16 still open, and 17 reopened after a later change broke something already verified.
What the numbers don't say
  • The baseline is weak by our standards. "Vanilla" is one ordinary pass of the agent, without HoH's separate planner and tester (the agent may still plan and test inside that pass). Nobody here works like that. The paper shows structure beats no structure; it doesn't compare against other structured loops (MetaGPT, ChatDev and AgileCoder are cited, not run).
  • Mostly greenfield. The game and program-rebuild tasks start from a spec; five of the 15 FrontierSWE tasks optimise an existing system. None looks like ours: a change to a large, living codebase with other agents' work in flight.
  • One long-run case. The 70-loop claim rests on a single game, with no comparison condition. It shows the loop doesn't fall apart; it doesn't show it beats anything.
  • 17 reopens out of 81 is a lot of regression. HoH does try to prevent it — each plan names what must not break, and the tester checks it — and when that fails, the reopened issue carries its history to the next planner. Still, "no humans" here comes with a standing backlog of known breakage.
  • Cost isn't reported in money. Tokens only, with a note that providers count cached tokens differently. For Codex on the game benchmark, three loops used about 3.25 times the tokens of one pass (8.4M against 2.6M per task).

The hard parts each system is built around

HoH's hard problem is drift over time. One agent, very long project: it forgets earlier decisions, repeats work, patches the same thing forever, or declares victory early. Every HoH mechanism — fresh invocations, evidence passed forward, increments that must both fix and grow, a tester who can't take the developer's word — is aimed at that.

The Overseer's hard problem is many things at once, safely. Thirty agents on one machine and two subscription budgets: agents silently stuck at a permission prompt (34.9 agent-hours lost over four days before that was fixed), test suites colliding on the shared database, a fleet that pauses and never wakes, a supervisor that burns the quota it is meant to protect. And a human whose authority mustn't leak: the runbook's worry is "telling another agent to do what you may not" — a sentence like "finish this work" is innocent text and an unlimited capability.

Both share one: things that report success while doing nothing. HoH's tester records "insufficient evidence" as a gap rather than a pass. Our equivalent is the house rule that a check you have never seen fail is not evidence, and the Overseer's insistence that a deploy isn't done until three independent signals agree.

Judgement

What might be worth borrowing

1. Check we actually re-review the reviewer's fixes

HoH's tester is read-only "to prevent the QA stage from silently repairing the candidate it is meant to evaluate". Ours writes fixes — a trade Greg chose on 2026-09-09 for the round trips it saves — and our rules already cover the hazard: the job agent reads the diff, and the next review round is told to treat Sol's fixes as unreviewed code written by someone else. The open question is whether that second round happens: the worked example's record shows one code review. Costs a look through recent plans' review files. Gives either reassurance, or the case for making the second round a checked step rather than a written one.

2. Run the loop more than once on the same thing

The paper's most interesting result is that loops 4–10 kept paying. Our jobs run plan → build → review per stage, then stop. For the things where quality is open-ended — a new mode, a prompt, a visual design — a second and third round, each starting from a fresh black-box test report ("drive the browser, list what's wrong against the plan's acceptance checks"), might be where the value is. The paper's long run also leaned on game-specific tools for driving and testing the game; extra loops alone are not the whole recipe. Costs roughly linear spend per extra loop. Gives polish that one pass doesn't reach.

3. One issue ledger with "reopened"

HoH's issue table makes regressions first-class: a reopened item carries its own earlier verification history. We have the pieces scattered (postmortems, feedback notes, a recheck table of every report), but no one place that says "this was verified on the 1st and broke on the 5th". Costs another store to keep honest. Gives a regression rate we could actually watch.

4. Measure whether our loop pays, the way they did

Their Table 2 — the same agent and model, the same number of passes, with and without the structure, with token use reported alongside — is the kind of evidence we don't have for our own process. We believe Sol reviews are worth it (and keep finding P1s like the two-queries one above), but we've never run a matched comparison. A small one on a handful of feedback reports would tell us which steps earn their cost.

Where we deliberately do the opposite, and should keep doing so

  • Nobody originating the work. HoH's planner picks increments, but always within a brief a person wrote; our job agents do the same. What the Overseer is forbidden is the level above — starting work nobody asked for. In a product, choosing what to build is the job Greg kept. "My job is basically new ideas" is why gate 3 says "is it in the queue?". A middle path exists and is already partly built: a slow lane of work Greg has approved in principle (overseer-queue.md), which the Overseer may pick from in a lull.
  • Same model everywhere. HoH needs it for a clean experiment. We want the opposite — a reviewer from a different family is less likely to share the builder's blind spots. Greg, 2026-09-30: if Sol runs out, "I'd rather we stop working than risk pushing lower-quality stuff."
  • Rolling back to the last good state. Sensible for one writer; destructive with thirty, because the "bad" commit may be braided with someone else's good work.

Risks and fragilities, seen in the paper's light

  • Our evidence doesn't travel between jobs as well as theirs travels between loops. Inside a job the plan doc is the memory; the next job on the same area starts from the docs and whatever postmortems someone remembered to write. HoH's ablation says losing the evidence costs about 6 points.
  • "Process prescribed" can crowd out "outcome checked". HoH checks every role's output against a schema and retries. Our debrief's three endings are a shape we ask for, not one a program checks.
  • Much of the Overseer is still proposing rather than acting as of this writing: the scheduler that would dispatch standing jobs is switched off, and the deterministic rules write proposals that no surface shows anyone yet. The comparison above is between a paper's running system and a partly armed one.

Open questions

  • Would a HoH-style "keep going until the tester runs out of complaints" mode suit a specific kind of job here — a new reading mode built from scratch, say — where the spec is ours and fixed?
  • Is the second review round — the one that checks Sol's own fixes — happening in practice?
  • Does the Overseer want the paper's "every increment must both repair and grow" rule when it chooses what to pull from the queue — or is ease × value already the better rule for a product?

FAQ

Is the Overseer a "harness of harnesses" too?

Literally, yes — it drives Claude Code and Codex sessions, which are harnesses. But the paper's term means a loop around one harness. Our closest match to that is a single job run by engineering-manager.md. The Overseer is one level further out again.

The paper used GPT-5.6 Sol for its game. Isn't that our reviewer?

The same model family, in a different role. In HoH it plays all three roles (planner, developer, tester). Here the usual arrangement is Claude builds and Sol reviews, so that builder and reviewer don't share a family — though Sol also writes its review fixes, and Codex can be handed building work when Claude's usage limits are tight.

Could we just run HoH on Spideryarn?

On a greenfield sub-project with a fixed spec, probably — that's what it's for. On the main product, three things get in the way: it assumes a single writer, it picks its own objectives, and it is happy to roll back. All three conflict with rules we hold for good reasons (a shared tree, Greg's ownership of product scope, never destroying work).

Where does the human sit in each?

HoH: writes the spec, then fixes the network when it drops. Ours: the source of every job, the owner of every product call, and the reviewer of the decisions the Overseer took on their behalf — which the runbook says must be visible: "A week with zero vetoes is a red flag, not a clean bill."

Glossary

HarnessThe program around a model that gives it tools and runs its actions — Claude Code, Codex CLI, OpenCode, Pi.
Loop (HoH)One round of plan → develop → test.
Warm start (HoH)Each loop's developer starts from the previous code rather than an empty folder.
Evidence bundle (HoH)The tester's structured report: each claim, what was observed, and whether it's verified, failed or unproven.
Runtime (HoH)The small deterministic program that enforces each role's permissions and output format.
Job / session (ours)One Claude Code conversation doing one piece of work, in its own worktree.
WorktreeA separate checkout of the repository on the same machine, so agents don't edit each other's files.
GPT SolOpenAI's model, run through Codex CLI, used for every plan and code review — the cross-family check.
The queueThe list of work Greg has authorised. Being in it is what lets the Overseer start a job.
