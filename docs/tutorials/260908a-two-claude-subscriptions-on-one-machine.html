Two Claude Subscriptions, One Machine

Skim in 6 minutes · deep dive in 25 · written 2026-09-08 against Claude Code 2.1.263 on macOS

You take on a client. Their work must not be billed to your own Claude subscription, and theirs must not be billed to yours. Claude Code offers you one login and a /logout command. This is how to do better than that, and — more importantly — how to know you actually did.

TL;DR

Claude Code keeps its identity in a directory, and the environment variable CLAUDE_CONFIG_DIR chooses which one. Point it somewhere new and you get a second, fully independent login; both stay signed in at once. On macOS the token itself lives in the Keychain, under a service name derived from a hash of that directory path — which is exactly why the two logins do not collide.

The whole job is therefore setting one environment variable before claude starts. The trap is that the obvious ways to set it — a setting in the repo, a shell function in your .zshrc — either do not work or work only when you are typing, leaving every script, cron job and dispatched agent quietly billing the wrong account with nothing looking wrong.

Mental models

An identity is a directory, not a login

The intuition to unlearn: you are not "logged into Claude Code", you are logged into ~/.claude. Hand it a different directory and it is a different person, with different history, different settings, a different subscription. Nothing was logged out.

The safe-deposit box, and the number on the key

On macOS the token sits in the Keychain, not in the config directory. The config directory's path is run through a hash to produce the box number. Same path, same box, same account. Change one character of the path — a tilde, a trailing slash — and you are politely handed a different, empty box, and told you are not signed in.

Alias at the door vs. sign on the corridor

A shell function greets only the people who walk in the front door and say your name. A script on PATH is a sign in the corridor that everyone passes — including the delivery drivers: cron, launchd, an IDE, and the Node script that spawns thirty agents. Almost every way this goes wrong is a rule that only the front door could see.

A fallback is worse than a crash

If the routing cannot find a credential, the tempting behaviour is to use the default one. That is the single worst outcome available: everything works, nothing is logged, and a month of a client's tokens lands on your personal subscription. Refuse and exit non-zero instead.

1. What happens when you type claude

End to end, with no detail at all: something decides which config directory this invocation belongs to, that directory's path is hashed into a Keychain box number, and the token in that box is the subscription that gets billed.

your shell environment & files macOS Keychain Anthropic account

If you stop reading here, the useful residue is: the account is chosen by an environment variable, before the process starts. That is why the fix lives in your shell rather than in any Claude Code setting, and why the failure modes are all about who got to set the variable.

2. The four pieces

A working setup has four parts, and only the fourth is subtle.

PieceWhat it isHow much work
A config directory An ordinary directory — ~/.claude-clientname. Holds settings, history, plugins. mkdir
A login in it One interactive sign-in, done once, that files a token in its own Keychain box. one command
Some seed config A copy of settings.json and plugins/, because the new directory starts empty. two cps
Something that sets the variable The part that has to be right. See §4. a small script

The first three are three lines:

D=/Users/greg/.claude-clientname
mkdir -p "$D"
cp    /Users/greg/.claude/settings.json "$D/settings.json"
cp -R /Users/greg/.claude/plugins       "$D/plugins"
CLAUDE_CONFIG_DIR="$D" claude auth login --claudeai --email you@example.com

Type --claudeai even though it is the default. The alternative, --console, signs you into Anthropic Console and bills metered API usage. It is a different product wearing the same login flow, and the difference does not announce itself afterwards.

What the new directory does and does not inherit

The second account starts almost empty, and the surprise is usually in the right-hand column rather than the left.

The session history is the one real loss. It stays under the old config directory and becomes invisible to --resume. Copying it across is safe when both directories are the same account, and a judgment call when they are not — a resumed transcript is submitted under whichever account resumes it.

3. Why the credential actually separates

This section is the one place worth understanding rather than accepting, because every macOS failure mode falls out of it.

The natural assumption is that a config directory holds a credentials file, so a second directory holds a second file. On macOS that is wrong. ~/.claude/.credentials.json does not exist; the token is a Keychain generic-password item. This is why third-party switchers that copy credential files around struggle on macOS — they are fighting the Keychain rather than using it.

What actually happens is that the Keychain service name is computed from the config directory path:

let t = e !== void 0 ? !e : !process.env.CLAUDE_CONFIG_DIR,
    r = e !== void 0 ? e.normalize("NFC") : be(),
    c = t ? "" : `-${sha256(r).hex.substring(0, 8)}`;
return `Claude Code${OAUTH_FILE_SUFFIX}${n}${c}`;

Read out of the v2.1.263 binary. Unset, the service is Claude Code-credentials. Set, it gains a -<first 8 hex of sha256(path)> suffix.

So the two logins do not overwrite each other because they were never in the same place. You can derive any directory's box number yourself:

printf '%s' /Users/greg/.claude-spideryarn | shasum -a 256 | cut -c1-8
# 54a3298a
security find-generic-password -s "Claude Code-credentials-54a3298a"

The path is never tilde-expanded, and the hash is over the raw string. The resolver is process.env.CLAUDE_CONFIG_DIR ?? join(homedir(), ".claude") — no expansion, no normalisation beyond Unicode NFC. A literal ~, a relative path, or a stray trailing slash each hash to a different box. The symptom is a session insisting you are not signed in, plus a directory literally named ~ appearing under your working directory. Absolute paths, no trailing slash.

How this was verified, rather than assumed

Reading the code tells you what should happen. What was actually run on this machine:

  1. security find-generic-password -s "Claude Code-credentials" returned an item, and ls ~/.claude/.credentials.json returned no such file — establishing that the credential is in the Keychain on this platform.
  2. Pointing CLAUDE_CONFIG_DIR at a throwaway directory and running claude auth status --json returned loggedIn: false, while the same command with the variable unset still returned loggedIn: true for greg@rehearsable.ai. That is the whole claim in one command pair: the credential is per-directory, and creating a second one does not disturb the first.
  3. The throwaway directory came back holding a fresh .claude.json and reporting a projectsDirectory inside itself — which is how we know what else moves.

The step that has not been done from a terminal is a two-real-account acceptance test, because that needs a second subscription. The Keychain naming above is read from the binary and is the part to re-check first if something ever behaves oddly.

4. Why the wrapper must be a script

Two of the three obvious ways to set the variable are wrong, and both fail quietly.

Not a setting in the repo

The tidiest-looking answer is an env block in the repo's own .claude/settings.json, so the rule travels with the project. It does not work: Claude Code ignores CLAUDE_CONFIG_DIR from project settings, and it is circular anyway — the config directory is what decides where settings are read from in the first place.

Measured — a repo whose settings named a config directory ran on the default account and left the named directory empty.

Not a shell function

The common community answer is a function or alias in ~/.zshrc. It works when you type claude, and it does not exist for anything else: a script that spawns claude, cron, launchd, an IDE, an SSH command, a non-interactive shell.

This is not hypothetical, and it is expensive. In this repository scripts/run-claude.ts spawns bin: 'claude' through PATH and deliberately strips CLAUDE_CONFIG_DIR from the child environment. With a shell function, every dispatched agent would run on the default account while your terminal ran on the right one, and nothing anywhere would look wrong.

A neighbouring repo lost hours to exactly this class on 2026-09-04 — see §8.

A script on PATH

An executable early on PATH is re-entered by every caller, after whatever environment sanitising they do, so it can re-derive the answer from the working directory:

#!/bin/zsh
set -eu
REAL_CLAUDE=/Users/greg/.local/bin/claude
CONF=/Users/greg/.claude-accounts        # "<repo root>:<config dir>", one per line

if [[ -n "${CLAUDE_ACCOUNT_DIR:-}" ]]; then
  export CLAUDE_CONFIG_DIR="$CLAUDE_ACCOUNT_DIR"        # explicit override always wins
else
  unset CLAUDE_CONFIG_DIR 2>/dev/null || true
  here="$(pwd -P)/"                      # not $PWD: that is logical, and a symlinked
  while IFS= read -r line; do            # path into the repo would slip past the test
    [[ "$line" == \#* || -z "${line// }" ]] && continue
    [[ "$here" == "${line%%:*}/"* ]] && { export CLAUDE_CONFIG_DIR="${line#*:}"; break; }
  done < "$CONF"
fi
unset CLAUDE_SECURESTORAGE_CONFIG_DIR 2>/dev/null || true
exec "$REAL_CLAUDE" "$@"

Three details that each exist for a reason:

  • pwd -P, not $PWD. $PWD is the logical path, so entering the repo through a symlink would slip past the prefix test and silently use the default account.
  • "$(pwd -P)/" against "$root/"* — the trailing slashes on both sides match the repo root and everything under it, git worktrees included, without also matching a sibling directory called reading2-old.
  • REAL_CLAUDE points at the launcher symlink, never a versioned path. The installer moves the symlink forward; a pinned version would quietly stop updating.

And then refuse to fall back

If the routed directory has no login, the wrapper must not use the default one:

hash8="$(printf '%s' "$CLAUDE_CONFIG_DIR" | shasum -a 256 | cut -c1-8)"
security find-generic-password -s "Claude Code-credentials-$hash8" >/dev/null 2>&1 || {
  print -u2 "claude: $CLAUDE_CONFIG_DIR has no login — refusing to fall back to the default account."
  exit 78
}

find-generic-password without -w reads only attributes, so it triggers no Keychain prompt and costs nothing per invocation. It proves a credential exists, not whose it is — for that question see §5.

5. One invocation, followed all the way through

Greg types claude in ~/dev/spideryarn/reading2. Here is every step, and what would go wrong if it were missing.

Proving it, rather than believing it

There is one command, it starts no session, and it costs nothing:

$ claude auth status --json
{ "loggedIn": true, "authMethod": "claude.ai", "email": "greg@rehearsable.ai",
  "subscriptionType": "max", "orgId": "…",
  "projectsDirectory": "/Users/greg/.claude-spideryarn/projects" }

authMethod and email are the assertion worth making. authMethod: "claude.ai" is what rejects an API key, a Console profile, or a Bedrock/Vertex provider having quietly outranked your subscription — several things beat the login you think you are using:

ANTHROPIC_AUTH_TOKEN > ANTHROPIC_API_KEY > apiKeyHelper > CLAUDE_CODE_OAUTH_TOKEN
                     > profile/federation > subscription OAuth from /login

Before any unattended run that costs money, assert it in the same environment the real invocation will use:

claude auth status --json | jq -e '.loggedIn and .authMethod == "claude.ai"
                                   and .email == "you@example.com"'

A Keychain item existing is not this check. It proves only that some blob is filed under that name. /status inside a session is fine for a human, but it reports after startup and possibly after a paid turn has already happened.

6. Switching by hand

Per-directory routing covers the steady state. You still want to sign in, look, and occasionally force an account regardless of where you are standing — so wrap those four things in one command rather than memorising environment-variable invocations:

claude-acct              # which account would this directory use?
claude-acct list         # every config dir on the machine, and who is signed into each
claude-acct login work   # create ~/.claude-work, seed it, sign a subscription in
claude-acct use work     # a subshell pinned to that account, wherever you are
$ claude-acct list
~/.claude                          greg@rehearsable.ai (max, claude.ai)
~/.claude-spideryarn               greg@rehearsable.ai (max, claude.ai)

use exports CLAUDE_ACCOUNT_DIR, which the wrapper honours ahead of its routing table — so the override reaches subprocesses too, not only the interactive shell. That is the same reasoning as §4, applied to the manual case.

You cannot put the account in the status line. The statusLine JSON on stdin carries model, cwd, cost, context_window, rate_limits, session_id, version, agent, worktree and more — and no account, email or config-dir field. A status-line script can read $CLAUDE_CONFIG_DIR from its inherited environment, or shell out to claude auth status --json at the cost of a subprocess per refresh. Terminal-level indicators (an iTerm2 badge keyed off the config dir) are the cheaper answer.

Should you use one of the third-party switchers instead?

They exist and some are popular: claude-swap (~2.4k stars, pushed the day this was written) and clauth are the two with real traction, adding usage dashboards, menu-bar apps and rate-limit-triggered automatic switching. Several others sit between 40 and 120 stars.

They all wrap the same environment variable. The case for one is the dashboard and the auto-switching; the case against is that a tool holding your credentials is a tool you should have read, and the thing it wraps is twenty lines. If you want the usage dashboard, take the tool. If you want two accounts to stay separate, the wrapper is less to trust.

One thing to check in any of them: switchers built on copying credential files cannot isolate OAuth on macOS, because the token is in the Keychain (§3). Only ones that rely on the config-dir hash actually work here.

7. The parts that are genuinely hard

Everything above works. These are the things that bite afterwards.

The VS Code extension does not respect CLAUDE_CONFIG_DIR. Not one bug but several open ones — it is ignored entirely (#30538), per-workspace auth is ignored while the terminal CLI works (#34888), and shell-integration lock files hardcode ~/.claude/ (#56370). JetBrains is unconfirmed but shares the code path. Treat the terminal as the only place the routing is real.

Do not symlink settings.json between config directories

Maintaining settings twice is annoying, so the obvious move is to symlink the second directory's settings.json at the first's. Claude Code resolves the link and replaces the target atomically, so — contrary to the first worry — the symlink survives and does not degrade into a regular file.

The actual problem is worse and quieter: each config directory takes its own lock while both replace the same target, so the locks do not coordinate. Concurrent settings changes from two accounts silently lose one. GPT Sol measured this at 30 trials out of 30 on v2.1.263 when reviewing the draft of this document.

Copy the file. Accept that the copies drift. The same argument applies to plugins/, which additionally holds mutable marketplace clones and caches.

Every OAuth'd MCP server must be re-authorised per account

MCP OAuth tokens live in the config directory, so a new account starts with none of them and every server needs /mcp again. What softens this is the split from §2: servers declared in the repo's committed .mcp.json are found again automatically, and only their authorisation is missing. Servers declared user-scoped in ~/.claude.json are missing entirely and have to be re-added.

Worth seeding deliberately when you create the directory, alongside hasTrustDialogAccepted for the repo, so the new account does not re-ask the trust dialog for a project you already trusted.

The macOS Keychain caches for about 30 seconds

After a switch, a session can appear not to have picked up the change for up to half a minute. Linux and Windows pick it up immediately. If a check disagrees with what you just did, wait and re-run before debugging.

ANTHROPIC_PROFILE looks like the answer and is not

The binary reads a profile store at $ANTHROPIC_CONFIG_DIR (else ~/.config/anthropic) holding active_config, configs/<name>.json and credentials/<name>.json, where a profile's authentication.type can be user_oauth. It looks exactly like the first-party multi-account feature everyone wants.

It is the Anthropic Console / workload-identity-federation profile store, written by a separate CLI. Selecting a profile switches you to Console API billing rather than to a second subscription, and it outranks your /login credential while doing so. claude --help exposes no --profile flag and no profile subcommand. This is the trap that most rewards checking authMethod rather than assuming.

8. A different problem: pooling, not separating

Everything above answers which account does this directory bill? There is a second, genuinely different question — which account does this process bill? — and it has a different answer. Greg's MindstoneRebel repo has been running it in production for longer than this document has existed.

CLAUDE_CONFIG_DIR="$dir" claude setup-token   # long-lived token, requires a subscription
export CLAUDE_CODE_OAUTH_TOKEN_2=…            # injected per shell / per tmux pane

There, several subscriptions are a pool of capacity rather than a set of identities. A daemon picks the least-loaded account and can hot-swap a running session onto another one mid-conversation. Auth binds to the shell or tmux pane, not to the directory and not to the worktree. Each account is deliberately signed in twice — an auth login so a usage dashboard can read its quota, and a setup-token that is the credential actually spent — and the token is minted before the sign-in, so a half-failed setup cannot file one account's credential under another's export.

CLAUDE_CONFIG_DIRCLAUDE_CODE_OAUTH_TOKEN
answerswhich account does this directory bill?which account does this process bill?
set bya PATH wrapper, from the working directorythe launcher, per shell or pane
isolateshistory, settings, plugins, MCP auththe credential only
good forkeeping a client's work off your own subscriptionspreading load, unattended dispatch, a headless box

Two hazards carry across whichever you pick, and both are worth knowing even if you never build a pool.

apiKeyHelper outranks an injected token, and a settings file cannot be unset from a child environment. A lane can therefore report subscription while actually billing a metered API key. This is the concrete reason to assert authMethod rather than intent.

Shell startup files are the wrong place for the export. MindstoneRebel lost hours on 2026-09-04 to exports sitting below the non-interactive-shell guard in ~/.bashrc: interactive terminals got the right account, every dispatched agent silently got account 1, and nothing looked wrong. That is the same failure the PATH script in §4 exists to prevent — arrived at independently, from a real incident, in a different repo.

9. Trade-offs, risks, open questions

Trade-offs, where reasonable people differ

DecisionThe other choiceWhat it costs
Pin the exception, leave the default alone Move everything into named config dirs, leave ~/.claude unused Pinning one repo is a two-line change and cannot break the other ninety. Naming everything is tidier and more uniform, but every repo now depends on the wrapper being correct.
A hand-written wrapper claude-swap or clauth You give up a usage dashboard and rate-limit auto-switching. You gain twenty readable lines instead of a dependency that holds credentials.
Leave the old session history behind Copy projects/<repo> across 1.9 GB here. Leaving it costs --resume on pre-switch sessions; copying it duplicates a large tree that then diverges. Cheap to change your mind later.
Refuse to run when not signed in Fall back to the default account Refusing means a broken window between installing the wrapper and doing the login. Falling back means that window is invisible and lasts until the invoice.

Risks and fragilities

  • The whole thing is a string prefix match on a path. Move or rename the repo and the routing silently stops applying — no error, just the default account. A rename is the most likely way this breaks.
  • The Keychain check proves existence, not identity. If you ever sign the wrong account into a routed directory, every check in the wrapper still passes. Only claude auth status --json catches it, and only if something runs it.
  • The wrapper shadows claude for everything. That is the point, but it means a bug in twenty lines of zsh takes out every Claude invocation on the machine, including the ones you would use to debug it. ~/.local/bin/claude remains the escape hatch.
  • IDE integrations quietly opt out (§7). Anyone who does most of their work in the VS Code extension does not have the separation they think they have.
  • Nothing tests any of this. There is no red-going-green check that the right account is billed; there is a command you have to remember to run.

Open questions

  • Should the preflight be automatic? A SessionStart hook asserting authMethod and email would turn "a command you remember" into "a check that runs". The cost is a subprocess on every session start.
  • Is the status line worth the subprocess? Today there is no account field, so showing it means shelling out per refresh. An iTerm2 badge set once at launch is cheaper and probably enough.
  • What happens on the Linux box? The wrappers are macOS-specific and deliberately outside the repo. The remote box runs the same checkout with its own authentication, and nothing yet asserts that the two machines agree about which account a given repo should use.
  • Will this survive first-party support? Anthropic has not shipped account switching and has closed the main request as a duplicate — but eight overlapping issues is real demand, and a native claude auth switch would make this wrapper legacy overnight. Worth writing thin enough to throw away.

10. FAQ

Do I need two subscriptions, or can I split one?

Two accounts means two subscriptions. A subscription is for your own individual use — you may not route another person's usage through your seat, and the moment work is really someone else's, that is what an API key is for. One person holding two of their own subscriptions and using each from a different directory is not addressed explicitly anywhere in the docs, but it is your own use in both cases.

Can I just use an API key for the second one?

You can, but it is not a second subscription — it is metered Console billing, a different product with different economics. It also outranks your subscription login wherever it is set, which is a common way to accidentally stop using the subscription you are paying for.

Will my existing login be disturbed?

No. Creating a second config directory files a new Keychain item under a different service name; the original is untouched. This was checked before and after on this machine.

What about git worktrees?

Covered for free when they live inside the repo, because the routing is a path-prefix test — ~/dev/…/reading2/.claude/worktrees/foo starts with ~/dev/…/reading2/. Verified from inside a real worktree. Worktrees kept outside the repo need their own ~/.claude-accounts entry.

How do I undo all this?

rm ~/bin/claude. That restores the previous behaviour immediately, because ~/.local/bin/claude was never touched. The config directory and its Keychain item can stay until you want the space back.

Why is my new account asking to trust a repo I already trust?

Trust is recorded per project in .claude.json, which moves with the config directory. Seed hasTrustDialogAccepted for the repo when you create the directory, or answer the dialog once more.

11. Appendix: what is where

On this machine, as of 2026-09-08

PathWhat it is
~/.claudethe default account, greg@rehearsable.ai (Max) — every repo
~/.claude-spideryarnseeded (settings, plugins, the user-scoped MCP server, the repo's trust flag) and not yet signed in
…/claude-wrapper.zshthe routing wrapper, staged rather than armed — deliberately not on PATH
~/bin/claude-acctlook at and switch accounts
~/bin/claude-acct-arminstalls the wrapper as ~/bin/claude, and refuses to until the login exists
~/.local/bin/claudethe real launcher symlink, untouched — the escape hatch
claude-acct login spideryarn   # browser opens; sign in as the account this repo should bill
claude-acct-arm                # installs ~/bin/claude, which precedes ~/.local/bin on PATH

Why it was left staged. The wrapper refuses to fall back (§4), so arming it before the login makes claude exit 78 inside the repo — and this machine was running a fleet of agents in worktrees that would have started failing immediately. Because the account being pinned to is already the default, waiting costs nothing and bills nothing wrongly. That trade — a loud refusal is right, but arming it at the wrong moment is still disruptive — is the practical shape of the fourth mental model.

Both accounts are the same today. The point of pinning is that they need not stay that way: adding a client subscription later is claude-acct login <name> plus one line in ~/.claude-accounts, and this repo cannot drift onto it by accident.

Glossary

TermIn plain words
