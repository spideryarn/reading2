A work graph for agents

Beads is an issue tracker written for AI coding agents rather than for people. It is worth understanding even if you never install it, because the idea underneath it — that the plan should be a queryable graph rather than a document — is the part that transfers.

7 minutes to skim · ~30 to read everything · written 2026-09-06 from the project's own public docs at version 1.1/1.2 · nothing here was run, see what this page did not check

TL;DR

An agent finishes a session and forgets everything. The next one starts from whatever you wrote down. Beads makes that written-down thing a dependency graph in a database instead of a markdown file, and gives it one important query: bd ready — which items have no unfinished blockers, and so could be started right now. An agent asks that question, takes one item, does it, closes it, and the closing automatically makes the next items available. Nobody re-plans.

The database is Dolt, a MySQL-compatible SQL database that is version-controlled like git: it branches, diffs and merges, and it merges per cell, so two agents editing two fields of the same issue do not conflict. It rides in your existing git remote under a side reference called refs/dolt/data, so the issue history travels with the repo without ever appearing on a branch.

Around that core sits a great deal more: about 120 subcommands, a template language for repeatable workflows, agent-to-agent messaging, bidirectional sync with GitHub/Jira/Linear, and cross-repo federation. The core is roughly a weekend of work and carries most of the value; the rest is the part to think hard about before adopting. §7 is what a stripped-down version looks like, with two other models' opinions on it.

Four ways to picture it

1 · Amnesiac shift workers, and a handover book

Every agent session is a new worker who has read nothing, remembers nothing from last time, and will be gone in an hour. What survives is the book on the desk. A markdown plan is a book written in prose that the next worker must read end to end and interpret. Beads makes it a book with an index and a rule: turn to the page marked READY and take the top item.

2 · A departure board, not a timetable

A timetable lists everything that is planned. A departure board shows only what is boarding now. bd ready is the departure board: of two hundred open items it might show four, because the other 196 are waiting on something. The agent never reads the timetable, which is the whole point — a plan the agent has to hold in its head is a plan that costs tokens and gets mis-remembered.

3 · Git, but for the issues

Your issues get commits, branches, diffs and merges, in the same repository as the code and pushed to the same remote. Two consequences follow immediately: you can work on issues offline on a plane, and a feature branch can carry its own issue changes and merge them back. The cost is that you are now running a database engine inside a CLI binary, and databases have opinions.

4 · Cloakroom tickets, not queue numbers

Issues are identified by a short hash — bd-a1b2 — rather than #1, #2, #3. Sequential numbers require a single authority handing them out. Two agents on two branches both take "#7", and merging is then a mess. A hash needs no authority and no coordination: everyone mints their own. Collisions become unlikely rather than impossible, and beads detects them on import and appends a disambiguator rather than losing an issue.

Pass 1 The loop, in one page

There is one loop and it has five steps. Everything else in the product is in service of it.

In commands, a whole session looks like this:

$ bd ready
Ready work (2 issues with no active blockers):
  1. [P1] bd-7f2a.1: Signed upload URL + storage bucket
  2. [P2] bd-4d80:   Add the /changelog page

$ bd update bd-7f2a.1 --claim        # sets assignee AND in_progress, in one atomic step
$ ... does the work ...
$ bd close bd-7f2a.1 --reason "Bucket + signed URL endpoint landed in 4f2a10"

$ bd ready
Ready work (3 issues with no active blockers):     # two new ones appeared by themselves

Why the atomic claim matters more than it looks

Two agents running bd ready a second apart get the same answer. If claiming were "read, then write", both would take bd-7f2a.1 and one would waste a session. The --claim flag is a compare-and-set: it succeeds only if the item is still unclaimed, and the loser is simply told to pick another. This is the single mechanism that makes running several agents at once sane, and it is why a shared markdown TODO list does not work — a file has no way to say "I got there first".

Pass 2 The pieces: a bead, four kinds of edge, one query

A bead

A "bead" and an "issue" are the same thing; the docs use both. It is one unit of work with the fields you would expect and two you might not.

FieldWhat it holdsWorth knowing
idbd-a1b2 a hash of the title, the creation timestamp and a random salt. Grows from 3 to 8 characters as the database grows, so short IDs stay short in small projects.
title, descriptionthe work free text; the description is where an agent puts its plan.
typetask · bug · feature · epic · chore plus gate, which is a wait rather than a job — see below.
priority0–4, 0 is critical orders the ready list; does not affect what is ready.
statusopen → in_progress → closed plus deferred and blocked, which are derived rather than typed by hand.
assigneewho claimed it usually an agent identity, not a person.
labels, comments, notesthe usual comments are threaded, and agents use them as a work log.

Beads also have hierarchical child IDs: an epic bd-a3f8 has children bd-a3f8.1, bd-a3f8.2, and those can have .1.1, up to three levels. Those are readable structure sitting on top of the unreadable hash, which is a nice trick: the parent's identity is coordination-free, and the children are numbered locally, where there is already an authority.

Four kinds of edge — and only two of them block

This is the part most worth copying. The graph has four ordinary edge types, and the difference between them is not decoration. (Gates, later, add two more — waits-for and conditional-blocks — which also hold work back; the four here are the ones you wire by hand.)

discovered-from is the one to steal

An agent fixing a bug finds three more. In a markdown plan those become a bullet list at the bottom that nobody reads, or they are lost. As an edge, they are first-class items that show up in bd ready later, and they still carry the answer to "why is this here?" six weeks on. The docs call it provenance; in practice it is the mechanism that stops "while I was in there…" from being either scope creep or amnesia.

The one query

The definition, in the project's own words, is: open beads with no open blockers, excluding anything in progress, blocked, deferred, or held by a gate. That is the whole scheduler. There is no priority queue, no sprint, no assignment algorithm — priority only sorts the result.

Two commands matter around it. bd ready --json is what an agent calls, and bd ready --explain is what a person calls when the list is empty and they want to know which blocker is holding everything up.

Pass 2 Where the bytes live, and how they travel

This is the part with the most machinery and the least product in it, so here it is in one picture and three paragraphs.

The engine is embedded. bd is a single static binary with the Dolt database compiled into it — no server to install, no daemon, nothing to start. The cost is that exactly one process may write at a time, enforced by a file lock. If you want several processes writing concurrently you switch to server mode, which means running a real dolt sql-server and taking on a process to supervise.

Merging happens per cell. This is Dolt's actual selling point. If one agent changes an issue's status while another changes its description, a file-based tracker sees two edits to the same line and hands you a conflict; Dolt sees two different cells and merges them. In a world where four agents on four branches all touch the tracker, that is the difference between "merges usually just work" and "somebody resolves conflicts every afternoon".

Sync piggybacks on git without being git. bd dolt push writes the database history to your existing remote under refs/dolt/data. There is no server to run, no account, no second remote. It is also not automatic: pushing your code does not push your issues, and the docs' recommended habit is bd dolt push at the end of a session.

The JSONL file is a trap if you assume it is a backup

The README says it directly: ".beads/issues.jsonl is an export for viewers and interchange, not the source of truth or a backup." It is easy to see a plain-text file in a git repo and conclude that worst case you can recover from it. You cannot: a snapshot cannot restore the database's history, and anything since the last export is simply absent. Whether all current edge data round-trips through it, the docs do not say. The real backup story is "push the Dolt history somewhere", and it is a thing you have to remember to do.

Pass 3 One feature, followed all the way through

Take a real-shaped piece of work: let a reader upload a PDF and read it like an article. Two agents are working, in separate git worktrees, on the same repo.

Monday, planning

$ bd create "Reader can upload a PDF" -t epic -p 1
bd-7f2a

$ bd create "Signed upload URL + storage bucket"  -p 1 --parent bd-7f2a   # -> bd-7f2a.1
$ bd create "Extraction path for PDFs"            -p 1 --parent bd-7f2a   # -> bd-7f2a.2
$ bd create "Upload control in the reading view"  -p 2 --parent bd-7f2a   # -> bd-7f2a.3
$ bd create "Ship it"                             -p 2 --parent bd-7f2a   # -> bd-7f2a.4

$ bd dep add bd-7f2a.2 bd-7f2a.1      # extraction needs the bucket
$ bd dep add bd-7f2a.3 bd-7f2a.1      # so does the upload control
$ bd dep add bd-7f2a.4 bd-7f2a.2
$ bd dep add bd-7f2a.4 bd-7f2a.3

Four steps and four edges. Nobody has decided an order; the edges have.

Tuesday, two agents

Agent A starts. bd ready returns one item, it claims it, and while wiring the bucket it notices the storage client never closes its connections. That is not this job, and it must not be forgotten:

$ bd create "Storage client leaks connections" -t bug -p 1 --discovered-from bd-7f2a.1
bd-9e11
$ bd close bd-7f2a.1 --reason "Bucket + signed URL endpoint, commit 4f2a10"

The moment that close lands, bd-7f2a.2 and bd-7f2a.3 both become ready — and so does bd-9e11, which was never blocked by anything. Agent B, in its own worktree, runs bd ready, sees three items, and claims one. The two agents never spoke and never collided, because the claim is atomic and the list is derived.

Wednesday, waiting on the world

Both middle steps close. bd-7f2a.4 — "ship it" — should now be ready, but you want CI green first. That is a gate: a bead whose job is to be open until something outside the repo happens.

Gate typeCloses whenWho closes it
humana person approvesbd gate resolve, by hand — the docs say these should never auto-close
timera duration elapses (30m, 24h) bd gate check, next time anyone runs it
gh:runa GitHub Actions run finishes bd gate check, which shells out to gh run view
gh:pra pull request reaches a state same, via gh pr view

Gates do not fire; somebody has to ask

A timer gate does not go off. A CI gate does not get told. They close when bd gate check runs and evaluates them. So "async coordination" here means polling that has been given a nice place to live, and if nothing on your machine ever runs bd gate check, a gated workflow simply stops. That is not a criticism of the design — a CLI with no daemon has no other option — but it is the thing to notice before you build a release process on it.

Formulas and molecules — the same graph, stamped out repeatedly

If you do the four-steps-and-four-edges dance every release, you can write it once as a formula: a TOML file describing a DAG with {{variable}} holes.

title = "Release Process v{{version}}"

[[steps]]
id = "qa"
title = "QA Testing"

[[steps]]
id = "docs"
title = "Update Documentation"

[[steps]]
id = "tag"
title = "Create Git Tag"
needs = ["qa", "docs"]        # both must close first

[[steps]]
id = "announce"
title = "Public Announcement"
needs = ["tag"]

bd cook release.formula.toml compiles and validates it into a proto; bd mol pour release --var version=1.0.0 stamps out a molecule — real beads with real IDs, dependency-wired, flowing through bd ready like anything else. A wisp is the throwaway version, purged at the next bd purge.

The vocabulary is heavier than the idea. It is a template engine for subgraphs. Worth having if you run the same multi-step process weekly; pure overhead if you do not.

Pass 2 The part that is specifically about agents

Everything so far would make sense in a tracker for people. Three things here would not.

The startup injection

bd setup claude writes a SessionStart hook into .claude/settings.json that runs bd prime whenever a session begins and after every context compaction. That prints roughly 1–2k tokens of "here is how to use this tool, and here is what you were doing" straight into the agent's context. The equivalent integrations exist for Codex, Cursor, Aider, Gemini CLI, Windsurf, Copilot and a dozen more, plus an MCP server for hosts with no shell.

The re-injection after compaction is the clever bit. An agent that has been compacted has forgotten the workflow it was told about at the start; without something to re-establish it, a long session drifts back to writing markdown TODOs. This is a real failure mode and it is nice to see it addressed at the plumbing level rather than by asking the model to be more careful.

Memory, and letting it decay

bd remember "the extraction step assumes UTF-8, and PDFs are not" stores a project memory; bd recall retrieves; bd compact semantically summarises old closed work so that a two-year-old project does not carry two years of detail into every prompt. The premise — that the memory has to shrink or it eats the thing it was meant to help — is right, and it is one of the few tools that treats it as a first-class problem rather than an afterthought.

Agents talking to each other

bd mail and bd ping give agents threaded messages, with a replies-to edge type; bd swarm and bd merge-slot coordinate several of them; federation shares graphs across repositories with encryption and peer discovery. This is the far end of the product, and whether it is visionary or premature depends entirely on whether you are running three agents or thirty.

Pass 4 The genuinely hard parts

Nothing above is hard. These are, and they are hard in a way that does not go away if you write your own — see §7, where the same list reappears.

One writer, until you run a server

Embedded mode holds a file lock, so one process writes at a time. For a human that is invisible. For four agents in four worktrees firing bd calls, contention is real, and the answer is to run dolt sql-server — which is a process to start, supervise, and debug when it does not come up. The docs have a troubleshooting entry for exactly that (bd doctor, .beads/dolt-server.log, bd dolt stop && bd dolt start), which tells you it happens.

A pinned database engine, because of a bug in the newer one

Beads pins Dolt to 2.2.0. Dolt 2.3.x regressed DOLT_RESET('--hard') in "approximately 3–5% of freshly created databases", which breaks bd flatten, bd admin compact and merge rollbacks. This is the tax on embedding somebody else's database engine: their release schedule is now partly your problem, and a 3–5% failure rate is precisely the kind that looks like flakiness rather than a bug.

Version skew between binaries

An older bd refuses to query a database migrated by a newer one, with BD_IGNORE_SCHEMA_SKEW=1 as the escape hatch. This is the right call — the alternative is cryptic SQL errors — but it means upgrading is a team event, not a personal one, and a colleague or a CI runner on last month's binary is simply locked out until they upgrade.

Two things that both mean "done"

An item is closed in the tracker and the code is pushed. Those are two separate writes to two separate systems, and no transaction spans them. Close-then-crash leaves the graph claiming work that never landed; push-then-crash leaves work done and the graph saying otherwise. Every tracker that sits beside a version control system has this problem, beads included, and the only real mitigations are ordering (push first, record second) and a habit of putting the item's ID in the commit message so the two can be reconciled afterwards.

An agent that dies holding a claim

A claim has no lease. If an agent is killed mid-task, its item stays in_progress forever and no other agent will take it. Beads gives you bd stale to find them and leaves the decision to a person, which is the honest choice — an agent that has been quiet for two hours may be dead or may be thinking — but it does mean somebody has to look.

Three smaller ones worth knowing before you commit

Hash collisions are handled, not prevented. IDs start at 3–4 characters and grow to 8. Collisions are called "rare"; on import, a disambiguator is appended and both issues are kept. You can count them with bd info --schema --json | jq '.collision_count'. A four-character hash is 16 bits or so of space — fine for a few hundred issues, and the adaptive length exists because it is not fine for a hundred thousand.

Never let the database directory into git. The generated .gitignore covers it, but the recovery docs describe cleaning it out with git rm --cached and history rewriting, which means people do it. Git LFS is called out as also wrong.

Shared server mode needs unique prefixes. Several projects pointing at one Dolt server without distinct database prefixes causes, in the docs' words, silent data corruption. "Silent" is doing a lot of work in that sentence.

An 80/20 version, and two second opinions

Beads is about 120 subcommands. Suppose you wanted most of the benefit for a fraction of the surface — what would you build? I put that question to two other models alongside my own reading, with the same brief. They converged on five mechanisms, each added one thing the other left out, and they disagreed on three things worth knowing about. Below, "both" means both of them said it; where only one did, it says which.

The five mechanisms all three of us kept

KeepWhy it is load-bearing rather than nice
Durable items with stable IDs Something an agent can name in a commit message and a later session can look up. A title alone preserves almost none of what you need to resume.
One edge type: blocks "B requires A" as executable information rather than prose. Everything the scheduler needs. Parent-child, related and the rest are convenience.
ready as a computed query, never a stored state This is the trick. Because readiness is derived, closing an item updates the world for free, and there is no second list to keep in step with the first.
An atomic claim The concurrency problem that appears the moment there are two agents, and the one a shared file cannot solve at all. Not the only one — Astra also names lost updates, concurrent cycle creation, and a stale owner writing after being replaced.
Something that injects the list at session start A tracker nobody queries is a markdown TODO with extra steps. Beads ships hooks for fourteen agent hosts; you need one.

Then one each, and they are worth having both:

  • Astra added an explicit handoff — the owner's session, the worktree it is in, the last checkpoint and the next action. Without it, as it put it, the next agent "knows something was happening but must rediscover everything". A plain issue tracker has no such field.
  • Fable kept discovered-from as one nullable column, against Astra's advice to keep exactly one edge type. Fable's framing: "'I noticed this while doing that' is the provenance markdown loses first, and it costs one integer." On this one I think Fable is right and it is the cheapest thing in the schema.

The shape of the minimal thing

One table, one view's worth of query, seven commands. Concretely:

items
  id           serial primary key          -- printed as w-142
  title        text
  body         text                        -- outcome + acceptance criteria
  status       open | doing | done | dropped
  priority     smallint  0..4
  owner        text                        -- agent/session identity, while doing
  claimed_at   timestamptz
  found_while  integer references items(id)      -- "I noticed this while doing that"
  plan         text                              -- the doc this belongs to
  handoff      text                              -- where the last agent got to, and what is next
  created_at, closed_at

deps
  item_id      integer references items(id)      -- cannot start until...
  blocker_id   integer references items(id)      -- ...this one is done
  primary key (item_id, blocker_id)
  check (item_id <> blocker_id)

Two tables, not one — a blocked_by integer[] column is the tempting shortcut, and it is a trap

An array of blocker IDs on the item row keeps it to one table and reads nicely. It also gives up the foreign key, so an array can name an item that no longer exists and the query silently treats that dangling ID as satisfied. It gives up the uniqueness constraint, so duplicates and self-edges need hand-written checks. Two agents adding a blocker to the same item at the same time read-modify-write the array and one edit vanishes. And the reverse question — "what does this block?" — stops being an index lookup. A two-column table costs one more create table and removes all four problems, which is what "prefer simple over easy" means in practice.

Ready is one query — "open, and every blocker of mine is done":

select w.* from items w
where w.status = 'open'
  and not exists (
    select 1 from deps d join items b on b.id = d.blocker_id
    where d.item_id = w.id and b.status <> 'done')
order by w.priority, w.id;

Note the predicate: <> 'done', not "still open or doing"

The obvious version says a blocker stops mattering once it is no longer open — which means dropping a blocker silently releases everything behind it. That is the wrong default, and it is Astra's point: cancellation is not completion. A dropped blocker should keep its dependents blocked, and show should name it, so that somebody removes or replaces the edge deliberately. Two characters of SQL decide whether abandoning a piece of work quietly unleashes the work that depended on it.

Claim is one statement, and it is the interesting one:

update items set status='doing', owner=$1, claimed_at=now()
where id=$2 and status='open'
  and not exists (                          -- still ready, checked at the moment of writing
    select 1 from deps d join items b on b.id = d.blocker_id
    where d.item_id = items.id and b.status <> 'done')
returning id;                               -- no row back means you did not get it

Two agents claiming the same row serialise on it, and exactly one sees a row come back. Two things about that are easy to get wrong. First, say "you did not get it" rather than "somebody else got there first": no row also means the item does not exist, was already finished, was dropped, or has acquired a blocker since you last looked — and an agent that reports the wrong one of those wastes somebody's afternoon. Second, the readiness check has to be in the statement. The shorter version, with only status='open' in the WHERE, happily claims an item that is open but blocked, because ready was a separate query a moment earlier.

Then: add, ready, show, claim, release (write a handoff, put it back), done, and a prime that prints the top dozen ready items plus anything stuck in doing for hours, wired into whatever session-start hook your agent host offers.

Where the two reviewers disagreed — the disagreements are the interesting part

How big is it? Fable said ~200 lines and a morning. Astra said 700–1,000 lines plus 300–500 of tests. The gap is not really about the feature list; it is about how much you harden. Fable's version trusts one UPDATE statement; Astra's adds revision numbers on every mutation, claim tokens, and serialises every mutation — claims included — through one transaction-scoped advisory lock. Both are right about different things. A claim on its own needs no lock: a conditional UPDATE is atomic, and two claimers serialise on the row. But adding a dependency edge means reading the graph, checking for a cycle, and writing, and two concurrent writers can each pass that check and jointly create a cycle neither could see — so everything that can invalidate the invariant has to take part in one shared serialisation. An advisory lock is one way; SERIALIZABLE with retry is another. Astra's blanket lock is the cautious version, and it costs milliseconds, which makes it a defensible default rather than an overreaction.

Serial IDs or UUIDs? Fable: serials, because with one database they cannot collide. Astra: UUIDs displayed as an eight-character prefix, resolved by prefix when unique. The serial is nicer to type and the UUID is the one that still works the day somebody creates an item offline. Note that this is exactly the argument beads settled with hashes — so choosing a serial is choosing "there will only ever be one database issuing IDs", explicitly. Many writers against that one database are fine.

Which database? This is the one to think hardest about. Both reviewers observed the same trap: a local database shared between git worktrees does not make two machines share anything, so a work queue on localhost silently becomes two work queues. Fable would put it in a separate schema on the existing remote database and accept the coupling; Astra would stand up a separate tooling database with its own credentials and a lifecycle excluded from application resets. Astra's is more correct and is more work, and both agreed on the operational consequence either way: if that endpoint is down, no agent can safely claim anything.

The parts you cannot cheat

Four of beads' complications are essential. You will meet them too, just later:

  • One arbiter for claims. Beads pays for it with an embedded database and a file lock; a Postgres version pays for it with a connection string. What you cannot do is keep the tracker in a per-branch file, because then a claim is invisible to other worktrees until it is pushed and merged — which is the exact window you were trying to close.
  • Stale claims. Agents die. claimed_at, and a prime that shouts about anything old, is the cheap version. Recovery itself is solvable — a coordinator can force-release a claim, and a claim token makes the old owner's later writes bounce. What is not solvable is deciding by timeout alone that an agent is dead, because a slow one looks identical; and no token stops a still-running agent editing files.
  • The context budget. Whatever gets injected at session start has to be capped and ranked from day one. Open items do close, so the ready list rises and falls — but the corpus behind it only grows, and an uncapped list is a slow leak into every prompt. Beads' memory-decay machinery is the expensive descendant of exactly this problem.
  • Drift between the tracker and reality. An item done in code but open in the table is worse than no item at all, because it is confidently wrong. The mitigation is habit — the item's ID in the commit message, and a sweep that reconciles the two — not machinery.

And one thing no tracker fixes: a claim says who owns an item, not who owns a file. Two agents on two unrelated items can still collide in the same module, or in the same database.

When the small version stops being enough

These are review triggers rather than measured limits — symptoms you can notice, which is the useful kind:

  • A writer that cannot reach the database — an offline laptop, a CI runner, an outside contributor. At that point you need files-in-git, and beads' entire sync story becomes yours to write.
  • A second repository sharing one backlog. This is where federation begins.
  • Roughly ten concurrent agents, or abandoned claims appearing weekly. The problem has moved from storage to supervision.
  • A few hundred open items, with useful work routinely buried. You now need grouping, labels and hierarchy, and the flat list stops being readable.
  • A human who wants to browse the backlog on a phone. The answer there is GitHub Issues with a thin sync, not a richer CLI.
  • Repeated manual approvals or CI polling dominating the day. That is what formulas and gates are for — and the point at which adopting beads properly starts to look like the cheaper option.

What both reviewers said when asked about this repo specifically

Neither recommended adopting beads, and neither recommended adopting a subset of it — the reasoning being that a subset still brings the storage engine, the sync machinery and the upgrade procedure, which is where nearly all the complexity is. Both recommended building the small version, and Fable added the test that matters: wire it into the session-start hook, and if agents act on it for a month, keep it; if it is ignored, drop the table and you have lost a morning.

Astra's caution is the counterweight: "A 30-line script can list structured TODOs. It cannot credibly deliver concurrent ownership, graph integrity, and recovery." The small version is small because it drops sync, not because the remaining problems are easy.

Trade-offs, risks and open questions

Trade-offs, where reasonable people would choose differently

The choiceWhat it buysWhat it costs
A database, not files Atomic claims, a real query, no parse step — and, because the database is Dolt specifically, merges resolved per cell rather than per line. You cannot read your issues with cat, diff them in a pull request, or edit them in your editor. For a tool whose users are agents that is a fair trade; for a tool a person also uses daily it is a real loss.
Dolt, not SQLite Branching, diffing, merging and sync for free — the things that make a per-clone tracker work at all. A pin to Dolt 2.2.0 — because 2.3.x reportedly regressed DOLT_RESET('--hard') in 3–5% of fresh databases — plus a schema-skew guard, a recovery chapter and a much larger binary. SQLite would have been boring, and boring is usually right.
Sync on a git side-ref No server, no account, no second remote; issue history travels with the repo and branch protection never sees it. It is invisible. git push does not push it, git log does not show it, a fresh clone does not have it until bd bootstrap runs. Clever plumbing that people will not expect.
Agents first, humans second JSON everywhere, no markdown to parse, commands shaped like the loop an agent runs. No web UI, no phone, no glance-at-the-board. The docs say beads is "a good CLI issue tracker for humans too", which is true and is not the same as a good tracker for a team.
120 subcommands Whatever you need is probably in there. The surface an agent must learn, and the surface you must trust. Most of the value is in about six of them.

Risks and fragilities

  • The failure mode is quiet. If nobody runs bd dolt push, work simply stays local and everything looks fine. If nobody runs bd gate check, gated work stops with no error. If the tracker drifts from the code, it reports confident nonsense. None of these produce a message.
  • Two systems of record for the same thing. Adopting a graph tracker beside existing planning documents invites keeping the same checklist in both, which reliably rots. The rule both reviewers reached independently: the documents own intent and reasoning, the graph owns current status and ownership, and neither duplicates the other.
  • Embedding somebody else's database engine. Their bugs and their release schedule are now partly yours, and the pinned-version note in the docs is evidence that this already happened once.
  • Project maturity. The docs describe it as "a 1.x product used in production for AI-assisted development", and the recovery section covers database corruption, sync failures, circular dependencies, history bloat and an accidental release. That section existing is a good sign about the authors and a fair warning about the terrain.

Open questions

  • Does an agent actually use it? The whole design assumes the agent reaches for bd ready instead of writing a TODO list. The startup hook plus re-injection after compaction is a serious attempt at making that stick, and whether it holds over a long session is an empirical question nobody can answer from the documentation.
  • Is a work graph the right shape for exploratory work? A dependency DAG is a good model for a release process and a poor one for "figure out why this is slow". Beads' answer is discovered-from, which lets the graph grow sideways as you learn. Whether that is enough is the interesting product question here.
  • Where does the plan document go? If the graph holds the work, something still has to hold the reasoning, the option that was rejected, and the evidence. Beads has descriptions, comments and memories; none of them is a document. The likeliest good answer is both, with a link between them and a strict rule about which owns what.

FAQ

Why not just GitHub Issues?

No dependency edges that mean anything, no local database to query offline, no atomic claim, and every read is a network round trip. The project's own answer is that GitHub Issues and Jira "excel for human teams" and beads targets agents. Note that beads will sync to them (bd github, bd jira, bd linear) if you want the board for the humans and the graph for the agents.

Why not just a markdown TODO file?

Three specific things it cannot do: say "I got here first" (no atomic claim), answer "what can start now" without a human reading it, and survive two branches editing it. The first is the one that bites immediately with more than one agent.

Does it need the network?

No. Everything runs against the local database; only bd dolt push and pull talk to anything. Offline-first is one of the design's genuine strengths, and it is also the thing the simplified Postgres version in §7 gives up.

Can several agents really work at once?

Yes, with a caveat. Hash IDs mean concurrent creation needs no coordination — collisions are unlikely, and detected and disambiguated on import rather than prevented — and --claim means concurrent claiming has one winner. But embedded mode is single-writer via a file lock, so heavy concurrent use is where you move to server mode and take on a process to supervise.

How big can it get?

The docs say Dolt "comfortably handles far more issues than a typical project accumulates", and suggest splitting into multiple databases past 100k issues. bd gc deletes old closed issues, squashes history and reclaims disk. The practical limit is not the database, it is the context window: whatever gets injected at session start has to stay small.

What happens to a fresh clone?

It gets the code and no issues, because the database directory is gitignored. bd bootstrap notices the data on refs/dolt/data, clones it, and wires up the remote. Worth knowing, because "I cloned the repo and there are no issues" is going to be somebody's first support question.

Is it worth adopting for a small project?

Probably not as-is, and the reasoning is in §7: most of the machinery exists to let independent clones merge issue changes, and a project with one database and a handful of agents does not have that problem. The ideas — a computed ready set, an atomic claim, discovered-from, an injected list at session start — are worth taking regardless of whether the tool is.
