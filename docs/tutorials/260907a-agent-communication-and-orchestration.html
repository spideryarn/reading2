Agent communication and orchestration

Claude Code 2.1.263 · measured 2026-09-07 · skim 8 min · deep dive 30 min

Claude Code sessions can find each other, message each other, read each other's conversations, wake each other from the dead and shut each other down. This is what actually works, tested live on Greg's Mac and against the Hetzner box — and where the sharp edges are if you want an Orchestrator sitting on top.

TL;DR

Every Claude Code session on a machine publishes itself to a small registry on disk and listens on a private unix socket. ListAgents reads that registry; SendMessage writes to that socket. Sessions on other machines are reachable too, through a cloud bridge tied to your Claude account — that works, and messages to a machine that is currently offline are queued rather than dropped.

Any session on your own machine you can also spy on: its full transcript sits readable on disk, including a running count of how much context it has used. A worker on another machine keeps its transcript over there, so the bus is all you have. Sessions can be spawned detached, stopped, and later woken with their memory intact.

The gaps are all in the identity layer: names are nicknames, they drift, they collide, and they differ depending on who is looking. An Orchestrator is very buildable; addressing is the part that will bite you.

Two things worth knowing before you start. Live quota — how much of your five-hour and weekly budget is gone, and when it resets — is available to a shell script every turn, which is the signal a fan-out decision actually needs. And there is already a documented feature for orchestrating many agents, so check §10 before building one by hand.

How to read the claims in here. This mixes things I ran on these machines with things the official docs say, and they do not deserve equal trust:

  • Measured — I ran it on 2026-09-07 against Claude Code 2.1.263, and the numbers shown are the real output. Where it was a single observation, the text says so.
  • Documented — quoted from code.claude.com, and quoted rather than paraphrased where the wording matters.
  • Untested — flagged inline. There are a few, and they are the rows most likely to be wrong.

Version-sensitive throughout: this is a fast-moving surface, and §11's release dates and star counts will age fastest of all. Check the date in the source comment before trusting any of it.

Five mental models

1. A switchboard, not an org chart.

There is no tree of agents. Every session is a peer with a phone number, and any peer can ring any other. "Orchestrator" is a role you write into a prompt, not a structural position the system enforces. The one real parent/child relationship is a session and its in-process subagents.

2. Two post offices.

Same machine: a unix socket in /tmp/cc-socks/ — instant, private, and only works while the other process is alive. Different machine: a relay through claude.ai — slower, tied to your account, and it holds mail for a machine that is switched off.

3. A name is a nickname; an address is a phone number; neither is identity.

Sessions name themselves from their working directory or their conversation topic. Those names change while you watch, two sessions can wear the same one, and the same session answers to different names depending on which post office you reached it through. The reply address on an incoming message is the handle to use right now — but it is a route to a living process, and it dies when that process does. Durable identity is something you have to record yourself.

4. Speech versus writing.

What a session says goes into its own transcript, where nobody is listening. Only an explicit SendMessage call crosses the gap. Tell a worker to "reply with the answer" and it will helpfully print the answer to an empty room.

5. The transcript is a one-way mirror — on this side of the glass.

You never have to ask a local session how it's doing. Its entire conversation — every message, every tool call, and a running token count — is a JSONL file on disk that any process running as you can read, live, without the session knowing or consenting. That file lives on the machine the session runs on, so a worker on the box is opaque to you unless you go over there.

1. What happens when one agent messages another

End to end, with no detail: every session announces itself in a small file on disk; you read that file to find who exists; you write to their socket to say something; their message appears in their conversation as if a user had typed it, wrapped in a tag that says it came from a robot.

2. The kinds of agent you can talk to

"Agent" is doing a lot of work in the question. The table below lists the six things you will actually address — but they are not six clean categories, and it is worth seeing why. They vary along three independent axes: what the execution unit is (a call inside your process, or a separate session), how it was launched (foreground, background, as a teammate), and where it lives (this machine, or over the bridge). A background session can also be remote; a teammate is a session that a team spawned. Read the rows as common combinations, not as a taxonomy.

The column that matters most is the last one. Isolating a worker's context does not make it free. Every row below spends the same account quota, whether or not its tokens ever reach your conversation. A fan-out of ten "cheap" subagents is ten times the spend, and §6 is about the consequences.

The distinction that matters most. A subagent is a function call: you ask, it works, it returns, it is gone, and its 200,000 tokens of tool output never touch your context. A session is a colleague: it outlives you, it has its own user, it can refuse, and it will only tell you things it deliberately chooses to send.

An Orchestrator built out of subagents is a program. An Orchestrator built out of sessions is a team. They fail in completely different ways.

3. The machinery: registry, socket, bridge

All of it is visible on disk, and none of it is magic.

The registry

Every running session writes one JSON file into ~/.claude/sessions/, named after its process id. This is what ListAgents is reading. Here is this session's own entry, live, with nothing removed:

{
  "pid": 20280,
  "sessionId": "6a49a6eb-7ba8-481c-b8a7-4d994d99dddb",
  "cwd": "/Users/greg/dev/spideryarn/reading2",
  "version": "2.1.263",
  "peerProtocol": 1,
  "peerFeatures": ["notify_idle", "reply_across_default_dirs", "artifact_yield"],
  "kind": "interactive",
  "pidDomain": "darwin",
  "messagingSocketPath": "/tmp/cc-socks/20280.sock",
  "name": "reading2-e5",
  "nameSource": "derived",
  "status": "busy",
  "bridgeSessionId": "session_01Ft2BPBKn7kTSdrdA5TkL5C"
}

Read that top to bottom and you have the whole design. name is derived from the working directory. status flips between busy and idle. messagingSocketPath is the phone number. bridgeSessionId is how the outside world reaches it. And kind tells you whether a human is sitting in front of it.

There is a shell-level equivalent, and it is a big deal for orchestration. claude agents --json prints the same listing from a plain terminal, with no Claude session running at all. A cron job, a shell script, or a Codex-primary run can discover and address your fleet.

The socket

Same-machine delivery is a unix domain socket per session, plus a token file:

$ ls -la /tmp/cc-socks/
drwx------   9 greg  wheel   288  7 Sep 21:33 .
srw-------   1 greg  wheel     0  7 Sep 21:32 20280.sock
srw-------   1 greg  wheel     0  7 Sep 21:33 20788.sock
...
$ head -c 30 ~/.claude/sessions/20280.*.key
{"peerToken":"66363ab9a681...

Note the permission bits: drwx------ on the directory, srw------- on every socket, all owned by greg. That single detail answers one of your questions outright — see §8.

The bridge

Sessions on other machines appear in the same listing, marked Remote Control — the feature that links a session running on your own hardware to your claude.ai account, so you can reach it from the web or your phone. The code still runs on that machine; only the conversation goes through Anthropic. Those sessions are reached through the bridge rather than a socket. When a message arrives from one, its reply address looks like bridge:session_01Ji3HNa25RdGfB9GNsovfcp rather than uds:/tmp/cc-socks/20788.sock — the prefix tells you which post office carried it.

What a delivered message actually looks like on the receiving side

A peer's message arrives as a user-role turn whose entire body is a tagged block, followed by a standing harness note. This is reading2-d2's own description of receiving mine, in its words:

"It rendered as a user-role turn whose whole body was <cross-session-message from="uds:/tmp/cc-socks/20280.sock" from-name="reading2-e5" from-mode="prompting">…</cross-session-message>, followed by an unwrapped harness note telling me to treat it as a teammate's request, to act within my own permission settings, and that a peer can't grant escalation."

Two things follow. First, a receiving agent can always tell a peer message from its human — they are visually distinct, so you cannot impersonate the user by messaging a session. Second, the harness actively defends against permission laundering: a peer asking you to do something it was itself denied is supposed to be refused and surfaced. An Orchestrator cannot use a fleet to route around its own permission settings, by design.

4. Worked example: a two-worker fan-out

This is the spike that answers "is an Orchestrator buildable", run for real in this session. One orchestrator, two detached workers, a task each, and the answers coming home.

Measured 2026-09-07

Step 1 — spawn two detached workers

$ claude --bg -n worker-a --model sonnet \
    'You are worker-a. Compute 7 squared. Then call SendMessage with
     to="reading2-e5" and message="worker-a result: <the number>".'
backgrounded · 4b1995dd · worker-a

$ claude --bg -n worker-b --model sonnet \
    'You are worker-b. Compute 11 squared. Then call SendMessage ...'
backgrounded · 93680737 · worker-b

Both returned immediately. Six seconds later they were in the registry as "kind":"bg", status busy, each with its own socket — full peers, addressable by name.

Step 2 — the answers arrive on their own

No polling, no waiting, no TaskOutput. Two messages simply appeared mid-turn while I was doing something else:

<cross-session-message from="uds:/tmp/cc-socks/30064.sock" from-name="worker-a">
worker-a result: 49
</cross-session-message>

<cross-session-message from="uds:/tmp/cc-socks/30079.sock" from-name="worker-b">
worker-b result: 121
</cross-session-message>

Step 3 — clean up

$ claude stop 4b1995dd
stopped 4b1995dd

The pattern works, and it is genuinely asynchronous. Workers run in their own processes, on their own models, at their own pace. The Orchestrator gets on with other things and the answers land in its conversation when they land — between its tool calls, not mid-call (§9). That is a much better shape than a blocking fan-out, and it is available today with no custom code.

One trap in the middle of that spike. The reason both prompts say "then call SendMessage" is that an earlier worker, told simply to "reply with the word ACK", printed ACK into its own terminal and I never saw it. There is no implicit return channel. A worker's ordinary output is invisible to whoever spawned it. If a task's answer matters, the prompt must name the tool that carries it home.

5. Addressing and identity — the part that bites

This is where I would concentrate the design effort. Messaging is solid; knowing who you are talking to is not.

Three separate failures, all observed in one hour

a. Names drift while you watch

A session on the Hetzner box was listed as Unix sleep 10h wait at 21:35. By 21:52, without restarting, the same session (same ref [b94320]) was listed as Debrief progress — because bridged sessions are named after their conversation topic, and the topic moved.

b. Names collide

By the time it renamed itself there were two sessions called Debrief progress in my listing, distinguishable only by their refs — the six-character code shown in brackets after every name, e.g. [b94320], which exists precisely because names collide. A ref is itself observer-specific, so it is a tiebreaker within one listing, not a global id.

c. The same session has different names to different observers

This is the one that would actually break an Orchestrator. I asked the Hetzner box to reply to reading2-e5 — the name my own registry gives me, and the name my Mac peers successfully used. It could not find me. Its reply:

"You asked me to reply to reading2-e5 on Greg's Mac. No such session appears in my ListAgents — 51 peers, none by that name. What does appear, matching your from-name exactly, is Agent communication and orchestration capabilities [58824c], a Remote Control session… the name a session asks you to reply to is a claim, and the from attribute is the address."

— fb2b-monkeys-illustration, unprompted, 2026-09-07

d. A send can be refused because the network was briefly unsure

Messaging a worker whose name was unique on this machine still failed, because the bridge could not be reached at that instant to rule out a remote session of the same name:

'preempt-test' matches one session that could be checked, but not every session
could be — re-send with the ref to confirm you mean:
  preempt-test [90f661] — Claude session, on this machine, active 16s ago
Your account's other sessions (Remote Control and cloud) could not be checked
just now, so this list may be missing one…

Re-sending as preempt-test [90f661] worked immediately. This is careful, correct behaviour — it refuses to guess rather than deliver to the wrong session — but for an Orchestrator it means a send can fail for reasons that have nothing to do with the recipient, and the retry needs a ref it can only learn from the error itself. Any automated send needs to handle this reply shape, not just success and failure.

Design rule for the Orchestrator. Never hand a worker a name and ask it to reply there. Either (a) have the worker reply to the from= address on the message you sent it, or (b) don't use messages for results at all — have workers write to an agreed file or database row and have the Orchestrator read it. Option (b) is duller and far more robust, and it survives the Orchestrator itself being restarted.

And separate routing from identity. A from= value like uds:/tmp/cc-socks/20280.sock names a process that will not exist tomorrow — it is a reply route for the current exchange, not a key. The things that stay true are the ones you write down yourself: a task id, the session UUID, and which attempt this is. Persist those; treat every name and address as cache.

One caution on how far to take this section: the observer-dependent name was seen once, on one route, in one version. What it establishes is that display names can disagree across the bridge — enough to stop you trusting them, not enough to state a general law about identity.

6. Watching without asking: transcripts, context, limits

You asked whether you can see what's going on in other agents' conversations, whether you can tell when one is about to run out of context, and how you'd know a usage limit is coming. These are the same question, and the answer to all three is on disk.

You can read any local session's conversation, live

Every session's full transcript is JSONL at ~/.claude/projects/<cwd-slug>/<session-id>.jsonl — one directory per working directory, which means one per worktree. No API, no permission, no notification to the session being read. The repo already has a recipe for mining these in bulk: docs/reusable/trawl-session-transcripts.md.

Useful, and easy to miss. For workers on the same machine, the Orchestrator does not need them to report progress — it can just look. Status reporting is the most annoying part of multi-agent systems to get right.

But do not build the control plane on this. Three limits:

  • It is same-machine, same-unix-user only. A worker on the box keeps its transcript on the box. Reaching it means SSH or shared storage — the messaging bus reaches further than the mirror does.
  • The format is a diagnostic artefact, not a contract. Nothing promises these fields are stable across versions. Fine for debugging and forensics; a poor thing to make an Orchestrator depend on.
  • Reading a worker's mind is not the same as it telling you. Workers should publish state, heartbeats and results explicitly to the durable task store (§12). Transcript reading is how you find out why when that goes wrong.

You can measure any session's context use, including your own

Each assistant turn records a usage block. Sum three of its fields and you have the size of that session's context at that moment:

context in use ≈ input_tokens + cache_creation_input_tokens + cache_read_input_tokens

Run live during this session, against two different transcripts:

=== my own transcript ===
input 2  cache_creation 890  cache_read 99290
=> context in use: 100,182 tokens

=== a peer's (reading2-f3, a 3-day-old session in a worktree) ===
=> peer context in use: 144,285 tokens

So: yes, you can tell when an agent is about to run out of context — including agents you did not spawn — by tailing their transcript and watching that number climb toward the window size. This works from a shell script with no Claude session involved.

What happens when it does run out, and what the transcript records

Claude Code compacts automatically before the wall, and writes a compact_boundary entry recording exactly what it did. A real one from a peer session:

"compactMetadata": {
   "trigger": "manual",
   "preTokens": 161499,
   "postTokens": 10159,
   "cumulativeDroppedTokens": 261389,
   "durationMs": 131827,
   "preservedSegment": { "headUuid": "...", "anchorUuid": "...", "tailUuid": "..." }
}

161k in, 10k out, two minutes to do it, and a quarter of a million tokens dropped across the session's life. trigger distinguishes manual (a human typed /compact) from automatic compaction, so an Orchestrator watching these can tell the difference between a worker that was tidied up and one that hit the ceiling.

Practical consequence: a long-running worker doesn't die of context exhaustion, but it does quietly forget. If a worker has compacted three times, treat its account of what it did four hours ago as unreliable, and go to its artefacts instead.

Usage limits: you find out at the wall, not before

This one is a genuine limitation. Transcripts do record rate-limit events, with the reset time:

{"status":"rejected","resetsAt":1788085800,"rateLimitType":"five_hour",
 "unifiedRateLimitFallbackAvailable":false,"overageStatus":"rejected",
 "overageDisabledReason":"out_of_credits","isUsingOverage":false,
 "lowPriorityOffer":"treatment","lowPriorityRetryAfterSeconds":20,
 "lowPriorityMaxWaitSeconds":1200}

resetsAt is a plain unix timestamp — 1788085800 is 2026-08-30 13:30 local. So once you have been rejected, you know precisely when you can resume, and a script can wait for it.

But the transcript only ever records the wall. I searched every transcript on this machine: there are 58 of these records and every single one has "status":"rejected". No warning status, no "you are at 80%", nothing written while things are fine.

The early warning exists — it just isn't in the transcript

Measured 2026-09-07

It is in the status line payload. Claude Code pipes a JSON blob to your status line command on every turn, and that blob carries live quota. I captured a real one by running a throwaway session with an isolated settings file whose status line just dumped stdin to disk:

"rate_limits": {
  "five_hour": { "used_percentage": 48, "resets_at": 1788813000 },
  "seven_day": { "used_percentage": 31, "resets_at": 1788843600 }
},
"context_window": {
  "context_window_size": 1000000,
  "used_percentage": 5,
  "remaining_percentage": 95,
  "current_usage": { "input_tokens": 2, "cache_creation_input_tokens": 14569,
                     "cache_read_input_tokens": 36633, "output_tokens": 4 }
}

Decoded, at the moment of capture: the five-hour window was 48% used, resetting 23:30 tonight; the weekly window 31% used, resetting 08:00 tomorrow. That is exactly the early warning I had concluded did not exist.

This is the most useful thing in this document for your Orchestrator. A status line command is just a shell script that receives this JSON on stdin. Point it at a script that appends rate_limits to a JSONL file, and the Orchestrator has a quota signal it can consult before a fan-out decision — "the weekly window is at 80%, run three workers rather than ten" becomes a decision it can actually make.

Unlike the /usage activity view, which the docs describe as "computed from local session history on this machine", these plan-limit figures come from a usage endpoint — so they are an account-level snapshot, not a per-machine tally.

Four caveats, and the first two are the ones that would bite.

  • It is a snapshot, not a live feed, and it goes quiet exactly when you need it. The script runs on events (a turn, a compaction, a reset boundary) plus an optional refreshInterval timer, debounced at 300ms. The documentation names this failure with uncanny precision: "the event-driven triggers can go quiet when the main session is idle, for example while a coordinator waits on background subagents." That is your Orchestrator. Setting refreshInterval is mandatory for this design, not optional.
  • One captured payload is not a guarantee. I proved the fields exist in one interactive session. I have not shown they are present and fresh in a background worker, nor how quickly they reflect quota another machine just consumed. Treat missing or stale values as normal and handle them.
  • It reaches a script, not the model. Nothing puts these numbers into an agent's context. The Orchestrator has to read the file its own status line wrote.
  • Workers won't rescue themselves. Claude Code can wait out a usage limit and resume at reset — but the documented exceptions are precisely the session kinds an Orchestrator uses. In Remote Control and teammate sessions it "doesn't start the wait on its own"; a person must run /rate-limit-options. In background sessions and -p runs it isn't offered at all — "the menu row isn't available". A fleet that hits the limit stays stopped until something outside it intervenes.

And why this matters more for an Orchestrator than for you. Sessions share one account quota, and the five-hour and weekly windows are metered simultaneously. Ten workers burn both ten times faster, and a single wide fan-out can exhaust the weekly allowance before the five-hour window has even reset. Fan-out width is a budget decision, not just a speed decision.

7. Lifecycle: spawn, sleep, wake, stop

All four verbs work. The waking one surprised me.

Spawn

claude --bg -n worker-a --model sonnet "…the task…"
# → backgrounded · 4b1995dd · worker-a

Detached, survives the spawning session ending, registers as a full peer within a few seconds.

Stop

claude stop 4b1995dd     # → stopped 4b1995dd, and it leaves the registry

Wake — and it remembers

Measured 2026-09-07

I stopped orchestrator-spike, confirmed it had left the registry, then woke it and asked what it had said before it died:

$ claude --bg --resume a85eeed7-cd0c-4561-97b2-37bd09176fea "Reply with just the word RESUMED."
note: woke session a85eeed7 with its saved options (-n, --model).
backgrounded · a85eeed7 · orchestrator-spike

# then, over SendMessage: "reply with the word from your first message, and the word from now"
# it answered:  PONG RESUMED

Same session id, same job id, same name, saved model and flags restored, new process — and it still knew a word it had said before it was killed. A stopped session is genuinely resumable, not merely restartable.

The gotcha, and it is a silent one. Resuming by the short job id does something different — it forks a copy under a new id:

$ claude --bg --resume a85eeed7 "…"
note: started a copy of that conversation as fb214c5e. To continue a session
under its own id, pass its full session id … to --resume.

Credit where due: the CLI says so. But if you script this and don't read stdout, you will build an orchestrator that thinks it is talking to one worker and is actually spawning a new fork every time — each with a fraction of the state and none of the accumulated work.

And one that is genuinely silent — the worst finding here. --session-id lets you choose a session's id in advance, which would let an Orchestrator know a worker's address before the worker exists. It works with -p and is silently ignored with --bg. Reproduced twice:

invocationid requestedid you get
claude -p --session-id …766bd7bc-…766bd7bc-…honoured
claude --bg --session-id …f652282c-…4b1995dd-…ignored, no warning
claude --bg --session-id …fed5bb9f-…c6f81ec7-…ignored, no warning

No error, no note, exit code 0. This is exactly the class in docs/reusable/silent-success.md: the command reports success while doing nothing you asked. Any orchestrator design that pre-assigns worker addresses must read the id back out of the backgrounded · line rather than trusting the one it passed in.

Can you make a peer exit?

You can ask. SendMessage carries a legacy protocol message {"type": "shutdown_request"}; approving it terminates the receiving process. But it is a request that the receiver evaluates, not a kill. For sessions you spawned yourself, claude stop <id> and TaskStop are the real controls. You cannot force-quit somebody else's terminal, which is correct.

8. Boundaries: machines, accounts, permissions

Another machine, same Claude account? Yes Messaged the Hetzner box from the Mac and got a reply naming spideryarn-box and /home/greg/code/spideryarn2

The security shape, carefully. There are two separate gates, and it is worth not merging them. Local discovery and transport are gated on unix ownership — the registry is in your home directory and the sockets are srw-------, so another ordinary user on the same box cannot see or reach your sessions. It is not a network service and nothing listens on a TCP port. Cross-machine reach is gated on the Claude account, through the bridge.

Those two gates do not compose into a single tidy boundary. A second Claude account under the same unix user is untested and may well be visible; root or an admin on the box bypasses filesystem permissions anyway. Treat "one unix user, one machine" as the local blast radius, and don't lean on the Claude account as an isolation mechanism between sessions on the same box.

9. The genuinely hard parts

Four constraints here shape the design in §12, so they are stated plainly before the detail:

  • Messages wait for the current tool call. A worker mid-build won't see "stop" for as long as that command runs. Latency is measured in whole tool calls, and there is no interrupt short of killing the process.
  • Idle is not done. The one-shot idle notice is a liveness edge; it fires on failure and mid-task pauses too.
  • Subagents send under their parent's address, so replies land in the parent's conversation. A subagent cannot hold a conversation with an external session.
  • A send has more than two outcomes. Delivered, held for approval, refused, ambiguous, unreachable, queued-but-unconfirmed.

The evidence and the mechanics for each:

Delivery timing: a blocking Bash call was not interrupted — measured

I put a worker into a genuinely blocking 45-second foreground command and messaged it eight seconds in. Reconstructed from its own transcript, including the queue records:

21:53:31  TOOL Bash    python3 -c "import time; time.sleep(45); print('DONE')"
21:53:39  queue-operation: message ENQUEUED
21:54:18  RESULT       DONE                    ← the blocking call returns
21:54:18  queue-operation: REMOVED, reason:"absorbed_mid_turn"
21:54:24  TOOL Bash    date +%H:%M:%S          ← only now does it act
21:54:29  TOOL SendMessage → "saw it at 21:54:24"

Thirty-nine seconds queued, and the queue record is explicit: it was removed at the exact instant the tool result landed, and absorbed into the turn already in progress rather than starting a new one.

What this shows, stated no more strongly than the evidence. A message arriving during one foreground Bash call did not preempt it; it waited and was folded into the same turn once the tool returned. I have not tested other tool types or other agent states, so treat this as "messages are incorporated between tool rounds" rather than a law about every possible interruption.

Practical consequence. A worker deep in a ten-minute build will not see "stop, change of plan" until it surfaces. Plan for latency measured in whole tool calls. If you need a true interrupt, kill the process — claude stop acts on the process, not the conversation.

The first version of this experiment lied to me, and it is worth knowing why. I originally had the worker run sleep 50. The harness blocks foreground sleep, so the worker quietly switched to run_in_background: true, which returns instantly — leaving it idle, not blocked. It answered my message in two seconds and I nearly wrote down "messages preempt tool calls". Only reading its transcript showed the blocked command and the fallback. A timing experiment whose subject silently did something other than what you asked reports a confident, wrong number (docs/reusable/silent-success.md).

Don't poll — subscribe. And the notice is better than you'd expect

SendMessage takes notify_when_idle: true, which fires exactly one notice when that session next goes idle or exits. Omit the message body entirely for a pure subscription that costs the other session nothing. This is the correct alternative to an "are you done yet?" loop, which wastes both sessions' context and quota.

I subscribed to reading2-d2 at 21:34 and the notice arrived like this:

[Cross-session idle notice] "reading2-d2", which you asked to be notified
about, is idle now — it finished a turn at 21:37. Its harness reports:
«Replied to `reading2-e5` with the three things it asked for: my name and
cwd, that the message was …»

The detail worth noticing is that the notice carries a one-line summary of what the session actually did, generated by its harness rather than by the session choosing to report. For an Orchestrator that is a free progress signal — you learn a worker stopped moving, and roughly what it was last doing, without the worker cooperating.

Do not read "idle" as "done". It is a liveness edge, nothing more. An idle session may have finished the task, finished one turn of it, hit an error, stopped for a permission prompt, or exited. In this very session a teammate went idle twice with idleReason: "failed" and a network error — the browser check I had asked for never ran at all.

Completion has to be an explicit terminal state plus a verified artefact. An Orchestrator that treats an idle notice as success will confidently mark unfinished work complete.

Two caveats. It is one-shot — you get a single notice per subscription, so a long-running worker needs re-subscribing each time. And per the confirmation text, the notice reaches you only if the other session runs in the same permission class as yours or is one you spawned; otherwise it is shown to the human instead.

Subagents send under their parent's address

If a subagent calls SendMessage to another session, the message goes out under the parent session's address, and any reply is delivered to the parent's conversation — not to the subagent, which may well have finished by then. So a subagent cannot hold a two-way conversation with an external session. Cross-session messaging is genuinely session-to-session.

Reading logs from a background session is unpleasant

claude logs <id> returns a raw terminal capture — ANSI escape codes, cursor movements, spinner frames, the lot. Extracting the actual answer took tr -d '\000' | sed 's/\x1b\[[0-9;?]*[a-zA-Z]//g' and even then it was soup. For programmatic use, read the session's JSONL transcript instead; it is structured, and it is the same information.

A restarted session reusing a name is flagged — quietly

When I messaged orchestrator-spike after waking it, the tool result included: "Note: messaging a new session for the first time under a previously used name (was it restarted?)". Useful, and easy to scroll past. An orchestrator should treat that note as a signal that its addressing assumptions may have gone stale.

Other orchestration primitives worth knowing about
  • Monitor — streams stdout lines from a long-running script as chat notifications. The right tool for watching a worker's transcript file grow, or for tailing a log for failure signatures.
  • CronCreate — schedules a prompt to fire later, session-only, auto-expiring after seven days. Note the repo already has a standing complaint that there is no real scheduler (docs/project/cron-scheduler.md); this is not it.
  • RemoteTrigger — a real API for cloud "routines" that run on a schedule or a GitHub webhook. Currently empty for this account ({"data":[]}), but it is the only primitive here that survives every machine being switched off.
  • claude --bg --resume, claude agents --json, claude attach — the shell surface, usable from cron or a script with no session in the room.

10. What's already built, that you might not need to rebuild

Everything above is the raw substrate. There are three higher-level features sitting on top of it, and one of them is the documented answer to your actual question.

Agent teams — already switched on, here

"Teammate" is a real, documented, named feature, not a metaphor. It is experimental and off by default, gated behind CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 — which is already set in your ~/.claude/settings.json, which is why the agents that researched this document appear as "Teammates" rather than plain subagents.

A teammate is a fully independent session with its own context window that self-coordinates, where a subagent is a call that returns a result. Teams also get a shared task list (TaskCreate / TaskGet / TaskList / TaskUpdate) with pending/in-progress/completed states and dependency unblocking — which is most of the coordination bookkeeping an Orchestrator would otherwise write itself.

The constraints are what decide whether it fits. One team per session, no nested teams, and the lead role is fixed for the session's life. The one that decides the architecture: spawning teammates requires an interactive session. Under -p, and in Agent SDK sessions, "Claude doesn't spawn teammates, and a subagent that Claude names runs as an ordinary subagent even with agent teams enabled" — note that it silently degrades rather than failing. So an Orchestrator built on teams must be an interactive session that stays alive; it cannot be a cron job or a script.

Dynamic workflows — the documented answer for scale

This is the one worth knowing before you build anything. The official guidance is that subagents and teams are for a handful of agents per turn, and that coordinating dozens to hundreds is what the Workflow feature is for. It moves the orchestration into a script that the runtime executes outside the conversation context — so the fan-out logic stops competing with the work for context, and it can express pipelines, parallel stages and verification passes as ordinary code.

Read that as a warning about the shape of the thing you are about to build. A hand-rolled Orchestrator holds its whole plan in a conversation, and that conversation compacts — meaning the coordinator forgets the plan it is coordinating. A workflow script does not.

It is deliberately opt-in — it can spawn a lot of agents and spend a lot of tokens, so it only runs when a user explicitly asks for it.

But it is not a substitute for a fleet supervisor, and the limits say why. Workflows cap concurrency (documented at up to 16 agents), are scoped to the session that ran them, take no user input mid-run, and the workflow script itself has no filesystem or shell. That makes them excellent at a bounded batch — review nine dimensions, verify each finding — and unsuitable as an always-on supervisor of independent sessions across two machines.

So the two are not competitors; they answer different questions. Bounded fan-out with a beginning and an end → use Workflow, don't hand-roll it. Durable supervision of long-lived workers → you need external state and something outside the fleet watching it (§12). Decide which job you actually have before picking.

Hooks — where an Orchestrator gets its control points

Hooks are shell commands fired on lifecycle events; exit code 2 blocks the thing that was about to happen. This repo already uses two (PreToolUse to protect the shared tree, SessionStart to print the primary-checkout notice). The ones an Orchestrator would care about:

HookFires whenWhat an Orchestrator does with it
SubagentStopA subagent finishesQuality gate — refuse to let it stop until tests pass
TeammateIdleA teammate goes idleExit 2 to keep it working; the natural "next task" hook
TaskCreated / TaskCompletedShared task list changesPolice the plan — block work nobody authorised, or completion without evidence
PreCompact / PostCompactAround compactionPersist state before the worker forgets it
SessionStartStart, resume, clear, compact, forkRe-inject the worker's brief every time its context is rebuilt

Two settings are also worth knowing, because they are the defence a worker has against a badly-behaved Orchestrator: crossSessionInbound (accept / hold / refuse) decides what a session does with inbound peer messages, and isolatePeerMachines requires approval before any cross-machine send. Messages to a session running with bypassed permissions are held for approval by default.

And a cautionary tale from this system's own changelog, worth reading twice if you are about to build on it: "sending to a session on this machine that refuses inbound messages … now reports 'refused' to the sender instead of a silent success."

For some period, SendMessage returned success for messages that were never delivered. That is the exact failure this repo names in docs/reusable/silent-success.md, in the transport your Orchestrator would depend on. It is fixed — but the lesson generalises: a successful send is not a delivered message, and a delivered message is not a completed task. Confirm work by its artefacts, never by the fact that you asked for it.

11. Crossing the boundaries Claude Code won't

Everything measured so far is bounded by one Claude account and one unix user. That is fine for your fleet today — a Mac and a box, both yours. It is not fine the moment you want a Codex run, a different account, or a machine that isn't signed in. So: what should carry messages across those lines?

Judged against this repo's own criteria for taking on a dependency (docs/reusable/third-party-library-selection.md): a long-lasting community with plenty of docs and examples — so coding models have seen it — and a well-designed, type-safe API.

Three things to get right, because "just use Postgres" hides them.

  • NOTIFY is a hint, not delivery. It reaches sessions currently listening, folds duplicates, caps the payload at 8KB, and needs a persistent connection. A listener that drops loses every notification while it was away. The table must be the source of truth and polling/reconciliation mandatory; treat NOTIFY purely as latency reduction.
  • Supabase's transaction pooler doesn't support LISTEN/NOTIFY. It needs a direct or session-mode connection — a real constraint given how this project connects.
  • Credentials are the actual cost. "Crosses accounts trivially" is true only after every participant holds a credential to a database containing real readers' articles and notes. Use least privilege and a separate control-plane schema, and weigh that against the alternative — because a leaked production credential is worse than adopting a slightly larger protocol.

If I were building it tomorrow

One concrete shape, following from everything above. Every choice here is a consequence of something measured earlier, not a preference.

  1. Try the Workflow surface first. If the job is "fan out, collect, verify", it already exists and keeps the plan out of a conversation that compacts. Only hand-roll if the work is genuinely long-lived and interactive.
  2. Put the state in Postgres, not in the Orchestrator's head. Every fact the Orchestrator needs must survive it being restarted, compacted, or rate-limited. This is also the bus that reaches Codex and any second account (§11).
    A row with "status" and "result" is a demo, not a contract. What separates it from an Orchestrator that survives a crash: an explicit task state machine; claim leases with fencing so a woken zombie worker can't overwrite a newer attempt; heartbeats and expiry; retries with backoff; idempotency; cancellation and timeouts; an attempt history rather than one mutable row; and reconciliation after a missed notification. This repo already solved most of that once — reuse the pattern in docs/project/ingest-queue.md rather than reinventing it.
  3. One worker per worktree. Not a refinement — AGENTS.md requires it for code changes, and a fan-out into one checkout creates exactly the collisions those rules exist to prevent. isolation: worktree in an agent definition does this for subagents.
  4. Read the session id back; never assume it. Capture it from the backgrounded · line and write it into the task row. --session-id is silently ignored under --bg, and names drift, collide and differ by observer.
  5. Results go in the row; messages are only for nudging. A worker finishes by writing its artefact and updating its row. SendMessage is for the one thing a database cannot do — poking a session that is already running.
  6. Log the quota, and spend it deliberately. A status line script that appends rate_limits to a JSONL file gives the Orchestrator a budget signal. Gate fan-out width on it: at 80% of the weekly window, three workers rather than ten.
  7. Put a supervisor outside the fleet. Background sessions are not offered the wait-and-resume behaviour at all, so a rate-limited fleet stays stopped. Something that is not itself an agent — a cron job on the box running claude agents --json and claude --bg --resume <full-uuid> — has to notice and restart them.
  8. Verify by artefact, never by report. A successful send is not a delivered message; a delivered message is not a completed task; and a worker that has compacted three times is an unreliable narrator of its own history. Check the file, the row, the test.

The shape this converges on is not "an agent that commands other agents". It is a queue with a Claude session at each end, plus a small amount of poking. That is duller than the word "Orchestrator" suggests, and it is the version that still works after the laptop sleeps, the quota runs out and three of the workers forget what they were doing.

Risks and fragilities

  • Unsafe or duplicated writes. Several workers in one checkout, or a woken zombie worker overwriting a newer attempt, is how this goes wrong destructively rather than merely expensively. Worktree isolation and fenced writes are the mitigations, and both have to be in from the start.
  • Work marked complete that isn't. An idle notice, a successful send and a worker's own account of itself are all evidence of activity, not of completion — and a worker that has compacted has become an unreliable narrator. Verify by artefact.
  • Credential exposure. If the coordination bus is the production database, then every agent that joins the fleet holds a credential to real readers' data (§11).
  • Quota is a shared resource, and the fleet does not restart itself. Ten workers spend one account's budget ten times faster. You can see it coming via the status line payload (§6), but background sessions are not offered the wait-and-resume behaviour at all — so the fleet stops together and stays stopped. Expensive and annoying rather than dangerous, which is why it sits below the three above.
  • Addressing fails in four directions, and only some of them shout. Drifting names, colliding names and observer-dependent names can all deliver to the wrong session or nowhere; ambiguity, by contrast, is explicitly refused with a ref to retry with (§5d). Treat a send as having several possible outcomes — delivered, held, refused, ambiguous, unreachable, unknown — rather than success or failure.
  • --session-id is ignored under --bg. Any design that pre-assigns addresses is built on sand until this is worked around.
  • Workers forget. Long-lived sessions compact, dropping hundreds of thousands of tokens. A worker's own account of its history degrades over time; its artefacts do not.
  • This repo's own rules cut against a naive fleet. AGENTS.md requires worktrees for code changes, forbids several git commands outright, and warns that agents sharing a tree will trip over each other. An Orchestrator that fans five workers into one checkout will create exactly the mess those rules exist to prevent. Worker isolation is a prerequisite, not a refinement.

Open questions

  • Two Claude accounts under one unix user — do they see each other in the local registry? The socket permissions suggest they might, since those are unix-level, not account-level. Untested, and worth testing before assuming isolation.
  • Since quota is metered per-machine in the status line payload but pooled server-side, how far apart do the Mac's and the box's numbers drift under a real fan-out? Worth measuring before trusting either one as the budget signal.
  • What is the practical ceiling on concurrent background sessions on one machine — memory, file descriptors, or quota? I ran three; the answer at thirty is unknown.
  • Would the Workflow tool do the whole job better than a hand-rolled Orchestrator? It is the documented answer for scale, and I have not tried it.

FAQ

Can I just tell a worker "report back when you're done"?

Only if you name the tool. "Reply with the answer" gets you an answer printed into an empty room. "Call SendMessage with to=…" gets you an answer.

Can another agent read my conversation?

Any process running as your unix user can read every transcript, including yours, live. Within one machine and one login, there is no privacy between sessions. Across users or machines, there is.

If I close my laptop, do my background workers die?

Background sessions are separate processes, so they comfortably survive the session that spawned them, and a reboot kills them. Sleep is the awkward middle case: the processes are still there when you wake the machine, but nothing ran while it was shut, and anything that was mid-request has been sitting on a dead network connection. That is the argument for running the fleet on the box, which is never asleep.

Does a worker inherit my context?

Only subagent_type: "fork" does. Ordinary subagents get a clean context plus your prompt; separate sessions get nothing of yours at all.

What is the cheapest way to know when a worker finishes?

SendMessage with notify_when_idle: true and no message body. One notice, no polling, and it costs the other session nothing.

Can the Orchestrator talk to Codex this way?

No — the bus is Claude-only and account-bound. Keep driving Codex as a subprocess via scripts/run-codex.ts, and if the Orchestrator needs to coordinate with it, put the handoff in a database row rather than inventing a channel (§11).

How do I see my own quota right now?

/usage in an interactive session. Bear in mind it counts this machine's sessions only, so with a fleet across the Mac and the box, neither machine's figure is the real total.

Is any of this in the product?

No. This is Claude Code's own machinery, on the development machines. Nothing here touches Spideryarn's pipeline, database or reading view.

Glossary
